네이버 수집 · 이력 탭 /admin/naver-ingest/triage?tab=all — 상태 칸 재설계

지금 상태 칸은 배지를 있으면 붙이는 방식이라 ① 자리·순서가 행마다 달라 눈이 세로로 못 훑고 ② 재결제·추가결제가 아예 없고 ③ 발송처리 축이 통째로 빠져 있다. 아래는 페르소나가 이 칸에 던지는 질문 → 그 질문에 답하는 칸 설계다. 새로 부르는 네이버 API는 0건 — 전부 이미 저장된 값이다.

1. 이 칸을 읽는 사람 (페르소나 3)이력 탭은 ADMIN 전용 · 읽기 전용 표
P1 · 운영 실장 (주 사용자)
고객 전화 받는 중 — 3초 안에 답해야 한다
  • "제 주문 지금 어떻게 됐나요?" → 주문 만들었나 · 네이버에 발송처리 했나
  • "언제 나가요?" → 발송기한 · 발송처리 시각
  • 화면 규칙을 외우지 않고 읽고 싶다 (지금은 "배지 없음 = 완료" 규칙이 있다)
P2 · CS 응대
결제가 두 번 찍힌 건을 해명해야 한다
  • "왜 두 번 결제됐죠?" → 신규인가, 추가결제(차액)인가, 재결제인가
  • 붙은 상대 주문이 몇 번인가 (지금 이력 칸에 없음)
  • 취소·반품이 요청인가 확정인가 — 환불 언제 나가나
P3 · 정산 / 대표
월말 매출 대조
  • 재결제·추가결제를 매출 2건으로 세면 안 된다 → 관계 표시 필수
  • 취소·반품 확정분이 빠졌나
  • 우리는 발송처리 했다는데 네이버엔 안 찍힌 건이 있나 (불가역 호출이 유실된 자리)

장점 — 코드를 가장 적게 고친다(배지 추가 + 순서 고정). 약점 — 행마다 배지가 4~5개라 폭을 먹고, 배지가 늘수록 "전부 중요"가 되어 정작 눈에 안 띈다. 축이 섞여 있어 "네이버 쪽 일"과 "우리 쪽 일"이 한 줄에 붙는다.

B안이 푸는 것
  1. 축이 줄로 갈린다 — 왼쪽 라벨(FOMS / 네이버 / 취소·반품 / 옛 결제)이 고정이라 100행을 세로로 훑을 수 있다.
  2. 관계가 문장으로 — "추가결제 · #4362 에 붙음". 상대 주문번호까지 이 칸에서 끝난다(P2·P3).
  3. 발주확인 → 발송처리 파이프라 다음에 무엇이 남았는지가 색+글자 둘 다로 보인다. 완료도 보인다("무표시 = 완료" 규칙 제거).
  4. 부분 발송·부분 발주확인·어긋남·실패가 제 상태로 산다 — 지금 표에는 존재조차 없다.
  5. 예외 줄(취소·반품 / 옛 결제)은 있을 때만 나온다 — 평범한 행은 2줄로 끝나 표가 안 길어진다.
좁은 폭에서 무엇이 일어나는가
  1. 상태 칸에 container-type: inline-size 를 건다 — 접힘 기준은 뷰포트가 아니라 칸 폭이다. 같은 부품이 이력 표·처리 탭·도크(폭 358)에 실리므로 뷰포트 기준으로 짜면 한 곳에서만 맞는다.
  2. 칸이 330px 밑으로 내려가면 라벨(FOMS/네이버/…)이 값 위로 올라가 한 열로 쌓인다. 라벨 열을 그대로 두면 1fr 이 굶어서 배지 글자가 세로로 선다.
  3. 표 자체는 min-width: 720px + 가로 스크롤 — 칸을 무한정 짜내지 않는다. 이력 탭은 ADMIN 전용 PC 화면이라 이 선에서 끊는 것이 맞다.
