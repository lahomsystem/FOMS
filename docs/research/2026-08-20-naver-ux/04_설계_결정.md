# 네이버 수집 화면 개편 — 설계 결정 (2026-08-20)

리서치 3건(국내 SaaS·해외 OMS·현화면 감사)을 대조해 확정한 규칙. **다음 세션은 이 파일부터 읽고 v2 목업을 만든다.**

- 목업 v1(초안): `docs/design/mockups/naver-ingest-workbench.html`
- 근거: 같은 폴더 `01`(국내) · `02`(해외) · `03`(감사)

## 확정 (근거가 국내·해외에서 교차 확인된 것)

1. **화면 통합 + 탭 4개.** 처리 대기 / 발주확인 전 / 취소·반품 / 전체 이력.
   두 URL 왕복을 없앤다. 취소·반품은 사용자 요구이자, 네이버 판매자센터가 클레임을 별도 메뉴로 조회하는 관례(01 §3)와 일치.
2. **취소·반품은 탭으로 분리하되 전체 이력에서 빼지 않는다.** 회색 + 액션 비활성으로 같은 자리에 남긴다.
   Linnworks(Parked/greyed out)·Amazon(Pending grayed out)이 독립적으로 같은 답(02 규칙 5).
3. **숫자는 이중 표기.** `43집 (상품주문 140건)`. 플레이오토가 `0 / 7 (합포장: 0 / 7)`로 품목·묶음을 병기(01 §2).
   지금은 nav 배지 140(건)과 필터 43(집)이 따로 놀아 업무량이 3배로 읽힌다(03 결함 #2).
4. **상태는 3층으로 분리 표기.** 진행축 배지 1개 + 클레임축 별도 + "지금 처리 가능한가" 보조 표식.
   네이버 팝업이 `주문상태 | 클레임종류 | 클레임처리상태` 3컬럼(01 §3), 플레이오토는 `출고가능여부`를 별도 컬럼(01 §4).
   지금은 `확인 필요`와 `발주확인 전`이 같은 `bg-warning`이라 구분 불가(03 결함 #6).
5. **한 집의 상품주문 n건은 행 인라인 확장으로 편다.** 옵션 원문 전부를 그 자리에서 읽는다.
   지금은 pane이 링크 1건이라 6건 묶음을 다 보려면 페이지 6번 로드(03 결함 #3). ShipStation Multi-item Order View와 동형(02 규칙 2).
6. **불가역 액션(발주확인·발송처리)은 4종 세트.** 모달 + **건수 재진술 문장** + "되돌릴 수 없음" + 사후 경로 안내.
   플레이오토가 "전체 출고가능한 주문 13건을 일괄 출고 지시합니다" 식으로 건수를 문장에 다시 넣는다(01 §7).
7. **실패는 4단계로 보여준다.** 성공/실패 카운터 → 실패 전용 목록 → 건별 사유 → 실패건만 재시도.
   국내 3사가 동일하게 수렴(01 §8). 지금은 `.alert` 5초 자동 제거로 실패 문구가 증발한다(03 결함 #5).
8. **좌우 분할 유지.** 해외 OMS 표준이고(02 규칙 1), 국내는 풀폭+모달이지만 우리는 "원본 읽으며 규격 채우기"라 대조가 상시 필요.

## 반영하지 않기로 한 것

- **100건 일괄 덮어쓰기 설계**(Veeqo/ShipStation형): 우리는 한 집 안 2~14품목을 조립하는 반대 축. 일괄은 저위험(태그·숨기기)만.
- **선택 없이 버튼=전체 대상**(플레이오토 관례): 2026-08-14 일괄 완료처리 AS 증발 사고가 정확히 이 패턴의 위험. 선택 없으면 아무것도 안 한다.
- **스캐너·핫키 파워유저 최적화**: CS 병목은 키 입력이 아니라 건당 판단(02 §안 맞는 것 2).
- **배송축 상태 모델 이식**(Delivery/Label/Chargeback): 우리는 실측→도면→시공 축이라 영원히 빈 컬럼이 된다.
- **취소·반품 조회 전용 격리**: 플레이오토 최대 불만("쇼핑몰에서 직접 처리하세요" — 01 §6). 우리 탭에서는 최소한 **큐에서 빼기(확인 완료)** 는 되어야 한다.
