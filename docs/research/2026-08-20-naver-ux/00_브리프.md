# 네이버 수집 화면 UX 개편 목업 — 공용 브리프

## 배경 (실사용자 문제)
운영 중인 FOMS(가구 주문 관리 ERP)의 네이버 스마트스토어 수집 기능에 화면이 **둘로 갈라져 있다**.
CS 접수 담당이 두 화면을 왕복하며 일해서 가독성·효율이 떨어진다는 실사용자 불만이 나왔다.

- `/admin/naver-ingest` — 수집 상태(워터마크·마지막 실행·인증 만료 카드 3장) + 이력 표(집 단위) + 상태 필터
- `/admin/naver-ingest/triage` — 확인 대기 큐(좌) + 네이버 원본↔FOMS 대조 pane(우)

## 실사용자 페르소나 (이것 기준으로 판단하라)
**CS 접수 담당 (관리자 권한, PC 1440~1920 해상도, 하루 수십 집 처리)**
하루 흐름:
1. 새로 수집된 집을 확인 큐에서 연다
2. 오른쪽 네이버 원본(옵션 원문·주소·연락처)을 읽는다
3. "주문 만들기"를 눌러 FOMS 주문 1건을 만든다 (한 집의 상품주문 여러 건이 주문 1건으로 묶인다)
4. 편집기 새 탭에서 ERP 규격을 입력한다 (옵션 원문을 보고 폭·수량을 채운다)
5. 돌아와서 "확인 완료"를 눌러 큐에서 뺀다
6. 취소·반품 건은 건드리면 안 된다 / 발주확인(네이버 판매자센터 알림)도 눌러야 한다

## 도메인 규칙 (어기면 오답)
1. **한 집 = 한 줄.** 네이버는 본품과 구성 옵션을 각각 다른 상품주문으로 준다. 집 단위로 묶어 보여주고, 주문도 집 단위로 1건 만든다.
2. **숫자 단위는 집(묶음)으로 통일.** 상품주문 건수는 보조 표기.
3. 상태는 **서로 다른 3축**이다: 수집 상태(수집됨/주문 생성됨/확인 필요/실패) · 발주 상태(발주확인 전/완료) · 클레임(취소·반품). 한 배지 무더기로 섞지 마라.
4. **취소·반품 건은 주문을 만들 수 없다**(서버가 400 으로 막는다). 화면도 잠가야 한다.
5. CS 업무 범위는 ① 주문 만들기 ② ERP 규격 입력까지. **담당자 지정은 실측 일정 단계**라 이 화면 일이 아니다.
6. 규격 자동 파싱 금지 — 사람이 옵션 원문을 읽고 편집기에서 채운다. 화면은 원문을 **크고 읽기 쉽게** 보여주고 복사만 돕는다.
7. 발주확인·발송처리는 **되돌릴 수 없는** 네이버 호출이다. 확인 문구와 상태 표시가 필요하다.
8. 신규 기능: 재결제·차액 결제는 새 주문이 아니라 **기존 주문에 붙인다**(사람이 후보 중에 고른다). 후보가 있는 집은 그 사실이 보여야 한다.

## 산출물 규격
- 파일: `docs/design/mockups/<지정된 파일명>` (저장소 경로, 워크트리는 `c:/tmp/foms-s-naver-ingest`)
- 형식: **단독 실행 HTML 1개**. 외부 CDN·폰트·이미지 금지. `<style>`·`<script>` 인라인 허용(목업 관례 — `docs/design/mockups/mobile-*.html` 참고).
- 언어: 화면 문구 전부 한글. 코드 주석도 한글로, **왜 그렇게 배치했는지**를 적어라.
- 데스크톱 1440 기준. 목업이므로 백엔드 연결·실제 라우트 없음. 클릭 시 탭/선택만 바뀌는 정도의 JS 는 허용.
- 기존 `erporder` 편집 폼은 이 개편 범위 밖이다(1px 도 안 건드린다).
