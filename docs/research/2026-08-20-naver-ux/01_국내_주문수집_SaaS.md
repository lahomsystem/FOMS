## 1. 주문 수집 목록을 어떤 단위로 보여주나 (주문 vs 상품주문 vs 묶음)

### 결론 먼저
조사한 모든 서비스에서 **목록의 한 행 = 상품주문(품목) 단위**다. 주문 단위로 행을 접는 서비스는 없었다.
묶음(합포장)은 **두 갈래**로 나뉜다 — ①목록 안에서 셀 병합으로 표현(플레이오토), ②목록 밖의 팝업/파이프라인 단계로 분리(네이버·이지어드민·사방넷).

### 플레이오토 2.0 — 목록 안에서 rowspan 병합 + 묶음번호 컬럼
근거: [주문관리 가이드 PDF](https://cloud.plto.com/plto20/download/guide/PLAYAUTO2.0_order_guide.pdf) p.12~13(신규주문), p.21(배송관리) 캡처

- 컬럼 순서: `No | ☑ | ⚙ | [상세][메모][주문분할] | 묶음번호 | 출고가능(여부) | 배송처 | 매칭여부 | 쇼핑몰(계정) | …`
- p.12 캡처에서 **No.2 한 줄에 품목 행이 2개** 붙어 있고, 묶음번호 `3727773459193755` 셀이 두 행에 걸쳐 **세로 병합(rowspan)** 되어 있다. p.21 배송관리 캡처에서는 No.1이 2행, No.2가 3행(`3748122723154820`)으로 병합.
- 즉 **`No` = 묶음 일련번호, 행 = 품목**. 사람 눈에는 "한 집 = 한 블록"으로 보이고, 체크박스는 묶음 블록에 1개 달린다.
- 목록 상단 카운터가 **이중 표기**: `0 / 7 (합포장: 0 / 7)` — 선택수/전체수를 **품목 기준과 합포장 기준으로 나란히** 보여준다(p.15·p.16·p.19 캡처). 이 패턴이 이번 조사 전체에서 가장 인상적이었다.
- 묶음 해제는 행마다 붙은 **[주문분할]** 버튼. 묶음 생성은 출고지시 시점 팝업의 라디오 선택(§4 참조).
- 엑셀 연계까지 묶음이 SSOT로 관철됨 — 원문: *"묶음 주문건에는 동일한 운송장 번호가 업로드 될 수 있게 동일한 묶음 번호가 출력됩니다. 묶음 주문으로 업로드 하지 않는 주문건은 '주문분할' 처리 이후 엑셀을 다운로드 합니다."* (p.16)

### 네이버페이센터 — 상품주문번호/주문번호 두 컬럼, 묶음은 팝업으로 분리
근거: [주문형 판매관리 가이드](https://campaign-cdn.pstatic.net/filemanager/static/naverpay_guide/pdf/9_%EC%A3%BC%EB%AC%B8%ED%98%95_%ED%8C%90%EB%A7%A4%EA%B4%80%EB%A6%AC_713.pdf) p.6·p.13

- 발주/발송관리 목록의 첫 두 컬럼이 `상품주문번호 | 주문번호` → **행은 상품주문, 소속 주문은 컬럼 값으로만 표시**. 병합·그룹헤더 없음.
- 합포장은 **[합포장 일괄 발송처리] 팝업**에서만 다룬다(p.13). 원문: *"합포장 일괄 발송처리는 합포장 묶음 단위로 송장정보를 한번만 입력하여 한번에 발송처리를 할 수 있는 기능입니다."*
- 팝업이 **선택 범위를 스스로 확장**하는 점이 특이 — 원문: *"팝업에는 목록에서 선택한 주문건과 합포장이 가능한 모든 발송대기 주문건을 노출 합니다. (따라서 목록에서 선택하지 않은 주문도 팝업 내 노출될 수 있습니다.)"*
- 팝업 컬럼: `☑ | 주문번호 | 상품주문번호 | 배송방법 | 택배사 | 송장번호` — 여기서는 같은 묶음이 세로로 병합되어 송장번호 셀 하나를 공유한다.

### 이지어드민 — 묶음이 UI가 아니라 '파이프라인 4단계' 중 하나
근거: [발주 도움말](https://help.ezadmin.co.kr/index.php?title=%EB%B0%9C%EC%A3%BC)

- 발주 화면이 **발주 → 메모 → 매칭 → 합포** 4단계 순차 위저드. 각 단계 좌측 상단 [다음] 버튼으로 진행.
- 합포 단계 규칙(원문 요지): *수령자명·주소·전화·핸드폰 중 **2개 이상 일치**(반드시 수령자 또는 주소 포함)하는 주문을 자동 합포 처리*.
- 즉 사용자는 묶음을 "보는" 게 아니라 "통과시킨다". 목록 UI에서 묶음을 조작할 여지가 적다.

### 사방넷(풀필먼트) — 합포 키가 '엑셀 행 인접성'
근거: [발주 매뉴얼](https://www.sbfulfillment.co.kr/manual/order)

- 엑셀 발주 등록 시 원문 요지: *합포장은 **연속된 행**에서 받는분 이름·전화번호1·주소가 **모두 동일**해야 처리됨.*
- 즉 묶음 키 = (수령인, 연락처, 주소) + 행 인접성. 목록 표시 방식은 확인 불가.

### 넥스트엔진 — 묶음 자동 검출
근거: [受注管理](https://next-engine.net/functions/jyuchu/)

- 기능 목록에 `同梱対応`(합포장 대응)이 있고, 원문: *"問題がない注文は『すぐに出荷できる注文』として自動で振り分け"*, *"同梱可能な注文は自動で検出"* — 묶음 후보를 시스템이 찾아주고 사람은 확인만 한다.

## 2. 상태 축을 몇 개로 나누고 어떻게 표기하나

### 결론 먼저
**진행 축(1개, 단일 직선)** + **클레임 축(별도)** + **"처리 준비됐나" 보조 축(별도 컬럼 배지)** 의 3층 구조가 공통이다.
결제/발주확인/발송은 **한 축에 직렬로** 놓고, 클레임은 **컬럼 또는 메뉴를 분리**한다. 한 컬럼에 섞는 사례는 없었다.

### 플레이오토 — 상태 = 좌측 메뉴(페이지) 그 자체 + 페이지 내 탭
근거: PDF p.12·13·15·19·21·24 캡처

- 좌측 메뉴 `주문` 그룹: **결제완료 / 신규주문 / 출고관리 / 배송관리 / 전체 주문 조회 / 클레임주문 관리 / 기초상품 매칭 / 매칭규칙 관리**. 즉 상태 전이가 곧 페이지 이동이다.
- 페이지 안에서 다시 **건수 붙은 탭**으로 세분:
  - 신규주문: `신규주문 6` / `오늘수집 0`
  - 출고관리: `전체 7` / `출고대기 3` / `출고보류 1` / `운송장출력 3`
  - 배송관리: `전체 38` / `출고완료` / `배송중 12` / `배송완료 0` / `구매결정 0`
- **행 안의 상태는 배지**:
  - 출고상태 컬럼 — 초록 채움 배지 `운송장출력`
  - 주문상태 컬럼 — 초록 `출고완료`, 파랑 `배송중`
  - 클레임 목록 — 파랑 테두리 배지 `반품완료`, 빨강/주황 테두리 배지 `취소완료`
- **보조 축을 별도 컬럼으로 분리**한 게 핵심:
  - `출고가능(여부)` — 초록 텍스트 `가능` / 빨강 `불가(재…)` / 초록 점 ●
  - `매칭여부` — 주황 테두리 배지 `미매칭` vs 회색 버튼 `수정`
  - 진행 상태와 "지금 처리 가능한가"를 **다른 컬럼**으로 쪼갠 것. 목록에서 `불가`·`미매칭`만 눈으로 골라내면 된다.

### 네이버페이센터 — 흐름 6단계 → 관리 메뉴 4개 매핑, 클레임은 컬럼 분리
근거: 가이드 PDF p.3(판매관리 개요), p.4(주문조회 팝업)

- p.3 다이어그램: `① 주문완료(미결제확인) → ② 결제 → ③ 발주확인(발주/발송관리) → ④ 발송확인(발주/발송관리) → ⑤ 배송 Tracking(배송현황 관리) → ⑥ 구매확정(구매확정 내역)`
- 각 단계 아래 카드에 **"판매자 상태_구매자 노출 상태"** 를 병기: `주문확인_결제대기중`, `발주확인_배송준비중`, `발송처리_배송중`, `배송 Tracking_배송완료`, `구매확정_구매확정`. → **상태 이름을 2벌 운영**한다(내부 상태 vs 고객 노출 문구).
- p.8 원문: *"발주확인으로 **주문세부상태**가 변경되며, 구매자에게는 **상품준비중**으로 노출됩니다."* → `주문상태` / `주문세부상태` 2층.
- p.4 주문조회 팝업 컬럼: `상품주문번호 | 주문번호 | **주문상태** | **클레임종류** | **클레임처리상태** | 상품번호 | 상품명` → **결제 축과 클레임 축을 3개 컬럼으로 명시적으로 분리**. 캡처에서 같은 주문번호의 두 행이 `결제완료 / (공란) / (공란)` 과 `결제완료 / 취소 / 취소중` 으로 다르게 표시된다.
- 색: 네이버는 배지 대신 **평문 텍스트 + 초록 강조**(브랜드 그린)를 쓴다. 상단 요약 타일만 초록 원형 아이콘.

### 넥스트엔진 — 단일 축 9단계 + "확인대기"라는 예외 버킷
근거: [ステータス管理](https://next-engine.net/functions/jyuchu/jyuchu-status/)

- 9개 상태: `新規受付(신규접수)` → `確認待ち(확인대기)` → `引当待ち(재고할당대기)` → `入金待ち(입금대기)` → `発売日待ち(발매일대기)` → `印刷日待ち(인쇄일대기)` → `印刷待ち(인쇄대기)` → `印刷済み(인쇄완료)` → `出荷済み(출하완료)`
- 원문: *"受注伝票の内容に応じて、いずれかのステータスに自動で振り分けられます"* — 사람이 상태를 옮기는 게 아니라 **전표 내용을 보고 시스템이 자동 배분**한다.
- `確認待ち`(사람이 봐야 하는 건) 판정 조건이 **80항목 이상**, 점포별 커스터마이즈 가능. → "예외를 상태로 승격"시킨 설계.
- 표준 9개로 안 되는 분류는 **オリジナルステータス**(임의 검색조건을 상태처럼 저장)와 **受注分類タグ**(주문에 태그 부여)로 처리 — 즉 상태 축을 늘리지 않고 **태그 축을 따로 둔다.**
- 참고로 [개발자 포럼](https://developer.next-engine.com/questions/1120/)에서 운영진 답변: *"１対１の対応表はございません"* — 화면 상태와 API 필드가 1:1이 아니고 **여러 필드 조합으로 상태가 결정**된다. 즉 상태는 저장 컬럼이 아니라 **파생 계산값**.

## 3. 취소·반품 건을 목록에서 어떻게 다루나

### 결론 먼저
**조회는 별도 메뉴로 분리, 하지만 "지금 발송하면 안 되는 건"이라는 경보는 정상 목록으로 끌어온다.** 이 두 가지를 동시에 하는 게 공통 해법이다.
그리고 국내 통합솔루션의 가장 큰 실무 불만이 여기서 나온다 — **보이기만 하고 처리가 안 된다.**

### 플레이오토 — 별도 메뉴 [클레임주문 관리], 상태별 탭 11개, 그러나 처리 불가
근거: PDF p.24 캡처 + p.23

- 탭 구성(캡처 실측): `전체 17` / `취소요청 0` / `취소완료 8` / `반품요청 1` / `반품회수완료 0` / `반품완료 7` / `교환요청 0` / `교환회수완료 1` / `맞교환요청` / `맞교환완료` / `ⓘ 주문재확인 0`
- 페이지 설명 원문: *"반품이나 취소 교환같은 클레임 주문건으로 동기화된 전체 주문을 **상태별로 한 페이지에서** 확인하실 수 있습니다."*
- **결정적 한계** — 같은 페이지 원문: *"클레임 주문의 경우 **솔루션을 통해 별도 처리를 진행하지는 않고** 취소요청, 반품요청, 교환요청 건에 대하여 **해당 쇼핑몰에서 직접 처리**해주셔야 합니다"*
  → 즉 이 화면은 **읽기 전용 모니터**다. 실무자는 여기서 건을 확인하고 다시 각 오픈마켓 관리자로 로그인해야 한다. §6의 불만 2번 근거.
- 정상 목록에는 클레임을 섞지 않는다. 대신 **[동기화] 버튼**으로 취소 여부를 발송 전에 당겨온다. p.23 원문: *"솔루션에 수집된 주문건이 쇼핑몰에서 취소나 반품 또는 구매확인 등의 상태로 변경되었을때 솔루션의 주문건을 쇼핑몰과 동일한 상태로 맞춰주는 작업입니다. **신규주문 단계에서 동기화 작업 시 발송처리 전 고객의 주문 취소여부를 확인**할 수 있습니다."*
- 동기화 버튼은 `결제완료 / 신규주문 / 배송관리 / 전체주문조회 / 클레임 주문관리` **5개 페이지 모두에** 배치되어 있다(p.23 '알고가기' 박스).

### 네이버페이센터 — GNB 분리 + 정상 목록 상단에 클레임 경보 타일 + 하단에 취소 액션
근거: 가이드 PDF p.6·p.8·p.13

- 상단 GNB에 **[취소 반품 교환관리]** 가 [판매관리]와 **별도 메뉴**로 존재.
- 그런데 발주/발송관리(정상 목록) 화면 최상단에 **경보 타일 2줄**이 있다:
  - 1줄 "먼저 확인하세요!": `신규주문 지연 4건` / `배송준비 지연 0건` / **`발송전 취소요청 7건`** / `발송전 배송지 변경 0건`
  - 2줄 "발송처리를 진행해 주세요!": `신규주문 18건` / `배송준비 0건` / `자동처리 예정 0건`
  - → **취소요청·배송지변경이라는 클레임성 이벤트를 정상 작업 화면 맨 위에 카운터로 노출.** 목록에 섞지 않으면서 놓치지 않게 하는 절충.

  - `주문확인 ⓘ` : [발주확인] [발송지연 안내] [주문자 정보수정]
  - `발송처리 ⓘ` : [발송처리] [합포장 일괄 발송처리] [엑셀 일괄발송] [… 처리] [굿스플로 송장출력] [송장수정]
  - `취소처리 ⓘ` : [판매취소] [집하취소]
  - → **조회는 분리하되, 지금 이 목록에서 즉시 해야 하는 취소 액션만 같은 화면에 남긴다.**
- 별도로 `자동처리예정` 타일이 있다(p.10). 원문: *"주문일로부터 **75일 이상** 배송 및 취소/반품/교환 완료되지 않은 주문 건이 '자동처리예정'으로 노출됩니다. … 주문 상태에 따라 **90일 째 자동으로 구매확정 또는 주문 취소**가 진행될 대상이 됩니다."* → 방치된 클레임이 자동으로 불리하게 끝나는 걸 카운터로 경고.

## 4. 되돌릴 수 없는 일괄 작업(발주확인·발송처리)의 UI

### 4-1. 선택 방식 — **"선택 없이 누르면 전체 대상"이 업계 표준** (⚠️)
가장 놀라웠던 공통 관례다. 세 군데에서 동일하게 확인:

- 플레이오토 p.13 원문: *"[신규주문] 페이지에서 '출고가능' 주문건을 **선택 또는 아무 주문건도 선택하지 않고** 출고지시 버튼 클릭"*
- 플레이오토 p.15 원문: *"[출고관리] 페이지에서 특정 주문건만 출력할 경우 리스트 상에서 출력할 주문건 선택 / 전체 주문에 대한 송장 출력을 진행할 경우 **선택없이 바로 [운송장출력] 버튼 클릭**"*
- 플레이오토 p.16 원문: *"엑셀을 다운로드 받을 특정 주문건만 선택하거나 **선택없이** [통합 엑셀 다운] 버튼 클릭"*
- 플레이오토 p.19 원문: *"송장입력이 완료된 [운송장 출력] 상태의 주문을 **선택 또는 선택 없이** [출고완료] 버튼 클릭"*
- 네이버 p.13: 합포장 팝업은 아예 **선택하지 않은 주문까지 팝업에 끌어온다**(위 §1 인용).

즉 "선택 0건 = 전체"가 관례이고, **안전장치는 체크박스가 아니라 확인 팝업 문구에 몰려 있다.**

### 4-2. 확인 단계 — 팝업이 대상 건수를 **문장으로 재진술**
전 사례에서 확인 팝업 첫 줄이 "무엇을 몇 건에 대해 하는지"를 문장으로 다시 쓴다. 실측 문구:

| 작업 | 팝업 첫 문장 | 출처 |
|---|---|---|
| 출고지시 | **"전체 출고가능한 주문 13건을 일괄 출고 지시합니다."** | 플레이오토 p.13 |
| 운송장 출력 | **"선택한 [출고대기] 주문 2건의 운송장을 출력합니다."** | 플레이오토 p.15 |
| 엑셀 다운로드 | **"선택한 주문 5건을 Excel로 다운로드합니다."** | 플레이오토 p.16 |
| 출고완료 | **"전체 운송장출력 상태 주문(4건)을 출고 완료 상태로 변경 합니다."** | 플레이오토 p.19 |
| 운송장 전송 | **"출고완료 주문 23건의 택배사 운송장 번호를 전송합니다. 작업을 진행할 쇼핑몰을 선택해 주세요."** | 플레이오토 p.21 |
| 주문 동기화 | **"선택한 쇼핑몰의 주문 상태를 쇼핑몰 기준으로 동기화합니다."** | 플레이오토 p.23 |

건수는 대부분 **빨강/강조색**으로 렌더된다(캡처상 `13건`, `2건`, `5건`, `23건`이 붉은 글씨).

### 4-3. 부작용을 팝업 안에서 라디오로 고르게 한다
플레이오토 출고지시 팝업(p.13)이 가장 좋은 사례. 팝업 본문:

> "출고관리에 존재하는 출고대기, 출고보류 상태 주문 중 현재 출고지시하는 주문과 묶음기준이 동일한 주문이 존재하는 경우, 출고관리에서 자동으로 묶음처리 하시겠습니까?"
> ○ 네, 묶음 주문으로 처리합니다. **(출고지시하는 주문의 묶음번호가 변경되니 주의하시기 바랍니다.)**
> ◉ 아니오, 묶지 않습니다. ← *기본 선택이 '안전한 쪽'*

+ 그 위에 ★ 주의 문구 4줄이 붙는다(일부만 선택 시 [취소] 후 재선택 안내, 출고지시된 주문은 출고 대기상태로 변경됨, 기초상품 미매칭이면 재고관리 불가 등).

### 4-4. 비가역 경고는 **빨간 별표 블록**으로 화면에 상주
- 플레이오토 p.21 `★주의사항★`: ***"[출고완료] > [배송중]으로 한번 변경된 이후에는 전상태로 별경할 수 없습니다.** [배송중] 상태의 주문건에는 송장 보내기 처리가 불가하므로 반드시 송장전송 처리 전 정상적으로 송장번호가 업로드 되었는지 확인해주시기 바랍니다."*
- 네이버 p.8 발주확인 화면의 빨간 테두리 박스: ***"중요!** 발송기한 내 발송처리 가능한 경우에만 발주 확인 처리를 하시기 바랍니다. (발송기한 내 발송처리가 불가한 경우 발송지연 안내 처리 필요) 발주확인 후 발송기한까지 발송처리가 완료되지 않으면, **구매자 임의의 취소 처리가 가능하며, 페널티가 부과될 수 있습니다.**"*
- 사방넷 풀필먼트: `발주합치기` = 2개 이상 발주를 하나로, **원상복구 불가**. `출고취소` = **재작업 불가**. ([발주 매뉴얼](https://www.sbfulfillment.co.kr/manual/order))

### 4-5. 2단 확정 — "입력"과 "실행"을 분리
네이버 합포장 일괄 발송처리(p.13) 원문:
> "팝업 내 리스트 우측 상단에서 배송방법, 택배사, 송장번호 정보 입력 후 [선택건 적용] 버튼을 클릭하면 리스트에서 선택한 묶음의 송장정보가 일괄 입력됩니다.
> **이는 단순 일괄 입력 기능이며, 반드시 하단의 [선택건 발송처리] 버튼을 클릭해야 최종처리가 진행됩니다.**"

→ `[선택건 적용]`(그리드에 값만 채움) → 눈으로 검수 → `[선택건 발송처리]`(실제 커밋). **grid 편집과 커밋을 두 버튼으로 쪼갠 것**이 이 패턴의 핵심.

### 4-6. 실패 건 처리·재시도 — 세 가지 구현이 모두 같은 모양
1) **네이버 — 결과 요약 패널 + 실패건 엑셀 다운로드** (p.12, 캡처 실측)
   - 결과 창 제목 `송장번호 일괄등록 결과`, 본문에 `등록 100 | 성공 100(초록) | 실패 100(빨강)` 3개 수치.
   - 버튼 `[등록 실패건 엑셀 다운로드]`.
   - 안내문: *"등록 실패한 건의 실패사유를 확인하신 후 재 업로드 해주세요."*
   - 좌측 설명 원문: *"등록 성공 및 실패 건수를 확인할 수 있으며, [등록 실패건 엑셀 다운로드] 버튼 클릭 시 실패 건 리스트를 다운 받을 수 있습니다. **리스트에는 각 주문의 등록 실패사유가 표시**됩니다."*

2) **이지어드민 — [출력목록] / [오류목록] 2탭 + 상단 상태 카운터** ([배송관리 매뉴얼 PDF](https://www.ezadmin.co.kr/manual/%EC%9D%B4%EC%A7%80%EC%96%B4%EB%93%9C%EB%AF%BC_%EC%A3%BC%EB%AC%B8%EB%B0%B0%EC%86%A1%EA%B4%80%EB%A6%AC_%EB%B0%B0%EC%86%A1%EA%B4%80%EB%A6%AC.pdf) p.9 캡처)
   - `송장 발행 상태` 패널: `대기 1건 / 완료 0건 / 오류 0건 / 취소 0건 / 상태변경 0건`
   - 하단에 탭 두 개: `출력목록` | `오류목록`
   - 화면설명 원문: *"송장출력 시 오류가 생기면 **오류목록에 따로 나타납니다**. 오류사항을 확인 및 수정하시고 송장출력을 진행하세요."*

3) **플레이오토 — 비동기 작업 큐 + 작업관리 탭** (p.18 팝업 본문)
   - *"업로드하신 Excel의 작업 현황 및 결과는 **[작업관리] 엑셀 작업 탭**에서 확인하실 수 있습니다. (실패된 **작업상세 > 결과 엑셀을 다운로드 > 사유 확인 및 수정**하여 Excel 업로드해 주시기 바랍니다.)"*

→ 세 곳 모두 **① 성공/실패 카운터 → ② 실패만 모은 목록(탭 또는 파일) → ③ 건별 실패 사유 → ④ 수정 후 재투입** 4단계로 동일하다.

## 5. 한 화면 vs 두 화면 (목록·상세 배치)

### 결론 먼저
**조사한 어느 서비스도 좌우 분할 마스터–디테일을 쓰지 않는다.** 전부 "풀폭 목록 1개 + 상세는 모달/팝업 또는 별도 페이지"다.
좌측 영역은 **상세 패널이 아니라 검색·메뉴 패널**로 쓰인다.

### 사례
- **플레이오토** (p.12·13·15·19·21·23 캡처): 화면 = `좌측 메뉴 트리` + `좌측 검색 패널(탭: 검색/요약/메모/로그, 검색어 입력·기간·초기화)` + `우측 풀폭 목록`. 상세는 **행 맨 앞 [상세] 버튼 → 모달**, 메모는 **[메모] 버튼 → 모달**(메모가 있으면 버튼이 주황으로 변함). 목록을 떠나지 않는다.
  - 좌측 검색 패널에 `요약 / 메모 / 로그` 탭이 붙어 있는 게 특이 — 선택한 건의 이력을 좌측에서 훑을 수 있다. **좌우 분할의 흔적**이지만 상세 편집 폼은 아니다.
- **네이버페이센터** (p.4·6·8·10·12·13 캡처): 단일 페이지 4층 구조 — `① 상단 요약 타일(경보 7종)` → `② 검색 필터 폼` → `③ 목록(총 N개, 정렬·페이지당 노출수·조회항목 설정·엑셀다운 버튼이 목록 우측 상단)` → `④ 하단 액션바 3그룹`. 상세는 우측 상단 **[주문조회] → 모달 팝업**(p.4). 합포장·엑셀발송도 전부 모달.
- **이지어드민**: 좌측 트리 메뉴 + 우측 작업 화면(예: `주문다운로드2(재고)`)의 전통적 2단 프레임. 상세 조회는 별도 화면 이동. 송장 출력은 아예 **별도 데스크톱 프로그램(`이지송장출력`)** 으로 빠져 있다([매뉴얼 PDF](https://www.ezadmin.co.kr/manual/%EC%9D%B4%EC%A7%80%EC%96%B4%EB%93%9C%EB%AF%BC_%EC%A3%BC%EB%AC%B8%EB%B0%B0%EC%86%A1%EA%B4%80%EB%A6%AC_%EB%B0%B0%EC%86%A1%EA%B4%80%EB%A6%AC.pdf) p.9).
- **넥스트엔진** ([受注管理](https://next-engine.net/functions/jyuchu/)): 원문 요지 — *"受注状況を一覧で表示し、メール送信や納品書印刷などが一括で行えます。**受注詳細画面**からはお届け時間などの詳細情報を確認できます。"* → 일람 화면 + **수주 상세 화면**(별도 화면).

### 어느 쪽이 선호되나
- **근거 있는 부분**: 실무 흐름이 "대량을 훑고 → 예외만 열어본다"이기 때문에 **목록이 풀폭을 차지하는 쪽**이 일관되게 선택된다. 컬럼 수가 많아서(플레이오토 목록은 가로 스크롤이 필요할 정도로 컬럼이 많음) 좌우 분할이 물리적으로 성립하지 않는다는 점도 캡처에서 확인된다.
- 그래서 상세는 **모달**로 뜨고, 모달을 닫으면 목록 위치·선택 상태가 유지된다(네이버·플레이오토 모두 모달 하단이 `[닫기]`).
- **확인 불가**: "좌우 분할과 모달 중 실무자가 어느 쪽을 선호하는가"를 직접 비교한 1차 자료(설문·후기)는 찾지 못했다. 위 결론은 **채택 사례의 일치**에서 나온 관찰이지, 사용자 선호 조사 근거가 아니다.

## 6. 실무자들이 반복해서 말하는 불만 Top 5

> ⚠️ 국내 커뮤니티(네이버 카페 등)는 로그인 벽이라 접근하지 못했다. 아래는 **접근 가능한 1차 자료(공식 도움말의 자기고백, 실무 블로그, 컨설팅/경쟁사 서술)** 로만 구성했고, 근거가 약한 항목은 그렇게 표기했다.

### 1위. 결국 엑셀로 되돌아간다 (근거 강함)
- [바티블로그](https://blog.bati.ai/commerce-solution-kr/) 원문 요지: *"데이터를 모아, **엑셀로 취합해서 사용하는 경우가 많다**"* — 합배송·사은품 분할 같은 기능이 부족해 결국 엑셀에서 수동 재처리해야 한다고 서술.
- 공식 가이드가 이를 뒷받침한다. 네이버의 대량 발송처리 정식 경로가 `엑셀 다운 → 로컬 편집 → 재업로드`(p.12 `4-7. 엑셀 일괄발송`)이고, 플레이오토도 `주문 EXCEL 다운로드 → 송장 EXCEL 업로드`가 4장 중 2절을 차지한다(p.16·p.18).
- 경쟁 제품의 세일즈 포인트가 곧 불만의 증거 — [셀메이트 소개 PDF](https://www.sellmate.co.kr/doc/sellmate.pdf) p.21은 기존 업무를 *"각각 판매처 로그인 → 주문서 엑셀 다운로드 → 택배사 프로그램에 들어갈 수 있게 엑셀편집 → 업로드 송장출력 → 배송처리 → 판매처 사이트별로 송장번호 입력"* 6단계로 나열하고 *"이 모든 작업을 셀메이트 한 사이트에서 진행!"* 이라고 판다. [토글](https://www.togle.io/)은 *"별도의 프로그램 설치 불필요, 심플하고 직관적인 UI"*, *"**엑셀없이 클릭만으로** 상품을 관리"* 를 전면에 건다.

### 2위. 클레임은 보이기만 하고, 처리는 결국 쇼핑몰 관리자에서 (근거 강함)
- 플레이오토 공식 가이드 p.24 원문: *"클레임 주문의 경우 **솔루션을 통해 별도 처리를 진행하지는 않고** 취소요청, 반품요청, 교환요청 건에 대하여 **해당 쇼핑몰에서 직접 처리**해주셔야 합니다"*
- "통합관리"를 표방하면서 CS의 가장 손 많이 가는 부분이 통합되지 않는다는 자기 고백이다. 취소/반품이 있는 날마다 화면 왕복이 발생한다.

### 3위. 화면·사이트 왕복에 하루가 녹는다 (근거 강함, 수치 있음)
- [비젠소프트 인사이트](https://www.vizensoft.com/about/itinsight/read?no=665) 원문 요지:
  - *"매일 아침 각 플랫폼에 일일이 로그인해 주문 현황을 확인해야"* 하며, *"자사몰 관리자 페이지 → 스마트스토어 → 쿠팡 → 오픈마켓 셀러툴"* 을 순회하는 데 **"하루에 2~4시간씩"** 소요.
  - *"이번 달 실제 매출이 얼마야?"* 라는 질문에 답하려면 채널별 데이터를 *"엑셀로 내려받아 합산하는 작업에 **30분에서 2시간**"*.
- **건수 세기가 어렵다**는 불만이 여기에 직결된다. 그래서 네이버·이지어드민·플레이오토 모두 **화면 최상단에 카운터 타일/탭 배지**를 박아 두는 것으로 대응했다.

### 4위. 상태를 못 믿는다 — 누락·이중처리·재고 미차감 (근거 강함)
- 이지어드민의 **[미처리현황]** 화면이 존재한다는 사실 자체가 근거다. 목적 원문: *"이지어드민 내에서 **배송 업무가 정상적으로 완료되지 않은 건**이 조회"* 되며 *"주문 미처리로 인해 발생할 수 있는 문제들을 미연에 방지"*. 4개 항목이 곧 4가지 실패 유형이다:
  1. `송장출력예정` (재고만큼 불러오기로 출력될 송장 개수 — 일반/합포 2개 이상 구분)
  2. `송장전송대기` — *"배송처리한 주문이지만 **판매처로 송장이 전송되지 않은** 주문"*
  3. `배송누락확인` — *"**주문상태가 배송 상태가 아닌데 실제로는 배송이 진행된** 주문"*
  4. `취소철회확인` — *"주문자가 판매처에서 주문을 **취소 철회**한 주문"*
- 상태와 부작용이 결합되어 있어 더 위험하다. [배송처리 도움말](https://help.ezadmin.co.kr/index.php?title=%EB%B0%B0%EC%86%A1%EC%B2%98%EB%A6%AC) 원문: *"**배송처리가 되지 않으면 재고 차감이 되지 않기에** 실출고된 주문은 반드시 배송상태로 만들어주셔야 합니다."*
- 수치: [비젠소프트](https://www.vizensoft.com/about/itinsight/read?no=665) — *"분리 운영 환경에서 **주문 처리 오류율이 평균 4.2%**"* → 통합 후 *"0.3% 이하로 감소"*. 오버셀링 실사례로 신제품 런칭일 재고 100개에 주문 150건이 몰려 *"**50건의 주문 취소**가 발생했고, 고객 불만 리뷰가 쏟아졌습니다."*

### 5위. 되돌릴 수 없는데 실수하기는 너무 쉽다 (근거 강함)
- 네이버: 발주확인 → `배송준비중`. [나셀러](https://naseller.com/openmarket/4443) 요지 — 이 상태에서 고객 취소요청이 오면 **반품으로 전환**되고 고객 귀책이면 왕복 배송비가 부과된다. 판매자는 "택배사 인계 전인가?"를 건별로 판단해 (a) 취소·환불 (b) 취소 거부 후 송장 입력 중 골라야 하는데, **대량 처리 중 건별 판단이 실무 부담**이라고 서술.
- 네이버 공식 경고(p.8): 발주확인 후 발송기한을 넘기면 *"구매자 임의의 취소 처리가 가능하며, **페널티가 부과**될 수 있습니다."*
- 플레이오토 공식 경고(p.21): *"[출고완료] > [배송중]으로 한번 변경된 이후에는 전상태로 별경할 수 없습니다."*
- 사방넷 풀필먼트: `발주합치기` **원상복구 불가**, `출고취소` **재작업 불가**.
- 그런데 §4-1에서 봤듯 **"선택 없이 버튼 = 전체 대상"** 이 표준이다. 비가역 + 전체 기본값 조합은 구조적으로 사고를 부른다.

### 6위(참고). UI가 복잡하고 초기 세팅이 어렵다 (근거 중간)
- [바티블로그](https://blog.bati.ai/commerce-solution-kr/): 사방넷 *"사용자 인터페이스가 다소 복잡하며 상대적으로 가격이 비싸다"*, 플레이오토 *"초보자의 경우 자동화 기능 설정이 어려울 수 있다"*, 이지어드민 *"대규모 쇼핑몰의 복잡한 요구사항을 충족시키기에는 기능적인 한계"*.

## FOMS 에 적용할 만한 패턴 7개

> FOMS 맥락: 가구 주문 ERP. 한 집(=한 주문)에 침대·매트리스·협탁처럼 **상품주문이 여러 건**. 워크플로우 9단계(RECEIVED→…→COMPLETED). AS는 status 독립축. **CS 1명**이 접수부터 시공까지 한 건을 끝까지 따라간다. 네이버 커머스 API 주문수집 도입 중.

1. **목록 행 = 품목, 한 집은 rowspan 병합 + `N / M (합포장: a / b)` 이중 카운터**
   근거: 플레이오토 신규주문/출고관리 목록(PDF p.12·p.15). — 가구는 "집 단위(시공·배송 일정)"와 "품목 단위(규격·재고·발주)"가 둘 다 1급 단위다. 카운터 하나로는 CS가 "오늘 15집 42품목"을 못 센다. 이중 카운터는 그 둘을 한 줄에 얹는 검증된 해법.

2. **진행축(단계) 옆에 "지금 진행 가능한가" 보조 컬럼을 따로 둔다**
   근거: 플레이오토 `출고가능여부`·`매칭여부` 별도 컬럼(p.13·p.15). — FOMS의 `workflow_stage`에 "실측일 미정", "도면 미승인", "잔금 미수" 같은 블로커를 섞으면 단계가 오염된다. 블로커는 주황 배지 컬럼으로 빼면 CS가 목록에서 눈으로 골라낼 수 있다. AS 축도 이미 status 독립이므로 같은 방식으로 3번째 컬럼이 자연스럽다.

3. **탭 라벨에 건수 상시 표기, 탭이 곧 필터. 단 페이지는 쪼개지 않는다**
   근거: 플레이오토 `출고대기 3 / 출고보류 1 / 운송장출력 3`, 네이버 `목록 (총 18 개)`, 플레이오토 클레임 탭 11종. — CS 1명이 "오늘 뭐부터"를 숫자만 보고 정한다. 다만 플레이오토처럼 **상태를 좌측 메뉴(페이지)로 분해하지는 말 것**(§따라하면 안 되는 것 참조) — 탭까지가 적정선.

4. **'미처리현황' 예외 대시보드를 목록 위에 얹는다**
   근거: 이지어드민 미처리현황 4종, 네이버 발주/발송관리 상단 경보 타일 7종("먼저 확인하세요!" / "발송처리를 진행해 주세요!" 2줄 구성). — 9단계 워크플로우에서 진짜 중요한 건 "단계별 몇 건"이 아니라 **"사람이 개입 안 하면 사고 나는 건"** 이다. FOMS 후보: `실측일 지난 미완료` / `도면 승인 3일 초과` / `시공일 D-2 미확정` / `네이버 취소요청 유입` / `잔금 미수 + 출고임박`. 네이버처럼 **경보줄(빨강)과 작업줄(초록)을 2줄로 분리**하면 더 좋다.

5. **비가역 일괄 작업은 "건수 재진술 + 부작용 라디오 + 빨간 비가역 경고" 3종 세트**
   근거: 플레이오토 확인 팝업 6종의 실측 문구, 출고지시 팝업의 묶음 라디오(기본값이 안전한 쪽), `★주의사항★` 블록. — FOMS는 **일괄 완료처리로 AS가 증발한 사고**(2026-08-14)를 이미 겪었다. 그 사고의 본질이 정확히 "대상이 뭔지 문장으로 재진술하지 않았고, 부작용을 선택하게 하지 않았다"이다. `"완료처리 대상 12건 중 AS 3건은 제외됩니다"` 처럼 **제외 건수까지 문장에 넣는 것**이 이 패턴의 완성형.

6. **일괄 작업 결과는 `성공/실패 카운터 → 실패 전용 탭 → 건별 사유 → 실패건만 재시도` 4단계**
   근거: 네이버 `등록 100 / 성공 100 / 실패 100` + [등록 실패건 엑셀 다운로드] + 사유 컬럼(p.12), 이지어드민 `[출력목록]/[오류목록]` 2탭 + `대기/완료/오류/취소/상태변경` 카운터, 플레이오토 [작업관리] 엑셀 작업 탭. — **네이버 주문수집은 부분 실패가 정상 상태**다(주소 파싱 실패, 매칭 실패, 중복). 전부 성공 아니면 전부 실패로 다루면 CS가 매번 전체를 다시 돌린다. 셋 다 같은 모양으로 수렴했다는 건 이게 정답에 가깝다는 뜻.

7. **상세는 모달/슬라이드오버, 목록 이탈 금지. 좌측은 검색·저장된 필터 패널**
   근거: 플레이오토 행 앞 `[상세][메모]` 모달 + 좌측 `검색/요약/메모/로그` 탭 패널, 네이버 `[주문조회]` 팝업. 좌우 분할 마스터–디테일 채택 사례는 **0건**. — CS 1명이 하루 수십 건을 훑는 워크로드에서 스크롤 위치·선택 상태 유지가 곧 생산성이다. 플레이오토의 `메모 버튼이 메모 있으면 주황으로 변함`은 **모달을 열지 않고도 존재 여부를 아는** 값싼 트릭이라 그대로 훔칠 만하다(FOMS는 해피콜 메모/특이사항에 적용).

## 따라하면 안 되는 것 3개

1. **"선택 없이 버튼 = 전체 대상"**
   근거: 플레이오토 p.13·15·16·19에서 4번 반복되는 관례, 네이버 합포장 팝업이 미선택 건까지 끌어오는 동작(p.13).
   **왜 안 맞나**: 오픈마켓 셀러는 "오늘 들어온 걸 다 보내는" 게 기본 동작이라 전체 기본값이 합리적이다. FOMS는 반대다 — 건당 수백만 원, 시공 일정과 기사 배정이 물려 있고, 잘못 넘긴 단계는 되돌릴 때 고객 통화가 필요하다. **선택 0건이면 버튼 disabled**가 맞고, "전체 대상"이 정말 필요하면 `[조건에 맞는 전체 42건 선택]` 같은 **명시적 선택 액션**으로 분리해야 한다.

2. **엑셀 다운로드 → 로컬 편집 → 재업로드를 '정식 처리 경로'로 삼기**
   근거: 네이버 `4-7 엑셀 일괄발송`, 플레이오토 `4-2 주문 EXCEL 다운로드 / 4-3 송장 EXCEL 업로드`, 셀메이트가 이 6단계를 "없애준다"고 파는 구조, 바티블로그 *"엑셀로 취합해서 사용하는 경우가 많다"*.
   **왜 안 맞나**: 저 서비스들은 **수십 개 판매처 × 수천 건**을 다뤄야 해서 엑셀이 최소공배수 인터페이스다. FOMS는 판매처가 사실상 단일 계열이고 건수가 적은 대신 **건당 정보량이 크다**(규격, 도면, 시공 일정, 첨부). 엑셀 왕복은 (a) structured_data 같은 중첩 필드를 표현 못 하고 (b) CS 1명 환경에서 로컬 파일이 곧 SSOT 분기이며 (c) 편집 이력이 남지 않는다. 엑셀은 **읽기 전용 리포트**로만 두고, 쓰기는 화면 안에서 끝내야 한다.

3. **취소·반품·AS를 '조회 전용' 별도 메뉴로 격리하기**
   근거: 플레이오토 클레임주문 관리 원문 *"솔루션을 통해 별도 처리를 진행하지는 않고 … 해당 쇼핑몰에서 직접 처리해주셔야 합니다"* (p.24).
   **왜 안 맞나**: 플레이오토는 클레임의 **실제 권한이 오픈마켓에 있어서** 어쩔 수 없이 모니터가 됐다. FOMS의 AS는 **자체 업무**다 — 방문 일정 잡고, 기사 배정하고, 첨부 붙이고, 채널톡 PUSH를 보낸다. 여기서 조회만 되는 화면을 만들면 CS는 즉시 엑셀이나 카톡으로 이탈한다. **별도 탭으로 분리하는 것은 좋되(네이버·이지어드민처럼), 처리 액션 버튼은 반드시 그 화면 안에 있어야 한다.** 추가로 네이버 방식대로 **정상 목록 상단에 `AS 유입 N건`·`취소요청 N건` 경보 타일**을 얹어, 분리해도 놓치지 않게 하는 짝 패턴을 함께 가져갈 것.
