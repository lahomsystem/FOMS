## 결함 목록

### D-01. 두 화면이 말하는 "집"의 정의가 서로 다르다 — 숫자가 원천적으로 안 맞는다 · 심각도 **높음**

- **증상**: 이력 화면은 `external_order_no` 하나로 묶고(`naver_ingest.py:120-126`, SQL은 `129-142`), 확인 화면은 `(orderId, 수취인 tel1, 주소)` 3중 키로 묶는다(`naver_ingest.py:571` → `mapping.py:425-442`). 분할배송 1건이면 이력=1집, 확인=2집이 된다.
- **근거**: `naver_ingest.py:120-126` / `naver_ingest.py:565-579` / `foms/services/integrations/naver_commerce/mapping.py:425-442`("같은 주문번호라도 **분할배송**이면 수취인·주소가 다를 수 있다").
- **손해**: 실측 스크린샷의 이력 `전체 45집` ↔ 확인 헤더 `43집`처럼 두 숫자가 항상 어긋난다. CS가 "몇 집 남았나"를 어느 화면에서 세느냐에 따라 답이 달라져, 인수인계·일일 마감 집계에 쓸 수 없다.
- 참고: 모집단도 다르다(이력=전체 이력, 확인=`reviewed_at IS NULL` `naver_ingest.py:498-508`). 두 차이가 겹쳐 원인 추적이 불가능하다.

### D-02. 같은 화면 안에서 "집" 단위와 "상품주문 건" 단위가 15px 간격으로 섞여 있다 · 심각도 **높음**

- **증상**: 이력 화면 헤더의 [수집 확인] 배지 `naver_triage_pending`은 **링크(상품주문) 수**다(`triage_count.py:47-55` `.count()` on `ExternalOrderLink.id`). 바로 아래 필터 버튼은 전부 **집** 단위다(`naver_ingest.html:81-93`, `naver_ingest.py:145-170`). 확인 화면 헤더도 `43집` 배지와 `상품주문 140건`을 나란히 놓는다(`naver_triage.html:10-11`).
- **근거**: `templates/admin/naver_ingest.html:12` / `templates/admin/naver_ingest.html:81-93` / `foms/services/integrations/naver_commerce/triage_count.py:30-55` / `templates/admin/naver_triage.html:10-11` / 전역 nav도 링크 수: `templates/partials/shared/layout_nav.html:173-174`.
- **손해**: 메뉴 배지 `네이버 주문 140`을 보고 "140집 밀렸다"로 읽는다. 실제로는 43집이다. 업무량 추정이 3배 부풀어 인력 배치 판단이 틀어진다. 브리프 도메인 규칙 2("숫자 단위는 집으로 통일") 위반.

### D-03. 6건 묶음인데 옵션 원문은 1건만 보인다 — 규격 입력에 필요한 정보가 한 화면에 없다 · 심각도 **높음**

### D-04. 취소·반품 건은 큐에서 뺄 방법이 없다 — 영구히 쌓인다 · 심각도 **높음**

- **근거**: `templates/admin/naver_triage.html:365, 369-371, 400-409` / 큐 이탈 조건은 `reviewed_at IS NOT NULL` (`foms/web/admin/naver_ingest.py:503`, `827-853`).

### D-05. 성공·실패 알림 박스가 페이지 로드 5초 뒤 DOM에서 제거된다 — 이후 모든 피드백이 보이지 않는다 · 심각도 **높음**

- **증상**: 두 화면 모두 결과를 고정 `.alert` 박스에 쓴다(`naver_ingest.html:20, 287-290` / `naver_triage.html:26, 431-435`). 공용 런타임이 로드 5초 뒤 `.alert:not([data-foms-no-autodismiss])` 전부에 `bootstrap.Alert.close()`를 걸고, Bootstrap의 close는 **엘리먼트를 DOM에서 제거**한다. 두 박스에는 `data-foms-no-autodismiss`가 없다(pane 안 배너들에는 붙어 있다 — `naver_triage.html:129, 141, 187, 200, 243`).

### D-06. 상태 배지가 3개 축인데 시각 토큰이 겹친다 — 무엇이 막힌 건지 읽어야만 안다 · 심각도 **높음**

### D-07. 대조표의 금액·제품은 단위가 달라 언제나 "불일치"로 보인다 · 심각도 **높음**

### D-08. 페이지 이동이 발주 필터를 조용히 버리고, "전체" 버튼 숫자가 상황에 따라 사라지거나 거짓말한다 · 심각도 **높음**

- **증상 A**: 페이지 링크가 `status`와 `page`만 넘기고 `place`를 빼먹는다 → `발주확인 전` 필터를 켠 채 2페이지로 가면 필터가 풀린다.
- **증상 B**: `전체 {{ total ~ '집' if not status else '' }}`는 `(total ~ '집') if (not status) else ('')`로 파싱된다. 상태 필터를 켜면 "전체" 버튼에 **숫자가 아예 사라진다**(모수를 잃는다).

### D-24. 되돌릴 수 없는 네이버 호출의 확인창이 대상을 특정하지 않는다 · 심각도 **중간**

- **증상**: `window.confirm('네이버에 발주확인을 보냅니다. 되돌릴 수 없습니다. 계속할까요?')` — 고객명·집·상품주문 건수가 문구에 없다(`naver_triage.html:495-500`). 화면의 보조 설명 "한 집의 상품주문 전부가 함께 처리됩니다"는 확인창이 아니라 배너 안 작은 글씨에 있다(`naver_triage.html:236-238`).
- **근거**: `templates/admin/naver_triage.html:495-500, 236-238` / 붙이기 확인창도 주문 id만 (`450`).
- **손해**: 브라우저 네이티브 다이얼로그는 대상 페이지를 가린다. 방금 어느 집을 보고 있었는지 확인창 안에서 재확인할 수 없어, 잘못된 집에 되돌릴 수 없는 호출을 보낼 위험이 남는다. 브리프 도메인 규칙 7 미충족.

### D-25. 화면이 "여기서 하지 마라"고 써놓고 그 컨트롤을 배치했다 · 심각도 **낮음**

- **증상**: 진행 스텝 우측에 `담당자 지정은 실측 일정 잡을 때`(`naver_triage.html:125`), 라벨에도 `담당 영업 (실측 일정 잡을 때)`(`naver_triage.html:388-391`) — 그런데 바로 옆에 select + [담당자 지정] 버튼이 실제로 동작한다(`naver_triage.html:392-399`, 라우트 `naver_ingest.py:937-991`).
- **근거**: 위 라인 / 브리프 도메인 규칙 5.
- **손해**: 푸터의 주 액션([확인 완료])이 부차적 컨트롤 2개와 같은 줄에서 경쟁한다. "하지 말라면서 왜 있지?"라는 망설임이 매 집마다 발생한다.

### D-26. 정작 작업하는 사람(STAFF)은 업무량 화면을 볼 수 없다 · 심각도 **중간**

- **증상**: 이력·필터·상태 카드·원본 스냅샷은 ADMIN 전용이고(`naver_ingest.py:354, 996`), 확인 화면만 STAFF에 열려 있다(`naver_ingest.py:483`). 확인 화면의 "수집 상태 화면으로" 링크도 ADMIN에게만 렌더된다(`naver_triage.html:14-18`).
- **근거**: 위 라인 / 라우트 주석 `naver_ingest.py:491-493`("규격을 실제로 입력하는 사람이 CS 접수 담당이라 전 직원에게 개방한다").
- **손해**: 규격을 채우는 실사용자가 `발주확인 전 21집`·`실패 0집` 같은 자기 업무량 지표를 못 본다. 수집이 멈췄는지(만료·실패)도 알 수 없어, 조용한 중단을 CS가 먼저 발견할 방법이 없다.

### D-27. 상태 필터 숫자들의 합이 "전체"를 넘는데 화면에 설명이 없다 · 심각도 **낮음**

- **증상**: `_status_group_counts()`는 `(묶음키, 상태)` 쌍을 세므로, 한 집에 `COLLECTED`와 `FAILED`가 섞이면 **두 버튼 모두에 카운트된다**(`naver_ingest.py:145-170`). 표도 같은 규칙("해당 링크가 하나라도 있는 집")으로 뽑는다(`naver_ingest.py:223-227`). 화면에는 중복 집계라는 표시가 없다(`naver_ingest.html:79-94`).
- **근거**: `foms/web/admin/naver_ingest.py:145-170, 205-210` / `templates/admin/naver_ingest.html:79-94`.
- **손해**: 40 + 6 + 0 + 0 = 46 ≠ 전체 45. 사용자가 산수를 맞춰보다 "숫자가 틀렸다"고 판단하고 화면 전체를 불신하게 된다.

### D-28. 결과 알림 박스가 액션에서 멀리 떨어져 있다 · 심각도 **낮음**

- **증상**: 알림 박스는 두 화면 모두 **최상단**(`naver_ingest.html:20`, `naver_triage.html:26`)인데, 실제 버튼은 표의 40행 아래(`naver_ingest.html:183`) 또는 pane 푸터(`naver_triage.html:364-417`)에 있다. `show()`는 스크롤·포커스 이동을 하지 않는다(`naver_ingest.html:287-290`, `naver_triage.html:432-435`).
- **근거**: 위 라인.
- **손해**: 5초 안에 눌러 알림이 살아 있어도(D-05) 뷰포트 밖이라 못 본다. 실패했는데 성공한 줄 알고 다음 집으로 넘어간다.

### D-29. 첫 열 헤더에 접근 가능한 이름이 없다 · 심각도 **낮음**

- **증상**: `<th style="width: 2rem;"></th>` — 빈 헤더 셀(`naver_ingest.html:101`). 펼침 버튼 자체엔 `aria-label="상품주문 펼치기"`가 있다(`naver_ingest.html:125`).
- **근거**: `templates/admin/naver_ingest.html:101`.
- **손해**: 스크린리더가 12열 표에서 이름 없는 열을 읽어 열 위치 감각이 깨진다(경미하나 새 화면에서 반복하면 안 될 패턴).

### 3) 특히 위험한 3가지 (개편 설계 시 먼저 결정할 것)

- **`<span class="badge bg-primary">…</span>` 정확 마크업 2건**(#1·#2, `test_naver_triage.py:186-187`) — D-06(축별 배지 시각 분리)을 구현하면 **반드시 깨진다**. Bootstrap `badge bg-primary`를 `.erp-pro-badge--*`로 바꾸려면 이 두 assertion을 함께 갱신해야 한다.
- **`수집됨(주문 전) 2집` / `전체 2집` 붙여쓰기**(#23·#24) — D-02(단위 통일)에서 라벨을 `수집됨 · 2집`처럼 바꾸면 깨진다. 그리고 `전체` 버튼 숫자 표기를 고치는 D-08 수정과 정면으로 충돌한다.
- **버튼 태그 내부 문자열 파싱 2건**(#4·#5) — `naver-create-order-btn` / `id="triage-create-order"` 를 가진 요소가 **`<button …>` 여야 하고 그 여는 태그 안에 `disabled` 문자열이 있어야** 한다. 버튼을 `<a>`나 커스텀 컴포넌트로 바꾸거나, `disabled` 대신 `aria-disabled`/클래스로 잠그면 깨진다.

### 4) 문구가 아닌 계약 (UI 개편과 무관하지만 함께 어기기 쉬움)

- 큐/이력 묶음 단위 카운트 규약: `수집됨 링크 3 + 1` → `2집` (`test_naver_admin_surface.py:206-218`).
- 발주확인 전 필터가 `NULL`·비-OK 를 모두 포함하고, 한 건만 남아도 그 집이 뜰 것 (`test_naver_admin_surface.py:296-320`).
- 실패 링크가 있는 집은 **같은 집의 정상 링크도 함께** 보일 것 (`test_naver_admin_surface.py:112-114`).
- `PENDING_REVIEW`는 이력엔 뜨고 확인 큐엔 안 뜰 것 (`test_naver_admin_surface.py:71` vs `test_naver_triage.py:118`).
