## A. 정보구조 결정

### A.1 판정: (C) 하이브리드 — 탭 이름 "채널 정산"

- **새 탭**(탭바 맨 오른쪽, 4번째): 네이버 정산의 시스템 오브 레코드. 5종 API 데이터 전량이 여기에만 산다.
- **접점 2곳(v1.1)**: 요약 탭 1줄 스트립, 실무 탭 상태 컬럼 1개. 둘 다 **새 탭 API 가 계산한 값을 인용**만 하고 자체 계산하지 않는다.
- **탭 이름 = "채널 정산"**. 근거는 채널 확장(05 §2.2)보다 **명명 충돌 회피**가 더 급하다: 기존 실무 탭에는 이미 **"정산상태"** 컬럼이 있는데 그 뜻은 네이버 입금이 아니라 **내부 부서 차감 청구 발행 여부**다(`foms/services/settlement_rows.py:174,214-215` — `structured_data.settlement.deductions` 존재 여부, 필터값 `pending|issued`). 같은 화면에 뜻이 다른 "정산" 두 개가 공존하는 상태에서 탭까지 "네이버 정산"으로 부르면 회계팀이 필터를 잘못 걸어도 아무도 못 잡는다.
- 그래서 탭 라벨은 "채널 정산", **부제(sub)는 항상 `네이버 · 정산 예정일 기준`** 을 붙이고, 화면 어디서도 **수식어 없는 "정산"** 단독 사용을 금지한다(계약 테스트 가능: 새 partial 소스에 `>정산<` 류 단독 라벨 0건).
- 라우트/API/CSS 는 channel-agnostic: `GET /api/settlement/channel?channel=NAVER...`, CSS 접두어 `s-ch-`, 상태 노드 접두어 `data-settlement-ch-*`. 근거: `models.py` 의 `ExternalOrderLink.channel` 이 이미 같은 원칙을 선언하고 있고(02 §5.4·03 §4.1), 나중에 이름만 바꾸려면 자산 핀 계약·테스트 상수까지 전부 다시 손대야 한다.

### A.2 순수 A(별도 탭만) 스틸맨 — 그리고 기각 근거

**스틸맨**: 회계 정합성만 보면 A 가 최적이다. 접점이 0이면 축이 섞일 표면 자체가 없다. FOMS 는 이미 "완료일 단일 판정으로 이중 계상 금지"(SPEC §3.3)를 커널에 새겨 넣은 곳이고, 그 규율을 지키는 가장 싼 방법은 네이버 숫자를 기존 탭에 한 글자도 안 들여보내는 것이다. 접점 2곳은 그 자체가 "요약 탭 스트립 값이 새 탭 값과 다르다"는 새로운 회귀 표면을 만든다. 게다가 접점은 핫파일 2개(`settlement_dashboard_body.html`, `settlement_rows.py`)를 건드려 세션 충돌 위험까지 늘린다.

**기각 근거**: 접점 0은 오독을 없애는 게 아니라 **화면 밖으로 옮긴다.** 회계팀 최다 질문 1·3·6(04 §3)은 전부 "FOMS 숫자와 네이버 숫자를 견주는" 질문이다. 화면이 견주기를 거절하면 실무자는 두 화면을 엑셀에 붙여 손으로 합친다 — 그 순간 잘못된 합계가 우리 통제 밖에서 만들어지고, 우리는 그게 틀렸다는 사실조차 못 본다. 통제 가능한 곳은 화면 안이다. 다만 **견주기 ≠ 합치기**이므로, 접점은 병치와 링크만 허용하고 산술 합산은 계약으로 금지한다(§D.6). 이 제약을 붙인 C 는 A 의 안전성을 거의 그대로 유지한다.

### A.3 (B) 기존 3탭 업그레이드 스틸맨 — 기각 근거

**스틸맨**: 탭 축이 "페르소나"로 유지되고(05 §2.1), 커널 확장 → 계약 테스트 갱신은 이미 검증된 패턴이다(02 §7.2, 담당자별 매출 확장 선례). 사용자는 화면을 안 옮겨도 된다.

**기각 근거**: 기존 커널 `aggregate_settlement()` 의 모집단은 "완료일이 그 기간인 ERP 주문"이고(`foms/services/settlement_aggregation.py`, SPEC §3.3), 네이버 정산의 모집단은 "정산 예정일이 그 기간인 productOrder(+배송비·기타비용 행)"다. 모집단 단위가 N:1 이고(04 §5-2) 금액 정의도 다르다(출고가 vs 결제 정산 금액). 같은 필터바 한 벌(02 §2.5, 문서에 필터바는 정확히 한 개)이 두 기준일에 동시에 걸리면 **화면만 봐서는 "그 기간에 완료된 주문"인지 "그 기간에 정산될 금액"인지 구분 불가**하다. 이건 UI 취향 문제가 아니라 숫자가 틀리는 문제다. 게다가 커널 반환 스키마에 키를 더하는 순간 계약 테스트 4곳이 red 가 되고(02 §7.2-2), 그 갱신은 다른 세션이 동시에 만지는 파일에서 일어난다.

## C. 데이터 파이프라인

### C.1 형태 — 라이브 프록시는 불가능, 확정

web 프로세스에는 네이버 호출용 등록 IP 가 없다(03 §3.1-3.5: `client.py:279-284`·`ingest.py:11-12`·`foms/web/admin/naver_ingest.py:10-12`·`backfill.py:30` 이 같은 근거를 네 번 반복). 따라서 **enqueue → 워커 → DB → web 읽기**만 가능하고, 화면 문구는 "실시간"이 아니라 "마지막 동기화 HH:MM(N분 전)"이어야 한다.

### C.2 시간축 고정 (가장 중요한 설계 결정)

- **`settle/case` 는 `periodType=SETTLE_CASEBYCASE_SETTLE_SCHEDULE_DATE`(정산 예정일)로만 호출한다.** 다른 4개 `periodType` 은 v1 에서 호출하지 않는다 — 호출 수가 5배가 되고, 무엇보다 `settle/daily` 가 예정일 기준으로 필터되므로(Discussion #1481) 축을 맞춰야 §B-4 대조 배너가 성립한다(01 §교차 엔드포인트 분석).
- 완료일 기준 조회를 쓰지 않는 근거: 완료일은 은행 처리가 끝나야 채워져 항상 늦다(Discussion #414, 네이버 공식 권장도 예정일 기준).
- `vat/*` 는 `settleBasisDate` 축이며 **전월 말일까지만** 조회 가능(문서 명기) — settle 계열과 같은 표에 절대 놓지 않는다.

### C.3 테이블 설계 (마이그레이션 1개, slug `naver_settle_00`, `down_revision='wizsend_00'`)

공통 규칙: `channel`(String20, 기본 'NAVER') · `raw_snapshot` JSONB(원본 전량) · 조회축만 컬럼 복제(03 §4.4) · **금액은 `Numeric(16,2)`** · **날짜는 `Date`**(datetime 금지) · `sync_run_id` FK · `fetched_at`(now_utc_naive).

| 테이블 | 조회축 컬럼(인덱스) | 원자 교체 키 | 비고 |
|---|---|---|---|
| `naver_settle_daily` | `settle_expect_date`(idx)·`settle_complete_date`·`settle_method_type`·`merchant_id` | `(settle_expect_date)` | 금액 15종 전량 컬럼화(대조 배너가 전부 쓴다) |
| `naver_settle_case` | `settle_expect_date`(idx)·`settle_basis_date`·`settle_complete_date`·`pay_date`·`order_id_ext`·`product_order_id`(idx)·`product_order_type`·`settle_type`·`foms_order_id`(FK null)·`match_status` | `(settle_expect_date)` | 구매자명은 컬럼화하지 않고 `raw_snapshot` 에만 |
| `naver_settle_commission` | `settle_expect_date`(idx)·`product_order_id`·`commission_type`·`pay_means_type`·`tax_return_date` | `(settle_expect_date)` | 복합키 `product_order_id + commission_type`(01 §2) |
| `naver_vat_daily` | `settle_basis_date`(unique with `merchant_id`)·`is_final` | `(연-월)` | 8개 금액 컬럼 전량 |

| `naver_settle_sync_run` | `endpoint`·`target_date`·`started_at`·`status` | — | **소급 변경 감지 원장**: `pages`·`elements`·`sum_amount`·`prev_sum_amount`·`delta_amount`·`error` |

**왜 자연키 unique 가 아니라 날짜 단위 전면 교체인가**: `settle/daily` 의 행 카디널리티(가맹점 수 = 행 수인지, 정산 방법별로도 갈리는지)가 문서에 없다(01 §3 NOT IN DOCS). 불확실한 자연키로 upsert 를 짜면 **키가 틀렸을 때 중복 행이 조용히 쌓여 합계가 두 배가 된다.** 한 트랜잭션 안에서 `DELETE WHERE settle_expect_date=?` → `INSERT` → commit 하면 키 추정 없이도 멱등이고, 실패 시 롤백으로 직전 데이터가 그대로 남는다.

**워터마크**: 기존 패턴 그대로 `SystemSetting` 새 키 `naver_settle_sync_watermark`(03 §4.2, `watermark.py:24`·`backfill.py:55` 선례) = `{last_success_date, coverage_from, coverage_to, rolling_days, last_run_at, rev}`. 성공 구간만 전진. 전용 워터마크 테이블 불필요.

### C.4 동기화 스케줄

- **일 배치**: `scripts/maintenance/run_naver_settle_sync.py --loop --at 05:30 --window 10`(03 §7.1 패턴 b, 하루 1회 시각창 + DB 로 멱등). `start.sh` 에 `FOMS_NAVER_SETTLE_SYNC_ENABLED=1` 일 때만 도는 서브셸 1블록 추가(기존 4블록과 동형, `start.sh:34-48`).
- **시각 선택 근거**: 16:40~17:10 은 자동 발송처리 창(`--at 16:50 --window 10`)이라 피한다. 05:30 은 전일 정산이 확정될 시간대이면서 실사용자 요청이 없는 창이다.
- **롤링 재조회 창 R=14일**: 소급 변경 실사례(Discussion #3123)와 "직전 1일만 수집하지 말라"는 공식 권고(#3674)에 대응. 완결 신호가 API 에 없으므로 재조회 외에 확정 방법이 없다.
- **미래 구간**: `settle/daily` 는 `endDate = 오늘+14` 로 조회해 정산 예정 행을 미리 받는다(예정일 기준 필터라 논리적으로 가능하나 **미래 날짜 조회 허용 여부는 NOT IN DOCS → T0 실측**. 400 이면 `endDate=오늘`로 축소하고 예정액은 `settle/case` 로만 낸다).

- **백필**: rq 큐가 아니라 **스크립트(서브셸) 경로**로만 실행하고, 야간 창에서 50일 청크로 나눈다. 기본 off.

### C.6 "확정본" 규칙 (네이버가 확정을 안 알려주므로 우리가 정한다 — 화면에 규칙을 적는다)

- **롤링 창 안(예정일 D-14 ~ D+14)**: 매일 전면 교체. 값이 바뀌는 것이 정상.
- **창 밖**: 재조회하지 않는다(사실상 확정). 단 월 1회 전월 전체 재조회로 델타를 확인한다.
- **델타 발견 시**: 최신값으로 **자동 반영**하되 `naver_settle_sync_run` 에 `prev_sum_amount`/`delta_amount` 를 남기고 화면 상단에 `지난 확정 구간 N건 · ₩X 변동` 경보 배너를 띄운다. 승인 게이트는 두지 않는다(신규 mutation = manifest 2종 + 감사 라벨 계약이 딸려온다). **금지하는 것은 반영이 아니라 "조용한 반영"이다.**
- **`vat` 계열**: 익월 6일 재조회분을 `is_final=true` 로 잠그고 이후 조회하지 않는다. 화면에 "확정 기준: 익월 6일 재조회분(FOMS 자체 규칙, 네이버는 확정 시점을 제공하지 않음)" 각주 상시.

### C.7 429 / 토큰 / 권한 리스크 대응

- **절대 규칙: 새 클라이언트 파일·새 토큰 발급 경로 금지.** `client.py` 에 public 메서드 5개(`get_settle_case`·`get_settle_commission_details`·`get_settle_daily`·`get_vat_case`·`get_vat_daily`)만 추가하고 내부는 기존 `_request`(`client.py:786-846`)를 쓴다. 그러면 토큰 캐시(Redis, TTL=expires_in-300)·429/5xx 백오프·401 1회 재발급·레이트리밋 헤더 로깅을 그대로 물려받고, `EXT-TOKEN-01` 계약(`tests/contracts/test_external_token_client_discipline.py`) 등재도 유지된다(03 §6.3).
- 기존 토큰 발급은 이미 form-urlencoded·`grant_type=client_credentials`·`type=SELF`(`client.py:352-373`)로 #3751 규격을 충족한다 — **새 경로를 만드는 것만이 신규 위험이다.**
- **401 `GW.AUTHN`** 이 뜨면 코드 버그가 아니라 커머스API센터 애플리케이션에 **[정산] API 그룹 권한**이 없다는 뜻이다(#1013·#1205). 이 문구를 그대로 로그·화면 오류에 넣어 잘못된 코드 수정으로 시간을 태우지 않게 한다.
- **정산 전용 서킷 브레이커**: 정산 잡이 429 를 2회 연속 맞으면 그날 정산 동기화만 중단하고 워터마크를 전진시키지 않는다(주문 파이프라인 보호). 실패는 `sync_run.status='failed'` + 화면 지연 배지로 드러낸다.
- **금액 파싱**: `_parse_json` 은 `response.json()`(`client.py:891-899`)이라 금액이 **float 으로 들어온다.** 정산 메서드는 저장 직전 `Decimal(str(v))` 로 변환한다. float 합산은 0.01원 오차를 만들고 §B-4 대조 배너를 상시 빨강으로 만든다.

## D. 회계 정합성 가드레일 (계약으로 강제할 것)

1. **부호 규약 — FOMS 는 부호를 만들지 않는다.** `NORMAL_SETTLE_AFTER_CANCEL`·`NORMAL_SETTLE_BEFORE_CANCEL`·`QUICK_SETTLE_CANCEL`·`QUANTITY_CANCEL_RESTORE` 등 차감/환급 계열이 응답에서 이미 음수로 오는지, 양수로 오고 `settleType` 으로만 구분되는지는 **문서에 없다**(01 §1 부호 규칙은 "묶어서 합산하라"까지만 말한다). 그러므로 v1 은 **응답값 그대로 저장·합산**하고, T0 에서 `settle/daily.settleAmount == Σ settle/case` 항등식으로 실측해 확정한다. 소스에 `abs(` 로 금액을 뒤집는 코드가 없어야 한다(소스 스캔 계약).
2. **날짜 축 5종 + FOMS 1종을 라벨 없이 섞지 않는다.** `payDate`(결제일)·`settleBasisDate`(정산 기준일)·`settleExpectDate`(정산 예정일 = **화면 SSOT**)·`settleCompleteDate`(정산 완료일)·`taxReturnDate`(세금 신고 기준일) + FOMS `schedule.construction.date`(완료일 = 매출 인식). 모든 카드 헤더에 기준일 라벨 상시 노출.
3. **"입금 예정"에서 반드시 빼는 3종**: `settleMethodType='CHARGE_AMT'`(충전금 상계 — 실제 은행 입금 없음, `minusChargeAmount` 로 별도 추적)·`payHoldbackAmount`(지급 보류)·`settlementLimitAmount`(한도 보류/해제). 계약 테스트: **입금 예정 KPI 는 `settleMethodType='ACCOUNT'` 행만으로 계산된다.**
4. **KST**: API 응답은 날짜 문자열(시각 없음)이고 플랫폼 공통 규약이 KST(#32). DB 는 `Date` 타입으로 저장한다 — `DateTime` 으로 저장하면 FOMS 의 naive=UTC 규약과 충돌해 **하루가 조용히 밀린다**(프로젝트 메모리 규약). 수집 시각(`fetched_at`)만 `now_utc_naive`.
5. **재계산 금지**: 수수료·세액·정산액을 FOMS 가 다시 계산하거나 반올림하지 않는다. 수수료율(%)처럼 우리가 나눗셈으로 만든 값은 **"표시용 파생"** 각주를 단다. CSV 는 축약 없이 원 단위 원본.
6. **"정산 예정 ≠ 정산 완료"**: KPI 타일 분리, 자동 합산 금지. `settleCompleteDate IS NULL` = 미완료. 색 진하기(진함=완료/옅음=예정)로 구분하되 상태색(양호/경고/심각)과는 다른 축으로 유지.
7. **접점 합산 금지(A.1 의 계약화)**: 요약 탭 스트립·실무 탭 컬럼은 네이버 값과 FOMS 값을 **더한 수를 만들지 않는다.** 병치 + "정산" 단어 포함 라벨 + 새 탭 딥링크만.
8. **부가세 과세표준 ≠ 정산 입금액**: 부가세 블록 상단에 상시 각주 — "신고 과세표준은 결제금액 총액 기준이며, 정산 입금액은 수수료·할인·환불이 차감된 뒤 금액이라 항상 다릅니다. 수수료는 네이버가 발행하는 세금계산서로 매입세액공제 대상입니다"(04 §2.5, 총액법). 입금액으로 신고하면 매출 누락이다.
9. **VAT 전월 말일 제약 표기**: "부가세 자료는 네이버 제약으로 **전월 말일까지만** 제공됩니다(당월분은 익월 마감 후)"를 블록 헤더에 상시. 당월 조회 시 빈 화면이 나오는데 이걸 "데이터 없음"으로 그리면 오독이다.
10. **"0건" 과 "미동기화" 를 구분해 렌더**: 빈 배열을 0 원으로 그리지 않는다. 예외 큐가 비었을 때도 "예외 0건"과 "아직 동기화 안 됨"을 다른 문구·색으로(계약 테스트 대상).
11. **혜택 정산 각주**: `benefitSettleAmount` 는 합산값만 제공되며 항목별 분해는 API 로 불가(#3649) — 화면에 명시.
12. **매칭 항등식**: `매칭 + 미매칭 = 전체 건수`, `Σ 건별 = 헤더 합계 ± 표시 오차 0`. 두 항등식을 계약 테스트로 강제하고, 런타임에 깨지면 배너로 노출한다(숨기지 않는다).

### E.3 충돌 가능 지점 열거

1. **자산 `?v=` 핀 값** — 다른 세션이 같은 날 핀을 통일하면(직전 커밋 416a3acfc 가 정확히 그 작업) 같은 줄에서 충돌. 신규 자산 2개만 새 핀으로.

5. **`_GRID_HEADERS` 리터럴 순서**(실무 탭 11칸) — v1.1 접점 컬럼에서만 발생. v1 에서는 0.
