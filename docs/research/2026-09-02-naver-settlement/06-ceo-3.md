## A. 정보구조 결정

### 판정: C(하이브리드), 탭 이름 "채널 정산"

**축이 다르다는 05 의 논지가 맞다.** 기존 3탭은 페르소나 축(경영진/경리/분석)이고 네이버 정산은 데이터소스+현금 축이다. 그런데 회계팀 top-3 질문 중 1번("오늘 얼마 들어오나")과 6번("매출과 정산액이 왜 다르냐")은 본질적으로 자사+네이버 크로스라(04 §3), 순수 A 로는 못 채운다. 그래서 C.

**이름을 "채널 정산"으로 잡는 이유는 취향이 아니라 개명 비용이다.** `_TABS`(`tests/domains/test_settlement_dashboard_render.py:158-162`)는 **눈에 보이는 라벨까지 계약**으로 못 박고 있고(주석: "라벨은 사용자가 이 화면을 부르는 이름이라 계약이다"), 자산 이름을 바꾸면 `?v=` 핀 계약 + 서비스워커 캐시 함정(프로젝트 메모리 `project_sw_stale_js_version_bump`)이 따라온다. 라벨 문자열 하나는 나중에 바꿔도 2줄이지만, **네임스페이스(`settlement_channel.py` / `s-ch-*` / `data-settlement-ch-*` / `/api/settlement/channel` / `naver_settle_*` 테이블의 `channel` 컬럼)는 나중에 못 바꾼다.** 그래서 네임스페이스 중립은 비타협, 라벨은 사용자가 "네이버 정산"을 원하면 그때 2줄만 바꾸면 된다.

### 스틸맨 1 — "B(기존 3탭 업그레이드만)가 옳다"

가장 강한 형태: *탭을 늘리면 실무자가 "네이버 주문 미수금"을 두 곳에서 찾는다. 이미 실무 탭에 채널 칩 `NAVER` 가 있고(`templates/cs/partials/settlement_operations_body.html:87`), 요약 탭도 `ExternalOrderLink` LEFT JOIN 으로 채널 비중을 낸다. 즉 접점은 이미 절반 존재한다(04 §5-4). 새 탭은 새 CSS·새 JS·새 핀 계약·새 렌더 스위트를 통째로 하나 더 만드는 영구 유지비다. 데이터를 기존 카드에 녹이면 유지비 0 이다.*

**기각 근거(코드로 확인함)**:
- 집계 커널 반환 스키마가 **정확일치 계약**이다(`tests/domains/test_settlement_aggregation.py:187 test_returns_exact_schema_keys`, 반환 키 13개는 `foms/services/settlement_aggregation.py:1014-1029` 에서 확인). 여기에 네이버 정산 키를 더하는 순간 이 계약 + `test_settlement_dashboard_api.py:375` M1 스키마 계약이 함께 red 가 된다. 그건 감수할 수 있지만, 진짜 문제는 커널 구조다 — `_load_rows()` 는 "완료일 기준 ERP 주문 1건 = 1행"을 단일 순회로 집계한다. 네이버 정산은 (a) 정산예정일 축, (b) productOrder 단위(1 주문 : N 행), (c) 소급 이동하는 행이라 이 불변식 밖이다. 같은 커널에 넣으면 커널이 자기 불변식을 잃는다.
- 실무 탭 파셜은 **리터럴 "수수료" 자체가 금지**다(`tests/domains/test_settlement_operations_render.py:452-457 test_no_unbacked_teaser_features_are_rendered`, 금칙 문구 `("마감 잠금","알림톡","수수료")`). 수수료 데이터를 실무 탭에 넣으려면 이 계약을 되돌려야 한다.
- 그리드 컬럼은 **11칸 순서 정확일치**다(`_GRID_HEADERS`, `tests/domains/test_settlement_operations_render.py:111-114`, `:344` 리터럴 비교). 컬럼 추가는 계약 개정이다.
→ B 는 계약 3종 이상을 되돌려야 성립한다. C 의 크로스 접점 2개만 하면 그중 1종(그리드 헤더)만 개정하면 된다.

### 스틸맨 2 — "순수 A(별도 탭만, 기존 3탭 무변경)가 옳다"

가장 강한 형태: *충돌 0, 유지비 경계 명확, 롤백은 탭 4줄 삭제로 끝. 크로스 KPI 는 사용자가 탭을 한 번 누르면 되는 일이라 굳이 기존 파일을 열 이유가 없다.*

**부분 수용, 부분 기각**: v1 의 **출하 형태는 사실상 A** 다(이건 A 의 장점을 그대로 취한다). 다만 A 를 **최종형으로 못 박는 것**을 기각한다 — 04 §3 top-3 의 1·6 번이 미충족으로 남기 때문이다. 그래서 T12/T13 을 같은 플랜에 PENDING 으로 남기고, "v1 이 끝났으니 됐다"로 닫지 않는다. 축소가 아니라 순서라는 뜻이 이것이다. 사용자가 "한 번에"를 원하면 T12/T13 을 T9 와 묶을 수 있으나, 그 경우 정산 기존 테스트 파일 3개를 동시에 여는 세션 충돌을 감수한다는 선택임을 착수 전에 밝힌다.

## C. 데이터 파이프라인

### C.1 형태 (변경 불가 제약)

web 프로세스는 네이버를 호출할 등록 IP 가 없다(03 §3.1-3.5 의 5개 파일 docstring 근거를 재확인). 따라서 **enqueue → 워커 → DB → web 읽기**만 가능하다. 화면 문구는 "실시간"이 아니라 "마지막 동기화 HH:MM".

```
[WORKER]  run_naver_settle_sync.py --loop --at 05:30 --window 10
   └ NaverCommerceClient(5 신규 메서드) → GET /v1/pay-settle/{settle,vat}/*
   └ 일자 파티션 치환 적재 + SystemSetting 워터마크 전진(성공 구간만)
[web]     GET /api/settlement/channel  → DB만 읽음
[web]     POST /erp/settlement/channel/sync-now → enqueue only (v1.1, §F 리스크4)
```

시각 `05:30` 근거: 네이버 정산은 구매확정 익영업일 처리라 전일 마감분이 새벽에 안정된다. 그리고 자동 발송처리(16:50)와 큐를 겹치지 않게 띄운다.

### C.2 테이블 (5종, 단일 마이그레이션 `naversettle_00`)

설계 근거:
- **자연키 UNIQUE 를 걸지 않고 "일자 단위 삭제 후 재삽입"(한 트랜잭션 안)** — 이유 둘. (a) `settle/daily` 는 하루에 여러 행이 나올 수 있는데 그 카디널리티(가맹점별? 정산방법별?)가 문서에 없다(01 §3 NOT IN DOCS) → 좁은 UNIQUE 를 걸면 실데이터에서 IntegrityError 로 파이프라인이 죽는다. (b) 정산건이 다른 정산일로 **소급 이동**한 실사례가 있다(#3123) → upsert 는 옛 날짜에 유령 행을 남기지만 파티션 치환은 자연히 흡수한다.
- 금액 breakdown 은 컬럼화하지 않고 JSONB 에 둔다. 화면이 SQL 로 좁히는 축만 컬럼(`ExternalOrderLink` 의 확립된 원칙, `models.py:3550-3568` 주석의 "45집 vs 43집" 사고 근거와 동일).
- `foms_order_id` 매칭은 **`product_order_type == 'PROD_ORDER'` 인 행에만 적용**한다. `DELIVERY`/`EXTRAFEE` 행의 `productOrderId` 는 별도 채번이라(#2818) 절대 `external_order_links.external_id` 와 안 맞는다 — 이 가드가 없으면 예외 큐가 배송비 행으로 영구히 넘친다(03 §8.2 가 놓친 지점, §부록 D6).
- `channel` 컬럼 기본값 `'NAVER'` — `external_order_links.channel` 과 같은 원칙(`models.py:3526-3527`).
- 마이그레이션: `down_revision = 'wizsend_00'`(현재 단일 head 실측 확인), 상수 리터럴 동결(models import 금지), `downgrade()` 는 인덱스→테이블 역순.

### C.3 워터마크·확정본

- `SystemSetting` 키 **`naver_settle_sync_state`** 신설(전용 테이블 없음 — `watermark.py:24`/`backfill.py:55` 의 확립된 패턴). 값: `{rolling_from, rolling_to, per_endpoint:{...:{last_ok_date, last_error}}, vat_final_month, last_run_at, rev}`.
- **성공 구간까지만 전진.** 중간 실패면 그 지점에서 멈추고 워터마크를 안 옮긴다(다음 run 이 같은 구간을 다시 시도).
- **확정본 규칙(자체 정의, 네이버가 신호를 안 준다)**:
  - Settle: `settleExpectDate + 30일 < 오늘` 이면 `is_final`. 확정 행은 롤링 재조회 대상에서 제외(호출 예산 절약).
  - VAT: 전월분을 **익월 10일 이후 1회** 조회한 스냅샷을 확정으로 본다(`vat_final_month` 로 1회만). 근거: `vat/*` 는 전월 말일까지만 조회 가능(01 §4).
  - 이 규칙은 **화면에 문자로 노출**한다("정산예정일 30일 경과분을 확정으로 표시합니다"). 규칙을 숨기면 회계팀이 확정치로 신고한다.

### C.4 동기화 주기·호출 수 추정

| 작업 | 창 | 호출 수 | 워커 점유(0.5초 간격) |
|---|---|---|---|
| 일 배치 롤링 | settle/daily 1회(범위, `오늘-30 ~ 오늘+14`) + settle/case 30일 + commission-details 30일 + 페이지 여유 | **≈ 72** | **≈ 36초** |
| 부가세 월 마감(익월 10일) | vat/daily 1 + vat/case 1~3 | ≈ 5 | ≈ 3초 |
| 초기 백필 365일 | case 365 + commission 365 + daily 12 + vat 24 | ≈ 766 | ≈ 6.4분 |

- `settle/case`·`commission-details` 는 **기간 조회 자체가 불가**(단일 `searchDate`, #3709)라 일수만큼 호출이 선형으로 는다. 이게 이 설계의 비용 구조 전부다.
- 롤링 30일 근거: 구매확정 자동 8일 + 정산 1영업일 + 소급 이동 여유. 그 밖은 확정 처리로 안 부른다.
- `endDate = 오늘+14` 로 미래 예정일까지 당긴다(`settle/daily` 는 예정일 기준 필터, #1481) — "이번 주 입금 예정"(04 top-1)을 만들려면 필수.
- 호출 간격 상수는 `backfill.py:63 CALL_INTERVAL_SECONDS = 0.5`(2 RPS 고정 제약의 정확한 준수치)를 **그대로 재사용**한다. 새 상수 만들지 않는다.
- **백필은 절대 자동 실행하지 않는다.** 워커 1대·큐 FIFO 라 6.4분 백필 = 그 시간 동안 실사용자 요청(발주확인·발송처리)이 통째로 밀린다(메모리 `project_worker_redeploy_stalls_queue` 의 14분 실사례와 같은 부류). 야간에 사람이 수동 enqueue 하고, 30일 창 12개 job 으로 쪼개 진척을 저장한다.

### C.5 429·토큰 규격 리스크

- **신규 리스크가 아니다.** 429 는 이미 `RETRYABLE_STATUS`(`client.py:56`)에 있고 지수 백오프가 붙어 있다. 429 의 진짜 원인은 토큰 발급 규격 위반인데(#3709/#3751), `_issue_token()`(`client.py:352-373`)이 form-urlencoded + `grant_type=client_credentials` + `type=SELF` 로 이미 규격을 지킨다(코드 확인). 정산 메서드를 같은 `_request` 로 붙이는 한 이 표면은 안 바뀐다.
- 추가로 넣을 것 하나: **`gncp-gw-quota-limit` 헤더가 오면 그 run 을 즉시 중단하고 워터마크를 전진시키지 않는다.** 현재 `_log_rate_limit`(`client.py:848-882`)은 관측만 한다 — 정산은 순회 호출이라 관측만으로는 벌칙 구간을 그대로 다 태운다.
- 401 `GW.AUTHN` 이 오면 코드 문제가 아니라 **애플리케이션에 [정산] API 그룹 권한 미등록**이다(#1013/#1205). T0 에서 먼저 확인한다.

## D. 회계 정합성 가드레일 (비타협)

1. **부호 그대로.** `NORMAL_SETTLE_AFTER_CANCEL`/`_BEFORE_CANCEL`/`QUICK_SETTLE_CANCEL`/`QUANTITY_CANCEL_RESTORE` 는 음수로 온다(01 §1). 절대값+아이콘 치환 금지, 합계는 음수를 포함해 실제로 더한 값. 계약 테스트로 못 박는다(§F).
2. **날짜축 4종을 절대 혼용하지 않고, 화면 어디서든 "이 숫자는 O일 기준"을 상시 노출.**
   - 주문/결제일 `payDate` · 정산기준일 `settleBasisDate` · **정산예정일 `settleExpectDate`(우리의 기본축)** · 정산완료일 `settleCompleteDate`(은행 처리 후에만 값 존재) · 세금신고기준일 `taxReturnDate`(commission-details 전용).
   - 기존 3탭은 "완료일 기준"(FOMS 시공완료일)이라 **다섯 번째 축**이다. 요약 탭 상단이 이미 "매출 인식: 완료일 기준"을 박아두고 있다(`settlement_dashboard_body.html:90` 확인) — 새 탭도 같은 자리에 "정산예정일 기준"을 박는다.
   - 기본축으로 **완료일이 아니라 예정일**을 쓰는 근거: 완료일 기준 조회는 은행 입금이 끝나야 값이 채워져 더 느리다(#414 공식 권고).
3. **KST.** 커머스API 응답은 전부 KST 기준 날짜 문자열이고 시각 필드가 없다(01 공통사항). FOMS 의 naive=UTC 규약(메모리 `project_timestamp_utc_convention`)과 **충돌 축이다** — 그래서 정산 날짜는 `DateTime` 이 아니라 **`Date` 컬럼**으로 저장하고, 화면 버킷 경계는 `get_today_kst()`(date 반환, 메모리 함정 주의)로만 계산한다. 날짜를 datetime 으로 승격시키는 코드가 들어오면 그날 하루가 밀린다.
4. **재계산 금지.** 수수료·세액·정산액은 네이버가 준 값을 그대로 저장·표시한다. 표시 축약("₩62.1M")은 표시 단계에서만, 합계는 원 단위로 합산 후 마지막에 축약. 수수료율(%)만 파생 허용이며 그 정의를 각주로 쓴다.
5. **"정산 예정 ≠ 완료".** 예정액은 확정 금액이 아니므로 완료액 KPI 에 합산하지 않고 별도 타일로 분리한다. 색은 같은 hue 의 진하기 차이(진함=완료), **상태색(양호/경고/심각)과는 별개 축**으로 유지(라벨+아이콘 이중 신호).
6. **충전금(`CHARGE_AMT`) 라벨링.** `settleMethodType=CHARGE_AMT` 행은 마이너스 충전금과 상계돼 **통장에 안 찍힌다**. 입금 대사 대상은 `ACCOUNT` 행만이고, 화면은 두 값을 별도 줄로 나눠 "계좌입금 예정 ₩X / 충전금 상계 ₩Y(통장 미반영)"로 쓴다. 합산 한 줄로 보여주면 회계팀이 은행 내역과 못 맞춘다.
7. **VAT 전월 말일 제약 표기.** `vat/*` 는 당월 조회가 불가하다(01 §4, 문서 명기). 부가세 블록 상단에 "당월 데이터는 익월 마감 후 제공됩니다(네이버 제약)"를 **빈 화면이 아니라 문구로** 띄운다 — 안 그러면 "이번 달 부가세 0원"으로 읽힌다.
8. **은행 실계좌 대사는 범위 밖**임을 각주로 명시("이 금액이 실제 계좌 입금과 자동 대사되지는 않습니다").
9. **`benefitSettleAmount` 는 합산값만 제공**되고 항목별 상세 API 가 없다(#3649). "혜택 정산" 카드에 상세 드릴다운을 만들지 않고, 각주로 "항목별 내역은 스마트스토어센터 엑셀에서만 확인 가능"을 쓴다. 없는 걸 있는 척하는 UI 금지.
