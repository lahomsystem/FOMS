# 05 — 회계 SW 설계 전문가 페르소나: 네이버 정산 대시보드 IA·시각화 판정

- 작성: 2026-09-02 (R5-design-expert)
- 페르소나: 15년차 정산/대사 화면 설계자 (Amazon Settlement Report, Shopify Payments Payouts, Stripe Balance/Payouts, Xero/QuickBooks 은행 대사, 더존 Smart A·이카운트 정산 모듈 경험 가정)
- 전제: 소스 미편집(리서치 전용). `docs/specs/2026-08-31-settlement-dashboard_SPEC.md`, `docs/design/settlement-dashboard-research-2026-08/`, `settlement-dashboard-v1/v2/v3` 목업, `models.py:3521`(`external_order_links`) 확인 완료. 네이버 정산 API 5종 원문 필드는 `apicenter.commerce.naver.com` fetch 가 이 세션에서 차단돼(WebFetch 거부) **원문 대조 못함** — §3 은 마켓플레이스 정산 API 일반형 지식 기반 "추정"이며 실제 필드명은 R1-api-spec 산출물로 교차검증 필요.

## 결론 (10줄 요약)
1. **판정 = 옵션 C(하이브리드), 세부적으로는 "네이버" 대신 "채널 정산" 탭명 채택** — 지금 결정해도 되고, 나중에 바꿔도 손해가 적은 이름을 지금 고른다.
2. 이유: 탭 3개(요약/실무/분석)는 **페르소나 축**, 네이버 정산은 **데이터소스+현금기준 축** — 축이 다른 것을 억지로 포개면(B) 세 탭 모두 "이게 매출 인식이야 현금 정산이야"를 매번 재설명해야 한다.
3. 순수 A(네이버 정산 탭만, 기존 3탭 무변경)는 페르소나가 화면을 두 번 오가야 해서 실무자 워크플로가 끊긴다. 순수 B는 SSOT 오염(완료일 매출과 정산일 현금을 한 카드에 섞음) 위험이 크다.
4. C = **새 탭(시스템오브레코드) + 요약 탭 KPI 스트립 1줄 + 실무 탭 상태 컬럼 1개** 조합. 3곳 모두 "네이버 정산"이 아니라 **그 탭 문맥에 맞는 요약치**만 보여주고, 상세는 항상 새 탭으로 링크.
5. 새 탭 내부는 **날짜별(daily) 정산 총계 + 건별(case) 대사 + 수수료(commission) 상세 + VAT 요약 + 예외 큐** 5블록 — 정확히 API 5종에 1:1 대응, 3버전 목업의 차트 어휘(lineChart/columnChart/barList/meter, **도넛·파이 금지**)를 그대로 재사용.
6. 핵심 가드레일: **정산일(네이버) ≠ 완료일(FOMS 매출인식)** 이 화면 전체에서 라벨로 항상 노출돼야 한다 — 섞으면 CEO L-1급 회귀(금액이 다른데 같은 라벨) 재발.
7. 취소/환불은 **음수 행으로 유지**(절대값+아이콘 치환 금지), 정산 대상 KST 자정 경계, 반올림은 원 단위 절사 규칙을 API 응답 그대로(재계산 금지).
8. "정산 예정" vs "정산 완료"는 색이 아니라 **라벨+아이콘 이중 신호**로 분리(상태색 재사용 금지 규칙, design_brief.md 규칙 8 재사용).
9. MVP v1 = daily 트렌드 + case 대사 표 + 예외 큐(미매칭/음수) + KPI 스트립. 뒤로 미룸 = commission 유형별 세부 차트, VAT 신고용 export, 캘린더 히트맵.
10. 5대 설계 리스크: (1) 이중 SSOT 착시, (2) 매칭 실패(case↔order) 침묵 누락, (3) 캘린더 창 밖 데이터 상시 미표시, (4) 라운딩 재계산 오류, (5) 향후 채널 확장 시 탭 폭발 — 전부 §5 에 완화책.

## 2. 정보구조(IA) 판정

### 2.1 세 옵션의 원리적 비교

**옵션 A — 맨 오른쪽 "네이버 정산" 별도 탭, 기존 3탭 무변경**
- 장점: SSOT 분리가 가장 깔끔(네이버 데이터는 네이버 탭에만 있다). 구현 격리도 최대(§13.1 "행 표면은 aggregates 와 분리" 원칙과 결이 같음).
- 단점: **탭 축이 깨진다.** 지금 3탭은 "누가 무엇을 하려고 왔는가"(경영진 요약 / 경리 실무 / 분석) 축인데, 4번째 탭만 "어느 채널 데이터인가" 축으로 분류 기준이 바뀐다. 사용자는 "네이버 주문의 미수금은 어디서 보나?" 를 물을 때 실무 탭과 네이버 탭 두 곳을 오가야 한다 — task-tab 정합성 붕괴.
- IA 원칙 위반: Nielsen 류의 "분류 축을 화면 전체에서 하나로 유지하라"에 정면으로 위배. 탭바가 "요약·실무·분석·네이버정산"이 되는 순간 사용자는 매번 "이건 페르소나 탭인가 채널 탭인가"를 재해석해야 한다(인지부하 증가).

**옵션 B — 기존 3탭에 네이버 데이터를 녹여 업그레이드**
- 장점: 탭 축 유지(페르소나 정합성 100%). 사용자가 화면을 안 옮겨도 됨.
- 단점: **의미론 충돌이 구조적이다.** 요약 탭의 "매출"은 완료일 기준 출고가(매출 인식, 발생주의)이고, 네이버 정산은 정산일 기준 현금 지급(현금주의)이다. 같은 카드 안에 두 숫자를 나란히 놓으면 "이번 달 매출 2.1억"과 "이번 달 네이버 정산 6,200만"이 같은 축인 것처럼 보여 오독 유발 — SPEC §3.5 가 이미 "수금 근사를 실입금으로 오독" 위험을 §14 위험 표에서 별도 관리하는 것과 같은 급의 함정이다. 게다가 기간 선택기(일/주/월 + 전월비교)가 두 기준일(완료일 vs 정산일)에 동시에 적용되면 필터 결과가 "그 기간에 완료된 주문"인지 "그 기간에 정산된 금액"인지 화면만 봐선 구분 불가.
- IA 원칙 위반: "한 카드=한 진실"(single source of truth per surface) 원칙 위배. 완화하려면 카드마다 기준일 라벨을 이중 표기해야 하는데, 그러면 결국 옵션 C 의 복잡도를 B 안에서 재발명하는 꼴이 된다.

**옵션 C — 하이브리드(시스템오브레코드 탭 + 요약 KPI 스트립 + 실무 상태 컬럼)**
- 페르소나 축(탭)과 데이터소스 축(정산 탭 내부)을 **분리해서 둘 다 만족**시킨다: 탭 분류는 그대로 "누가 왜 왔는가"를 유지하되, 그 안에서 네이버 관련 정보는 "이 페르소나가 지금 필요한 최소치"만 보여주고 상세는 항상 새 탭으로 연결한다.
- A 의 단점(화면 왕복)은 요약/실무 탭에 KPI 스트립·상태 컬럼을 심어 완화. B 의 단점(의미론 충돌)은 새 탭을 시스템오브레코드로 격리해 완화.
- 비용: 구현 표면이 3곳(새 탭 + 요약 스트립 + 실무 컬럼)으로 늘어난다. 그러나 셋 다 **읽기 전용이고 기존 SSOT 함수를 재사용**하는 얇은 확장이라 SPEC 이 이미 확립한 "SSOT 재사용" 원칙(13.3-5)을 넘지 않는다.

### 2.2 향후 채널 확장(쿠팡·카카오 등) — "네이버 탭"이 아니라 "채널 정산" 탭

지금 "네이버 정산"이라는 이름으로 탭을 만들면, 쿠팡 정산 API 를 붙이는 날 탭이 5개, 6개로 늘어난다. 이건 스케일하지 않는다 — 탭바는 유한한 자원이고, 탭이 채널 수만큼 늘면 그 자체가 다시 "채널 축 vs 페르소나 축" 혼란을 재생산한다(§2.1 A 의 문제가 채널마다 반복).

**설계 원칙**: 탭 이름과 라우트를 **"채널 정산"(channel-agnostic)** 으로 잡고, 내부에 채널 스위처(세그먼트 컨트롤: 네이버 | 전체채널 | 향후 쿠팡...)를 둔다. v1 에서는 네이버 단일 채널이라 스위처가 사실상 "네이버" 한 알만 있어도 되지만, **라우트·API·CSS 컴포넌트 이름에 `naver` 를 하드코딩하지 않는다** — `channel=NAVER` 쿼리 파라미터, 컴포넌트 클래스는 `s-channel-*` 류로. `models.py:3521` 의 `external_order_links.channel` 컬럼이 이미 "v1 은 NAVER 뿐이지만 컬럼으로 둬 채널 확장을 막지 않는다"는 주석으로 이 설계를 선언하고 있다 — 화면 설계도 DB 설계와 같은 원칙을 따라야 정합적이다.

### 2.3 기간 선택기 일관성

새 탭 내부의 기간 토글은 기존 요약/분석 탭과 **같은 컴포넌트(같은 CSS 클래스, 같은 일/주/월 세그먼트)** 를 재사용하되, 기준일 라벨을 명시적으로 다르게 붙인다:
- 요약/분석 탭: "완료일 기준" (기존 그대로)
- 채널 정산 탭: "**정산일 기준**"(네이버 `settleCompleteDate`/`settleExpectDate` 추정 — R1 확인 필요)

같은 시각적 언어(토글 모양)를 쓰되 라벨로 의미를 분리하는 것은 §1 패턴 규칙 8(역할별 밀도 차등)과 dataviz 팔레트 규칙(형태는 재사용, 의미는 라벨로)의 자연스러운 연장이다.

## 4. 회계 정확성 가드레일

1. **부호 규칙**: 취소·환불·조정은 항상 **음수 값 그대로 표시**(절대값 변환 후 "환불"이라는 텍스트로만 구분하는 방식 금지). 합계 라인은 음수를 포함해 실제로 더한 값이어야 하고, "정산완료액 KPI"에 취소분이 이미 반영됐는지/별도인지 라벨로 명시. Amazon 정산 리포트가 "Order/Refund/Adjustment 를 별도 행으로, 부호 있는 금액으로" 유지하는 것과 동일 원칙.
2. **날짜 기준 3종 분리 — 절대 혼용 금지**:
   - 주문일(네이버 발주일) / 완료일(FOMS 매출 인식, `schedule.construction.date`) / 정산일(네이버 `settleExpectDate`/`settleCompleteDate` 추정).
   - 화면 어디서든 "이 숫자는 O일 기준"이라는 라벨을 상시 노출(요약 탭이 이미 "완료일 기준"을 상단에 박아둔 관례 — `templates/cs/partials/settlement_dashboard_body.html:90` 부근 `s-who` 스트립과 동일 패턴 확장).
   - 기간 필터도 "그 기간에 완료된 주문" vs "그 기간에 정산된 금액"이 다른 모집단임을 배너로 고지(§3.1 "정산 대사 요약" 블록의 존재 이유).
3. **기간 경계는 KST 자정**: 네이버 API 응답의 날짜가 KST 기준인지 UTC 기준인지 R1 검증 필수(NAIVE UTC 관례 — 메모리 "naive timestamp=UTC 규약"과 충돌 지점). 화면의 "일별" 버킷 경계는 사용자가 보는 KST 자정과 반드시 일치해야 하며, 어긋나면 그날 매출이 하루 밀려 보이는 침묵 오류가 난다.
4. **반올림/절사**: 네이버가 이미 계산한 수수료·세액 값을 **그대로 표시**하고 FOMS 가 재계산·재반올림하지 않는다(정합성 SSOT는 네이버 응답 자체). 화면에서 표시 자릿수를 줄일 때(예: "₩62.1M")도 내부 값은 원 단위 그대로 유지하고 합계는 원 단위 합산 후 마지막에만 축약 표시.
5. **"정산 예정" vs "정산 완료" 분리**: 같은 색 계열의 진하기 차이(진함=완료/옅음=예정)로만 구분하고, 상태색(양호/경고/심각)과는 별개 축으로 유지(design_brief.md 규칙 8 — 상태색 재사용 금지). "예정"은 확정 금액이 아니므로 KPI 합계에 자동 합산되지 않고 별도 타일로 분리(§3.1 KPI 스트립처럼).
6. **은행 입금 대사**: v1 범위에서는 "네이버 정산 API 응답 = 정산완료"까지만 다루고, 실제 은행 계좌 입금 확인까지는 **범위 밖**(별도 재무 시스템 영역, SPEC 이 이미 "수금일 실기록 없음"을 v1 비목표로 명시한 것과 동일 수준의 절제). 화면에는 "이 금액이 실제 계좌 입금과 자동 대사되지는 않습니다" 각주를 둔다.
7. **CSV/Excel export 컬럼셋(더존 Smart A/이카운트 연동 가정)**: 최소 컬럼 = 정산일, 주문번호(FOMS), 채널 주문번호, 고객명, 과세유형, 공급가액, 세액, 판매수수료, 결제수수료, 기타수수료, 정산액, 매칭상태, FOMS 완료일. 더존/이카운트는 통상 전표 업로드 시 거래일자·거래처·공급가액·세액을 분리된 열로 요구하므로 **공급가액과 세액을 이미 분리해 둔 열 구조**가 그대로 임포트 친화적이다(vat/case 매핑이 이 요구를 정확히 충족 — §3 표 근거).
8. **동기화 감사 추적**: 새 탭 헤더에 "최종 동기화 시각 + 커버리지 갭"을 상시 고정(패턴 9). 워터마크 기반 폴링(브리프 "네이버 API 호출은 WORKER 단일 서비스" 제약)이라 지연·누락 가능성이 구조적이므로, 지연 시 "지연 없음" 배지를 "N시간 지연" 경고로 바꾸는 임계값 로직이 필요(임계값은 R2/R3 산출물의 실측 폴링 주기에 맞춰 결정 — 이 문서에서 숫자 확정 안 함).
9. **데이터 결측/지연 시 표시**: 빈 배열을 "0"으로 그리지 말고 "동기화 대기"/"해당 기간 데이터 없음(수집 전)"을 구분(완료 대시보드의 "완료일 미상 버킷 암묵 drop 금지" 원칙, SPEC §14 위험표와 동일선상). 예외 큐가 비었을 때도 "예외 0건"과 "아직 동기화 안 됨"을 구분되게 표기.

## 5. 최종 추천

### 5.1 판정: 옵션 C(하이브리드), 탭명은 "채널 정산"

- **새 탭**(요약/실무/분석 옆, 맨 오른쪽): 시스템오브레코드. §3 5블록 전부(daily 트렌드·case 대사표·commission 구성·vat 표·예외 큐).
- **요약 탭**: 기존 KPI 히어로 줄 옆(또는 "채널별 매출 비중" 카드 안)에 "네이버 정산완료 ₩62.1M · 정산예정 ₩8.4M · 예외 3건" 한 줄 스트립만 추가, 클릭 시 새 탭으로 이동. 새 숫자를 만들지 않고 새 탭이 계산한 값을 그대로 인용(SSOT 재사용).
- **실무 탭**: 주문 행에 "네이버 정산" 상태 컬럼 1개 추가(`external_order_links` 조인, 값: 정산완료/정산예정/미매칭/해당없음). 버튼(입금확인/정산청구)과는 별개 — 이 컬럼은 표시 전용, 액션 없음(v1 규칙).

### 5.2 MVP(v1) 범위

**포함**
- 새 탭: KPI 스트립, daily stacked column, case 표(그룹 접기+페이지네이션), commission 구성 barList, vat/daily+case 병합 표, 예외 큐(기존 워크벤치 딥링크).
- 요약 탭 1줄 스트립, 실무 탭 상태 컬럼 1개.
- CSV export(컬럼셋 §4-7).
- 동기화 상태 헤더(최종 동기화 시각).

**뒤로 미룸(v2+)**
- 캘린더/타임라인 형태의 정산 예정일 뷰(패턴 7) — 네이버 정산 주기가 규칙적이면 ROI 낮음, R1 실측 후 재평가.
- 결제수단별 세부 차트(개념적으로 commission-details 안에 있지만 v1은 수수료 유형까지만, 결제수단 축은 드릴다운 표로 대체).
- 채널 스위처 실동작(쿠팡 등 실제 2번째 채널이 붙기 전까지는 UI 자리만 예약, "예정" 배지).
- 은행 입금 실계좌 대사(§4-6, 범위 밖 명시).
- 세금계산서 자동 발행 연동.

### 5.3 5대 설계 리스크 & 완화책

| # | 리스크 | 완화책 |
|---|---|---|
| 1 | **이중 SSOT 착시** — 사용자가 요약 탭의 "매출"과 새 탭의 "정산액"을 같은 숫자로 오인 | 두 카드 모두에 기준일 라벨 상시 표기 + 요약 탭 스트립은 "정산"이라는 단어를 반드시 포함(예: "네이버 정산완료"이지 "네이버 매출" 아님) + §3.1 "정산 대사 요약" 블록으로 차이를 항상 노출 |
| 2 | **매칭 실패(case↔order) 침묵 누락** — 미매칭 정산행이 화면 어디에도 안 잡히고 합계에서만 조용히 빠짐 | 예외 큐를 새 탭의 1급 시민 섹션으로(스크롤 안 필요, 접지 않음) + 합계 KPI 옆에 항상 "매칭률 %" 타일 동반(패턴 5·10) + 계약 테스트로 "예외 건수 합 + 매칭 건수 합 = 전체 건수" 항등식 강제 권고(구현 단계 제안) |
| 3 | **캘린더/기간 창 밖 데이터 상시 미표시** — 워터마크 폴링 지연이 "그 기간엔 정산 데이터가 원래 없다"처럼 보임(네이버 피드가 "마지막 변경 시각"으로 색인되는 것과 유사한 함정, 프로젝트 메모리 사례) | 동기화 상태 헤더(§4-8)를 데이터 없음 상태와 분리해서 렌더 — "0건"과 "동기화 대기"를 시각적으로 다른 문구/색으로 |
| 4 | **라운딩 재계산 오류** — FOMS 가 수수료·세액을 자체 재계산해 네이버 원본과 다른 숫자를 보여줌 | §4-4 원칙(네이버 응답값 그대로 저장·표시, FOMS 는 표시 자릿수만 축약) + CSV export 는 원 단위 원본 그대로 |
| 5 | **향후 채널 확장 시 탭/컴포넌트 폭발** — 쿠팡·카카오 정산이 붙을 때마다 새 탭·새 CSS 클래스가 늘어남 | §2.2 "채널 정산"(channel-agnostic) 명명 원칙을 지금부터 강제 — 라우트·API·CSS 클래스에 `naver` 하드코딩 금지, `channel` 파라미터화. `external_order_links.channel` 컬럼 설계와 동일 원칙으로 화면도 맞춘다 |
