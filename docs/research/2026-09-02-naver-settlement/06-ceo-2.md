# CEO #2 판정 — 네이버 정산 대시보드 (렌즈: 사용자 가치 · 화면 완성도)

## 결론 (10줄)

1. **판정 = C(하이브리드).** 새 탭 1개(맨 오른쪽) + 요약 탭 크로스 스트립 1줄. 실무 탭 접점은 v1.1로 미룬다.
2. **내부 이름은 `channel`로 확정**(라우트·API·CSS·JS·DB 컬럼에 `naver` 하드코딩 금지). **화면 표시 이름만 사용자 확인 대상** — 권장은 탭 이름 `채널 정산` + 탭 힌트 `네이버`(기존 `s-tab-name`/`s-tab-hint` 2줄 마크업 그대로, `settlement_dashboard_body.html:63-78`).
3. **"API가 주는 모든 데이터"는 v1에서 100% 존중하되, 존중의 층을 나눈다** — **적재(DB) 100% · 내보내기(CSV) 100% · 화면 렌더는 단계적**. 47개 카탈로그 필드 전부가 v1에 적재·내보내기되고, 그중 화면 블록에 즉시 그려지는 것이 41개, 나머지 6개는 v1.1 표로 간다(§B 소진표).
4. **한 탭 = 한 스크롤 괴물**을 막는 장치가 이 설계의 핵심이다: 위쪽 절반(동기화 헤더·KPI 6타일·일별 흐름·정산 구성 워터폴)은 **항상 고정**, 아래쪽 절반만 **원장 스위처**(건별 / 수수료 / 부가세 / 예외)로 갈린다. 중첩 탭이 아니라 "고정 컨텍스트 + 교체되는 작업면"이다(Stripe Balance·Shopify Payouts 형).
5. 그래프 어휘는 기존 탭과 **동일**하다 — `columnChart`/`lineChart`/`sparkSvg`/`barList`/share bar/meter만. 파이·도넛 금지, 외부 차트 라이브러리 금지(계약 테스트 `test_settlement_dashboard_render.py:468`, `:453`). 신규 렌더러는 **워터폴 하나뿐**(부동 막대 = `columnChart` 변형).
6. **파이프라인의 정본 규칙 = "하루 = 원자 교체 단위"(replace-by-day).** 네이버가 완결 신호를 안 주고 소급 이동이 실증됐으므로(#3123/#3674), 자연키를 추측하지 말고 `(channel, search_date, period_type)` 파티션을 트랜잭션 안에서 통째로 교체한다. 소급 변경은 교체 전후 diff로 **감지해서 예외 큐에 올린다**.
7. **호출량은 문제가 아니다.** 롤링 30일 일 배치 = 61요청 ≈ 31초(0.5초 간격), 초기 백필 180일 = 372요청 ≈ 3분. 진짜 리스크는 호출량이 아니라 **토큰 발급 규격 위반 벌칙(#3751 → 429 도미노)**이고, 그건 기존 `client.py`를 재사용하는 것으로 이미 회피돼 있다.
8. **충돌 표면을 5 hunk로 압축했다.** 요약 탭 크로스 스트립을 `channel.js`가 렌더하게 하면 `dashboard.js`·`settlement_aggregation.py`·`aggregates` 스키마를 **한 줄도 안 건드린다** — 정산 5스위트 중 가장 깨지기 쉬운 "커널 반환 스키마 정확 일치"·"M1 스키마 정확 일치" 계약을 통째로 회피한다.
9. **회계 정합성의 1순위는 부호와 축이다.** 네이버 응답값 재계산 금지(표시 축약만), 취소·환급은 음수 그대로, 기준일 5축 셀렉터의 기본값은 **정산 예정일**(settle/daily와 정렬, #1481), 화면 어디서나 "정산 예정일 기준(완료일 아님)" 상시 라벨.
10. 일정 = **`**C` 릴레이 등급, v1 22 task**(3~4세션). v1.1 5 task. 완료 기준은 신규 계약 2스위트 + 파이프라인 멱등·소급감지·부호 항등식 + 스테이징 실계정 읽기 1회 실측(NOT IN DOCS 5건 확정).

## A. 정보구조 결정

### A-1. 판정: C(하이브리드) — 새 탭 + 요약 스트립 1줄, 실무 접점은 v1.1

| 옵션 | 사용자 가치 | 화면 완성도 | 판정 |
|---|---|---|---|
| A 별도 탭만 | 상세는 완벽, 크로스 질문(Q1·Q6, 매일·고통 높음)은 영원히 두 화면 왕복 | 새 탭 안은 자유롭게 설계 가능 | 부분 채택 |
| B 기존 3탭 업그레이드만 | 크로스 질문은 좋아지나 "모든 데이터+그래프" 요구를 **물리적으로 못 담는다** | 요약 탭은 12컬럼 5카드 고정 좌표(`settlement-dashboard.css:197-217`), 분석 탭은 span 카드 8장 — 5종 API를 얹으면 카드 20장 | 기각 |
| **C 하이브리드** | 상세는 새 탭, 크로스 KPI는 요약 탭 1줄 | 새 탭 내부를 "고정 컨텍스트 + 원장 스위처"로 설계 가능 | **채택** |

**C를 고르는 결정적 근거는 "요구 규모"다.** 사용자 요구는 5종 API × 47개 데이터 포인트 전량 + 그래프다(`01-naver-settle-api-spec.md` §데이터 카탈로그 #1~47). 이 규모는 기존 3탭 어디에도 안 들어간다 — 요약 탭 그리드는 `.s-card--main{1/10,2/4}` 처럼 **명시 좌표로 못 박힌 5카드 배치**라 카드를 하나 더 끼우면 좌표를 전부 다시 짜야 하고(2026-09-02에 이미 폭·높이 개편을 한 화면이다, 796d26982), 분석 탭은 이미 span 카드 8장이 차 있다. B는 "섞으면 헷갈린다"는 이유(축 충돌) 이전에 **자리가 없다**는 이유로 먼저 탈락한다.

### A-2. 탭 이름: 내부는 `channel` 확정, 표시 이름은 사용자 확인

- **되돌릴 수 없는 것(지금 확정)**: 라우트·API 경로(`/api/settlement/channel/*`)·CSS 접두어(`s-chn-`)·데이터 속성(`data-settlement-chn-*`)·DB 테이블(`naver_settle_*`이되 `channel` 컬럼 보유)·JS 파일(`channel.js`)·탭 키(`data-settlement-tab="channel"`). `external_order_links.channel` 컬럼이 이미 "v1은 NAVER 뿐이지만 컬럼으로 둬 채널 확장을 막지 않는다"(`models.py:3526-3527`)고 선언했으므로, 화면도 같은 원칙을 따르는 게 정합적이다.
- **되돌릴 수 있는 것(질문 대상)**: 탭에 찍히는 **글자**. 권장안은 `<span class="s-tab-name">채널 정산</span><span class="s-tab-hint">네이버</span>` — 확장성 있는 이름과 오늘의 구체성을 둘 다 얻는다(요약 탭이 `요약`/`경영진`으로 이미 쓰는 2줄 패턴, `settlement_dashboard_body.html:63-68`).
- **`s-chn-` 접두어를 쓰는 이유**: `s-ch-`는 이미 임자가 있다 — `.s-chbar`/`.s-chlegend`가 요약 탭 "채널별 매출 비중" 카드에 쓰인다(`settlement_dashboard_body.html:214-215`). `grep -rn "s-chn"` 결과 0건으로 충돌 없음(본 세션 실측).

### A-3. 스틸맨 2건과 기각 근거

**스틸맨 ① "순수 A가 맞다 — 기존 3탭을 한 글자도 건드리지 마라."**
정산 대시보드는 최근 2주에 폭·높이 개편(796d26982) → 집중 모드 버그픽스(606a178e3) → 자산 핀 CI red 수정(416a3acfc)을 연달아 겪은 화면이다. 계약 테스트가 425개 이상이고 그중 다수가 **정확 일치(exact match)** 방식이라, 기존 파일에 손대는 것 자체가 회귀 비용이다. 새 탭만 추가하면 기존 파일 hunk는 4개(자산 링크·탭 버튼·pane·script)로 끝난다. 크로스 KPI는 "나중에 필요해지면 그때" 붙여도 늦지 않다.

→ **기각 근거**: 요약 탭 크로스 스트립의 실제 비용이 이 스틸맨이 가정하는 것보다 훨씬 싸다. 스트립을 **`channel.js`가 렌더**하게 하면(요약 pane 안에 빈 앵커 `<div id="foms-settle-chn-strip">` 한 줄만 서버 렌더) `dashboard.js`도, `settlement_aggregation.py`의 커널 반환 스키마도, `aggregates` API의 M1 스키마도 **전혀 안 건드린다**. 즉 기존 파일 hunk가 4개에서 5개로 늘 뿐이고, 그 1줄이 회계팀 top-10 질문 중 빈도 1위(매일)·6위(월+수시)를 커버한다(`04-persona-accounting-team.md` §3 표). 비용 대비 가치가 압도적이라 미룰 이유가 없다.

**스틸맨 ② "실무 탭 정산상태 컬럼도 v1에 넣어야 한다 — 없으면 하이브리드가 반쪽이다."**
회계팀 질문 4위("이 주문 정산됐나", 하루 여러 건)는 실무 탭에서 발생한다. 새 탭으로 딥링크만 걸어두면 매번 탭을 옮겨야 하고, 그건 A안의 약점을 그대로 남기는 것이다. 컬럼 1개면 그 자리에서 답이 나온다.

→ **기각(v1.1로 이연) 근거**: 실무 탭 그리드 헤더는 **11칸 문자열 리터럴 정확 일치 계약**이다(`test_settlement_operations_render.py:336` `_GRID_HEADERS = ("고객","채널","완료일","출고가","예약금","잔금","과입금","경과일","현금영수증","정산상태","액션")`, 실측 `settlement_operations_body.html:171-183`). 여기에 12번째 칸을 넣으면 (a) 그 리터럴, (b) `test_js_binds_every_exposed_row_field`, (c) `settlement_rows.py`의 행 필드셋 정확 일치 계약(`test_settlement_rows_api.py:141`), (d) 노출 계약 테스트가 동시에 red가 된다. 게다가 "정산상태"라는 **이름이 이미 쓰이고 있어**(FOMS 자체 정산 청구 상태) 12번째 칸의 이름이 "네이버 정산"이 되면 한 표에 뜻이 다른 "정산"이 두 개 생긴다 — 내 렌즈(화면 완성도)에서 이건 가치가 아니라 혼란이다. v1.1에서 두 컬럼의 라벨을 함께 다시 설계하는 게 옳다. v1의 대체 답은 **새 탭 건별 원장의 FOMS 주문번호 검색 상자**(주문번호 붙여넣기 → 그 건의 정산 상태 한 줄)로, 왕복 1회는 남되 답은 3초 안에 나온다.

## C. 데이터 파이프라인

### C-1. 형태 — 라이브 프록시 불가, enqueue → 워커 → DB → web

web 프로세스에는 네이버에 등록된 출구 IP가 없다(3=3 슬롯 전부 WORKER, `client.py:279-284`·`ingest.py:11-12`·`naver_ingest.py:10-12`·`backfill.py:30`이 같은 근거를 4중으로 명시). 따라서 화면 문구는 "실시간"이 아니라 **"최종 동기화 HH:MM (N시간 전)"**이 정직한 상한이다(S0 블록의 존재 이유).

### C-2. 동기화 3층

| 층 | 트리거 | 대상 | 호출 |
|---|---|---|---|
| 일 배치 | `run_naver_settle_sync.py --loop --at 04:20 --window 15` | 최근 **30일** 롤링 재조회(settle/case·commission-details 각 30일) + settle/daily 31일 범위 1회 | 61요청 ≈ 31초 |
| 월 마감 | 매월 **6일** 04:40 창 | 전월 vat/daily + vat/case 범위 조회 + 전월 settle 전량 재확정 패스 | 약 35요청 ≈ 18초 |
| 수동 | web "지금 동기화" 버튼 → `enqueue_naver_settle_sync()` | 최근 7일 축소 롤링 | 15요청 ≈ 8초 |
| 백필 | `run_naver_settle_backfill.py`(1회성, 관리자 실행) | 초기 **180일**(기본) | 372요청 ≈ 3분 6초 |

- 간격 상수는 기존 `backfill.py:63` `CALL_INTERVAL_SECONDS = 0.5`(2 RPS의 절반) 재사용. 워커 동시성 1 전제.
- `settle/case`·`commission-details`가 **기간 조회 불가**(#3709)라 하루씩 도는 것이 유일한 방법이며, 위 계산이 그 비용의 실체다. "한 달치에 6시간" 같은 사례는 페이지가 수천 장인 대형 셀러 이야기이고, FOMS 규모(하루 수십 건, pageSize=1000이면 1페이지)에서는 문제가 되지 않는다.
- `settle/daily`의 범위 최대 폭은 문서에 없음(NOT IN DOCS) → **안전측으로 31일 창으로 잘라** 호출한다.

### C-3. 테이블 설계 — "하루 = 원자 교체 단위"

자연키를 추측하지 않는다. 같은 `productOrderId`가 원거래·취소·수량취소로 여러 행이 되고, `settle/daily`의 행 카디널리티(가맹점 × 정산방법 × ?)가 문서에 없기 때문이다(NOT IN DOCS). 대신 **"조회일 파티션을 트랜잭션 안에서 통째로 교체"**한다 — 네이버가 그 `searchDate`에 대해 주는 답이 그 날의 진실이고, 소급 이동(#3123)도 교체로 자연히 해결된다.

| 테이블 | 파티션 키(UNIQUE) | 조회축 컬럼(인덱스) | JSONB | 비고 |
|---|---|---|---|---|
| `naver_settle_daily` | `(channel, settle_expect_date, row_seq)` | settle_expect_date, settle_complete_date, settle_method_type, merchant_id | `raw_snapshot` | 금액 15종은 컬럼(차트가 SQL로 합산) |

### C-4. 워터마크 · 확정본 규칙

- 새 테이블을 안 만들고 `SystemSetting` 재사용(`watermark.py:24`·`backfill.py:55` 선례): 키 `naver_settle_sync_state`, `naver_settle_backfill_state`. 값 = `{last_run_at, covered_from, covered_to, rolling_days, per_endpoint:{...}, last_error, rev}`. `version += 1` 낙관적 락, 성공 구간만 전진.
- **"확정본" 규칙(네이버가 확정 신호를 안 주므로 FOMS 자체 규칙, 추정 설계)**:
  1. settle 계열 — `settle_complete_date`가 채워졌고 + 정산 예정일 기준 **D+35 경과** + 마지막 재조회에서 금액 무변동 → `is_final = true`. 확정 파티션은 일 배치 롤링 대상에서 제외하고, 월 1회 검증 패스에서만 다시 읽어 변동 시 **덮지 않고 예외 큐에 올린다**.
  2. vat 계열 — 익월 **6일** 마감 패스에서 읽은 월치를 `is_final = true`로 동결. 이후 재조회로 덮지 않는다(신고 자료의 재현성이 세무 리스크의 핵심).
  3. 화면 표기: S0에 "확정 구간 ~2026-07-31", 확정 행에는 표 안에 잠금 배지.
- **소급 변경 감지**: 파티션 교체 직전에 기존 행의 (건수, 금액 합계) 지문을 계산해 교체 후와 비교, 다르면 `naver_settle_drift_log`(경량, SystemSetting JSONB 배열로도 충분) 기록 → S8 예외 큐 "소급 변경 감지" 행. **조용히 덮어쓰지 않는 것**이 회계 화면에서 가장 중요한 성질이다.

### C-5. 429 · 토큰 규격 리스크 대응

- 근본 원인 1순위는 호출량이 아니라 **토큰 발급 규격 위반 벌칙**(#3751 → 시간당 1회 제한 → 정산 API 429 `GW.QUOTA_LIMIT`, #3709). FOMS의 `_issue_token()`은 이미 form-urlencoded + `grant_type=client_credentials` + `type=SELF`(account_id 미포함)로 규격을 지키고 있다(`client.py:352-373`) → **기존 client 재사용이 곧 대응책**이고, 별도 클라이언트 파일을 새로 만들지 않는 이유이기도 하다(EXT-TOKEN-01 계약 자동 유지, `test_external_token_client_discipline.py:42-51`).
- 추가 방어: (a) 정산 잡 전용 실행 락(SystemSetting)으로 수동+스케줄 동시 실행 방지, (b) 429 수신 시 **그날 잡 즉시 중단 + 워터마크 미전진 + S0에 "지연" 경고 배지**(다음 날 이어받기), (c) `[정산] API 그룹 권한` 누락 시 나오는 401 `GW.AUTHN`(#1013/#1205)은 재시도 대상이 아니라 **설정 오류**이므로 백오프 없이 즉시 실패 + 관리자 알림 문구를 다르게 낸다.
- 앱 종류 주의(#2788): 반드시 "내스토어 애플리케이션" 토큰. FOMS는 이미 그 자격증명 하나만 쓰므로 신규 리스크 없음(`client.py:310-313`).

## D. 회계 정합성 가드레일 (구현 시 계약 테스트로 고정)

1. **부호 규약** — 네이버 응답 부호를 그대로 저장·표시. 취소/환급 계열(`NORMAL_SETTLE_AFTER_CANCEL`·`NORMAL_SETTLE_BEFORE_CANCEL`·`QUICK_SETTLE_CANCEL`·`QUANTITY_CANCEL_DEDUCTION`/`_RESTORE`)은 **절대값 변환 + 아이콘 치환 금지**. 합계는 음수 포함 실제 합. 계약: "화면 합계 == 원본 행 부호 포함 합" 항등식 테스트.
2. **날짜 축 5종을 셀렉터로 명시 분리** — `periodType` 5종(정산 기준일 / 정산 예정일 / 정산 완료일 / 결제일 / 세금 신고 기준일)을 그대로 축 셀렉터로 노출하고, **기본값은 정산 예정일**(`settle/daily`의 필터 기준과 동일, #1481 — 그래야 일별↔건별 대사가 성립한다). 축을 바꾸면 KPI·차트·표가 **함께** 바뀐다(한 화면 안에 두 축이 섞이는 상태를 만들지 않는다).
3. **"정산일 기준(완료일 기준 아님)" 상시 라벨** — 필터바 아래 한 줄 고정. 요약/분석 탭의 "매출 인식: 완료일 기준" 스트립(`settlement_dashboard_body.html:88`)과 대칭이 되게 같은 자리·같은 톤.
4. **KST** — 5종 응답은 전부 `date`(시각 없음)이고 커머스API 전체가 KST 기준(#32). 따라서 **DATE 컬럼으로 저장**하고 타임존 변환을 하지 않는다. 프로젝트의 "naive timestamp = UTC" 규약과 충돌하지 않도록, 마이그레이션·모델 주석에 "이 컬럼은 timestamp가 아니라 KST 달력 날짜"라고 못 박는다. 동기화 시각(`synced_at`)만 `now_utc_naive`.
5. **재계산 금지** — 수수료·세액·정산액을 FOMS가 다시 계산하지 않는다. 유일한 파생은 **실효 수수료율**이고, 그 분모(`paySettleAmount` 합)·분자(`commissionSettleAmount` 합)를 툴팁에 그대로 노출한다. 표시 축약(₩62.1M)은 표시 계층에서만, 내부·CSV는 원 단위 정수.
6. **"정산 예정 ≠ 완료"** — KPI 타일 2장으로 분리하고 **절대 합산하지 않는다**. 예정은 은행 미입금이므로 "정산 완료액"에 포함되지 않음을 부제로 명시. 색은 같은 계열의 진하기 차이로만 구분하고 상태색(양호/경고/심각)과 축을 섞지 않는다.
7. **충전금(CHARGE_AMT) 라벨링** — `settleMethodType=CHARGE_AMT` 행은 S4에 "통장에 기록되지 않는 상계"로 별도 표기하고 **은행 대사 대상에서 제외**한다. `minusChargeAmount`는 잔액 흐름으로 별도 추적. `ACCOUNT` 행만 `bankType`+`accountNo`+예정일로 은행 거래와 대응한다.
8. **VAT 전월 말일 제약 상시 표기** — S7 상단 고정 배너 "부가세 자료는 2026-08-31까지 제공됩니다(당월분은 익월 마감 후)". 당월을 고르면 빈 표가 아니라 **이 안내를 렌더**한다(빈 배열을 0으로 그리지 않는다). 부가세 각주 2줄: (a) 과세표준은 통장 입금액이 아니라 결제금액 총액, (b) 차감된 수수료는 네이버 발행 세금계산서로 매입세액 공제(`04-persona-accounting-team.md` §2.5).
9. **개인정보 경계** — `purchaserName`은 실무 탭이 이미 고객 성명을 같은 actor 집합에 노출 중이므로 **"신규 PII 획득 actor 0"** 논증이 성립한다(같은 `SETTLEMENT_DASHBOARD_READ` 게이트). 연락처·주소는 정산 API가 아예 주지 않는다. `raw_snapshot` 원본 뷰어는 **ADMIN 전용**(S17, 보류). CSV에는 성명 포함, 다운로드 자체를 `log_access`로 남긴다.
10. **결측·지연을 0으로 그리지 않기** — "0건"과 "아직 동기화 안 됨"과 "이 기간은 적재 범위 밖"을 서로 다른 문구·색으로 구분(S0의 적재 구간 표시와 연동). 예외 큐가 비었을 때도 마찬가지.
11. **혜택 정산 상세 미제공 각주**(#3649) — S3 워터폴의 "+혜택 정산" 막대에 "항목별 상세는 API 미제공(스마트스토어센터 엑셀에서만 확인)" 툴팁.
12. **은행 실계좌 대사는 범위 밖** 각주 — "이 금액은 실제 계좌 입금과 자동 대사되지 않습니다"(S4 하단).
