> 2026-08-31. 선행: `2026-08-31-naver-return-approve_SPEC.md`(반품 승인, **운영 배포 완료**

## 0. 한 줄

고객이 낸 반품 요청을 **FOMS 안에서 거부**한다. 지금은 거부만 하러 판매자센터로 간다.

## 1. 왜 지금 여는가

- **거부는 실제 업무다**(사용자 확인 2026-08-31). 2026-08-27 원장이 "착수 불가"로 닫았던
  이유는 승인 규격 미확인과 보류 분기였는데, 승인은 §T1 에서 규격을 확보해 운영에 나갔고
  보류는 운영 25건 전수 0건으로 **주 경로가 아님**이 확인됐다.
- 접수·승인만 있고 거부가 없으면, **고객이 반품을 걸어 온 건**에서만 판매자센터를 다시
  열게 된다. 한 업무가 두 군데로 갈리면 사람은 처음부터 판매자센터에서 끝낸다 —
  승인 설계서가 적은 것과 같은 실패다.

## 2. 규격 — **미확인 (이 문서의 유일한 공백)**

승인 설계서 §2 가 참고로 적어 둔 것:

```
POST /v1/pay-order/seller/product-orders/:productOrderId/claim/return/reject
필요 필드로 rejectReturnReason (string, required) 가 있다고 적혀 있음
```

**그 문장은 우리 문서에만 있다.** 공식 문서(apicenter, 로그인·JS)는 세션이 직접 못 연다.
`approvalData` 사고가 정확히 이 자리에서 났다 — 우리 원장이 근거라고 적은 문장이 출처에
없었고, 그대로 갔으면 **없는 필드를 불가역 API 에 보낼 뻔했다.**

착수 전에 문서 원문에서 확인할 것:

| # | 확인할 것 | 왜 |
|---|---|---|
| 1 | 엔드포인트 경로와 메서드 | 접수·승인과 형제인지 |
| 2 | Request Body **필드명**(`rejectReturnReason` 맞는가)·**필수 여부** | 승인은 body 자체가 없었다 |
| 3 | 사유 문장 **글자수 제한**·허용 문자 | 자유 입력이라 상한이 곧 화면 제약 |
| 4 | 사유가 **구매자에게 노출되는가**(어디에 어떻게) | 문안 규칙의 전제 |
| 5 | 응답 형태 — `successProductOrderIds`/`failProductOrderInfos` 동형인가 | 동형이면 `_split_result` 재사용 |
| 6 | 거부 뒤 `claimStatus` 가 무엇이 되는가 | 화면 배지·유령 판정이 그 값을 읽는다 |
| 7 | 되돌리는 엔드포인트가 있는가 | 없다고 보고 설계하되 확인은 필요 |

|---|---|---|
| 반품 **거부** 단건 | 만든다 | 위 |

| **일괄** 거부 | 안 만든다 | 문장이 건마다 다르다. 한 문장을 여러 집에 뿌리면 그게 곧 오발송이다 |
| 자동 거부 | 안 만든다 | 돈과 분쟁이 걸린 판단이다 |

## 4. 설계

### 4-1. 발동 — 반품 축 카드의 버튼

접수 모달의 체크박스가 아니다. **접수와 거부는 대상이 다르다** — 접수는 *우리가* 반품을
내는 것이고, 거부는 *고객이 낸* 반품 요청을 되돌려보내는 것이다. 같은 모달에 두면
"반품을 접수하면서 동시에 거부"라는 없는 상태가 화면에 생긴다.

자리는 pane 의 **반품 진행**(`_return_axis_view`) 카드다. 거기가 이미 "이 집의 반품이
어디까지 왔나"를 말하는 자리다.

### 4-2. 술어 — `fulfillment.is_return_rejectable(link)`

화면 재진술과 서버 처리가 **한 벌**을 쓴다(`is_return_pending` 과 같은 규율 — 어긋나면
불가역 호출이 과대 진술 위에서 나간다). 조건:

1. 클레임이 **반품 요청 상태**다(`RETURN_REQUEST` 축 — 정확한 값 집합은 §2-6 확인 후 확정).
2. **보류가 걸려 있지 않다**(`extract_claim_holdback`). 걸렸으면 우리가 풀지 않는다.
3. 아직 우리가 **승인·거부하지 않았다**(`triage_state['return']` 표식으로만 판정 —
   네이버 `requestChannel` 은 API 분과 수동분을 갈라 주지 않는다).

### 4-3. 문안 — **담당자 자유 입력** (사용자 결정 2026-08-31)

사용자가 고정 문구 대신 자유 입력을 골랐다. 그 선택을 지키되, 자유 입력이 여는 위험
(오타·감정 표현이 그대로 고객에게 간다, 되돌릴 수 없다)에는 **문장을 검열하지 않는 방식**
으로만 대응한다:

- **상용구 채우기 버튼** — 누르면 입력칸에 문장이 들어가고, 그 자리에서 고칠 수 있다.
  강제하지 않는다. 초안 5종(업무 상황은 사용자가 지목한 그대로 — **문장은 사용자 확정 필요**):

  | 상황 | 초안 문장 |
  |---|---|
  | 제작 착수 | `주문하신 상품은 고객님 치수에 맞춰 이미 제작에 들어가 재판매가 불가능하여 반품이 어렵습니다.` |
  | 시공 완료 | `시공이 완료된 건으로 원상 복구가 불가능하여 반품이 어렵습니다.` |
  | 사용·파손 | `제품에 사용·파손 흔적이 확인되어 반품 조건에 해당하지 않습니다.` |
  | 기간 경과 | `반품 가능 기간이 지나 단순 변심에 의한 반품이 어렵습니다.` |
  | 실측 후 | `실측 방문이 완료된 건으로 방문 비용이 발생하여 단순 변심에 의한 반품이 어렵습니다.` |

  이 문장들은 **법률 검토를 거친 문안이 아니다.** 주문제작품 청약철회 제한은 조건이
  걸리는 영역이므로, 운영에 넣기 전 사용자가 문장을 확정한다(§7 Q1).
- **모달이 보낸 문장을 그대로 재진술한다** — "이 문장이 구매자에게 그대로 전달됩니다"
  아래에 입력값을 그대로 보여준다. 불가역 4종 세트의 ④(필요한 입력) 자리다.
- **빈 문장·공백만은 막는다.** 서버에서도 막는다(빈 사유로 불가역 API 를 때리지 않는다).
- **보낸 문장 원문을 남긴다** — `triage_state['return']['reject_reason']` 과 감사 로그
  `detail` 양쪽. 자유 입력에서 분쟁이 나면 **무슨 말을 보냈는가**가 유일한 방어선이다.

### 4-4. 경로 — 새 mutation 하나

`POST /admin/naver-ingest/<link_id>/return-reject` (payload: `reason` 문장).
큐·태스크는 기존 갈래에 얹는다(`enqueue_naver_return_reject` →
`run_naver_fulfillment_task(action="return-reject")` → `fulfillment.reject_return`).

**신규 mutation 계약 5종**이 그대로 붙는다(이 프로젝트가 네 번 데인 자리):
policy manifest · write guard manifest · audit coverage inventory ·
감사 라벨 `NAVER_INGEST_RETURN_REJECT_ENQUEUE` · (docs 읽는 테스트면 ci.yml 등재 — 지금은 해당 없음).

**권한은 접수·승인보다 좁다**(사용자 결정 2026-08-31): `ADMIN`·`MANAGER` 만.
거부 문장은 분쟁으로 돌아올 수 있어 쓰는 사람을 좁힌다. 라우트와 버튼이 **같은 조건**을
써야 한다 — 한쪽만 좁히면 열린 버튼이 403 을 받는다(v2 에서 실제로 났던 결함).

**여섯 번째 계약: 주문 이력 이벤트 라벨.** 거부 표식을 주문에도 남기므로(§4-5)
새 `OrderEvent` 종류가 생긴다. `foms/services/order_event_display.py` 의 라벨 표와 문장
빌더에 등재하지 않으면 주문 이력에 **영문 코드가 그대로 뜬다**(감사 라벨과 같은 함정,
`NAVER_ORDER_ATTACHED` 가 등재된 자리).

### 4-5. 화면이 말할 것

- 거부 성공: `반품 거부됨` + 보낸 문장 + 누가·언제.
- 부분 실패: 집 안 일부만 거부될 수 있다. **숨기지 않는다**(승인과 같은 규율).
- 보류 걸린 건: 거부하지 않고 `판매자센터에서 처리하세요`.
- **주문 화면에도 남긴다**(사용자 결정 2026-08-31): `OrderEvent`
  `NAVER_RETURN_REJECTED` 를 그 주문에 쌓아 **주문 변경 이력**이 "반품을 거부했고 이런
  문장을 보냈다"를 말한다. 워크벤치를 안 여는 담당자가 나중에 맥락을 읽는 자리다.
  주문 자체는 **그대로 살려 둔다** — 거부는 "반품을 안 받겠다"는 뜻이라 시공·제작 일정은
  계속 간다. 붙이기 이력과 같은 규율로 **실제로 바뀐 때만** 한 줄 남긴다.

### 4-6. 조작 뒤 자동 다시 읽기

T3 규율 그대로 — 성공·실패와 무관하게 그 집을 다시 읽는다(`enqueue_naver_refresh`).
불가역 경로에서 재조회는 낭비가 아니라 **확인**이다.

## 5. 위험과 대응

| 위험 | 대응 |
|---|---|
| 사유 문장이 **고객에게 그대로** 간다 | 모달이 문장을 재진술 · 상용구 채우기 · 원문 기록. 검열은 하지 않는다(사용자 결정) |
| 되돌릴 수 없다 | 불가역 4종 세트 모달. 단건만(일괄 없음) |
| 거부가 **분쟁으로 돌아온다** | 보낸 문장·시각·행위자를 감사 로그에 남긴다 |
| 보류 걸린 건 | 거부 중단 + 판매자센터 안내. 우리가 풀지 않는다 |
| 규격 추측 | **§2 가 차기 전에는 호출 코드를 쓰지 않는다** |
