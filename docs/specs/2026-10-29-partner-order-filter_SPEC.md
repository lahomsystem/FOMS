# 협력사 주문 필터와 검색 범위 정합 Spec

> 작성일: 2026-10-29 | 상태: 승인됨 (사용자: 구현 → staging 검증 → 이상 없으면 production)

## 1. What — 무엇을 만드는가

### 1.1 최종 결과물

공용 헤더의 내 담당 아이콘 옆에 악수 아이콘을 추가한다. 아이콘을 열어 `전체 주문`,
`협력사 전체`, `라운즈` 등 등록된 협력사를 선택한다. 선택한 회사의 주문만 서버에서 조회한다.
주문 대시보드에서 `라운즈`를 검색하면 최근 실측·도면 주문도 같은 작업 큐에 표시한다.

### 1.2 기능 요구사항

1. 협력사 선택지는 DB의 협력사 목록에서 만든다. 회사명과 ID를 하드코딩하지 않는다.
2. 협력사 전체는 `orders.partner_org_id IS NOT NULL`, 특정 회사는 해당 ID 일치로 판정한다.
3. 우선 적용 화면은 사용자 제시 화면인 전체 주문(`/`), ERP 주문 대시보드(`/erp/dashboard`),
   이력(`/erp/history/`)이다. 공용 헤더의 다른 화면에서 선택하면 선택값을 가진 주문 대시보드로 이동한다.
4. 위 세 화면 사이 이동, 검색, 단계 선택, 페이지 이동, 새로고침에 선택값을 유지한다.
   검색어·내 담당·단계 필터와는 교집합으로 동작한다. 해제하면 전체 주문으로 복귀한다.
5. 선택 중에는 아이콘 색과 접근 가능한 이름으로 `협력사: 라운즈`를 알린다.
6. 주문 작업 큐의 고객명·전화·주소 검색에 **실제 협력사 주문의 협력사명**을 추가한다.
   담당자 등 모든 필드로 검색을 넓히지 않는다. 기존 이력·통합 검색의 넓은 검색 범위를 보존한다.
7. 이력 링크는 서로 다른 검색 결과 총수를 단순 차감하지 않는다. 실제로 주문 대시보드
   모집단 밖에 있는 주문을 세고, 이력에 레거시 주문도 포함되는 점을 반영해 `전체 이력`으로 표시한다.
8. 필터는 조회 편의 기능이다. 기존 협력사 계정 접근 통제와 시공팀의 본인 주문 제한을 보존한다.

### 1.3 예외/제약 조건

- 존재하지 않는 회사 ID는 다른 회사나 전체 주문으로 조용히 넓히지 않고 빈 결과로 처리한다.
- `focus_order`로 행을 강제 주입할 때도 선택 회사 범위를 지킨다.
- 협력사 전용 포털, 주문 데이터, DB 스키마, 기존 쓰기 API는 변경하지 않는다.
- 별도 ERP 실측·도면·생산·출고 보드까지 필터를 확장하는 작업은 이번 세 화면 범위에 포함하지 않는다.

## 2. How — 어떻게 만드는가

### 2.1 수정 대상 파일

| 파일/영역 | 변경 내용 |
|---|---|
| `templates/partials/shared/layout_nav.html` 및 외부 JS/CSS | 악수 아이콘, 회사 선택, 활성 상태 |
| `foms/services/common/`의 신규 협력사 필터 서비스 | 입력 정규화, 공통 SQL 조건, 선택 상태 |
| `foms/services/orders/dashboard_filters.py`, `dashboard_read_model.py` | 목록·단계 집계에 동일 회사 조건 적용 |
| `foms/web/orders/dashboard.py` | 집계 캐시 키, 이력 링크·이동·focus 행 범위 |
| `foms/web/orders/listing.py`, `history.py` | 전체 주문과 이력 필터, 이동 인자·캐시 정합 |
| `foms/services/erp_dashboard_search.py` | 고객 중심 검색에 협력사 주문의 회사명 추가 |
| 관련 검색/이력/내비게이션 템플릿 및 테스트 | 필터 유지와 교집합, 검색 오분류 회귀 검증 |

### 2.2 아키텍처 방향

- 판정 SSOT는 기존 `partner_org_id`다. 발주사 이름만으로 일반 주문을 협력사로 분류하지 않는다.
- 기존 `erp-mine-only.js`의 셸 전환·캐시 무효화 방식과 정합시키되 책임은 별도 서비스로 둔다.
- 필터는 count/pagination 이전에 적용한다. 목록·단계 숫자·이력 링크의 범위를 일치시킨다.
- 서버 집계/fragment 캐시 키에 회사 선택값을 넣는다. 선택 변경 시 클라이언트 fragment 캐시도 무효화한다.
- 신규 스크립트는 defer, 이벤트는 singleton 위임으로 재진입 시 중복 실행을 막는다.

### 2.3 의존성 및 영향 범위

- 기존 `ix_orders_partner_org_id`와 협력사명 검색 경로의 기존 인덱스를 먼저 활용한다.
- 기본 설계상 마이그레이션은 필요 없다. PostgreSQL 실행계획에서 인덱스 불일치가 드러나면
  별도 설계를 확정한 뒤 진행한다.
- 여러 파일에 걸치는 조회 동작 변경이므로 구현 전 이 계획에 대한 승인이 필요하다.

## 5. 참고 자료와 현재 증거

- `docs/harness/policy/DECISIONS.md`, `docs/ARCHIVE_INDEX.md` 조사: 해당 필터에 직접 대응하는 항목 없음.
- `docs/specs/2026-10-08-partner-portal_SPEC.md` §3.3: 협력사 판정은 `partner_org_id`.
- `dashboard_read_model.py`: 작업 큐가 `customer_contact_only=True` 검색 사용.
- `dashboard.py::_history_more_link`: 넓은 이력 검색 총수에서 좁은 대시보드 총수를 차감.
- 로컬 재현: 오늘 생성한 실측·도면 각 1건, 회사명은 모두 라운즈. 고객명에 라운즈가 있는
  실측만 작업 큐에 잡혀 `dashboard_count=1`, `history_count=2`, `history_more.count=1`.
  두 주문 모두 `dashboard_active_filter(60)`를 통과하므로 날짜 때문에 빠진 것이 아님.
- 기존 관련 테스트: `test_erp_dashboard_search_service.py`와 `test_erp_dashboard_active_filter.py`,
  합계 11 passed. 기존 테스트에는 위 협력사 검색의 오분류 대조군이 없다.
- 스테이징에는 라운즈 검색 결과가 없었다. 사용자 첨부 운영 5건의 DB 값은 미검증이다.
- 이 checkout에는 gstack 브리지에서 언급한 `task_classifier.py`, `run_codex.ps1`,
  `run_gstack_qa.ps1`가 없다. 조사 단계는 gstack 절차와 Aside 직접 브라우저 확인을 사용했다.
- 사용자 구현·스테이징 검증·정상 시 운영 승격 승인 후 기능 코드를 구현했다.
- 헤더는 셸 이동 후에도 유지되므로 작은 defer 스크립트로 메뉴를 열 때 현재 URL 기준
  선택 링크를 다시 만든다. 회사 선택 자체는 전체 문서를 새로 받아 셸 캐시를 초기화한다.
- PostgreSQL 읽기 전용 EXPLAIN(스테이징): 회사 ID는 Index Scan 0.148ms,
  고객/협력사 검색은 Bitmap Heap Scan 18.362ms. 주문 테이블 Seq Scan 없음.
- 기존 검색 성능 계약은 phase D/E 마이그레이션만 읽고 있어 이미 존재하는 phase F의
  협력사명 인덱스도 검증하도록 정본 목록을 보완했다. common 파일 목록·writer 줄번호
  인벤토리도 실제 코드와 동기화했다. 접근 통제·writer 허용 범위는 넓히지 않았다.
