# 재결제 원 주문 네이버 취소/반품 — 설계서

- 2026-08-28 · 워크트리 `C:/tmp/nvrepay` (session/nvrepay-cancel @ origin/deploy 88f09df2)
- 판정 원장: `docs/plans/2026-08-28-naver-repay-origin-cancel-ledger.md`
- 상태: **설계 승인 대기** (사용자 선택 완료 — Shape A · 설계서 먼저 · 곁다리 4건 전부 포함)

## 1. 문제

재결제 건을 ERP 주문에 붙이고 나면, 담당자는 **네이버에 남아 있는 옛 주문을 취소(발송 전) 또는
반품(발송 후)** 해야 한다. 지금은 그 일을 네이버 판매자센터에서 손으로 한다.

FOMS 에는 그 일에 필요한 것이 이미 거의 다 있다 — 취소·반품 API, 버튼, 확인 모달, 가드, 감사 로그가
운영에 돌고 있고(원장 §2), 옛 주문의 화면도 `?link_id=<N>` 로 이미 열린다. **없는 것은 옛 주문을
가리키는 앵커 하나**다. 재결제로 붙이는 순간 옛 결제 섹션이 화면에서 통째로 사라지고
(`templates/admin/partials/naver_workbench_pane.html:575`), 후보 조회가 옛 주문의 `link_id` 를
SELECT 절에서 빠뜨린다(`foms/services/integrations/naver_commerce/order_candidates.py:226-229`).

동시에, **예약금 건**(최초 접수가 네이버가 아니고 ERP 에 직접 등록된 주문)은 옛 네이버 주문이
아예 없을 수 있다. 이때 화면은 "없다"고 단정하면 안 된다 — 실제로 있었는데 우리가 못 가져온
경우와 관측이 같기 때문이다(§4.1).

## 2. 결정

### D1. Shape A — 길만 낸다

재결제 pane 은 옛 주문의 **상태를 보여주고 그 화면으로 보낸다**. 불가역 호출은 옛 주문 자신의
pane 에서 사람이 **기존 모달·기존 가드·기존 감사·기존 권한**으로 실행한다. 신규 불가역 경로 0.

Shape B(재결제 pane 에서 직접 옛 집에 거는 버튼)는 기각한다. 근거 5개는 원장 §3.
가장 무거운 것: 모달의 건수 재진술(`pane:1003-1004`)이 pane 자기 집에 묶여 있어,
옛 집을 겨냥하면 **새 결제 고객 이름과 새 집 건수를 읽어주면서 옛 집을 환불**한다.

### D2. R-4 게이트 개방

`docs/specs/2026-08-25-naver-repay-reconcile_SPEC.md:184-186` 이 요구한 별도 승인 게이트를 연다.
2026-08-25 결정(`:63-65`)은 **R-3 자동 정리 트랜잭션 한정**이며, 그 문서가 스스로 재편입 조건을
적어 뒀다(`:107-109`). 근거 전문은 원장 §1.

**여전히 금지**: R-3 `정리 실행` 버튼에 네이버 호출을 넣지 않는다. `pane:805-810` 의
"네이버로 나가는 요청은 없습니다"는 계속 참이어야 한다.

### D3. 출신 표식과 도크 게이트를 가른다

`structured_data['source']` 가 뜻 두 개를 지고 있다 — ① 주문 **출처** ② 도크 **렌더 게이트**.
붙이기(`promotion.py:361`)가 게이트를 켜려고 출처를 덮어써서, ERP 직접 등록 주문이 재결제를 붙이는
순간 네이버 출신으로 뒤집힌다. 둘을 가른다(§7).

CEO 는 이것을 별건으로 미루자고 판정했으나 **사용자가 이번 범위에 넣기로 결정**했다.

## 3. 데이터 — 되살릴 것

### 3.1 후보/alive-row 투영

`_naver_facts` 의 SELECT 절에 `ExternalOrderLink.id`·`external_id` 를 추가하고
(`order_candidates.py:226-229`), `_add_alive_row` 가 만드는 행에 실어 보낸다(`:150-151`).

행 스키마 (현행 → 신규):

```
현행: {external_order_no, amount_total, product_order_count}
신규: {link_id, external_order_no, product_order_ids[], amount_total, product_order_count,
       dispatched, read_at}
```

초안에 있던 `place_pending` 과 행 단위 `claim_phase` 는 **뺐다** — 화면 상태 5종(§4.1) 어디에서도
분기에 쓰이지 않는다. `claim_phase` 는 집 단위 `naver_claim_code` 가 이미 담당한다.

- `link_id` — 앵커 주소(`?link_id=<N>`). **집 대표 1개**면 충분하다. 옛 집 pane 이
  `_group_of_link` 로 형제 전체를 다시 모으므로(`foms/web/admin/naver_ingest.py:1020`) 대표만 있으면 된다.
- `dispatched` — 취소/반품 갈림. `triage_state['fulfillment']['dispatched_at']` **또는**
  `raw_snapshot.delivery.sendDate`(`fulfillment.py:596-614` `_naver_dispatched_at`). 둘 중 하나라도 있으면 발송으로 본다.
  판매자센터에서 사람이 발송한 건을 놓치지 않기 위해 두 신호를 모두 본다.
- `read_at` — 마지막으로 네이버를 읽은 시각 = `max(claim_sync.refreshed_at, created_at)`.
  근거는 §5.2. 집 안에서는 **가장 오래된** 값을 남긴다(형제 하나가 최신이어도 집 전체를
  최신이라 말하면, 정작 취소가 나갈 다른 건은 낡은 값 위에서 나간다).
- 집 단위 분기는 기존 `naver_claim_code` 를 그대로 쓴다. **라벨이 아니라 코드로 분기한다** —
  한국어 문자열 `==` 비교로 분기가 죽은 2026-08-28 결함 재발 방지(`order_candidates.py:154-156`).

### 3.2 성능

조회 자체는 이미 도는 쿼리다(`order_id.in_(order_ids)`, 인덱스 `ix_external_order_link_order`
`models.py:3532`). 컬럼 2개 추가일 뿐 새 쿼리가 아니다. `raw_snapshot` 은 이미 SELECT 에 있다.

**금지**: `external_order_no` 로 되짚는 2차 조회를 넣지 않는다 — 그 컬럼엔 단독 인덱스가 없다
(`models.py:3515-3537`).

근거가 음성 신호 하나뿐인데 확정형으로 말한다. 계약 테스트로 부정 단언을 건다(§9-T9).

**왜 S1 이 두 경우를 안 가르는가**: 수집 필터는 `productOrderStatus == PAYED` 하나뿐이라
**취소 요청 중인 건은 그대로 수집된다**(`mapping.py:407-411`, 2026-08-14 스테이징 실측:
"상태가 PAYED 인데 claimStatus = CANCEL_REQUEST 인 건이 실재했다"). 못 가져오는 것은
**첫 스윕 시점에 이미 PAYED 를 떠난 주문**(배송중·배송완료·구매확정·취소완료)이다.
이걸 구별하려면 전화·이름으로 네이버를 조회해야 하는데 링크 테이블에 그 컬럼이 없고 인덱스도 없고
그런 읽기 경로 자체가 없다. **자신 있게 틀린 말보다 흐릿한 참말이 낫다.**

### 4.4 원 주문 모집단 — `NEW` 집만 (운영 실데이터 결함, 2026-08-28)

한 주문에는 재결제(REPAY) 말고 **추가결제(ADDON)** 도 함께 붙어 있을 수 있다. 그건 차액만
더 받은 **살아 있는** 결제이지 대체된 옛 주문이 아니다.

관계를 안 가린 첫 배포에서 운영 주문 **#4854** 가 배송 중인 25,000원 추가결제를
"네이버 옛 주문이 아직 살아 있습니다 — 이미 발송 처리된 주문입니다 … 반품으로 처리합니다"로
지목했다. 그대로 따르면 **받은 차액이 도로 나간다.** 실화면으로 확인한 결함이다.

판정 축은 도크와 같다 — `superseded = has_repay and relation == "NEW"`(`dock.py:423`).
구현: `order_candidates._naver_facts(relations=("NEW",))`, 호출은 `origin_facts` 에서만.

부수 효과로 **추가결제만 함께 붙은 주문은 "네이버 주문 확인 안 됨"** 이 된다. 그게 맞다 —
대체된 옛 주문이 없는 것이다.

계약: `test_addon_sibling_is_not_an_origin_order`(서비스) ·
`test_addon_sibling_does_not_make_the_screen_ask_for_a_return`(화면).
수정을 되돌리면 둘 다 빨강임을 확인했다.

## 5. 신선도

### 5.1 현황 (실측)

`refreshed_at` 은 저장소 전체에서 정확히 2곳 — 쓰기 `claim_watch.py:406`, 읽기 `naver_ingest.py:2194`.
읽기 용도는 **폴링 지문 해시 재료**다. **어떤 템플릿도 이 값을 렌더하지 않는다.**
즉 현행 화면은 신선도 근거 0 으로 "살아 있음"을 확정형으로 말한다.

자동 보충도 없다 — 스윕은 네이버 변경 이벤트에 뜬 건만 다시 읽고, "이벤트가 안 오는 건은 자동
경로로 **영영** 못 잡는다"(`claim_watch.py:510-514`).

### 5.2 정정 — "표식 부재 = 읽은 적 없음"은 틀렸다 (2026-08-28 구현 중 발견)

판정서 §5 와 이 설계서 초안은 `claim_sync.refreshed_at` 이 없으면 "언제 읽었는지 모른다"고 보고
불가역 버튼을 잠그라고 했다. **그 전제가 사실과 다르다.**

`refreshed_at` 은 `claim_watch` 가 그 링크를 **다시** 읽었을 때만 찍힌다(`claim_watch.py:406`).
방금 수집된 링크에는 아예 없다 — 그런데 **수집도 네이버를 읽은 것**이고 그 시각이
`ExternalOrderLink.created_at` 이다(`models.py:3511`, `nullable=False`).

초안대로 잠갔다면 **방금 수집한 건의 정상 취소까지 전부 막힌다.** 담당자는 `다시 읽기` 를
반사적으로 누르게 되고, 그러면 경고가 아무 의미도 없어진다 — 진짜 낡은 건에서 같은 문구가
그대로 흘러간다. 화면이 늑대를 너무 자주 외치면 아무도 안 믿는다.

**마지막 조회 시각 = max(`claim_sync.refreshed_at`, `created_at`).** 재수집으로 스냅샷이
갱신된 경우 `created_at` 은 실제보다 이르게 잡히는데, 신선도를 **과소평가**하는 방향이라 안전하다.
구현: `order_candidates._dispatch_facts`.

### 5.3 규칙 R1 — 표시 의무 (유지)

네이버 상태를 주장하는 자리에 붙인다. 순수 추가, 동작 변경 0.

> *이 상태는 {YYYY-MM-DD HH:MM} 에 읽은 것입니다.*

값은 §5.2 의 `read_at`. 실무상 항상 존재하므로 "모름" 갈래는 두지 않는다.

### 5.4 규칙 R2′ — 새 결제 이후 확인한 적 없으면 경고하고, 앵커가 먼저 다시 읽는다

초안의 하드 잠금(R2)을 **대체한다**. 임계값이 필요 없으면서 실제 위험만 겨냥하는 규칙:

**옛 집을 마지막으로 읽은 시각이 재결제 링크의 수집 시각보다 이르면**, 우리는 고객이 새로
결제한 뒤로 그 옛 주문을 **한 번도 확인하지 않은** 것이다. 그 구간이 바로 "고객이 스스로
취소했는데 우리가 또 취소를 거는" 위험이 사는 자리다(위험 등록부 R2).

- 관계 블록이 말한다: **새 결제를 받은 뒤로 이 옛 주문을 확인한 적이 없습니다.**
- 앵커를 `[옛 주문 다시 읽고 열기 →]` 로 한다 — 누르면 그 집의 `다시 읽기` 를 큐에 넣고
  그 pane 으로 이동한다. `다시 읽기` 는 읽기 전용이라 되돌릴 것이 없고
  (`naver_ingest.py:2616-2632`), 도착한 pane 은 기존 폴링 지문(`rev` 에 `refreshed_at` 포함,
  `naver_ingest.py:2194`)으로 값이 도착하면 스스로 갱신된다.
- **버튼을 잠그지 않는다.** 정상 경로에 거짓 경고를 심지 않는 것이 이 규칙의 요점이다.

### 5.5 정하지 않는 것

### 6.2 SOLD_OUT 경고

공식(#2823): `SOLD_OUT` 사유 취소는 **대상 상품 또는 옵션 조합의 재고가 품절 처리**되고
**판매관리 프로그램 패널티 대상**이다.

- ~~**삭제하지 않는다** — 품절 취소는 정당한 별도 용례~~ ~~라벨을 결과가 보이게 바꾼다~~
  → **뒤집혔다 (사용자 지시 2026-09-01): `CANCEL_REASONS` 에서 삭제.**
- 이유: 우리 스토어는 시공 제품이라 **품절 취소가 업무에 없다.** 목록에 남겨 두면 누가 한 번
  고르는 것만으로 상품이 내려가고 패널티가 붙는다. 라벨 경고는 되돌릴 수 없는 경로에서
  충분한 방어가 아니다 — **고르기 전에 보이게**가 아니라 **고를 수 없게** 한다.
- **화면에서만 빼지 않는다.** 라우트와 서비스가 `CANCEL_REASONS` 로 검사하므로 목록에서
  지워야 열린 탭·북마크·직접 호출로도 못 나간다. `BANNED_CLAIM_REASONS` 튜플과 계약 테스트
  3종(상수 부재 · 서비스 거절 · 화면 select 부재)이 되살아나는 것을 막는다.
- 읽기 범례 `OFFICIAL_CANCEL_REASONS`·`OFFICIAL_RETURN_REASONS` 에는 **그대로 둔다** —
  네이버가 그 값을 보내오면 읽어야 하고, 읽는 축과 보내는 축은 다르다.
- 재결제 문맥의 올바른 코드는 `INTENT_CHANGED`(구매자 귀책). 기본 선택으로 둔다.
