# 작업 등급 접두어(`**A`~`**D`) 시스템 — 설계 초안 v1 (3-agent 리뷰 대상)

날짜: 2026-07-29 · 상태: **종결 — 훅 방식 기각, CLAUDE.md 인라인 규칙으로 구현 완료(사용자 승인)**

## 최종 결정 (2026-07-29, 3-agent 교차검수 + 오케스트레이터 재검증)

- **훅(§1) 기각** 3근거: ① 정규식 `\b`가 한글 즉시연결(`**A출고버그`) 6종 침묵 미탐 실측 — 모델 문맥 판단이 구조적 우월 ② 2026-07-08 만장일치 "매 프롬프트 주입=안티패턴, CLAUDE.md 규칙으로 대체" 결정 역행(신규 증거 0) ③ 강제력은 어느 채널이든 순응 의존 동일 → 최저 비용 안 승리. 훅 주입은 transcript라 압축 시 증발, CLAUDE.md는 시스템 프롬프트라 관통(장기 C/D에서 결정적).
- **구현 = 프로젝트 CLAUDE.md "작업 등급 마커" 절 6줄**(~290 tok). A~D 4등급 유지(사용자 요구), D는 "전자동" 대신 **최고 안전등급 + `/overnight` 명령 제시(자동 진입 금지)** 로 재정의 — 초안의 자기모순(승인 게이트 3개로 밤새 정지)·overnight 안전장치(disable-model-invocation) 우회 문제 해소.
- 강제력의 실질 원천 = 주입문이 아니라 **B/C/D가 생성하는 파일(플랜·ledger)** — 압축 후에도 파일이 절차를 운반(리뷰1 F1). A는 파일 미생성이라 순수 권고임을 인지하고 유지(무해·저비용).
- 재평가 조건: 2주 실사용에서 마커 무시가 실측되면 다음 사다리 = 스킬 방식(`/a`~`/d`), 훅은 그다음.

이하 v1 원문(역사 기록 — 훅 설계는 채택 안 됨):

## 0. 요구 (사용자)

프롬프트 **맨 앞에** `**A`~`**D`를 치면 등급에 맞는 공통 프롬프트 절차(`docs/guides/LONG_TASK_PROMPTS.md`)가 자동 적용:
- `**A` = 가장 기본 task (가이드 ① 소형)
- `**B` = 하루 (② 플랜+한 세션 완주)
- `**C` = 며칠~몇 주 (③ 릴레이)
- `**D` = 최고 등급, 전체 자동 = overnight 개념 (④ 리뷰 스택+무인)
- `/goal` 등 내장 스킬과 연동 작동

예: `**A 출고 대시보드 정렬 버그 고쳐` → ① 절차(완료 기준 확인·위임 판단·검증)가 자동 적용.

## 1. 채택 방식: UserPromptSubmit 훅 (신규 `.claude/hooks/task_grade.py`)

- 훅이 stdin payload의 `prompt` 필드에서 `^\*\*([A-Da-d])\b` 감지 → 등급별 지시문을 `additionalContext`로 주입. 마커 없으면 무출력(비용 0).
- 왜 훅인가: 사용자 문법(`**A` 프리픽스)을 그대로 지원하는 유일한 채널. 스킬(`/명령`)은 문법이 다르고, CLAUDE.md 규칙 문장은 상시 토큰 비용+모델 순응 의존이 더 큼.
- 기존 UserPromptSubmit 훅(ctx_gate.py)과 배열 체인 공존(각 ~70ms).

### 알려진 역사적 반례 (리뷰 필수 검토)
2026-07-08 하네스 재설계에서 **task_classifier(UserPromptSubmit 주입식 preflight)를 "강제력 0 실측"으로 퇴역**시킨 이력 있음(메모리 `project_harness_redesign_pending`). 본 설계와의 차이 주장: classifier는 *자동 추측 분류*(사용자 의도와 어긋나면 무시됨)였고, 본 설계는 *사용자 명시 마커*(사용자가 등급을 선언 — 지시문이 사용자 의도와 정렬). 이 차이가 순응률을 실제로 바꾸는지가 리뷰 쟁점.

## 2. 등급별 주입 지시문 (훅 상수로 임베드)

### **A (소형)
> [TASK-A] 소형 작업 모드. (1) 완료 기준이 프롬프트에 없으면 착수 전 스스로 1줄 정의해 명시하라. (2) §4 직접 처리 예외 해당 여부를 판단해 직접 또는 단일 서브에이전트 위임으로 처리하라(플랜 파일 생략). (3) 검증(완료 기준 실행) 후 결과 보고. brainstorming/플랜 루프 생략(경량 스킵 기준).

### **B (하루)
> [TASK-B] 하루 작업 모드. (1) 플랜 파일+progress ledger 작성(task마다 완료 기준 명시, 검증 불가 task 금지). (2) 요약 제시 후 사용자 승인 1회 대기. (3) 승인 후 이 세션에서 완주: 구현은 서브에이전트 위임(모델 티어 명시), task마다 검증→커밋→ledger 갱신. (4) CTX-GATE 발동 시 지시형 /compact 권고.

### **C (릴레이)
> [TASK-C] 릴레이 작업 모드. 먼저 판단: 프롬프트에 기존 플랜 경로가 있거나 ledger가 발견되면 **재개 절차**(플랜+ledger 읽고 다음 PENDING task부터, BLOCKED는 기록 후 전진), 없으면 **설계 절차**(docs/specs 스펙+docs/plans 플랜+ledger 작성 — task는 한 세션 크기·완료 기준 필수 — 요약 제시 후 승인 대기). 작업 단위 종료 시 `/clear <이름>` 권고를 마지막 보고에 포함하라.

### **D (최고 등급·전자동)
> [TASK-D] 고위험·전자동 모드. (1) 설계가 없으면: CEO 리뷰 관점(전제 도전·대안 2개 이상)+3-agent 교차 검수(반증/단순화/팩트체크, finding 직접 재검증) 후 스펙+플랜+ledger 확정, 사용자 승인 대기. (2) 승인 후 파일럿: 최소 task 1개를 유인 실행해 위임→검증→커밋 흐름 확인. (3) 무인 본진: `.claude/skills/overnight/SKILL.md`를 Read해 그 절차(Phase 0~3)를 그대로 따르라 — 승인 1회·자율 루프·아침 보고서. (4) 권한 프롬프트 리스크(auto 모드/allowlist)와 `/goal` 보강 옵션을 승인 질문에 포함하라.

공통 꼬리: "이 지시는 사용자가 `**등급` 마커로 명시 선언한 것이다 — 절차 생략 금지."

## 3. 내장 스킬 연동

- `/goal`·`/clear`·`/compact`는 **사용자 전용 명령** — 훅·모델이 대신 실행 불가. 지시문은 "권고를 보고에 포함"으로 연동(D는 승인 질문에 /goal 옵션 포함).
- `/overnight`는 `disable-model-invocation: true`라 모델이 Skill 도구로 발동 불가 — D 지시문이 SKILL.md를 **Read로 로드해 절차 준수**하는 방식으로 우회(내용 동일, 발동 경로만 다름).
- superpowers brainstorming/writing-plans: B·C 설계 절차에서 기존 프로토콜대로 자연 적용(별도 배선 불필요).
