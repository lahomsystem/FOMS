## 1. 왜 하는가

라홈 스마트스토어 주문은 **정산을 앞당기려면 발송처리를 먼저 찍어야 한다.** 발송처리 →
일정 시간 경과 → 구매확정요청 순으로 정산 시계가 돈다. 현재는 판매자센터에서 사람이
건별로 누르거나, 워크벤치에서 집 1개씩 누른다.

대상 선별이 한 번만 틀려도 구매자에게 "배송 시작"이 뜨고 취소 버튼이 사라진다. 대상이
항상 맞는다는 것을 실운영에서 확인한 뒤에 자동화로 넘어간다(사용자 확정: "먼저 버튼,

### 3.1 이것이 설계에 주는 답 — 배열을 키우지 않는다

배열 상한을 몰라도 된다. 우리 호출 단위는 이미 **집(household) 1개 = 호출 1회**이고,
한 집의 상품주문은 보통 1~3건이라 상한 근처에 갈 일이 없다.

그래서 "일괄"은 배열을 키우는 게 아니라 **집 단위 호출을 큐에 N개 넣는 것**이다.
기존 `refresh-all` 과 같은 패턴이다. 이 선택의 값어치:

- 집별 가드(취소·클레임·이미 발송)와 부분 실패 표식이 **그대로 살아 있다.** 전 주문을
  한 배열로 뭉치면 `fulfillment.py` 의 가드·멱등 기록 구조를 전부 갈아엎어야 한다.
- 워커 동시성 1이라 자동으로 순차 → 2 RPS를 넘길 구조가 아니다.
  **단 Worker replica 를 2 이상으로 올리면 이 전제가 깨진다** (`Procfile`·`railway-worker.toml`
  둘 다 단일 `rq worker default`, 현재 Worker×1).
- 배열 상한이라는 **모르는 값에 의존하지 않는다.**

## 4. 대상 선별 규칙 (조사 완료 · 재검증됨)

### 4.1 단계

1. **모집단** = 실측 대시보드의 당일 실측 술어와 같은 것.

   | 화면 요소 | 일괄이 상속하는가 |
   |---|---|
   | `OrderScheduleDate.kind=='measurement' AND date==오늘` (`dashboard.py:150-156`) | **상속** |
   | `Order.dashboard_active_filter(days=60)` (`dashboard.py:130`) | **상속** |
   | `apply_measurement_dashboard_order_scope` (`measurement_read_model.py:26-41`) | **상속** |
   | 검색어 필터 (`dashboard.py:130`) | **버린다** |
   | 담당자 필터 · mine 필터 (`dashboard.py:162-169`) | **버린다** |
   | 표시 캡 `MEASUREMENT_MAIN_DISPLAY_CAP = 300` | **버린다** (캡은 표시 장치지 모집단이 아니다) |

   화면 필터는 보는 사람마다 다르다. 일괄 대상이 그걸 상속하면 **누가 눌렀느냐에 따라
   나가는 주문이 달라진다** — 되돌릴 수 없는 조작에서 절대 안 된다. 버튼 문구도
   "오늘 **전체**"라고 말해야 한다.
2. **네이버 유래 판정** = `ExternalOrderLink.channel=='NAVER' AND order_id IN (모집단)`.
   기존 술어 `dock.py:727-737` 을 그대로 쓴다.
3. **집으로 접기** = `_links_of_group` 이 되찾는 집. 대표 link_id 는 아무거나 좋다(§4.3).
4. **처리 가능 판정** = 워크벤치 `can_dispatch` 와 같은 규칙 + **§4.4의 교정**.

라홈 조건은 따로 걸지 않는다 — 2번이 이미 그것을 함의한다(§4.2).

### 4.2 발견 ④ — "네이버 유래"는 링크 존재로만 판정한다

`structured_data['source'] == 'NAVER_SMARTSTORE'` 를 쓰면 안 된다. 운영 실측
(`docs/plans/2026-08-28-structured-source-dual-meaning-followup.md`, 2026-08-28)에서
`source` 가 네이버인 주문 29건 중 3건이 **오염 의심 최대치**로 남았고, 소급 구별이
불가능하다고 기록돼 있다. `naver_linked` 는 "보여 줄 원본이 있나"라는 **다른 축**이다
(`constants.py:25-26`: "예약금 건처럼 ERP에서 직접 받은 주문에 재결제를 붙이면 뒤만 참").

**링크 존재가 유일하게 신뢰 가능한 축이다.**

### 4.3 발견 ⑤ — 대상 단위는 주문이 아니라 **집**이다

`dispatch_order` 는 `order_id` 를 **전혀 보지 않는다**. 대상은 `_links_of_group` 이
`external_order_no` + `household_key` 로 되찾는 집이다(`fulfillment.py:261-287`).

따라서:
- 한 주문에 집이 **여럿** 붙을 수 있다(원 주문 NEW + ADDON 집 + REPAY 집). 각 집이 독립된
  발송처리 단위이고, 한 호출로 두 집이 함께 처리되는 경로는 **없다**.
- 집 안에서는 어느 link_id를 넘겨도 같은 집합을 되찾으므로 **대표 선정이 결과를 바꾸지
  않는다**(`dock.py:661-662`).
- 그래서 미리보기의 단위도 **집**이어야 한다. 주문 수로 세면 어긋난다.

관계별 발주확인 선행 규칙(`CLOSE_NOW_RELATIONS = ("ADDON",)`, `all()` 판정):

| 집 구성 | 발주확인 선행 |
|---|---|
| 전부 ADDON | 불필요 — 바로 발송처리 |
| 전부 REPAY / 전부 NEW / 혼재 | **필요** |

### 4.4 발견 ⑥ (치명) — 화면 큐와 워커의 발송 판정이 다르다

**재검증 완료:**

| 자리 | 세는 신호 |
|---|---|
| 워크벤치 큐 `_dispatched_count` (`naver_ingest.py:3291-3292`) | **우리 표식만** (`triage_state.fulfillment.dispatched_at`) |
| 이력 탭 칩 `_dispatch_pending_clause` (`naver_ingest.py:349-351`) | **두 신호 모두** (+ `raw_snapshot.delivery.sendDate`) |
| 워커 `dispatch_order` (`fulfillment.py:733-735`) | **두 신호 모두** |

**결과**: 판매자센터에서 사람이 직접 발송처리한 집은 워크벤치 큐에 **"미발송"으로 보이고**,
실행하면 `FulfillmentError("네이버에 이미 발송 기록이 있습니다…")` 로 떨어진다.

단건이면 실패 1건이지만, **일괄에서는 이게 대량 실패 띠가 된다.** 라홈은 판매자센터
수동 발송을 해 온 이력이 있으므로 실제로 밟는다.

→ **일괄 선별은 반드시 `_dispatch_pending_clause` 쪽(두 신호) 술어를 쓴다.** 화면 큐 술어를
쓰면 안 된다. 부분 인덱스 `ix_external_order_link_dispatch_pending` 과 조건식이 **글자까지
같아야** 한다(`naver_ingest.py:322-336`).

### 4.5 발견 ⑦ — `_broken_collection_guard` 는 발송처리에 없다

**재검증 완료**: 호출부는 `fulfillment.py:549`(`confirm_place_order`) **한 곳뿐**이다.

즉 `sync_status ∈ {PENDING_REVIEW, FAILED}` 인 깨진 수집분이라도 `place_order_status=='OK'`
이면 발송처리가 **그대로 나간다**. `order_id` 도 `reviewed_at` 도 보지 않는다.

단건에서는 사람이 그 집을 보고 누르니 문제가 덜하다. 일괄에서는 **아무도 안 본 채로**
나간다. → **일괄 선별은 `sync_status ∈ ("COLLECTED","LINKED")`(`HEALTHY_SYNC_STATUSES`)를
스스로 요구한다.** 서비스 가드에 없는 조건을 선별이 대신 건다.

### 4.6 음성 대조군 (요구 확인 — **존재한다**)

"예약금·전화 접수 건은 링크가 없다"는 **기본값이지 불변식이 아니다.**

- 링크 행을 만드는 코드는 **딱 2곳**(`ingest.py:125`, `ingest.py:234`) — **재검증 완료**.
  둘 다 커머스API 응답에서만 생기고 ERP 폼 경로에는 없다. 자동으로는 절대 안 붙는다.
- 그러나 `attach_link_to_order`(`promotion.py:516-600`)는 **대상 주문의 출처를 검사하지
  않는다.** 예약금 주문에 재결제(REPAY) 집을 손으로 붙이면 링크가 생긴다. 설계 주석이
  이 경우를 명시적으로 인정한다.

**대조군이 통과해도 사고가 아니다** — 그렇게 붙은 링크는 진짜 네이버 상품주문이므로
발송처리 대상이 맞다. 다만 **그 주문의 예약금 부분에는 대응하는 네이버 상품주문이 없다.**
그래서 §4.3대로 **집 단위로 세야** 하고, 주문 단위로 세면 틀린다.

§7의 검증은 "링크 없는 주문이 빠지는가"만 보면 안 되고, **링크가 붙은 예약금 주문이
집 단위로 정확히 나오는가**까지 봐야 한다.

## 5. 화면 (진입점 2곳)

공통: 서버 쪽 처리는 **한 군데로 공유**하고 진입점만 둘로 낸다.

- **실측 대시보드** — 실측 담당자가 그날 일이 끝난 것을 보면서 그 자리에서 누른다.
- **네이버 워크벤치** — 발송처리 관련 기능이 이미 모여 있는 관리 화면.

### 5.1 실측 대시보드 (조사 완료 · 재검증됨)

라우트 `foms/web/measurement/dashboard.py:93` → 풀페이지 `templates/measurement/dashboard.html`,
셸 프래그먼트 `partials/dashboard_fragment.html`. 본체는 `partials/dashboard_main.html`.

**당일 술어(정본)** — `dashboard.py:150-156`:
`OrderScheduleDate.kind == 'measurement'` AND `OrderScheduleDate.date == selected_date` + `.distinct()`.
`Order.measurement_date` 컬럼이 아니다. 필터 미지정 시 오늘 단일일
(`measurement_dashboard_filters.py:81-84`). scope 는 `apply_measurement_dashboard_order_scope`
(`measurement_read_model.py:26-41`) — 자가실측 상태이면서 자가실측·지방 플래그가 둘 다 없는
수도권 주문만 제외한다. 목록 상한 `MEASUREMENT_MAIN_DISPLAY_CAP = 300`.

> **캡 함정 주의**: 300건 캡이 파이썬 필터보다 **앞에** 있으면 대상이 조용히 빈다
> (`project_dashboard_cap_before_python_filter`). 일괄 대상 선별은 **화면 캡을 타지 않는
> 독립 쿼리**로 세야 한다 — 화면에 안 보이는 건이 대상에서 빠지는 것도, 대상에만 있고
> 화면에 없는 것도 둘 다 사고다.

#### 발견 ① — **이 화면에 "라홈 그룹"이라는 구획은 없다**

발주사는 **테이블 컬럼 하나**다(`dashboard_main.html:774` `<th>발주사</th>`, 셀 `:850-862`
`{{ orderer }}` 순수 텍스트). 라홈 vs 하우드로 나뉜 섹션·탭·필터가 없다. 화면의 그룹 축은
**담당자**(`manager_filter` 드롭다운 `:86-92`)이지 발주사가 아니다.

`:855` 의 "라홈시스템" 배지는 발주사가 아니라 `structured_data.flags.factory2`(2공장)라
**이름만 같고 다른 축**이다. 이걸 대상 판정에 쓰면 통째로 틀린다.

→ **사용자 확인 필요**(§9): "당일 실측 스케줄 > 라홈 건"은 발주사 컬럼이 라홈인 행을
가리키는 것으로 읽었다. 맞다면 화면에 그 구획이 없으므로 **일괄 버튼이 그 구획을 처음
만드는 셈**이다. 미리보기가 더 중요해진다.

다만 실무상 이 조건은 거의 자동 충족이다 — 네이버 수집 주문은 발주사가 항상 라홈으로
박힌다(`naver_commerce/constants.py:49`). 즉 **대상 = 당일 실측 + 네이버 링크 존재**로
정의하면 라홈 조건은 따라온다(§7에서 음성 대조군으로 검증).

#### 발견 ② — **v3 셸 풀페이지에서 페이지 스크립트가 통째로 빠진다**

`templates/measurement/dashboard.html:14-16`:

```jinja
{% if shell_variant != 'v3' %}
{% include 'measurement/partials/dashboard_scripts.html' %}
{% endif %}
```

v3 풀페이지 진입에서는 `measurement-entry.js` 체인 전체가 DOM에 안 나온다. 그런데
`dashboard_main.html:1137-1144` 는 v3에서도 데스크톱 본체(테이블·필터·헤더)를
`fos-v3-desktop-fallback` 으로 **그대로 출력한다** — 마크업은 있는데 그걸 구동할 JS가 없는
상태다. 프래그먼트 경로(`dashboard_fragment.html:10`)는 게이트 없이 include 하므로 셸 탭
스왑 진입은 정상. **풀페이지 직접 진입만 구멍이다.**

→ 일괄 버튼 JS를 `dashboard_scripts.html` 에 넣으면 **v3 풀페이지에서 버튼이 죽는다**
(보이는데 안 눌리는 상태 — 가장 나쁜 실패 모양). 선택지:
1. 버튼 마크업도 같은 게이트 안에 넣어 v3 풀페이지에선 **버튼 자체를 안 보이게** 한다.
2. 공유 스크립트를 `layout_scripts` 전역 1곳에 둔다(기존 규칙과 일치).

**권고: 1번.** 없는 기능을 없게 보이는 것이 있는 척하는 것보다 낫고, 전역 자산을 늘리지
않는다.

#### 붙일 자리
- 헤더 액션 영역 `dashboard_main.html:16-29` (주문 생성 / 이미지 저장 / ERP 옆)
- 다중선택 UI는 **현재 0개** — 체크박스·전체선택 마크업이 이 화면에 없다. 1단계는 개별
  선택 없이 "오늘 라홈 네이버 건 전체"를 미리보기에서 확인 후 실행하는 형태가 맞다.

#### 자산 핀
CSS 는 `dashboard.html` 과 `dashboard_fragment.html` **양쪽에 같은 `?v=`로 중복 선언**해야
한다(셸이 프래그먼트의 link 를 스캔해 주입). JS 핀은 `dashboard_scripts.html:1` 과
`measurement-entry.js:10` 두 곳 수동 동기화. 중앙 관리 장치 없음.

### 5.2 네이버 워크벤치 (조사 완료 · 재검증됨)

집 목록은 부분 템플릿이 아니라 인라인이다 — `templates/admin/naver_workbench.html:375`
`<div class="wb-queue">`, 행 루프 `:376-512`. 상세 pane 은
`partials/naver_workbench_pane.html`.

#### 발송처리 가능 판정 (서버·클라 동일 규칙)

`naver_workbench_pane.html:98-99` — **재검증 완료**:

```jinja
{% set can_dispatch = not locked and not dispatched and not naver_sent_at
                      and (not place_pending or close_now) %}
```

버튼을 닫는 상태 4개: `locked`(클레임 진행 중 또는 취소 완료) · `dispatched`(집 전원
발송됨) · `naver_sent_at`(네이버 원본에 발송 기록) · `place_pending && !close_now`(발주확인
미완). 서버 최종 방어선은 `fulfillment.dispatch_order` 의 가드들이다.

**일괄 미리보기는 이 술어를 그대로 재사용한다.** 화면이 따로 세면 어긋난다.

#### 발견 ③ — **기존 "벌크 발주확인"은 벌크 라우트가 아니다**

`naver-workbench.js:1230-1258` (재검증 완료): 선택한 집마다 **순차로**
`POST /<id>/fulfillment {action:'confirm'}` 을 N번 호출한다. 벌크 전용 라우트가 없다.
`wb-retry-failed` 도 같은 패턴.

즉 **일괄 발송처리도 새 라우트 없이 만들 수 있다** — 클라가 `{action:'dispatch'}` 로 같은
루프를 돌리면 끝이다. 다만 그러면:

| | 클라 N회 루프 (기존 벌크 발주확인 방식) | 새 서버 벌크 라우트 |
|---|---|---|
| 대상 결정 주체 | **화면** | **서버** |
| 새 라우트·매니페스트 등재 | 불필요 | 필요(§6.1) |
| 감사 로그 | 건별 N건 | 요약 1건 |
| 화면이 거짓말할 여지 | 있다 — 화면이 보낸 목록을 서버가 그대로 믿는다 | 없다 |

**권고: 새 서버 라우트.** `origin-cleanup/refresh`(`naver_ingest.py:3759-3760`)가 주석으로
**"화면이 보낸 목록을 믿지 않는다"**고 못박아 둔 이유가 그대로 여기 적용된다. 발주확인은
틀려도 클릭 한 번 비용이지만, **발송처리는 되돌릴 수 없다.** 되돌릴 수 없는 조작의 대상
목록을 화면이 정하게 두면 안 된다.

#### 기존 일괄 선례 2종 (대조)

| | `refresh-all` | `origin-cleanup/refresh` |
|---|---|---|
| 라우트 | `naver_ingest.py:3578` | `naver_ingest.py:3749` |
| 권한 | ADMIN | ADMIN/MANAGER/STAFF |
| 대상 결정 | 서버 (`refreshable_household_link_ids`) | 서버 (`pending_origin_cleanup`) |
| 상한 | 200 (`REFRESH_ALL_LIMIT`), 응답에 `truncated` | 20 (`ORIGIN_CLEANUP_LIMIT`) |
| 큐 전멸 시 | 503 | 503 |
| 대상 0 | 200 + `queued:0` | 200 + `queued:0` |
| 진행률 | **있다** — `refresh-progress` 3초 폴링, 조회는 집 수와 무관하게 2회 | 없다 |
| 감사 | 요약 1건 + detail | 요약 1건 + `link_ids` |

**상한은 반드시 붙이고 잘린 사실을 로그·응답에 남긴다.** `origin-cleanup` 은 20건만
enqueue 하면서 응답 `count` 는 전체를 줘서 화면이 두 값을 함께 읽지 않으면 어긋난다 —
같은 실수를 반복하지 않는다.

#### 진행률: 그대로 못 쓴다

`_fulfillment_progress`(`naver_ingest.py:3131-3191`)는 세는 술어가 `is_place_pending`
**하나뿐**이다. 발송 진행률을 세는 코드는 리포지토리에 없다. 선택지:
1. 진행률 없이 "요청했습니다" + 사용자가 새로고침 (`origin-cleanup` 방식)
2. `dispatched` 술어를 세는 진행 라우트 추가

**권고: 1단계는 1번.** 실패는 기존 실패 띠(`#wb-result`)가 이미 `dispatch` 를 지원한다
(`naver-workbench.js:1798` 이 `<link_id>:<action>` 쌍을 다룬다).

#### 게이트 주의

`POST /<link_id>/fulfillment` 에는 워크벤치 피처 게이트가 **없다**(cancel·return 에는 있다).

**초안의 "게이트를 넣자"는 권고는 철회한다(CEO 지적).** `is_naver_workbench_enabled` 는
user-id 코호트 방식이라(`feature_flags.py:325`) **코호트 밖 실측 담당자에게 새 라우트가
403** 이 된다 — 진입점 2곳 중 실측 대시보드 쪽이 통째로 죽는다.

→ 게이트는 **전역 킬스위치 1개 + 롤**로 간다. 코호트를 쓰지 않는다.

## 6. 서버 설계

- 미리보기(GET): 대상 집 목록 + 각 집의 처리 가능 여부·사유. **읽기 전용.**
- 실행(POST): **서버가 대상을 다시 계산**하고 `enqueue_naver_fulfillment(link_id, "dispatch")`
  를 집마다 넣는다. 화면이 보낸 목록은 믿지 않는다.
- 네이버 HTTP는 **WORKER에서만** 나간다(호출 IP 3슬롯 계약) — web은 enqueue만.
- 상한을 두고, 잘렸으면 응답·로그·화면 문구 **셋 다**에 남긴다.
- 큐 전멸 시 503 + "판매자센터에서 처리하세요" (기존 문구 재사용).

## 8. 위험

| 위험 | 대응 |
|---|---|
| **발송처리는 되돌릴 수 없다.** 잘못 고른 집이 나가면 구매자에게 배송 시작으로 뜨고 취소 버튼이 사라진다 | 1단계는 사람이 누른다 + 미리보기 필수 + 대상 술어를 화면과 공유 |

| 5시 일괄이 수집 스윕(5분 주기, 같은 워커)을 밀어냄 | 실측 후 판단. 필요하면 enqueue 간격 |
| 클레임·취소 진행 중인 집 | 기존 가드가 막는다. 결과에 "건너뜀 + 사유"로 표시 |
| 화면과 일괄의 세는 법이 어긋남 | `group_key` SSOT 공유, 소스로 판정 |
| **우리 취소 버튼도 함께 죽는다** — `cancel_order` 는 `dispatched_at` 이 있으면 거부한다(`fulfillment.py:869-877`, 재검증 완료). 실측 후 시공 전 취소(시공 불가·고객 변심)가 나면 남는 길은 반품 요청뿐이고 승인은 판매자센터다 | 사용자에게 명시. 미리보기 문구에 "발송처리 후에는 FOMS에서 취소할 수 없습니다" |
| **구매확정이 시공 전에 도래할 수 있다.** 실측→시공은 수 주인데 발송 시계를 실측일에 돌린다. 구매확정 후에는 취소 API 자체가 불가 | 정산을 앞당기는 대가가 "문제 생겼을 때 손이 묶인다"임을 사용자가 알고 결정 |
| 실측 **스케줄**과 실측 **완료**는 다르다 — 방문 취소·부재 건이 5시 대상에 든다 | 미리보기가 집별로 실측완료 여부 표시(§7) |

### 9.1 상한 = **50** (관측으로 확정, 2026-08-31)

CEO 권고는 50이었고 주 세션이 보류했다. 근거는 같은 원장의 기록이었다 —
`2026-08-23-naver-workbench-v3-ledger.md:474`: "**상한 50 이 실제 운영 물량(58집)보다
작았다.** 상한은 '평소엔 안 닿는 안전장치' 여야". 측정 없이 50을 고르면 같은 실수를
반복할 위험이 있었다.

**측정 결과 50이 맞다.** 관측된 하루 최대는 **7집**(§1.1)이고 50은 그 **7배**다 — "평소엔
안 닿는 안전장치" 조건을 만족한다. 58집은 하루 대상이 아니라 전 기간 잔량이었으므로
원장의 그 사례와 모집단이 다르다.

잘렸을 때 응답·로그·화면 문구 **셋 다**에 남긴다(`origin-cleanup` 이 count 와 queued 를
어긋나게 준 실수를 반복하지 않는다).

### 9.2 사용자 확인 — 답변 받음 (2026-08-31)

2. **발송처리 후 FOMS에서 취소가 막히는 것 — 받아들인다** (사용자 확답: "정산이 더 중요").
   §8 위험표의 그 행은 알려진·수용된 거래다. 다만 **미리보기 문구에는 그대로 명시한다** —
   누르는 사람이 매번 알고 눌러야 한다.

아직 안 받은 것:

## 9.4 실행 게이트 (T4 확정)

- **전역 킬스위치 `FOMS_NAVER_BULK_DISPATCH_ENABLED`** (기본 **꺼짐**). 코호트를 쓰지
  않는다 — 워크벤치 게이트는 user-id 코호트라 그걸 재사용하면 코호트 밖 실측 담당자에게
  실행 라우트가 403 이 되어 진입점 두 곳 중 하나가 조용히 죽는다.
- 권한 **ADMIN·MANAGER** (`MANAGER_MUTATION` 정책).
- **v3 풀페이지에서는 버튼을 렌더하지 않는다.** 그 셸은 페이지 스크립트를 통째로 안 실어
  버튼이 보이는데 안 눌린다 — 불가역 조작에서 가장 나쁜 실패 모양이다. 목록은 그대로 보인다.

## 10. 구현 순서 — 미리보기가 본체다

**범위는 줄이지 않는다. 순서를 뒤집는다.** 하루 대상이 한 자릿수라면 이 기능의 값어치는
클릭 절약이 아니라 **빠뜨림 방지**다. 그러면 미리보기가 본체이고 실행 버튼이 부속이다.
미리보기는 읽기 전용이라 먼저 배포해도 안전하고, 그것만으로 이미 쓸모가 있으며, 실제
대상 수를 관측한 뒤 실행을 붙이면 상한·권한·자동화 판단이 추측이 아니라 관측 위에 선다.

| task | 완료 기준 |
|---|---|
| ~~**T0a** 기존 발송 이력으로 G2 답하기~~ | **완료 (2026-08-31)** — §1.2. `DIRECT_DELIVERY` 108/108, PURCHASE_DECIDED 도달 확인 |
| ~~**T0b** 단건 실호출~~ | **불필요** — T0a 가 답했다. 되돌릴 수 없는 시험 호출을 하지 않는다 |
