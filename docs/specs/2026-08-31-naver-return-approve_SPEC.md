# 네이버 반품 **승인** — 설계서 (T8-S2)

> 2026-08-31. 선행: `2026-08-27-naver-return-send_SPEC.md`(반품 접수, 운영 배포 완료).
> 이 문서는 그 설계서 §3 이 "**안 만든다 (이번엔)**"으로 미뤄 둔 칸을 연다.

## 0. 한 줄

발송된 주문의 반품을 **접수하면서 승인까지 한 번에** 끝낸다. 지금 사람이 판매자센터에서
22~60초에 하는 일을 FOMS 안으로 옮기는 것이다.

## 1. 왜 지금 여는가 — 2026-08-27 "착수 불가" 판정이 무엇으로 뒤집혔나

| 그때 차단 요인 | 지금 |
|---|---|
| **B1 보류 분기** — 승인 전에 `holdbackStatus`·`claimDeliveryFeePayMethod` 를 읽고 갈라야 하는데 스테이징 0건이라 모양을 모른다 | **닫힘.** 근거 셋: ① 운영 고유 클레임 **25건 전수**에 그 두 필드와 `claimDeliveryFeeDemandAmount` 가 **전부 없음** ② **판매자 접수 9건이 22초·60초 만에 `RETURN_DONE`** — 보류가 걸렸으면 승인이 막혀 불가능한 속도 ③ 사용자 확인: "운영하면서 **네이버에서 반품보류를 거는 적은 한번도 없었다**" |
| **승인 API 규격 미확인** | **해소.** 공식 문서 v2.86.0 확인(§2) |
| SPEC:47 "`접수 → 수거정보 → 실제 회수 → 검수 → 승인` 가운데 셋은 버튼으로 못 만든다" | **전제가 무너졌다.** 시공 제품이라 **회수도 검수도 없다.** 운영 25건 전부 `collectCompletedDate == returnCompletedDate`(같은 시각) — 데이터가 그걸 찍는다. 가운데가 비면 흐름은 **두 칸**이다 |

**보류 자동 발동 조건**은 "반품 비용 결제 방식이 **환불금에서 차감**"인데
([#398](https://github.com/commerce-api-naver/commerce-api/discussions/398)), 우리는
`deliveryFeeAmount` 206행 전부 0이고 반품배송비 청구 흔적이 없다. 그래서 보류는 **주 경로가
아니라 가드**다(§4-3).

### 접수만 있는 버튼은 사람 일을 안 줄인다 (이 설계의 진짜 이유)

반품 접수 기능은 운영에 있고 **실호출 0회**다. 그런데 같은 기간 사람은 판매자센터에서
**9건을 접수+승인까지 한 번에** 처리했다(`취소 재결제` 5 · `반품 재결제` 4). 접수만 FOMS 에서
하고 승인하러 판매자센터로 또 가야 하면 두 군데를 왕복하게 되니, 처음부터 판매자센터에서
끝내는 것이 빠르다. **승인이 붙어야 이 기능이 쓰인다.**

## 2. 네이버 규격 (공식 문서 v2.86.0 원문 확인, 2026-08-31)

```
POST /v1/pay-order/seller/product-orders/:productOrderId/claim/return/approve
1건의 상품 주문에 대한 반품 요청을 승인합니다.

Request  : Path Parameters — productOrderId (string, required)
           **Request Body 항목 없음**
curl 예시: -X POST + Accept + Authorization 만. Content-Type 도 -d 도 없다.
Response : data.successProductOrderIds / data.failProductOrderInfos
```

- **body 를 보내지 않는 것이 공식이다.** 2026-08-27 원장이 "빈 body → 400, `approvalData` 넣으면
  200"을 근거로 삼았으나 그 출처(#3693)는 **취소** 승인 문서이고 해당 문장이 없다. 근거 폐기.
- 응답이 취소·반품요청과 **동형**이라 `fulfillment._split_result`(`:320`)를 그대로 쓴다.
- **되돌리는 엔드포인트는 없다.** 승인은 환불 확정이다.

참고(이번 범위 아님): 거부는 `claim/return/reject` 이고 **`rejectReturnReason`(string, required)**
가 필요하다 — 그 문장은 구매자에게 그대로 전달된다.

## 3. 범위

| 조각 | 이번 | 이유 |
|---|---|---|
| 반품 **승인** | **만든다** | 위 |
| 반품 **거부** | 안 만든다 (**다음**) | 실제로 쓰는 업무임이 확인됐다(사용자). 사유 문장이 구매자에게 그대로 가므로 문안 규칙을 먼저 정해야 한다 |
| 보류 / 보류 해제 | **영구히 안 만든다** | 우리가 걸 이유가 없고, 안심케어 건은 **보류해제 자체가 금지**다([#3329](https://github.com/commerce-api-naver/commerce-api/discussions/3329)). 상수로도 두지 않는다 |

## 4. 설계

### 4-1. 발동 — 접수 모달의 체크박스 (사용자 결정 2026-08-31)

별도 버튼을 만들지 않는다. 접수 모달(`naver_workbench_pane.html`)에
**`승인까지 한 번에`** 체크박스를 둔다. 끄면 지금과 똑같이 접수만 나간다.

별도 버튼이 아닌 이유: 접수 후 화면을 다시 열어 승인을 또 누르게 하면 지금의 판매자센터
왕복과 같은 모양이 된다 — 이 기능이 존재하는 이유를 스스로 지운다.

체크박스를 켜면 모달의 빨간 띠가 한 문장 더 말한다: **환불이 즉시 나간다.**

### 4-2. 경로 — 새 라우트를 안 판다

기존 `POST /admin/naver-ingest/<link_id>/return` payload 에 `approve: true` 를 더한다.
큐·태스크도 기존 것을 쓴다(`enqueue_naver_return(..., approve=)` →
`run_naver_fulfillment_task(action="return", approve=)` → `fulfillment.request_return(..., approve=)`).

새 태스크를 파지 않는 이유는 접수 때와 같다 — `except FulfillmentError` 로 실패 사유를 DB 에
남기고 커밋하는 규율이 그 자리에 이미 있고, 갈래를 새로 파면 그 규율이 두 벌이 된다.

### 4-3. 승인 절차 (WORKER, 상품주문 1건씩)

접수 성공분에 대해서만 돈다. 각 건마다:

1. **상세 재조회** — 접수 직후 네이버 상태가 아직 안 넘어왔을 수 있다. 조회는 우리가 이미
   쓰는 `client.get_product_orders`.
2. **보류 가드** — `mapping.extract_claim_holdback` 로 `holdback_status` 를 읽는다.
   값이 있으면 **승인하지 않는다.** 우리가 보류를 풀지 않는다(안심케어 금지 + 반품비 초기화
   위험). 사유를 상태에 남기고 화면이 "판매자센터에서 처리하세요"로 보낸다.
3. **상태 가드** — `claimStatus` 가 반품 축(`RETURN_REQUEST`·`COLLECTING`·`COLLECT_DONE`)이
   아니면 승인하지 않는다. **여기서 sleep 루프를 돌지 않는다** — 워커를 점유하고, 실패를
   숨긴다. 재조회 **1회**로 안 되면 "접수는 됐고 승인은 남았다"를 화면이 말한다.
4. 승인 호출 → `_split_result` 로 성공/실패 가른다.
5. 성공분에 `triage_state['return']['approved_at']`·`approved_by` 기록(멱등 키).

**부분 승인이 정상이다.** 집 안 상품주문 일부만 승인될 수 있고, 그 상태를 숨기지 않는다.

### 4-4. 중간 상태를 화면이 말한다

"접수됨 / 승인됨"이 갈리므로 배지가 둘을 구분해야 한다. **접수는 됐는데 승인이 안 된 건**이
가장 위험한 상태다 — 아무도 말 안 하면 환불이 안 나간 채 잊힌다.

- 승인 성공: `반품 승인 완료`
- 접수만 성공: `반품 접수됨 — 승인 남음` + 사유(보류 / 상태 미도달 / 호출 실패)

### 4-5. 안 하는 것

- 보류·보류해제 호출 (상수로도 두지 않는다)
- 자동 재시도 루프
- 승인 취소(엔드포인트 없음)

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 승인은 **되돌릴 수 없다** — 환불 확정 | 체크박스는 기본 꺼짐. 모달 빨간 띠가 "환불이 즉시 나갑니다"를 말한다. 서버가 접수 성공분에만 승인한다 |
| 접수는 됐는데 승인이 안 된 중간 상태 | §4-4 배지로 명시. 조용히 두지 않는다 |
| 네이버 상태 전이 지연 | 재조회 1회 + 미도달이면 승인 보류(사람이 다시 누른다). sleep 루프 금지 |
| 보류 걸린 건 | 승인 중단 + 판매자센터 안내. **우리가 풀지 않는다** |
| 사유 오선택 제재([#2823](https://github.com/commerce-api-naver/commerce-api/discussions/2823)) | 접수 사유 화이트리스트는 이미 2코드로 좁혀져 있다. 승인은 사유를 새로 고르지 않는다 |
