# 주문 품목 안정 식별자 (ORDER-ITEM-UID) — 스펙

- 작성: 2026-08-11
- 상태: **승인 대기**
- 선행: ORDER-DIFF-00/01/02 (변경 기록·원장·이력 탭 — deploy `2c2f58b0`, 운영 `2b3c8bf0`까지 01)
- 관련: ITEM-ID-00(첨부·일정의 `item_index` → UUID 분류, `foms/services/orders/audit_order_item_identities.py`)

## 1. 문제

`structured_data['items']` 는 **위치 인덱스 배열**이고 안정 식별자가 없다. 그래서 변경 기록이
품목을 인덱스로만 짝짓는다:

```
저장 전: [붙박이장(50만)]
저장 후: [수납장(10만), 붙박이장(50만)]     ← 맨 앞에 하나 끼움

지금 기록되는 것:
  1번 품목 품목명  붙박이장 → 수납장      ← 사실이 아니다
  1번 품목 단가    500000 → 100000        ← 사실이 아니다
  2번 품목 추가(붙박이장)                  ← 사실이 아니다
실제로 일어난 일: 수납장 1건 추가. 붙박이장은 그대로.
```

변경 이력 탭(ORDER-DIFF-02)이 배포되면서 이 오해가 **직원 눈앞에 보이는 화면**이 됐다.
"내가 안 바꾼 걸 바꿨다고 나온다"는 신고가 나오면 감사 기록 전체의 신뢰가 깎인다.
NetSuite 서브리스트 사각지대와 같은 계열이며, 해법도 같다: **행마다 안정 id**.

## 2. 목표 / 비목표

**목표**
1. 품목마다 서버가 발급하는 안정 식별자 `uid` 를 갖는다(주문 수명 내 불변).
2. 변경 비교가 인덱스가 아니라 `uid` 로 짝짓는다 — 삽입·삭제·순서 변경이 정확히 기록된다.
3. 기존 주문(2,218건 규모, uid 없음)도 저장 시점에 조용히 채워진다(lazy backfill).

**비목표**
- 첨부·일정의 `item_index` → uid 이관(ITEM-ID-00 본체, 별도 backfill·수동 검토 필요)
- 품목 순서 변경 UI, 품목 병합/분할
- 과거 변경 기록의 소급 정정(불가능 — 그때는 uid 가 없었다)

## 3. 설계

### 3.1 발급·보존 (서버가 소유)

`foms/services/orders/structured_item_uid.py` (신규)

> **모듈명 주의**: `foms/services/orders/item_identity.py` 는 **이미 존재**한다 — ITEM-ID-00 의
> `OrderItemIdentity` 레지스트리(주문·슬롯 인덱스 기준 UUID, 첨부·일정 결합용)다. 키가 위치라
> 이 문제를 풀지 못하며, 용도도 다르다. 그래서 별도 모듈로 둔다(통합은 ITEM-ID-00 본체 몫).

```python
def ensure_item_uids(old_sd: dict, new_sd: dict) -> int   # 새로 발급한 개수
```

**2패스여야 한다**(구현 중 확인). 위치 상속을 먼저 돌리면 맨 앞에 끼운 새 품목이 0번 자리의
옛 uid 를 가로채고, 정작 그 uid 를 들고 온 품목이 새 값을 받는다 — 삽입 1건이 "앞 품목이
바뀌고 뒤에 하나 추가됨"으로 기록된다(정확히 uid 로 없애려던 그 오해).

1. **1패스** — 클라이언트가 보낸 uid 중 *이 주문에 이미 있던* 값만 확정(위조·도용 차단,
   `lock_provenance` 와 같은 철학). 중복은 뒤쪽을 탈락시킨다.
2. **2패스** — 남은 자리에 **같은 위치의 옛 uid** 중 아직 안 쓰인 것을 물려준다.
3. 그래도 없으면 UUID4 신규 발급.

호출 위치: `project_structured_form` 직후, `captured['diff']` 계산 **직전**(전체 저장 PUT).
인라인 PATCH 는 품목을 만들지 않으므로 기존 uid 를 건드리지 않는다.

### 3.2 클라이언트 왕복 (2곳)

- `erpNewItemRow(item)` (`static/js/orders/erp-order-shared.js:1261`) — 행 생성 시
  `row.dataset.itemUid = item.uid || ''`
- `erpCollectStructured()` (같은 파일 `:1949`) — 수집 시 `if (row.dataset.itemUid) obj.uid = ...`

품목 상위 키는 top-level allowlist(`enforce_form_allowlist`) 대상이 아니므로 `uid` 는 그대로
왕복한다(추가 허용 작업 불필요 — 확인 완료).

**uid 를 모르는 다른 입력 경로**(태블릿 실측 폼·도면 마법사 등)는 uid 없이 보낸다 → §3.1 규칙 2가
서버에서 채운다. 그 경로에서 순서를 바꾸면 여전히 인덱스 오탐이 나지만, 지금과 같거나 낫다
(회귀 없음). 경로별 uid 배선은 후속.

### 3.3 변경 비교 (`structured_diff`)

```
양쪽 모두 uid 보유 → uid 로 짝짓기(추가/삭제/수정 정확)
한쪽이라도 uid 없음 → 지금처럼 인덱스 짝짓기(레거시 문서 호환)
```

- 경로 표기는 **유지**한다(`items.2.price`) — 원장 인덱스·화면 라벨("3번 품목")이 그대로 읽힌다.
  단 비교 짝짓기만 uid 로 한다. **순서만 바뀐 품목은 기록하지 않는다**(값이 그대로면 변경이
  아니다 — 사용자 결정 2026-08-11).
- 삭제된 품목의 경로는 **삭제 시점 인덱스**를 쓴다.

### 3.4 원장 컬럼

`order_field_changes` 에 `item_uid` (String(36), nullable) 추가 — 마이그레이션 `itemuid_00`.
품목 축 조회("이 품목이 어떻게 바뀌어 왔나")를 열어 두는 값이며, 인덱스는 붙이지 않는다
(지금 그 질의를 하는 화면이 없다 — 필요해질 때 붙인다).

### 3.5 화면 detail 바이트 예산 (구현 중 발견한 결함)

`normalize_security_detail` 은 **4,000자를 넘는 detail 을 통째로** `{'truncated': True,
'size': N}` 표식으로 바꾼다. 그러면 변경 목록만이 아니라 `mode`·`customer_name` 같은 맥락까지
사라진다. 건수(40건)만 세던 기존 상한은 이 한도를 넘길 수 있었고(품목 46개 일괄 변경에서 실제
발생), uid 를 목록에 넣자 바로 재현됐다.

조치 2개:
- 화면 detail 의 변경 목록에 **바이트 예산**(3,200자)을 건다 — 건수 상한과 둘 중 먼저 걸리는 쪽.
- `uid` 는 화면이 쓰지 않으므로 **detail 에서 뺀다**. 질의용 값이라 원장 컬럼에만 둔다
  (같은 값을 두 곳에 두면 예산만 먹는다).

넘친 분량은 여전히 사라지지 않는다 — 원장에 전량이 있고 `truncated` 개수로 표시된다.

## 4. 백필

전량 일괄 backfill 을 **하지 않는다**. 저장 때 채우는 lazy 방식이면 활성 주문부터 자연히
채워지고, 손대지 않는 오래된 주문은 uid 없이 남아도 인덱스 비교로 지금과 동일하게 동작한다.
일괄 UPDATE 는 2,218건 JSONB 재작성 + 전 주문 `structured_updated_at` 오염 위험이 있다.

선택지로 `scripts/ops/backfill_item_uids.py --apply` 를 두되 기본 dry-run, `--order-ids` 로
범위 지정 가능하게 한다(운영에서 필요할 때만).
