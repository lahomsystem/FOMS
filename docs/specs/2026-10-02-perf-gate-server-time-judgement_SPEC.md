# 성능 게이트 판정값을 서버 처리시간으로 바꾸기 (SPEC, 승인 대기)

작성 2026-10-02 · 대상 `tools/perf/staging_perf_gate.py`, `tools/perf/perf_budgets.json`, `foms/platform/http.py`

## 1. 왜 (실측 근거)

2026-10-01 PR #487(라홈시스템 권한) 승격 때 perf-gate 가 4회 연속 FAIL 났다. 원인을 추적한 결과 **화면이 느려진 게 아니었다.**

| 런 | healthz min | 주문 대시보드 절대 min | 판정값(차이) | 결과 |
|---|---|---|---|---|
| 11:00Z (빠르던 때) | 258ms | 352ms | 94 | PASS |
| 15:08Z | 218ms | 378ms | 160 | FAIL 기준 |
| 10-02 직접 측정 | 134~194ms | 348ms | 154~214 | — |

- 판정값 = `min(경로 TTFB) − min(healthz TTFB)`. healthz min 이 7개 표본에서 1분 안에도 134~258ms 로 흔들린다.
- healthz 가 운 좋게 낮게 나오면 경로 절대시간이 같아도 차이값이 커져 FAIL 난다. 같은 코드 deploy 런(15:07Z)도 같은 줄에서 FAIL 이었다(advisory 라 초록으로 보였다).
- 같은 시각 서버 로그: 대시보드 캐시는 대부분 hit, `req_duration`(400ms 초과) 기록은 0건. 서버 쪽 변화는 없었다.
- 의심했던 11:07Z 묶음(3679913b 대시보드 캐시·5ca22302 AS 예열)은 GET 경로를 바꾸지 않는다. 예열은 브라우저 JS 가 부르는데 게이트는 JS 를 실행하지 않는다.

즉 판정값에 **네트워크 잡음이 두 번(경로 min, healthz min) 들어간다.** 예산 167ms 에 잡음 ±50ms 가 섞이면 오탐이 반복된다.

## 2. 무엇을

1. **서버가 자기 처리시간을 헤더로 낸다.** `foms/platform/http.py` 의 `_log_request_duration` 이 이미 `duration_ms` 를 계산한다. 같은 자리에서 `Server-Timing: app;dur=<ms>` 를 붙인다.
   - 인증된 요청에만 붙인다. 무인증 healthz·로그인 화면에는 붙이지 않는다(외부에 내부 시간을 노출하지 않음).
2. **게이트 판정을 서버 시간 min 으로 바꾼다.** 경로별 `server_ms_min_max` 예산을 새로 둔다. 시드는 기존 `--seed` 절차로 한다.
3. **기존 TTFB 차이값은 정보용으로 남긴다.** 리포트에는 계속 찍되 FAIL 판정에는 쓰지 않는다. wire 바이트 판정은 그대로 둔다(네트워크 무관이라 결정적).
4. 헤더가 없는 응답(옛 배포)이면 기존 TTFB 차이값 판정으로 되돌아간다. 배포와 게이트 변경 순서가 엇갈려도 안전하다.

## 3. 바꾸지 않는 것

- 측정 경로·횟수, 로그인 방식, exit code(0/1/2), advisory 모드.
- render_ms 판정(이미 서버 측 값이라 잡음이 없다).

## 4. 위험과 되돌리기

- 서버 시간은 응답 직렬화·네트워크 전송을 빼므로 "큰 HTML 을 보내 느려짐"은 못 잡는다. 이건 wire 바이트 예산이 계속 잡는다.
- 되돌리기: `perf_budgets.json` 에서 새 예산 키를 지우면 기존 판정으로 돌아간다(4번 폴백).

## 5. 완료 기준

- `tests/harness` 에 계약 테스트 추가: 헤더 있으면 서버 시간 판정, 없으면 TTFB 폴백, 무인증 요청에는 헤더 없음.
- `pre_push_smoke.ps1` exit 0, `tests/harness` 통과.
- 스테이징에서 게이트를 연속 3회 돌려 같은 코드에서 판정이 흔들리지 않음(PASS 3/3)을 확인한다.
