# 로그인 실패 잠금이 IP 하나에 기대지 않게 하기 — SPEC (2026-10-19)

## 목적
같은 아이디로 비밀번호를 계속 틀리면, 요청이 어느 IP 로 들어오든 결국 잠기게 한다. 여러 워커가 같은 카운터를 보는지 기동 때 로그로 드러내고, 저장소가 안 되면 로그를 남긴다(로그인은 막지 않는다). 계정이 있든 없든 응답은 같다.

## 증상(2026-10-19)
- 스테이징 `POST /login`, 없는 아이디 하나로 9번 → 9번 모두 200. 코드 기대는 8번째부터 429.
- 로컬, 같은 IP → `[200×7, 429, 429]`. 요청마다 IP 를 바꾸면 → `200×9`.

## 지금 구조
줄 번호는 변경 전(origin/deploy `4188600fb`) 기준.
- 잠금 카운터 키는 `foms-login:<아이디 해시>:<IP>` 하나뿐이다 — `foms/services/security/auth_rate/login_lockout.py:155-160`(IP 는 `get_remote_address()`), 실패 키 `:163-169`, 잠금 키 `:172-178`. **IP 와 상관없는 카운터가 없다.**
- IP 는 ProxyFix 가 `X-Forwarded-For` 오른쪽에서 `FOMS_TRUSTED_PROXY_HOPS`(기본 1)번째 항목으로 세운 `remote_addr` 다 — `foms/platform/app_factory.py:196-201`. 스테이징도 `RAILWAY_ENVIRONMENT == "production"` 이라 적용된다 — `:226-229`, `:267-269`. 홉 수는 한 번도 실측되지 않았다 — `docs/harness/foms_bugfix_progress_ledger.md:33`("Railway hop 실측 merge-gate").
- 저장소는 limiter 가 쥔 것을 그대로 쓴다 — `login_lockout.py:181-199`. limiter 는 `REDIS_URL` 이 있으면 Redis, 없으면 `memory://` — `foms/services/rate_limit.py:190`, `:233-241`. gunicorn 은 워커 2개 — `start.sh:27`.
- 저장소 호출이 실패하면 경고 로그를 남기고 잠그지 않는다 — `login_lockout.py:210-218`, `:228-236`.
- 없는 아이디도 센다 — `foms/web/auth/routes.py:416-420`(`_note_login_failure(username, None)`). 잠금 판정은 계정 조회보다 먼저다 — `routes.py:409`.
- 잠금 429 응답에 `Retry-After` 가 없다 — `routes.py:343-357`.

## 원인(로컬 재현으로 확정한 것)
임시 재현 테스트(커밋하지 않음)로 9회 연속 실패를 보냈다. 기본 임계 8.

| 경우 | 결과 |
|---|---|
| A. 같은 IP | `[200×7, 429, 429]` (정상) |
| B. ProxyFix(홉 1) 뒤, 요청마다 다른 `X-Forwarded-For` | `200×9` |
| C. ProxyFix(홉 1) 뒤, 손님 IP 는 같고 둘째 홉만 바뀜(`198.51.100.7, 10.0.0.N`) | `200×9` |
| D. 메모리 저장소 앱 2개(워커 2개 흉내)에 번갈아 | `200×9` |

1. **확정 — 잠금의 유일한 카운터가 IP 에 묶여 있다.** 앱이 보는 `remote_addr` 가 요청마다 달라지면 카운터가 매번 1에서 다시 시작해 절대 임계에 닿지 않는다(B·C). 달라지는 길은 둘이다: 손님 쪽 출구 IP 가 바뀌는 경우(B), Railway 프록시 체인이 홉 1보다 길어 오른쪽 끝이 엣지 주소가 되는 경우(C). Railway 는 헤더 규칙을 문서로 보장하지 않고, 2026-03 에는 CDN 주소가 `X-Forwarded-For` 에 섞이는 회귀도 있었다(Railway Help Station 글).
2. **조건부 — 워커별 메모리.** `REDIS_URL` 이 없으면 워커 2개가 카운터를 반씩 나눠 가져 잠기지 않는다(D). 스테이징·운영 web 은 `REDIS_URL` 이 있으므로 이번 원인은 아니다. 다만 지금은 이 상태가 되어도 아무 로그가 없다.
3. **조건부 — Redis 호출 실패.** 실패하면 잠금이 통째로 꺼지고 요청마다 "로그인 잠금 카운터 증가 실패" 경고가 남는다. 서버 로그를 볼 수 없어 배제하지 못했다. 아래 변경 뒤에도 스테이징이 20회 모두 200 이면 이것이다.
4. **배제 — 없는 아이디 제외.** 없는 아이디도 센다(위 `routes.py:416-420`, 재현 A 도 없는 아이디).

스테이징에서 1의 B·C 중 어느 쪽인지는 서버 헤더를 봐야 가린다(이 작업 범위 밖). 아래 변경은 둘 다를 막는다.

## 변경
1. **계정 카운터 추가** (`login_lockout.py`)
   - 키 `foms-login-acct:<정규화한 아이디 해시>:fail` / `:lock`. 정규화 = NFKC → 앞뒤 공백 제거 → 대소문자 접기(`casefold`). IP 는 넣지 않는다.
   - 실패 1건마다 (아이디, IP) 카운터와 계정 카운터를 함께 올린다. 어느 쪽이든 임계에 닿으면 그쪽 잠금 마커를 세운다.
   - 잠금 판정은 둘 중 하나라도 잠겨 있으면 잠김. 판정은 지금처럼 계정 조회 전에 하고, 계정이 있든 없든 같은 429 를 낸다.
   - 기존 (아이디, IP) 카운터는 그대로 둔다(임계 8 / 창 15분 / 잠금 15분). 한 사람이 한 자리에서 틀리면 지금처럼 8번째에 잠긴다.
2. **한도와 시간**
   - 계정 임계 **20회 / 창 15분 / 잠금 15분**. env `FOMS_LOGIN_ACCOUNT_LOCKOUT_THRESHOLD`(기본 20, 최소 1). 창·잠금 시간은 기존 env(`FOMS_LOGIN_LOCKOUT_WINDOW_SECONDS`·`FOMS_LOGIN_LOCKOUT_SECONDS`)를 같이 쓴다.
   - 20 인 이유: (아이디, IP) 임계 8 보다 충분히 커야 한 사람의 오타는 늘 (아이디, IP) 잠금이 먼저 걸린다(같은 자리에서 8회 뒤에는 더 세지 않는다). 사무실·휴대폰 두 자리에서 각각 7번씩 틀려도 14회라 계정 잠금까지 여유가 있다. 공격자는 IP 를 바꿔도 15분에 19번만 추측할 수 있다(하루 약 1,800회 → 비밀번호 정책 8자 이상이면 온라인 추측은 무의미).
   - 성공 로그인은 (아이디, IP) 카운터·잠금과 **계정 실패 카운터**를 지운다. 계정 잠금이 걸린 동안에는 비밀번호 대조까지 가지 않으므로 성공이 생길 수 없다(잠금은 시간이 지나야 풀린다).
3. **계정 잠금 남용(남의 아이디로 잠그기)**
   - 생기는 일: 아이디를 아는 외부인이 15분에 20번씩 틀리면 그 계정은 계속 잠긴다. 진짜 사용자는 맞는 비밀번호로도 15분 동안 429 를 본다.
   - 받아들이는 이유: 지금은 IP 만 바꾸면 무제한 추측이 된다(비밀번호 탈취 위험). 잠김은 15분 뒤 저절로 풀리고 데이터는 안전하다. 사내 ERP 라 아이디를 아는 외부인이 일부러 잠그는 일보다 무차별 추측이 더 흔한 위험이다.
   - 줄이는 장치: 임계를 (아이디, IP) 의 2.5배로 두고, 잠금 시간을 15분으로 짧게 둔다. 잠금이 걸리면 감사 로그 `LOGIN_LOCKED` 에 `scope=account` 로 남아 관리자가 공격을 알아챈다. 현장에서 문제가 되면 env 로 임계를 재배포 없이 올린다.
   - 다음 단계(이번 범위 밖): 한 번 로그인에 성공한 브라우저에 서명한 "아는 기기" 쿠키를 주고, 계정 잠금 중에도 그 기기는 통과시키는 방식(OWASP device cookie). 로그인 응답의 쿠키 순서를 기대하는 기존 테스트(`tests/domains/test_post_auth_navigation.py:96`)와 서명 키 운용을 함께 정해야 해서 따로 다룬다.
4. **응답** (`routes.py`)
   - 잠금 429 에 `Retry-After: <잠금 초>` 를 붙인다. 화면 문구는 그대로이고 두 잠금(자리·계정)이 같은 응답이라 어느 쪽이 걸렸는지, 계정이 있는지 드러나지 않는다.
   - 감사 `LOGIN_LOCKED` detail 에 `scope`(`ip`/`account`)를 더하고, `threshold` 는 그 범위의 임계를 쓴다.
5. **저장소 관측** (`rate_limit.py`)
   - 기동 때 저장소 종류를 로그로 남긴다. 배포 환경(`RAILWAY_ENVIRONMENT` 있음 또는 `FLASK_ENV=production`)에서 `memory` 이면 **경고**: 워커마다 카운터가 따로라 잠금과 한도가 사실상 꺼진다.
   - 실행 중 저장소 실패는 지금처럼 경고 후 통과(로그인을 막지 않는다). 다만 한 요청에서 첫 호출이 실패하면 나머지 호출은 건너뛰어 같은 장애로 경고가 여러 줄 쌓이지 않게 한다.

## 테스트
`tests/domains/test_login_rate_limit_lockout.py` 에 추가:
- 프록시 헤더(`X-Forwarded-For`)가 요청마다 바뀌어도 같은 아이디면 계정 임계에서 429, 이후 맞는 비밀번호도 429. 대조군: 다른 아이디는 같은 조건에서 그대로 로그인된다.
- 대소문자·앞뒤 공백만 다른 아이디가 같은 계정 카운터를 쓴다.
- 워커 2개: 같은 저장소 주소를 쓰는 앱 2개(시험용 공유 저장소 scheme)에 번갈아 보내도 임계에서 잠긴다. 음성 대조군: `memory://` 앱 2개는 카운터를 나눠 갖는다.
- 저장소 실패: 카운터 호출이 저장소 예외를 내면 로그인은 200(500 아님) + 경고 로그 1건.
- 기동 로그: 배포 환경 + `memory` 이면 경고, Redis 주소면 경고 없음.
- 성공 로그인 뒤 계정 실패 카운터 초기화.
- 잠금 429 에 `Retry-After`, 감사 `scope`.
- 기존 8건 회귀 + `tests/domains/test_rate_limit.py`·`tests/domains/test_proxy_xff_trust.py` 회귀.
- 기존 테스트 손질 2곳: 감사 테스트에 `scope == "ip"` 단언 추가, 폴백 경고 1건 테스트는 새 기동 INFO 를 세지 않도록 경고 수준만 센다(뜻은 그대로).

## 영향
- 저장소 호출이 실패한 로그인 1건당 2회(조회 1·증가 1) → 4회(조회 2·증가 2), 성공 로그인 1건당 조회 1·삭제 2 → 조회 2·삭제 3으로 는다(로그인 요청에만, 수 ms).
- 기존 (아이디, IP) 키 모양은 그대로라 배포 순간 진행 중인 카운터·flask-limiter 버킷이 무효화되지 않는다.
- 계정 잠금 남용 위험이 새로 생긴다(위 3).
- 범위 밖: 비활성 계정 분기(`routes.py:425-432`)가 비밀번호 대조 전에 다른 문구를 내 계정 존재가 드러나는 점, 없는 아이디는 비밀번호 해시를 계산하지 않아 응답 시간으로 존재가 드러날 수 있는 점, `FOMS_TRUSTED_PROXY_HOPS` 실측.

## 배포 뒤 스테이징 확인
- `POST /login`(form `username=<없는 무작위 아이디>&password=x`) 20회 → 늦어도 20번째에 429 + `Retry-After: 900`. 앱이 보는 IP 가 고정이면 8번째부터 429.
- 20회 모두 200 이면 원인 3(Redis 호출 실패) → web 로그에서 "로그인 잠금 카운터 증가 실패" 확인.
- 이어서 다른 없는 아이디 1회 → 200(다른 계정에 번지지 않음).
