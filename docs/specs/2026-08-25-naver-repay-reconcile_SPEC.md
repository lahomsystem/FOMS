## 0. 한 문단

재결제로 판명되면 담당자는 세 가지를 해야 한다: 새 집 **붙이기** · **ERP 기존 주문 처리** ·
**네이버 옛 결제 취소**. 지금은 세 화면에 흩어져 있고, 실데이터에 **하나만 하고 멈춘 흔적이 4건**
남아 있다. 셋을 한 화면의 **정리 계획**으로 묶되, 두 시스템에 걸친 트랜잭션은 불가능하므로
**되돌릴 수 있는 것을 먼저 / 불가역을 마지막에** 두고 **부분 완료를 화면이 추적**한다.

---

## 1. 문제 — 실데이터가 증거다

스테이징 `external_order_links` 281건 · `orders` 전수 조회(2026-08-25, 읽기전용).

| 주문 | ERP 상태 | 붙은 네이버 집 | 재결제 짝 | 무엇이 잘못됐나 |
|---|---|---|---|---|
| **#4467** 원주현 | RECEIVED | 4건 **전부 취소** (2,451,500원) | 없음 | **유령 주문** — 결제는 취소됐는데 주문이 살아 있다 |
| **#4462** 박선미 | **MEASURE** | 4건 **전부 취소** (579,200원) | 집 `2026082483898301`(8/24) **큐에 대기** | 재결제가 연결 안 됨. 실측까지 진행돼 폐기 불가 |
| **#4466** 강재상 | RECEIVED | 3건 **반품 완료** (497,490원) | 집 `2026081821290541`(8/18) **큐에 대기** | 반품 후 재결제 미연결 |
| **#4485** 신중섭 | RECEIVED | 집 A 취소(1,191,900) + 집 B `REPAY`(1,610,780) | 붙음 | 붙였으나 **금액 미정정**. 같은 고객 8/14 집 하나(`…21411031`)가 **살아 있는 채 미연결** |

읽어야 할 사실 셋:

1. **취소는 대개 고객이 한다.** 4건 중 우리가 취소해야 했던 건은 0건이다(전부 `CANCEL_DONE`/`RETURN_DONE`).
   우리가 취소를 걸어야 하는 경우는 **고객이 새로 결제만 하고 옛 주문을 안 지운 때**다(#4485 의 `…21411031`).
2. **금액이 같지 않다.** #4485 는 재결제인데 +418,880원이다. "재결제 = 같은 값 재결제"라는 전제는 거짓이다.
3. **진행 단계가 갈래를 정한다.** #4462 는 실측까지 갔다 — 지우면 방문 기록·치수가 사라진다.

## 2. 판정 근거 (사용자 지목 ①② + 실데이터가 요구한 ③④⑤)

| # | 근거 | 데이터 출처 | 판정 규칙 |
|---|---|---|---|
| ① | **ERP 기존 주문이 있는가** | `order_candidates.find_order_candidates` (수취인 전화 100 / 주문자 전화 80 / 이름+주소 60, 180일·5건) | 없음 → **신규**. 있음 → ②로 |
| ② | **네이버 옛 집이 취소됐는가** | 후보 주문에 붙은 `ExternalOrderLink.raw_snapshot.productOrder.claimStatus` | 전부 취소 → **재결제**. 살아 있음 → **추가결제** |
| ③ | **금액 관계** | 새 집 합계 vs 후보 주문에 붙은 옛 집 합계 | 비슷·큼 → 재결제(증액 포함). 훨씬 작음(예: 5% 미만) → 차액 결제 |
| ④ | **기존 주문 진행 단계** | `Order.status` + 실측·도면·첨부 유무 | RECEIVED·이력 0 → **폐기 갈래 열림**. MEASURE 이상 → **승계만** |
| ⑤ | 시간 간격 | 결제일 차이 | 참고값(180일 창) |

**②가 지금 화면에 없다.** 후보 표는 `naver_link_count`(붙은 링크 수)만 낸다 —
그 링크가 취소됐는지·금액이 얼마인지는 안 보여 준다. **이 스펙의 첫 번째 구현 항목이 ②다.**

원칙 유지: **자동으로 붙이지 않는다.** 시스템은 근거를 모으고 확정은 사람이 한다.
다만 **불가능한 갈래는 잠근다**(④가 MEASURE 이상이면 폐기 버튼을 비활성).

## 3. 정리 계획 — 3동작 1결정

```
1. 붙이기          새 집 B -> 주문 #N (relation=REPAY)        되돌릴 수 있음 (detach)
2. ERP 기존 주문   (a) 승계: 유지 + 금액 정정                 되돌릴 수 있음 (편집)
                   (b) 폐기: soft delete + 새 주문 생성        되돌릴 수 있음 (휴지통)
3. 네이버 옛 결제  이미 취소 -> 건너뜀 / 살아 있음 -> 판매자 직접취소   되돌릴 수 없음
```

**순서가 설계의 핵심이다.** 불가역(3)을 마지막에 둔다 — 1·2 에서 멈추면 잃는 것이 없고,
3 만 남으면 그것만 다시 보내면 된다. 반대 순서는 "네이버는 취소됐는데 ERP 는 안 고쳐진"
상태를 만들고, 그게 지금 실데이터에 4건 남아 있는 바로 그 모양이다.

### 3.1 원자성 — 없다. 대신 상태를 남긴다

ERP 는 우리 DB(즉시 커밋), 네이버 취소는 **WORKER 비동기**다(web 은 enqueue 만 —
IP 3슬롯 계약, `naver_ingest.py` 취소 라우트 참조). 두 시스템에 걸친 트랜잭션은 불가능하다.

그래서 정리 1건을 **작업 레코드**로 남긴다(제안 이름 `repay_reconcile`):

| 필드 | 뜻 |
|---|---|
| `order_id` · `link_id`(새 집 기준) | 대상 |
| `fork` | `SUCCEED`(승계) / `DISCARD`(폐기) |
| `step_attach` · `step_erp` · `step_cancel` | `PENDING` / `DONE` / `SKIPPED` / `FAILED` |
| `cancel_job_id` · `cancel_failures[]` | 비동기 결과 추적 |

화면은 이 레코드를 폴링해 "붙이기 완료 · 금액 정정 완료 · 네이버 취소 4건 중 2건" 을 말한다.
**부분 완료가 정상 상태다 — 숨기지 않는다.**

### 3.2 각 단계의 기존 자산

| 단계 | 재사용할 것 | 새로 만들 것 |
|---|---|---|
| 1 붙이기 | `promotion.attach_link_to_order` (집 단위·멱등·이력 1건) | 없음 |
| 2(a) 승계 | 주문 편집 mutation 경로(REV-00 `execute_order_mutation`) | 금액 정정 전용 커맨드 |
| 2(b) 폐기 | `foms/services/orders/soft_delete.py` (deleted_at + OrderEvent + 휴지통) | 폐기 사유에 "재결제 정리" 표기 |
| 3 취소 | `fulfillment.cancel_order` + `enqueue_naver_cancel` | 옛 집을 **대상으로 지정**하는 진입점(지금은 그 집을 손으로 찾아야 한다) |

## 4. 화면

### 4.1 판정 근거 패널 (상세 pane `관계` 섹션 확장)

후보 표에 **열 두 개**를 더한다:

- **네이버 옛 집 상태** — `취소 완료` / `반품 완료` / `살아 있음` / `네이버 아님`
- **금액 관계** — `새 1,610,780 vs 옛 1,191,900 (+418,880)`

이 두 열이 ②③를 화면에서 끝낸다. 지금은 담당자가 네이버에서 확인한다.

### 4.2 정리 계획 카드

목업 §2·§3. 갈래 선택은 라디오 2개(승계/폐기), **폐기는 ④가 허용할 때만** 활성.
불가역이 실제로 나갈 때만 4종 세트 모달(건수·금액 재진술 + 되돌릴 수 없음 + 사후 경로).

### 4.3 진행/실패 카드

목업 §4. 실패한 상품주문만 다시 보내는 버튼. 발송 뒤라 취소가 불가능하면
**반품 흐름으로 가라고 문장으로 말한다**(막다른 길 금지).

### 4.4 유령 주문 띠

목업 §5. 처리 탭 위에 `네이버 결제가 전부 취소된 주문 N건` 띠. 지금 이 사실을 말하는 화면이
하나도 없다 — 실데이터 3건이 아무에게도 안 보인 채 남아 있었다.

## 6. 구현 순서 제안 (승인 시)

1. **R-1 판정 근거 2열** — 후보 표에 네이버 옛 집 상태·금액 관계. 네이버 호출 0, 되돌릴 것 없음.
2. **R-2 유령 주문 띠** — 읽기 전용 집계. 실데이터 3건이 즉시 보인다.
3. **R-3 정리 계획(1·2단계만)** — 붙이기 + 승계/폐기. **네이버 호출 없음** — 여기까지가 안전 구간.
4. **R-4 3단계(네이버 취소) 편입** — 불가역. 모달·부분 실패 UI·재시도까지 한 묶음으로.

R-1~R-3 은 되돌릴 수 있는 작업만 다룬다. R-4 만 승인 게이트를 따로 둔다.
