# 도면·계약서 알림톡 "상담 먼저" — 설계·구현 기록

> 상태: **구현됨(env 꺼짐)** — 카카오 심사 승인 + 아래 §5 켜는 순서 전에는 지금 동작 그대로다.
> 근거: 2026-10-20 세션 조사(카카오·솔라피·채널톡 공식 문서, 채널톡 app-sdk `native.ts`), 목업 https://claude.ai/artifact/8ATRggRMw5M1TPMtVcQFbN

## 0. 왜 바꾸나

- 이전: 도면·계약서 알림톡에 링크가 들어 있다. 고객은 링크만 열고 대화방에 글을 안 쓴다. 카카오 규칙상 고객이 먼저 말을 걸기 전에는 우리가 먼저 상담을 열 수 없어서(카카오 공식 문서: "상담 세션이 열리기 전까지는 상담원이 카카오톡 이용자에게 먼저 말을 걸 수는 없습니다"), 영업이 전화로 "채팅을 쳐 달라"고 일일이 안내했다.
- 이후: 알림톡에서 링크를 뺀다. 버튼은 **[문서 받기]**(MD, 메시지 전달) 하나다. 고객이 누르면 알림톡 본문이 같은 카톡 대화방에 고객 메시지로 올라가 채널톡에 카카오 상담이 열린다. ERP 가 그 메시지의 주문번호·확인코드를 맞춰 보고 **같은 상담**에 링크를 써 준다. 링크와 상담이 카톡 한 대화방에 모인다.
- 8월에 쓴 상담톡 전환 버튼(BC)은 누르면 새 창이 떠서 뺐다(사용자 확인 2026-10-20). 그래서 이번에는 MD 를 쓴다.

## 1. 사용자 결정 (2026-10-20)

- 고객이 상담창을 먼저 열어야 도면·계약서가 간다(관건).
- 버튼을 누르면 목업 순서대로 자동 발송한다.
- 영업이 고른다: 도면만 · 계약서만 · 도면+계약서, 그리고 도면+계약서면 한 번에 · 따로따로.
- 서식은 하우드·라홈·하우드·라홈 공용(하우드 채널) 3벌을 심사에 넣는다.

## 2. 알림톡 서식 (솔라피, 심사 중)

| 이름 | id | 채널 |
|---|---|---|
| 하우드 | `KA01TP261020024519280XniXkJcLYr4` | 하우드 |
| 라홈 | `KA01TP261020024519365QEkjnUiYRRT` | 라홈시스템 |
| 하우드·라홈 공용 | `KA01TP261020024519461bWqdjUHSkFA` | 하우드 |

- 분류 005003(계약/견적) · 기본형 · 버튼 MD「문서 받기」1개.
- 변수: `#{문서종류}` `#{고객명}` `#{주문번호}` `#{확인코드}` `#{담당자}` `#{담당자연락처}`.
- 본문(첫 줄 브랜드만 다름):

```
[하우드] #{문서종류} 준비 완료

#{고객명} 고객님, 안녕하세요.
요청하신 #{문서종류} 준비가 끝났습니다.

■ 주문번호: #{주문번호}
■ 확인코드: #{확인코드}
■ 담당: #{담당자} #{담당자연락처}

아래 [문서 받기]를 누르시면 이 대화방으로 바로 보내드립니다.

받으신 뒤 궁금한 점이나 고칠 부분도 이 대화방에서 담당자와 바로 이야기하실 수 있습니다.
```

- 처음 제출본(주문번호만, 버튼「도면·계약서 받기」)은 같은 날 심사를 취소하고 위 본문으로 고쳐 다시 냈다.
  - 고친 이유 1: 주문번호는 짐작할 수 있는 숫자라서, 주문번호만으로 자동 발송하면 남이 남의 문서를 받아 갈 수 있다.
  - 고친 이유 2: 도면만·계약서만 보낼 때도 본문이 맞아야 한다.
- 공용본은 아직 어느 주문에 쓸지 기준이 없다. env 에 넣지 않으면 쓰이지 않는다.

2026-10-21 바꿈: 링크는 **버튼**([도면 보기]·[계약서 보기])으로 보낸다. 앱 함수 `writeUserChatMessage` 는 버튼을 422 로 거절했지만, Open API `POST /open/user-chats/{id}/messages` 에 공식 형식(`action={type: web, attributes: {url}}`, 한 글에 2개까지)으로 보내면 카카오 상담톡에도 버튼으로 간다(하우드 실폰 확인). `channel_client.send_user_chat_buttons` 가 쓰고, Open API 키(§5-1)가 없거나 쓰기가 실패하면 예전처럼 글 속 링크로 보낸다(`share_consult._send_link_message`). 따로따로면 글마다 버튼 하나, 한 번에면 버튼 둘.

## 5. 켜는 순서 (사람 손이 필요한 것 포함)

1. **카카오 승인 확인.** 솔라피 `GET /kakao/v2/templates/{id}` 가 APPROVED 인지 본다.
2. **채널톡 웹훅 — 하우드·라홈 채널마다 하나씩.** 라홈·하우드는 채널톡 채널이 따로다(사용자 확인 2026-10-20).
   - 각 채널의 채널 설정 > 보안 및 개발 > 웹훅 > [Webhook 만들기]에서 만든다.
   - 주소는 `https://<환경 주소>/api/channel/webhooks` 이고, 이벤트는 **고객 상담 메시지만** 고른다. 팀챗 메시지는 고르지 않는다(주문 자동 접수 경로라 켜면 안 된다).
   - 만들면 나오는 토큰을 하우드 것은 `CHANNEL_SIGNING_KEY_HAUD`, 라홈 것은 `CHANNEL_SIGNING_KEY_LAHOM` 에 넣는다. 기존 `CHANNEL_SIGNING_KEY` 와 셋 중 하나만 맞으면 통과한다(`verify_channel_signature`).
   - 하우드 채널에 이미 웹훅이 있으면 그것을 고치지 말고 새로 하나 더 만든다(기존 키를 건드리지 않게).
   - 채널톡이 이 토큰으로 `x-signature` 헤더에 서명하는지는 문서에 확답이 없다 → 스테이징에서 1회 받아 본다(401 이면 서명 방식부터 본다).
   - 링크는 메시지가 온 채널(`entity.channelId`)로 쓴다. 토큰은 채널마다 따로 받는다.
3. **웹훅 암호화 키.** 운영 `web` 에 `CHANNEL_WEBHOOK_ENVELOPE_KEY`(hex, 32바이트 이상)가 **없다**(2026-10-20 확인). 없으면 웹훅이 모두 503 이다. 스테이징·운영에 넣는다.
4. **워커.** `channeltalk_inbound` 작업은 RQ 워커(WORKER)가 처리한다. WORKER 의 `FOMS_BASE_URL` 이 그 환경 주소인지 확인한다(링크 주소가 이것으로 만들어진다. 비어 있으면 운영 주소).
5. **채널톡 앱 설치·권한.** FOMS 앱이 **라홈 채널에도 설치**돼 있어야 그 채널 토큰을 받을 수 있다. 앱 설정에서 `writeUserChatMessage` 함수 권한도 켠다. 지금 앱은 하우드 채널에서 `writeGroupMessage` 만 써 왔다.
5-1. **(선택) 받은편지함 이름표.** 채널마다 채널 설정 › 보안 및 개발 › API 에서 인증 키를 만들어 `CHANNEL_OPENAPI_KEY_{HAUD,LAHOM}`·`CHANNEL_OPENAPI_SECRET_{HAUD,LAHOM}` 에 넣으면, 링크를 보낸 뒤 고객 프로필 이름 = 주문 고객 이름, 상담 설명 = "주문 · 고객 · 담당" 을 적는다(`channel_client.label_user_chat`). 앱 함수에는 이름을 바꾸는 기능이 없어 Open API 를 쓴다. 키가 없으면 건너뛴다.
6. **스테이징 시험.**
   - env `SOLAPI_TEMPLATE_SHARE_CONSULT_ID_{HAUD,LAHOM}` 를 넣는다.
   - CLAUDE-TEST 주문으로 사장님 폰에 1통 보낸다.
   - 버튼을 눌러 다음을 본다: 같은 방에 남는지(새 창 안 뜸), 채널톡 상담이 생기는지, 링크가 자동으로 오는지, 내부 메모가 남는지, 상담원 답장이 같은 방으로 가는지.
7. 다 맞으면 운영 env 를 넣는다(웹 재배포 없이 `skipDeploys` 로 넣어 두고 다음 배포에 켜도 된다).

## 6. 남은 것 / 하지 않은 것

- **카톡을 못 받는 고객:** 상담 먼저는 문자 대체발송을 끈다. 그래서 카카오를 안 쓰는 고객에게는 아무것도 안 간다. 발송 1분 뒤 실패를 알아채 "문자로 링크 보내기" 칩을 띄우는 일(실측 안내의 `confirm_channel` 을 공유 이력에도 쓰게 넓히기)은 다음 묶음이다. 그 전에는 영업이 상태 줄을 보고 [내 폰 문자]로 보낸다.
- **고객이 안 누르는 경우:** 담당자에게 알려 주는 기능은 다음 묶음이다.
- ERP 공유 창(`erp-share.js`)은 상담 먼저를 쓰지 않는다(`consult:false`). 거기도 바꾸려면 화면 문구부터 바꿔야 한다.
- 확인코드 해시는 서버 비밀값 없이 sha256(주문 id 묶음)이다. DB 를 읽을 수 있으면 살아 있는 코드를 되찾을 수 있지만, 그 정도 권한이면 문서 자체를 이미 읽을 수 있다. 서비스마다 env 가 달라 비밀값을 섞으면 web·WORKER 가 어긋날 위험이 더 크다고 보았다.
- 내부 메모 옵션 `MESSAGE_OPTION_PRIVATE` 는 SDK 형식(`native.ts`)에서 가져왔다. 실제로 고객에게 안 보이는지는 §5-6 스테이징 시험에서 꼭 본다.
- 상담으로 간 링크는 도면 탭의 '링크 n번 열림' 수에 아직 안 잡힌다(짝 링크 연결은 다음 묶음).
- 고객이 버튼을 누르지 않아도 상담을 여는 것은 카카오 규칙상 불가능하다.
