## 0. 한 줄

**틀은 이미 Palantir · W3C 표준 꼴로 서 있다. 비어 있는 것은 (1) 그 틀 안의 물건(제품 · 옵션)과 물건끼리의 연결, (2) 상담 AI 가
그 연결을 따라가 판단하는 길이다.** 단계 1 은 계산기 정본에서 제품 · 옵션을 만들고 지식 글을 물건에 잇는 **제안**을 올린다(반영은
승인한 것만). 단계 2 는 초안 차례가 손님 말에서 물건을 찾고(SKOS 이름표) 연결을 1~2 걸음 따라가(Search Around) 그 상담에 걸린
'물건 · 속성 · 단위 · 출처' 묶음을 두뇌에 주고, 보내기 전 검사도 속성 값 · 단위로 맞춘다. 단계 3 은 회사 지식을 JSON-LD 로
내보내고 SHACL 로 검사한다.

판단 기준: 틀린 답 · 지키지 못할 약속이 0 인 채로, 같은 뜻을 다른 말로 물은 상담에서 '모름' 넘김과 숫자 막힘이 얼마나 줄었나 —
그 판단이 숫자로 남는가(8절).

## 2. 무엇을 따르나 — Palantir 꼴 · 국제 표준

**Palantir 온톨로지에서 가져오는 것**: Object Type(물건 유형) · Property(속성 틀) · Link Type(링크) · Action Type(사람 승인 동작) ·
Function(온톨로지를 읽어 판단하는 함수 — 단계 2 의 '찾기 · 따라가기 · 맞추기') · AIP 원칙 **'LLM 은 글 더미가 아니라 온톨로지
물건을 근거로 판단하고, 쓰기는 Action 으로만'**. 다른 점: 화면 유형 편집기는 두지 않는다(유형은 설계서 + 코드로만 — master brain
7.7).

**W3C · ISO 표준에서 따르는 것**(저장은 PostgreSQL 그대로, 꼴과 내보내기가 표준을 따른다):

| 표준 | 쓰는 자리 | 상태 |
|---|---|---|
| W3C SKOS(+ ISO 25964 시소러스와 같은 꼴) | 이름표 · 위 낱말 · 관련어 — 손님 말에서 물건 찾기 | 꼴 있음 → 단계 1 에서 채움 |
| W3C SHACL | 유형별 속성 틀 → shape 로 내보내 검사 | 틀 있음 → 단계 3 내보내기 |
| W3C PROV-O | 판 = entity · 제안 = activity · 제안자 · 승인자 = agent | 있음 → 단계 3 내보내기 |
| W3C RDFS · OWL 2(어휘만) | 유형 위계(`rdfs:subClassOf`) · 링크 정의역 · 치역 | 단계 3 내보내기만 — **추론기는 들이지 않는다** |
| schema.org `Product` · `PropertyValue` | 제품 라인 · 옵션 · 규격 내보내기 | 단계 3 |
| QUDT 단위 | mm · cm · m · 일 · 주 · 개월 · 자 · 통 단위 코드 | 단계 2 단위 맞춤 · 단계 3 내보내기 |
| JSON-LD 1.1 | 내보내기 꼴 | 단계 3 |

**들이지 않는 것(까닭)**: RDF 저장소 · 그래프 DB · OWL 추론기(지식 수천 개 크기에서 얻는 것이 없고 운영할 것이 늘어남 — master brain
7.7 판정 그대로) · ISO/IEC 21838(BFO) 같은 최상위 온톨로지(회사 지식에 넘치는 추상 — 대신 유형 위계를 schema.org 에 맞춘다).

## 3. 목표 꼴 — AI 가 온톨로지로 판단하는 길

```
손님 글(가린 글)
  → ① 찾기: 이름표(대표 · 다른 · 숨은 이름, 띄어쓰기 · 대소문자 무시) → 물건 후보(제품 · 옵션 · 용어 · 규격 · 공정 단계)
             [뜻 가까움 찾기는 켜져 있을 때만 '후보 힌트' — 이름표가 못 찾은 것만, 확신 낮음 표시]
  → ② 따라가기: 후보에서 applies_to · requires · excludes · value_from · at_step · broader · uses 를 1~2 걸음
             + 어느 물건에도 걸리지 않은 '두루 정책'(배송 · 설치 · 일정 일반)은 늘 함께
  → ③ 묶음: 물건마다 [키] 유형 · 대표 이름 · 속성(값 · 단위 · 기준) · 걸린 규칙(키 · 글) · 정본 자리(계산기 값은 견적 길 그대로)
  → ④ 두뇌: 지시문(그대로) + '이 상담에 걸린 물건' 묶음 + (처음엔) 지금의 지식 글 전부 — 근거 id 는 항목 키
  → ⑤ 맞추기(보내기 전 검사): 초안 숫자 = 묶음 속 속성 값(단위 바꿔도 같은 값) · requires / excludes 어김 · 최소 · 최대 가로 밖이면 막음 또는 넘김 까닭
  → ⑥ 넘김: 넘김 까닭을 물건 · 규칙에서(예: 정책 갈래 '할인' 이면 사람) — 두뇌 까닭과 다르면 둘 다 기록
```

## 4. 단계 1 — 뼈대 채우기 (자료 · 제안만, 상담 길 바뀜 0)

1. **제품 라인 · 옵션을 계산기 정본에서**: `foms/services/wdcalculator/catalog.py:66` `read_catalog` 의 제품마다 `product_line`
   항목(브랜드는 `pricing.py:144` `product_brand`), 옵션마다 `option` 항목을 **만들기 제안**으로. 속성은 `schemas.py` 틀
   (`quote_kind` · `price_unit` · `door_kinds` · `min_width_mm` · `max_width_mm` · 옵션 `category` · `unit`)을 계산기 값에서 채운다.
   **값(금액)은 복사하지 않는다** — `value_from` 링크로 `calc:product/<id>` · `calc:option/<묶음>:<옵션>`(`external.py:95`)을
   가리켜 정본은 계산기 하나. 이름표는 계산기 이름 = 대표 이름, 다른 이름은 비워 두고 2 에서 채운다.
2. **다른 이름 모으기**: 지난 상담 사례(`cs_case` · 직원 답 · [배우기] 답 · 고친 까닭)에서 손님이 그 제품 · 옵션을 부른 말을 AI 가
   뽑아 `aliases` 고침 제안으로(가린 글만 읽고, 손님 글은 제안에 싣지 않는다 — 낱말만). 밤 넘김 학습(`handoff_learning.py`)에
   '이름표 제안' 갈래를 더하는 꼴.
3. **글 항목을 물건에 잇기**: 정책 · 가격 규칙 · 사실 · 기준 답마다 AI(Opus)가 걸리는 물건을 골라 `applies_to` · `at_step` ·
   `uses` · `broader` **링크 제안**을, 사실은 규격 · 용어로 나누는 제안(master brain D103)을 올린다. 기존 도구 길(
   `scripts/maintenance/brain_plan_proposals.py` · `plan_links.py` — 모의 실행 기본 · 승인 표시 있어야 넣음 · 같은 제안 두 번 없음)을
   쓴다. 어느 물건에도 안 걸리는 글은 '두루 정책' 표시(`policy_kind` · 새 값 없이 링크 0 으로 판정).
4. **승인**: 받은 함에서 **제품 묶음별**(제품 하나 + 그 옵션 · 걸린 규칙 링크)로 본다 — 한꺼번에 반영(`bulk_apply`)은 묶음 단위만.
   반영은 지금처럼 표 → 지식 문서 다시 쓰기(`doc_sync.py`)를 지난다.

**완료 기준**: 라홈 계산기 제품 · 옵션이 모두 항목으로 있고(값은 `value_from` 으로만), 라홈 가격 규칙마다 걸린 제품 · 옵션 링크가
있거나 '두루' 판정이 있고, 제품마다 대표 이름 + 승인된 다른 이름이 있다. 품질 점검(`quality.py`)에 '물건에 안 걸린 가격 규칙' 수를
더한다.

## 5. 단계 2 — AI 가 온톨로지로 판단 (관리 칸, 처음 끔)

관리 화면 '바꿔 묻기 대응(온톨로지)' 묶음에 칸 하나 **'물건 찾아 따라가기'**(`onto_graph_enabled`, 처음 끔)를 더한다. 끄면 지시문 ·
요청이 글자까지 지금 그대로(11-11 칸들과 같은 원칙 — 시험이 강제).

1. **찾기**(`foms/services/cs_agent/onto_find.py` 새 모듈): 가린 손님 글 묶음 → `labels.py` 정규화로 이름표 맞춤(긴 이름 먼저, 겹치면
   긴 쪽) → 후보 키 목록(상한 8). 뜻 가까움(`embeddings.nearest`)은 관리 칸 `brain_embeddings_enabled` 가 켜져 있고 이름표가 0 개일
   때만 '확신 낮음' 후보 하나.
2. **따라가기**(`onto_walk.py`): `read.neighbours`(보기 범위 = 상담 에이전트 범위, 유효 기간 안 · 은퇴 뺌)로 1~2 걸음, 물건당
   링크 상한 · 전체 상한(글자 수 예산). '두루 정책'은 늘.
3. **묶음 글**(`onto_block.py`): 물건마다 머리표 줄 + 속성 줄 + 걸린 규칙 줄 — 손님 글 칸과 같은 가림 · 머리표 흉내 막기
   (`brain_photos.py` 의 사진 칸과 같은 꼴). 캐시: 지시문 앞부분(지식 글 전부)은 그대로 두고 묶음은 **차례 칸**(사진 칸 자리 옆)에
   싣는다 — 1시간 캐시가 갈리지 않게.
4. **맞추기**(`checks.py` 넓힘): 숫자 허용을 '글에 그 글자가 있나'에서 **'묶음 속 속성 값과 같은 값인가(단위 바꿈 포함 —
   `checks_same.py` 재사용)'**로 넓힌다. `requires` · `excludes` 어김(손님이 고른 조합이 묶음 안 제약과 맞지 않음)과
   `min_width_mm` · `max_width_mm` 밖은 **막지 않고 넘김 까닭**(새 코드 `constraint`, 메모 말 '제작 조건을 확인해야 해요')으로 —
   자동 거절 없음(master brain 7.8 다음 9 와 같은 원칙).
5. **근거**: 두뇌 출력 `evidence_ids` 에 물건 키를 받는다(지금 글 id 와 같이). 직원 메모 '근거' 줄에 물건 대표 이름.
6. **단계 끝(뒤 판)**: 묶음이 안정되면 지식 글 전부를 빼고 묶음만 주는 칸(토큰 · 돈 줄임)을 따로 묻는다 — 이 판에서는 하지 않는다.

**하지 않는 것**: 두뇌가 도구로 온톨로지를 직접 부르는 꼴(AIP 도구 호출) — 초안 한 번에 왕복이 늘어 늦고 비싸다. 찾기 · 따라가기는
코드가 먼저 하고(결정적 · 빠름), 두뇌는 묶음을 읽는다. 직원 챗봇은 지금처럼 도구 꼴.

## 6. 단계 3 — 표준 내보내기 · 검사

1. **JSON-LD 내보내기**(관리자만, `foms/api/brain` 읽기 API 하나 + 도구 `scripts/maintenance/brain_export_jsonld.py`):
   `@context` 에 `skos` · `sh` · `prov` · `schema` · `qudt` · `rdfs`. 유형 → `rdfs:Class`(위계는 schema.org 에 맞춤 — 제품 라인
   `schema:ProductGroup` · 옵션 · 규격 `schema:PropertyValue` · 용어 `skos:Concept`), 링크 → 속성, 판 · 제안 → PROV-O. **금액 ·
   정본 값은 내보내지 않는다**(가리킴 키만) · 보기 범위 '모두'만.
2. **SHACL shape 를 틀에서 만든다**: `TYPE_SCHEMAS` 하나가 정본 — 거기서 shape 를 만들어 내보낸 그래프를 검사. 시험에서만
   합성 자료로 돈다(운영 경로에 새 짐 없음). 새 꾸러미(rdflib · pyshacl — 시험용)는 넣기 전 사장님께 이름 · 까닭을 먼저 알린다.
3. **품질 점검 칸**: SHACL 위반 수 · 물건에 안 걸린 규칙 수 · 다른 이름 없는 제품 수를 회사 지식 화면 품질 칸에.

## 7. 저장 · 마이그레이션

마이그레이션 0 — 항목 · 링크 · 실음 칸(`payload`)과 관리 칸(SystemSetting)으로 충분하다. 새 넘김 까닭 코드 `constraint` 는
`brain_prompt.HANDOFF_REASONS` · `handoff_memo.HANDOFF_TEXTS` · 학습 까닭 말에 같이 더한다(시험이 짝을 강제).
