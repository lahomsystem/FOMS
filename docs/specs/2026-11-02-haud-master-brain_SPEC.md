## 0. 한 줄

**회사 지식의 정본을 한 곳(master brain)에 모으고 — 공통 바탕(회사 · 브랜드 · 제품 · 옵션 · 규격 · 제작 조건 · 정책 · 가격 규칙) 위에 팀별 층(상담 · 도면 · 생산)을 얹는다. 에이전트(상담 · 도면 · 생산)와 직원 챗봇은 모두 이 한 곳을 읽고, 바꾸는 일은 '제안 → 검토 → 반영'으로만 한다. 값이 여러 곳에서 엇갈리던 오늘의 사고를 '정본 하나 + 사본 감시'로 막는다.**

판단 기준(상담 설계서 0절을 회사로 넓힘): 틀린 답 · 지키지 못할 약속 · 볼 권한 없는 사람에게 보인 지식이 0인 채로, 직원이 지식을 찾는 시간과 사람 손이 얼마나 줄었나 — 그리고 그 판단이 숫자로 남는가.

### 3.1 공통 바탕 — 정본 하나

| 유형 | 예(값 없이) | 정본 자리 |
|---|---|---|
| 회사 · 브랜드 | 라홈 · 하우드 · 채널 · 영업 시간 | brain |
| 제품 라인 · 옵션 | 몰딩 · 무몰딩 · 슬라이딩 · 냉장고장 · 화장대 · 손잡이 셋 | 이름 · 설명 · 구성은 brain, **값은 계산기**(brain 은 계산기 id 를 가리킴) |
| 규격 | 깊이(여닫이 · 슬라이딩) · 몸통 높이 단계 · 통 폭 범위 · 무몰딩 천고 상한 | brain |
| 제작 조건(build_rule) | 'ㄱ자는 여닫이만' · 최소 길이 · 슬라이딩 깊이 | brain(코드가 읽는 `검사:` 줄 — `foms/services/cs_agent/quote_calc.py:15` 꼴 그대로) |
| 정책 | 환불 · 보증 · 일정 · 결제 · 매체 규칙 · 금지 약속 | brain — **사장님 승인만** |
| 가격 규칙(계산기 밖) | 운임 · 실측비 · 비규격 기준 | brain — **사장님 승인만** |
| 사장님 결정 | D 번호 결정 | brain(근거 = 원장 D 번호) |
| 용어 | 같은 것의 여러 이름(직원 말 · 손님 말 · 계산기 이름 · 도면 이름표) | brain |

**정본 규칙(오늘의 엇갈림을 막는 법)**:

1. **값마다 정본 자리는 하나.** 가격 값은 계산기, 나머지는 brain 항목 하나. 같은 값을 두 항목에 쓰지 않는다 — 라홈 · 하우드가 같은 사실이면 '공통' 항목 하나에 브랜드 칸을 단다(브랜드마다 문서가 따로인 지금 꼴이 같은 사실을 두 번 쓰게 만든다).
2. **사본 목록**: 정본 항목마다 '이 값을 쓰는 곳'을 적는다 — 채널톡 매크로 이름 · 스토어 상세 쪽 · 기준 답 항목 id · 화면 안내 글 · 도면 양식. 사본은 정본이 아니다.
3. **정본이 바뀌면 사본 할 일**: 승인으로 값이 바뀌면 사본 목록마다 '고칠 곳' 할 일이 생겨 담당자(사장님이 정함)에게 간다. 사본을 brain 이 직접 고치지 않는다.
4. **엇갈림 찾기(주 1회)**: 사본을 읽어(매크로 — 채널톡 Open API 읽기, 스토어 상세 — 사람이 승인한 읽기) 숫자 · 정한 말을 뽑아 정본과 맞춘다. 다르면 '엇갈림' 객체 → 사장님. **엇갈림이 열린 동안 그 항목은 '확인 필요'** — 에이전트 · 챗봇은 그 값을 답에 쓰지 않고 '담당자 확인'으로 넘긴다(틀린 값을 자신 있게 말하는 것보다 낫다).
5. **결정은 바로 항목으로**: 사장님 결정(D 번호)은 원장에 적는 때 같이 brain '사장님 결정' 항목 제안이 된다 — 다음 결정 때 빠뜨리지 않게(D83). 항목에는 그 결정이 바꾼 앞 항목 링크(supersedes)를 단다.

**확신 세 단계**: 확정(사람 승인) · 근거 있음(자동 관문 통과 — 17.6) · 관찰(사례뿐). 에이전트가 손님에게 혼자 보내는 길은 '확정'만(17.5 읽는 함수 둘 그대로). 챗봇 답은 확신을 같이 보인다.

**판**: 하루 한 판(17.6 — 사람 없이 넣는 것도 묶어서). 판마다 차이 · 되돌리기. 층마다 따로 되돌릴 수 있게 판 기록에 층 칸을 둔다.

**보기 범위(권한은 찾는 단계에서 — 17.9-2)**:

| 범위 표시 | 볼 수 있는 사람(처음 안 — 13절 4) |
|---|---|
| 모두(내부) | 로그인한 내부 직원 전부(VIEWER 포함) |
| 팀 | 그 팀(`User.team`) + ADMIN |
| 가격 재량 | 할인 폭 · 흥정 대응 · 내부 단가 판단 — 사장님 · ADMIN 만 |
| 관리 | 에이전트 설정 · 엇갈림 · 물어볼 것 — ADMIN 만 |
| 바깥 역할(PARTNER 등) | **brain 전체를 볼 수 없다**(챗봇 화면 · API 404) |

- brain 에는 **개인정보를 넣지 않는다**(손님 · 직원 이름 · 전화 · 주소 · 주문 번호). 사례 · 관찰은 가린 글 또는 숫자 · 코드만(상담 17.11 · 17.6.1 과 같은 원칙).
- 모아 센 결과에도 보기 범위를 건다(17.9-2 — 가격 재량 항목 수 같은 것도 새지 않게).

## 5. 에이전트 · 사람별 읽기 · 쓰기 · 승인

| 누구 | 읽기 | 쓰기 | 승인 |
|---|---|---|---|
| 상담 에이전트(cs_agent) | 공통 바탕 · 상담 층 · 도면 층의 그림 조각 종류 · 규격(그림 읽기용) | 상담 층 제안 · 관찰(사례 · 그림 읽기 결과) | 17.6 등급 그대로 |
| AI 도면팀원 | 공통 바탕(제품 · 규격 · 제작 조건) · 도면 층 | 도면 층 제안 · 관찰 · '물어볼 것' | 도면 규칙 = 도면팀이 정한 사람(TEAM-RULES 답 꼴) |
| 생산 에이전트(판 3) | 공통 바탕 · 도면 층(최종본 규칙) · 생산 층 · ERP 생산 · AS 보기 | 생산 층 제안 · 관찰 · '물어볼 것' | 생산 규칙 = 생산팀장(사장님이 정함) |
| 직원 챗봇 | **묻는 사람의 보기 범위만** | 없음 — 질문 기록 · '빈 지식' · 고칠 말 제안만 | — |
| 원격 루틴 · 총괄 PC(L2) | 가린 요약(읽기만) | 승인 파일 → 관리자 스크립트 길(D43)로 들어와 같은 제안함 · 같은 관문 | 같은 등급 |
| 사람(웹 승인 동작) | 범위 안 | 직접 고침도 '제안 → 반영' 기록을 남긴다 | 아래 |

- **가격 · 정책 · 사장님 결정 · 공통 바탕을 지우거나 은퇴시키는 일은 사장님만**(웹 승인 동작 · 사람 승인자 id). 다른 층 규칙은 그 층 승인자, 등급 A 는 17.6 열기 기준을 넘은 뒤 자동(D64 꼴).
- **쓰기는 액션(코드 함수)으로만**(F11-2) — 에이전트는 '제안'을 만들 뿐 정본을 직접 덮지 않는다. 에이전트마다 시스템 계정(로그인 못 함 · 지우지 않음 — 지식 이력이 계정 삭제로 함께 지워지는 함정, 17.5)을 둔다.
- **학습 자율 ≤ 발송 자율**(17.6): 손님에게 혼자 가는 길은 사람 승인 항목만 쓴다. 다른 팀 층을 고치는 제안은 그 팀 승인을 늘 거친다(상담 에이전트가 도면 규칙을 바꾸지 못함).

## 6. 변경 = 제안 → 검토 → 반영 · 되돌리기 (상담 17.5 · 17.6 원칙)

- 제안 하나 = 바꿀 항목 · 지금 값 · 새 값 · 까닭 · 근거 id · 등급 · 층. 팔란티어의 proposal(PR 같은 꼴 — F11-7)과 같은 뜻.
- **자동 관문(상담 17.6 다섯 그대로)**: ① 꼴 · 가림(개인정보 0 · 금액 · 날짜는 사람 승인 항목과 계산기 값에서만 · 한자 0) ② 승인 지식과 부딪침(Claude Haiku 판정 — 실패면 미통과) ③ 근거(서로 다른 손님 · 직원 2명 이상 — 층마다 근거 뜻을 정함: 도면은 서로 다른 주문 · 도면팀원 2명 이상) ④ 평가 묶음 재시험(층마다 — 상담 = 17.6 묶음 · 도면 = 그림 기억 맞힘 98% 묶음 · 챗봇 = 10절 질문 묶음) ⑤ 반영 뒤 감시 · 자동 되돌림.
- **사람 검토**: 학습 탭(상담 17.7)을 회사판으로 넓힌다 — 층 거르기 · 승인자별 '내 승인 대기'.
- **되돌리기**: 판 단위 · 층 단위. 되돌린 판도 이력에 남는다.
- **사본 할 일**: 반영이 사본 목록이 있는 항목을 바꾸면 3.1 규칙 3 의 할 일이 함께 생긴다.

## 7. 첫 판 저장 꼴 — 지식 문서를 넓혀 쓸까, 전용 표로 갈까

**상담 17.5 의 옮김 기준(하나라도 넘으면 전용 표)**: ① 한 브랜드 승인 항목 300 초과 ② 지식 블록 2만 5천 토큰 초과 ③ 지식 쓰기 하루 20번 초과 또는 판 충돌 주 3번 이상 ④ 항목별 '쓰인 횟수 · 마지막 확인'을 질의해야 할 때 ⑤ C15 시작.

**판정**: master brain 은 ⑤ 'C15 시작' 그 자체이고, 직원 챗봇은 ④(쓰인 횟수 · 빈 지식 질의)를 바로 부른다. 여기에 회사판 기준 둘을 더한다:

- ⑥ **두 팀 이상의 에이전트가 같은 항목을 읽기 시작할 때** — 브랜드마다 한 줄인 지식 문서는 '공통' 사실을 두 번 쓰게 만든다(3.1 규칙 1 과 부딪침).
- ⑦ **ADMIN 이 아닌 직원이 챗봇을 쓰기 시작할 때** — 지식 문서는 통째로 읽어 프롬프트에 넣는 꼴이라, 보기 범위를 '찾는 단계'가 아니라 '출력 쪽'에서 거르게 된다(F11-4 함정 — 17.9-2 와 어긋남).

**추천(13절 1)** — D95(온톨로지 화면) 뒤 **'판 1 부터 전용 표'로 바꿨다**(까닭 · 꼴은 7.5 끝 '저장 꼴'). 아래는 처음 추천(문서 먼저)으로, 사장님이 그쪽을 고르면 따른다:

- **판 1 은 지식 문서를 넓혀 쓴다** — 마이그레이션 0. 상담 C10-7(종류 넷 · 칸 넷 · 읽는 함수 둘)에 칸 둘(보기 범위 · 사본 목록)을 더하고, 도면 층은 '가리키는 항목'(자재표 규칙 키 · 그림 조각 종류 목록 · TEAM-RULES 줄)으로만 넣는다. 챗봇은 **ADMIN 만** 시범(⑦ 을 아직 안 넘음).
- **판 2 에서 전용 표로 옮긴다** — ⑥ 또는 ⑦ 을 넘기 전에. 표 꼴은 17.5 의 `cs_onto_*` 를 회사 이름으로: `brain_objects` · `brain_links` · `brain_changes`(제안) · `brain_releases`(판) · `brain_questions`(챗봇 기록). 옮긴 뒤 같은 평가 묶음이 같거나 나아야 켠다(플랜 C11 기준 그대로). 상담 두뇌의 읽는 함수 둘은 이름 · 뜻을 그대로 두고 안만 바꾼다(호출부 무변경).
- 비슷한 것 찾기: 판 1 · 2 는 링크 + 글자 비슷함(pg_trgm — 이미 쓰는 확장). 임베딩(pgvector)은 새 바깥 처리자 · 처리방침 문제라 원장 Q18 을 닫은 뒤(판 2 끝에서 적중률을 보고).

## 7.5 온톨로지 화면(GUI) — '회사 지식' 화면 (D95)

사장님 글(D95): 'master brain 은 ONTOLOGY GUI 를 만들어'. 깊은 조사(화면 사례 · 직원 큐레이션 · 그래프 라이브러리 · Postgres 저장 꼴 · 에이전트 쓰는 법 — 보고서 '마스터 브레인 온톨로지 화면 설계', 학습 폴더 `reports/`, 저장소 밖 · 출처 약 100개)의 결론만 적는다.

**원칙(조사 근거)**

- **매일 쓰는 화면은 그림이 아니라 찾기 · 표 · 항목 카드 · 제안함이다.** Palantir 도 구조 편집(Ontology Manager) · 개체 찾기(Object Explorer) · 카드(Object View) · 그래프(Vertex)를 화면마다 나눈다. 지식 그래프 실무자 19명 인터뷰(IEEE TVCG 2024)는 쓰기만 하는 사람에게 점 · 선 그림보다 카드 · 시간 흐름을 권한다. 수천 개를 한 장에 그리면 실뭉치(hairball)라 만들지 않는다.
- **'온톨로지 화면'은 두 겹**: ① **유형 지도** — 유형 약 20 · 링크 종류 9 를 한 장에 다 그린다(이 크기는 엉키지 않음, 층층 배치) ② **이웃 지도** — 카드 안 탭, 한 항목 둘레 1걸음(최대 2), 링크 종류별 펼치기 칩(수 표시), 관련 없는 것은 숨기지 않고 흐리게(Kumu · Obsidian 지역 그래프 꼴).
- **그림은 돕는 쪽, 진짜 화면은 HTML 목록.** 캔버스 그림은 키보드 · 화면 읽기가 안 된다(라이브러리 모두) — 서버가 그린 이웃 목록과 그림을 서로 맞물린다.
- **고치기를 넣기만큼 쉽게.** 고치기가 번거로우면 틀린 AI 제안을 더 받아들인다(2,784명 실험). 한꺼번에 넣기는 등급 A 만, 등급 B 는 핵심 값 하나를 직접 확인한다.
- 유형마다 색 · 아이콘 하나를 모든 화면에서 같게, 상태는 모양으로(은퇴 회색 · 초안 점선 · 낡음 주황 테두리).

**화면** — 새 `foms/web/` 블루프린트 '회사 지식' 한 곳에 탭. 상담 학습 탭(17.7)은 이 화면을 '상담 층'으로 거른 바로가기로 바꿔 두 벌을 만들지 않는다.

**라이브러리** — **Cytoscape.js 3.34.x**(MIT, 묶음 노드 · 터치 · 의존 없는 ESM 파일 하나) + 유형 지도 층층 배치용 **cytoscape-dagre**(MIT). `static/vendor/` 에 파일로 들이고(선례 `templates/drawing/wizard.html` 의 vendor 파일), SHA-256 을 적고 `?v=` 로 고정, 지도 탭을 열 때만 `import()`. 새 패키지 반입이라 이름 · 까닭을 먼저 알린다(13절 15). 2순위 sigma.js v4(2026-10 새로 쓴 판 — 묶음 노드 없음 · 한글 이름표 미검증)는 수천 개 전체 그림이 꼭 필요하다고 정할 때만 따로 시험. Apache AGE · 3D · GraphRAG 그림은 쓰지 않는다.

- 앱 코드: 순수 함수 파일(받은 자료 → 그림 요소, 유형 → 색 — node 시험)과 화면 파일(그리기 · 누르기 · 목록 맞물림)로 나눠 각각 300줄 아래, 인라인 스타일 0, 글은 `textContent` 만.
- 켜기 전 시험: 한글 이름표(화면 배율 1 · 2 · 3, Chrome · Android · iPhone Safari — 빈 글자 0, 긴 이름 줄임표) · 휴대폰 이웃 그림(한 항목 + 2걸음, 첫 그림 1초 안, 끌기 · 확대 끊김 없음) · 그림 없이 목록만으로 모든 동작 · 스테이징 gstack browse 반복 점검(카드 → 지도 → 펼치기 → 목록 맞물림). 한글 · 휴대폰 시험이 떨어지면 지도는 PC 에서만.

**API** — 읽기(찾기 · 표 · 카드 · 이웃(종류 · 걸음 · 상한) · 유형 지도 · 판 차이)와 제안 · 결정만. 정본 쓰기는 **반영 동작 한 곳**(5절 '액션으로만'). 모든 응답은 찾는 단계에서 보기 범위로 거른다(4절 — 모아 센 수 포함), 바깥 역할 404, CSRF, 응답 `{success, data, error}`.

**승인 흐름(6절에 보탬)**

- 항목당 열린 제안 하나(두 번째는 같은 카드에 붙음). 제안 카드: 한 줄 요약 · **칸별 전 → 후** · 사람 까닭과 사진 먼저, AI 일반화 다음 · 근거 대화 서랍(가린 글) · 비슷한 사례 수와 날짜 · 함께 닿는 항목 · 관문 결과 · '제안을 만든 뒤 항목이 바뀜' 경고(기준 판 비교) · 유형별 '승인의 뜻' 한 줄(승인 = 명백한 문제 없음 확인 — 위키백과 pending changes 꼴).
- 결정: 넣기 / 고쳐 넣기 / 거절(까닭 칩: 숫자 틀림 · 한 손님 일 · 정책 아님 · 사진 필요 — 남겨서 같은 제안이 다시 오지 않게) / PC 에서 볼게요.
- AI 제안은 주 상한 안에서 쓰인 횟수 순, 정한 기간이 지나면 AI 제안만 저절로 닫힘(Intercom 꼴). **은퇴 · 지우기도 같은 제안함**(PoolParty 는 지우기가 승인을 비켜 간다). 항목 하나 되돌리기 = 옛 값을 새 제안으로(Document360 꼴). 관문 ② 부딪침 판정은 두 순서로 돌린다(LLM 판정자 순서 치우침).
- 잘 도는지 숫자로 본다: 결정까지 시간 분포 · 5초 안 누름 비율 · 승인 뒤 되돌림 수 · 거절 까닭 분포.

**다시 확인** — 이번 기준 답 판의 가격 규칙은 같은 날 확인돼 같은 날 한꺼번에 낡는다. 유형별 확인 주기(가격 규칙 14일 그대로, 다른 유형은 사장님이 정함 — 13절 12), 묶음 알림 한 통, '아직 맞음' 한 번. **유효 기간(사실이 맞는 때)과 확인 날 · 낡음 날(다시 볼 때)은 다른 칸**이다(Graphiti: '느슨한 기한은 무효 날짜가 아니다').

**저장 꼴 — 7절을 다시 봄(D95 뒤)**: 화면이 항목별 승인 · 거꾸로 링크 · 공통 항목 · 항목별 기록을 요구한다. 지식 문서는 브랜드마다 한 줄(3.1 규칙 1 '공통 하나'와 부딪침) · 링크에 종류 없음(17.5 `links` = id 만) · 제안이 머물 자리 없음(항목 칸 열 개뿐 — `knowledge_doc.py`)이라, 문서 위에 화면을 만들면 판 2 에 다시 만든다. 그래서 **추천을 '판 1 부터 전용 표'로 바꾼다**(13절 1):

- 마이그레이션 `brain_00` = **빈 표 더하기**(되돌리기 쉬움). 표 이름은 7절 다섯 그대로.
- `brain_objects` · `brain_links` 는 **쌓기만 하는 판 행** — 항목 키 · 판 · 유효 시작 · 끝 · 확인 날 · 낡음 날 · 기록 시각 · 대체 시각 · 상태 · 확신 · 근거 종류 · 위치 · 만든 이 · 사람 승인자 · 보기 범위. '지금 판은 하나'는 부분 유일 색인. `brain_changes` 는 칸별 전 · 후 + 기준 판(반영 때 기준 판이 그대로인지 확인).
- 유형 · 링크 허용 짝(어떤 유형 → 어떤 유형 → 어떤 링크)은 도메인 모듈 옆 상수, 반영 동작 한 곳이 검사.
- 색인: 링크 양 끝 + 종류, (브랜드 · 유형 · 키) 유일, pg_trgm. 그래프 따라가기는 재귀 CTE(이 크기에서 충분 — 실제 자료로 잰다). Apache AGE 는 Railway 기본 이미지에 없고 관리 활동이 약해 쓰지 않는다.
- **상담 두뇌가 읽는 지식 문서는 반영 때마다 표에서 같은 꼴로 다시 만든다**(호출부 무변경). 그림자 기간에 옛 문서와 견주고, 상담 평가 묶음이 같거나 나아야 문서 직접 쓰기를 막는다.
- 임베딩(pgvector — 운영 0.8.2)은 Q18 뒤, 색인 없는 정확 검색부터. HNSW 는 수만 줄을 넘을 때 · pgvector 0.8.4 이상으로 올린 뒤(0.8.3 · 0.8.4 가 HNSW 손상 버그를 고침).

## 8. 도면 AI 와 잇기 — 그림 기억 · 자재표 규칙

- **그림 기억(`drawing_part_memory`)은 brain 에 복사하지 않는다.** 그림 특징 숫자는 양이 많고(줄당 약 1.7KB) 쓰임이 그림 분류 하나라, 그 표가 정본 그대로다. brain 은 **이름표 목록(그림 조각 종류)** 을 항목으로 갖고 제품 라인과 잇는다(`applies_to` — 어느 제품이 어느 조각을 만드나). 그래서 상담의 그림 읽기(17.11 — 손님 그림의 '도어 · 내부')와 도면 마법사의 이름표가 같은 말을 쓴다.
- **자재표 규칙 숫자**(`drawing_wizard_bom_rules`)도 그 SystemSetting 이 정본이다. brain 항목은 `value_from` 링크로 키 · 판(`d1` · `s<판>`)을 가리키고, 챗봇이 'SR 은 몇 mm 인가요?'를 물으면 그때 그 키를 읽어 답한다(복사본이 낡지 않게). 규칙 숫자를 바꾸는 길은 지금 규칙 창 그대로(도면팀 · 감사 기록).
- **도면 규칙**(`docs/research/drawing-agent/TEAM-RULES.md`)은 도면팀 답이 쌓이면 brain '도면 규칙' 항목으로 옮기고(근거 = 노트 주 · 질문 번호), 그 뒤 정본은 brain, 저장소 글은 사본(공개 저장소라 규칙 글만 — 손님 정보 없음).
- **물어볼 것 한 곳**: 도면 주간 노트의 '물어볼 것'과 상담의 '물어볼 것' · 챗봇 '빈 지식'을 한 제안함에 모은다(층 표시). 같은 질문을 두 팀에 따로 묻지 않는다.
- **공통 사실이 이어 주는 것**: 통 폭 · 깊이 · 몸통 높이 · 무몰딩 천고 같은 규격은 상담 답 · 도면 자재표 · 그림 읽기가 모두 쓴다 — 공통 바탕 한 항목.
- **그림 읽기 → 실측 → 도면 최종본(판 2 이후 학습 고리)**: 상담에서 손님 도면으로 읽은 가로 범위(17.11)와, 같은 손님이 주문으로 이어졌을 때 실측 뒤 도면 최종본의 폭을 견주면 직원 화면 없이도 정답이 생긴다. 상담 ↔ 주문 묶임은 늘 되지 않으므로(상담 설계서 2.3) 묶인 것만, ERP 는 읽기만.
- **계정 꼴**: 에이전트 계정은 AI 도면팀원 계정 꼴(시스템 계정 · 로그인 못 함 · 팀 알림 · 배정 후보에서 빠짐 — `foms/services/drawing_agent_account.py:18`)을 따른다.

## 9. 생산 에이전트 자리 (판 3)

- **먼저 지식, 그다음 에이전트.** FOMS 에는 생산 회차 · 도면 게이트 · AS 회차 표는 있지만 공정 · 작업 표준 · 불량 원인 같은 글 지식이 없다. 생산팀 계정도 적었다 — 생산 알림을 생산팀에 안 보낸 까닭이 '생산팀 계정 0명'이었다(`docs/specs/2026-10-27-drawing-team-production-fix_SPEC.md:14`, 지금 수는 다시 확인). 그래서 판 3 의 첫 일은 **모으기**다:
  1. 생산팀 질문표(총괄이 만들고 생산팀장이 답 — 사진 교훈 12질문 꼴) → 공정 · 작업 표준 항목 초안.
  2. AS 기록(`OrderASCycle` · AS 사진 — 가린 글 · 숫자 · 코드만)에서 'AS 원인' 관찰 → 원인 코드 묶기 제안.
  3. 도면 ↔ 생산 엇갈림(도면 수정 중인데 제작 시작 등 — 이미 막는 게이트가 있다)에서 규칙 후보.
- **생산 에이전트의 첫 일(손님 · 외부에 말하지 않음)**: 생산팀 물음에 답(챗봇 생산 층) · AS 원인 묶기 제안 · 불량 → 공정 링크 제안 · 주간 '생산 노트'(AI 도면팀원 주간 노트 꼴).
- **하지 않는 것**: 생산 일정 · 발주 바꾸기 · 작업자 배정 · 품질 판정(늘 사람).
- 생산 에이전트 자체 설계(계정 · 노트 · 루틴)는 판 3 앞에서 짧은 Spec 으로 따로 승인받는다.

## 10. FOMS 직원 챗봇 (D88)

### 10.1 무엇 · 누구

- **로그인한 내부 직원이 FOMS 안에서 묻고, brain 이 근거를 달아 답한다.** 처음엔 ADMIN 만(판 1) → 판 2 에서 내부 직원 전부(VIEWER 포함 · 협력사 등 바깥 역할 제외).
- 자리: 새 화면 하나(`foms/web/` 블루프린트 — 등록 정본 `foms/platform/blueprints.py`) + API(`foms/api/` — JSON `{'success','data','error'}` · CSRF · 로그인 필요). 화면은 Jinja + 순수 JS(새 JS 300줄 래칫 · 인라인 스타일 없음 · fetch 는 try/catch + `success` 검사 · `textContent` 만). 나중에 화면 구석 '물어보기' 단추.

### 10.2 답하는 길(순서 고정)

1. **가림**: 묻는 글을 상담과 같은 가림으로 가린다(직원이 손님 이름 · 전화 · 주문 번호를 적어 물을 수 있다). 가림 검사 0 이어야 다음.
2. **찾기 — 묻는 사람의 보기 범위 안에서만**(17.9-2): 범위 밖 항목은 후보에도 들지 않는다. '확인 필요'(엇갈림 열림) 항목은 '확인 필요'라는 사실만 후보로.
3. **두뇌**: 찾은 항목들(id · 글 · 확신)과 가린 질문을 Claude 에 — 도구 없음 · 구조화 출력 하나: `answer`(짧은 글) · `evidence_ids[]` · `unknown`(참/거짓) · `ask_team`(`User.team` 값 가운데 하나 · owner · admin) · `confidence`.
4. **코드 확인**: `evidence_ids` 가 찾은 후보 안에 있어야 한다(밖이면 답 버림). 근거가 0 이면 답을 쓰지 않고 **'모름 + 누구에게'**('이 내용은 지식에 아직 없어요 — 도면팀에 물어보세요' 꼴). 금액 · 날짜 · 기간 숫자는 근거 항목 · 계산기 값에 있는 것만(상담 4절 허용 목록 꼴).
5. **보이기**: 답 + 근거 항목 이름(누르면 그 항목 — 보기 범위 안) + 확신 + 마지막 확인 날. 낡은 값(확인 날 14일 넘음 — 7.1 꼴)은 '확인 필요' 표시.

- **ERP 자료를 묻는 질문**(예: '어느 주문 도면 언제 나와요?')은 판 1 · 2 에서 답하지 않는다 — '주문 화면에서 확인해 주세요' + 링크 없음. 판 3 에서 ERP 보기 객체를 묻는 사람의 FOMS 권한 안에서만 읽는다(17.9-2).
- **모델**: 패널 칸(처음 Sonnet 5.5 — 13절 8), 생각 깊이 · 시간 상한 · 돈 상한 칸. 돈은 챗봇 하루 상한을 상담 실시간과 따로 둔다 + 사람마다 하루 질문 수 상한.
- **주입 막기**: 묻는 글 · 항목 글은 자료일 뿐(지시문에 명시) · 도구 없음 · 출력 꼴 고정 · 근거 id 확인.

### 10.3 기록 · 빈 지식 찾기

- 기록 줄(판 2 의 `brain_questions`, 판 1 은 기존 기록 꼴): 가린 질문 · 답 · 근거 id · 모름 · 확신 · 묻는 사람 번호(ADMIN 만 봄) · 피드백(도움 됨 · 안 됨 · 틀림 + 고칠 말). 보관 1년. **직원별 모아 보기 화면은 만들지 않는다**(근로 감시 확인 — 원장 Q20 과 같은 줄).
- **빈 지식(주 1회)**: '모름' · '틀림' 질문을 뜻으로 묶어(Haiku) 층 · 팀별 '빈 지식' 목록 → 그 팀 '물어볼 것' → 답이 오면 6절 제안 길로 항목이 된다. 아침 보고 월요일판에 수만.
- **틀림 신고**: 피드백 '틀림'은 그 근거 항목에 '엇갈림 후보'로 붙는다 — 같은 항목에 서로 다른 사람의 틀림이 2건 이상이면 승인자에게 간다(6절 근거 관문과 같은 뜻).
