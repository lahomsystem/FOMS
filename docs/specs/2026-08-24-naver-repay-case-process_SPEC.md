## 1. 케이스 1 정의

### 1.1 무엇이 재결제 집인가

고객이 **이미 결제한 네이버 주문 A 를 취소하고, 같은 물건값을 새 네이버 주문 B 로 다시 결제**한
경우다. 색상·사이즈 변경, 금액 정정, 결제수단 변경이 흔한 사유다.

수집은 `productOrderStatus == PAYED` 인 순간만 본다(`claim_watch.py:3-4`). 그래서 B 는 FOMS 에
**완전히 새로운 집**으로 들어온다 — 원 주문과의 연결은 어디에도 없다. 그대로 `주문 만들기` 를
누르면 같은 고객의 시공 건이 둘로 갈린다(`promotion.py:414-417`).

**재결제 집 = 새 집 B 이고, 그 물건은 이미 FOMS 주문 #N 에 잡혀 있다.**
그래서 새 주문을 만들지 않고 **주문 #N 에 붙인다**(`relation='REPAY'`).

추가결제(`ADDON`)와의 구분:

| | 추가결제 ADDON | 재결제 REPAY |
|---|---|---|
| 고객이 낸 돈의 뜻 | 원 주문에 **더** 낸 차액 | 원 주문 값을 **다시** 낸 것(원 결제는 환불) |
| 원 주문 | 살아 있다 | **네이버에서 취소됐다** |
| 물건 | 따로 나가지 않는다 | **나중에 한 번 나간다** |
| 발송처리 | 발주확인 없이 바로 닫는다 | **발주확인 먼저 → 실제 출고 때 발송처리** |

이 표의 마지막 줄이 D1 개정의 전부다(`fulfillment.py:54-66` 주석, `:523-542` `close_now`/
`not_confirmed` 판정).

### 1.2 화면에서 어떻게 알아보는가

**붙이기 전** — 상세 pane 아래쪽 `관계` 섹션에 후보 표가 뜬다
(`templates/admin/partials/naver_workbench_pane.html:346-395`). 후보는 수취인 전화 → 주문자 전화
→ 이름+주소 앞 10자 순으로 점수를 매겨 180일·5건까지 제시한다
(`order_candidates.py:44-58`, `:111-198`). 각 후보 행 오른쪽에 버튼 두 개가 나란히 있다:
`추가결제로 붙이기` / `재결제로 붙이기`(`naver_workbench_pane.html:381-388`).
**자동으로 붙지 않는다** — 금액·시공이 걸린 판단이라 근거만 늘어놓고 사람이 고른다
(`naver_workbench_pane.html:322-330` 주석).

**붙인 뒤** — 다섯 자리에 표식이 생긴다.

| 자리 | 표식 | 근거 |
|---|---|---|
| 목록 줄 | 파란 `재결제` 배지 (`ADDON`/`REPAY` 에만 단다 — 결정 D4) | `templates/admin/naver_workbench.html:301-306` |
| 목록 줄 | `주문 #N` 배지 (FOMS 주문 번호) | `naver_workbench.html:352-353` |
| 상세 헤더 | 같은 파란 `재결제` 배지 | `naver_workbench_pane.html:85-87` (라벨식 `:23`) |
| 상세 `관계` 섹션 | "주문 #N 에 붙어 있습니다." + `되돌리기` 버튼 | `naver_workbench_pane.html:331-344` |
| 필터 칩 | `추가결제·재결제` 로 모아 본다 | `naver_workbench.html:157`, `naver_ingest.py:1086` |

**원 주문 집(A)과 짝을 찾는 법**: 두 집이 **같은 `주문 #N` 배지**를 단다
(`naver_workbench.html:352-353`, 상세는 `naver_workbench_pane.html:94-96`). A 는 취소돼 있으므로
빨간 클레임 배지가 함께 붙는다(`naver_workbench_pane.html:88-90`).
원 주문이 애초에 네이버에서 온 게 아니면(ERP 수기 주문) A 쪽 줄은 아예 없다.

### 1.3 원 주문과 새 집의 관계 (데이터)

붙이기는 **집 단위**다. 기준 링크 하나가 아니라 같은 집(주문번호 + `household_key`)의 링크
**전부**가 함께 붙는다(`promotion.py:461-470`, `_group_siblings_for_attach` `:525-551`).
네이버는 본품과 옵션을 각각 다른 상품주문으로 주기 때문에, 한 건만 붙이면 나머지가 미아가 된다.

붙은 결과(링크마다):
- `order_id = N`, `relation = 'REPAY'`, `sync_status = 'LINKED'` (`promotion.py:467-469`)
- 주문에 네이버 출처 표식 각인 (`promotion.py:472`, `_stamp_source_marker` `:237-276`)
- 각 상품주문의 결제 금액이 `structured_data['pricing']['extra_payments']` 에 **기록**된다
  (`promotion.py:475-477`). 항목에 `relation` 필드가 들어간다(`promotion.py:177`).

**원 주문 A 의 링크는 그대로 남는다.** 어떤 코드도 그것을 떼지 않는다. 취소는 `claim_watch` 가
5분 스윕에서 목격해 **표시 + 담당자 알림**까지만 한다 — 주문 상태를 자동으로 바꾸지 않는다
(`claim_watch.py:11-12`, `refresh_claims` `:202-286`).

## 2. 담당자 처리 순서

**요약표.** 굵은 단계가 **불가역**이다.

| # | 단계 | (a) 화면·버튼 | (b) 네이버 호출 | (c) 되돌리기 |
|---|---|---|---|---|
| 1 | 재결제인지 판정 | 상세 pane `관계` 섹션 후보 표 | 없음 | 해당 없음 |
| 2 | 주문 #N 에 붙이기 | 후보 행 `재결제로 붙이기` | **없음** | **가능** (`되돌리기`) |
| 3 | 원 주문에서 규격·금액 확인 | `ERP 규격 입력` | 없음 | 가능(일반 편집) |
| 4 | **발주확인** | `발주확인` → 모달 | **있음** | **불가** |
| 5 | 실제 출고·시공 대기 | — | 없음 | — |
| 6 | **발송처리** | `발송처리` → 모달 | **있음** | **불가** |
| 7 | 큐에서 빼기 | `확인 완료 — 큐에서 빼기` | 없음 | 화면에 되돌리는 버튼 **없다** |

### 1단계 — 이 집이 정말 재결제인가

- **어디**: 상세 pane 하단 `관계` 섹션(`naver_workbench_pane.html:346-395`).
- **볼 것**: ① 후보 행의 `reason`(전화 일치 등, `order_candidates.py:53-56`)
  ② 이 집의 금액 합이 원 주문의 물건값과 맞는가(상품주문 표 `naver_workbench_pane.html:297-323`)
  ③ 원 주문 쪽 네이버 집이 취소 배지를 달았는가.
- ③ 이 아니라 원 주문이 살아 있으면 **추가결제(ADDON)** 이고 이 문서의 케이스가 아니다.
- **붙이려는 집 자체에 빨간 클레임 배지가 없는지 확인한다**(§5 함정 4).
- 네이버 호출 없음. 되돌리기 해당 없음.

### 2단계 — `재결제로 붙이기`

- **어디**: 후보 행 오른쪽 두 번째 버튼(`naver_workbench_pane.html:385-388`).
- **확인 절차**: 네이티브 확인창 1회 — "주문 #N 에 재결제 로 붙입니다. 새 주문은 만들지
  않습니다."(`static/js/admin/naver-workbench.js:1026-1028`). 불가역 4종 세트 모달을 두지
  않는 이유는 **되돌릴 수 있기 때문**이다(`naver_workbench_pane.html:322-330` 주석).
- **일어나는 일**: §1.3 그대로. 금액은 **기록만** 한다 — 출고가·잔금·계약금 계산식은
  건드리지 않는다(`promotion.py:186-196` docstring, 2026-08-19 사용자 확정).
- **네이버 호출 없음.**
- **되돌리기 가능**: `관계` 섹션의 `되돌리기`(`naver_workbench_pane.html:342-343`) →
  `POST /detach`(`naver_ingest.py:2283-2316`) → 집 전체가 `order_id=None` · `relation='NEW'` ·
  `sync_status='COLLECTED'` 로 돌아가고, **붙일 때 남긴 금액 기록도 함께 걷힌다**
  (`promotion.py:512-518`).

### 3단계 — 원 주문에서 규격·금액을 확인한다

- **어디**: 상세 pane 의 `ERP 규격 입력` 버튼(`naver_workbench_pane.html:135-138`) → 주문 편집기.
- 규격은 네이버 옵션 원문을 **사람이 읽고** 채운다(자동 파싱 금지 — 도메인 규칙 6,
  `naver_workbench_pane.html:261-266`).
- 도크가 "추가결제 N건 · M원 (반영은 수동)" 을 보여준다(`static/js/orders/erp-naver-dock.js:156-162`).
  **재결제는 '더 받은 돈'이 아니다** — 이 표기를 그대로 믿고 총액에 더하면 안 된다(§4.4 · §5 함정 2).
- 네이버 호출 없음. 되돌리기: 일반 편집.

### 4단계 — **발주확인 (불가역)**

- **어디**: 상세 pane `발주확인` 버튼(`naver_workbench_pane.html:142-146`) → 4종 세트 모달
  (`:450-491`).
- **네이버 호출 있음**: WORKER 가 `confirm_place_orders` 를 부른다(`fulfillment.py:427`).
  web 은 enqueue 만 한다 — IP 3슬롯 계약(`naver_ingest.py:2104-2142`).
- **되돌릴 수 없다.** 모달이 그렇게 말한다(`naver_workbench_pane.html:474-476`).
- **시점**: 붙인 직후 바로. 미루면 네이버 **발송기한**을 넘겨 자동 취소될 수 있다
  (정렬 힌트 `naver_workbench.html:171`).
- 보낼 건수는 이미 확인된 형제를 뺀 수다(술어 `is_place_pending` `fulfillment.py:119-138`,
  모달 재진술 `naver_workbench_pane.html:461-472`).
- 화면이 재결제 집에 **먼저 이 단계를 하라고 문장으로 말한다**:
  "재결제 집이라 발주확인이 먼저입니다 — 원 주문의 물건이 나중에 한 번 나갑니다. 발송처리는
  실제 출고·시공 시점에 누르세요."(`naver_workbench_pane.html:195-201`).
- 끝나면 헤더에 `발주확인 완료` 배지가 붙고(`naver_workbench_pane.html:100-102`)
  발송처리가 열린다(모달이 그렇게 약속한다 — `:479`). **막다른 길은 없다.**

### 5단계 — 실제 출고·시공을 기다린다

재결제 집의 물건은 원 주문의 물건이다. 그 물건이 **아직 나가지 않았으면 발송처리를 누르지
않는다**. 이미 나간 뒤에 재결제가 들어온 경우(정산 정정 등)라면 6단계를 바로 눌러도 된다 —
기준은 관계가 아니라 **"그 물건이 실제로 나갔는가"** 하나다.

### 6단계 — **발송처리 (불가역)**

- **어디**: 상세 pane `발송처리` 버튼(`naver_workbench_pane.html:152-160`) → 모달(`:493-565`).
  D1 개정 뒤 재결제 집의 라벨은 `지금 닫기` 가 아니라 **`발송처리`** 다
  (`close_now` 판정 `naver_workbench_pane.html:36` · 라벨 `:158`).
- **네이버 호출 있음**: WORKER `dispatch_product_orders`, 배송방법 `DIRECT_DELIVERY`
  (택배사·송장 없음) (`fulfillment.py:550-555`, 상수 `:52`).
- **되돌릴 수 없다.** 구매자에게 **배송 시작**으로 보이고 구매확정·정산 시계가 돈다
  (`fulfillment.py:6-8` 모듈 docstring, 모달 `naver_workbench_pane.html:520-522`).
  모달이 재결제 집에 대고 "원 주문의 물건이 나중에 한 번 나갑니다 … 아직 물건이 나가지
  않았다면 지금 누르면 안 됩니다"라고 말한다(`naver_workbench_pane.html:523-535`).
- **이 순간부터 취소가 사라진다**: 화면은 취소 버튼을 아예 렌더하지 않고
  (`naver_workbench_pane.html:166`), 서버도 집 전체를 거절한다(`fulfillment.py:643-651`).
  이후는 **반품 흐름**뿐이다.
- 재결제 집의 이 발송처리가 **그 주문의 유일한 네이버 발송 기록**이다 — 원 주문 A 는
  네이버에서 취소돼 발송할 수 없다.

### 7단계 — `확인 완료 — 큐에서 빼기`

- **어디**: 상세 pane 오른쪽 끝 버튼(`naver_workbench_pane.html:175-182`).
- **네이버 호출 없음** — 우리 큐에서만 뺀다(`naver_ingest.py:2321-2345`).
- **되돌리는 버튼이 화면에 없다**: `reviewed_at` 은 한 번만 찍히고(`naver_ingest.py:2335-2336`)
  이를 지우는 라우트가 없다.
- **반드시 6단계 뒤에 누른다.** 4단계까지만 하고 여기를 누르면 그 집이 목록에서 사라져
  6단계에 도달할 길이 막힌다(§5 함정 1).

## 3. 재결제 집 자체를 취소해야 할 때

담당자가 붙인 뒤 "이 재결제도 취소해야 한다"가 되는 경우(고객 변심, 재고 없음 등)의 절차다.

### 3.1 언제 가능한가

**집의 상품주문 중 하나라도 발송처리가 나가기 전(`dispatched_any == False`)까지만** 가능하다.

- 화면: `{% if not dispatched_any %}` 일 때만 취소 버튼을 렌더한다
  (`naver_workbench_pane.html:166-172`, 판정 `:43`·`:70`).
- 서버: 발송된 형제가 하나라도 있으면 집 전체를 거절한다(`fulfillment.py:643-651`).
- 부분 발송(형제 일부만 나간 집)도 **집 전체가 막힌다**. 화면이 그 이유를 한 줄로 말한다
  (`naver_workbench_pane.html:228-235`).

### 3.2 가능할 때 — 절차

1. **취소처리** (`naver_workbench_pane.html:166-172`) → 모달(`:567-614`).
   - 사유 코드를 고른다. 네이버가 아는 7개만 보낸다(`fulfillment.py:69-79`), 서버가 화면
     select 를 믿지 않고 다시 본다(`naver_ingest.py:2167-2169`).
   - 상세 사유 500자(선택, `naver_workbench_pane.html:593-598`).
   - **네이버 호출 있음 · 불가역**: 구매자에게 환불이 시작된다
     (`naver_workbench_pane.html:582-585`). 네이버 취소는 배치가 없어 상품주문 1건씩 돈다 —
     한 건이 실패해도 나머지는 계속 부른다(`fulfillment.py:611-612` docstring, `:660-670`).
   - **FOMS 주문은 건드리지 않는다**(`fulfillment.py:614-615`, 모달 문구
     `naver_workbench_pane.html:600-604`).
2. 취소가 끝나면 집이 잠긴다: `canceled_at` 표식(`fulfillment.py:672-678`) → 화면 `취소 완료`
   배지(`naver_workbench_pane.html:91-93`) + 주문 만들기·발주확인·발송처리 전부 닫힘
   (`naver_workbench_pane.html:26-29`, 안내 `:186-190`).
   서버도 `_cancel_guard` 로 다시 막는다(`fulfillment.py:243-273`).
3. **`되돌리기` 를 눌러 붙이기를 되돌린다.** 이걸 빠뜨리면 **환불된 돈이 주문에 기록으로
   남는다** — `detach` 만이 그 항목을 걷어낸다(`promotion.py:512-518`).
   되돌리기는 취소 뒤에도 막히지 않는다 — `detach_link_from_order` 에 발송·취소 가드가 없다
   (`promotion.py:483-523`).
4. 우리가 낸 취소라 5분 뒤 클레임 알림은 오지 않는다 — 억제는 로그로만 남는다
   (`claim_watch.py:138-156` `_is_our_cancel`, `:263-276`).

**순서 주의**: 3번을 2번보다 먼저 하면(붙이기를 먼저 되돌리면) 그 집은 `relation='NEW'` 가 되어
`관계` 섹션과 함께 `되돌리기` 버튼이 사라진다(`naver_workbench_pane.html:331-344` 는
`rel_label` 이 있을 때만 렌더된다). 취소 자체는 여전히 가능하지만 되돌릴 것이 없다.
**취소 → 되돌리기** 순서를 지킨다.

### 3.3 불가능할 때 (`dispatched_any == True`)

FOMS 에서는 아무것도 할 수 없다. 화면이 버튼을 내지 않고 서버가 거절한다.

- **네이버 판매자센터에서 반품으로 처리한다.** 화면 문구가 그렇게 안내한다
  (`naver_workbench_pane.html:236-239`, 잠김+발송 조합은 `:240-245`).
- 반품이 진행되면 다음 수집 스윕에서 `claim_watch` 가 잡아 클레임 배지 + 담당자 긴급 알림을
  낸다(`claim_watch.py:263-285`). 그때부터 그 집은 `locked` 라 FOMS 액션이 전부 닫힌다
  (`naver_workbench_pane.html:26-29`).
- 금액 기록을 걷어내려면 `되돌리기` 를 눌러야 하는데, **클레임이 걸린 집도 `되돌리기` 버튼은
  그대로 열려 있다** — 잠금은 상단 액션 4종만 막고, 이 버튼은 `locked` 를 보지 않는다
  (`naver_workbench_pane.html:342-343`). 반품 확정 뒤 눌러 기록을 정리한다.

## 4. 원 주문(취소된 쪽) 처리 — Q3 답안

선행 스펙의 미결 질문:

> **Q3. 재결제(REPAY) 시 원 주문의 취소를 어떻게 남기나?** 현행 원칙은 "주문 상태 자동 변경
> 없음, 이력·알림만"이다(claim_watch). REPAY 도 같게 갈지, 이때만 원 주문에 취소 배지를
> 고정할지. (`docs/specs/2026-08-19-naver-order-relation-and-fulfillment_SPEC.md:172-174`)

### 4.1 지금 실제로 남는 것 (실측)

원 주문 A 가 네이버 수집분이었다면:

- A 의 링크는 주문 #N 에 계속 붙어 있다(떼는 코드 없음).
- `claim_watch` 가 취소를 목격해 스냅샷·클레임 상태를 갱신하고, 담당자(없으면 ADMIN 역할)에게
  **긴급 알림 1건**을 보낸다(`claim_watch.py:158-199` `_notify`, `:263-285`).
- 주문 편집 화면 도크에 **`⚠ 네이버 <취소 라벨>`** 이 뜬다. 도크는 주문에 붙은 링크들 중
  라벨이 있는 첫 건을 쓴다(`dock.py:275`·`:285`·`:354`, `erp-naver-dock.js:134-137`).
- **주문 상태·단계는 그대로다**(`claim_watch.py:11-12`).

원 주문 A 가 ERP 수기 주문이었다면 위 흔적이 **하나도 없다**. 남는 것은 재결제 붙이기가 만든
`extra_payments` 항목과 `log_access` 감사 1건뿐이다(`naver_ingest.py:2265-2271`).

### 4.2 선택지

**안 A — 현행 유지 (추가 조치 없음).**
claim_watch 알림 + 도크 ⚠ 라벨로 충분하다고 본다.
- 장점: 원칙과 100% 정합, 코드 0.
- 단점: 원 주문이 수기 주문이면 취소 사실이 **어디에도 없다**. 그리고 "왜 이 주문에 취소
  라벨과 재결제 금액이 같이 있는가"를 설명하는 문장이 화면에 없다 — 반년 뒤 다른 담당자가
  읽으면 사고로 읽힌다.

**안 B — 상태는 그대로 두고, 붙이기 시점에 주문 이력(`OrderEvent`) 1건을 남긴다.** ← **추천**
- 2026-08-19 스펙 §3.3 이 이미 약속한 것이다: "감사: `NAVER_INGEST_ATTACH_EXISTING` 이벤트 +
  `OrderEvent` 1건(무엇이 얼마 붙었는지 문장)"(`…2026-08-19…_SPEC.md:90`).
  **`log_access` 만 구현됐고 `OrderEvent` 는 빠졌다** — attach 라우트에 `OrderEvent` 생성 코드가
  없다(`naver_ingest.py:2227-2278`). 새 정책이 아니라 **미이행 정리**다.
- 이벤트는 관리자 `변경 로그` 화면에 한글 라벨로 뜬다
  (`foms/api/events.py:434-495`, `templates/admin/change_logs.html:144`,
  라벨 사전 `foms/services/order_event_display.py:126-`). 모델은 `models.py:808`.
- 장점: "주문 상태 자동 변경 없음" 원칙을 **건드리지 않는다** — 남기는 것은 이력뿐이다.
  수기 주문이어도 흔적이 남는다.
- 단점: 코드 변경이 필요하다(작다 — §6 R3).

**안 C — 원 주문에 '취소' 배지를 고정한다** (Q3 원문의 대안).
- **채택하지 않는다.** 배지는 상태의 얼굴이다. 재결제로 되살아난 주문에 '취소' 배지를
  고정하면 담당자가 진행을 멈춘다 — 그 주문은 살아 있고 물건이 나가야 한다. 거짓 신호다.
- 게다가 도크 ⚠ 라벨이 이미 그 사실을 말하고 있다(§4.1) — 중복이자 더 강한 오해다.

### 4.3 추천 — 안 B, 그리고 그 근거

**안 B 를 채택한다.**

1. **원칙 정합.** "주문 상태를 자동으로 바꾸지 않는다"는 2026-08-15 사용자 확정이고 코드에
   문장으로 박혀 있다(`claim_watch.py:11-12`). 안 B 는 상태를 한 글자도 건드리지 않는다.
   이력은 상태가 아니다 — 같은 원칙 아래서 claim_watch 도 이미 알림을 남긴다.
2. **이미 약속된 것.** 08-19 §3.3 이 `OrderEvent` 1건을 명시했다. 지키지 않은 약속을 지우는
   것보다 이행하는 쪽이 싸다.
3. **안 C 는 사고를 만든다** (§4.2).

**함께 지킬 규칙 두 개:**

- **원 주문 A 의 링크를 `되돌리기` 로 떼지 마라.** 떼면 도크의 ⚠ 취소 라벨과 네이버 원본이 그
  주문에서 사라진다. 다행히 A 가 `주문 만들기` 로 생긴 링크(`relation='NEW'`)면 detach 자체가
  거절된다(`promotion.py:506-508`) — 실수로 지워질 길은 코드가 이미 막고 있다.
- **원 주문의 FOMS 상태·단계는 담당자가 필요할 때 손으로 바꾼다.** 재결제는 주문이 살아났다는
  뜻이므로 대개 아무것도 바꾸지 않는 것이 맞다.

### 4.4 FOMS 주문의 금액·잔금은 어떻게 되나 — **오독 위험 있음(확정)**

**계산식은 바뀌지 않는다.** `extra_payments` 는 기록 전용이고, 출고가·잔금·계약금 어디에도
들어가지 않는다. 읽는 코드는 도크의 요약 하나뿐이다:

- 기록만 한다고 명시: `promotion.py:186-196` (docstring), 2026-08-19 사용자 확정.
- 유일한 독자: `dock.py:219-244` `_extra_payment_summary` → payload
  `extra_payment_count`/`extra_payment_total`(`dock.py:338-342`).
- 전 저장소 grep 결과 다른 소비자 0(계산식·집계 어디에도 없다).

**그런데 담당자가 총액을 잘못 읽을 위험이 있다 — 판단: 있다.**

1. 도크 라벨이 관계와 무관하게 **항상 "추가결제"** 다:
   `facts.push(['추가결제', N + '건 · ' + M + '원 (반영은 수동)'])`
   (`static/js/orders/erp-naver-dock.js:158-162`).
2. 요약이 관계를 보지 않고 **전부 합친다**(`dock.py:236-243`) — `ADDON` 과 `REPAY` 가 한
   숫자로 섞인다.
3. `ADDON` 에서 그 숫자는 "**더** 받은 돈"이라 출고가에 더하는 것이 맞다.
   `REPAY` 에서 같은 숫자는 "**다시** 받은 돈"이고 원 결제는 환불됐다 — 더하면 **두 번 센다**.

실사례 크기: 주문 4485 의 도크에 6건 **1,610,780원**이 "추가결제"로 떠 있다
(`docs/plans/2026-08-24-naver-attach-invisible-result-ledger.md:83`,
`docs/plans/2026-08-24-naver-workbench-ux-pass-ledger.md:59-60`).

> **관계 미확인.** 이 6건이 `ADDON` 인지 `REPAY` 인지는 **아직 모른다.** 두 원장 모두
> "추가결제 6건"이라 적었지만, 바로 위 1번에서 확인했듯 **그 라벨은 관계와 무관하게 항상
> "추가결제"** 다(`erp-naver-dock.js:158-162`) — 즉 그 관측은 relation 을 증명하지 못한다.
> 확정하려면 링크 264~269 의 `relation` 컬럼을 실데이터로 조회해야 하고, 그건 사용자
> 승인이 필요한 별건이다(§8 미결 U-1).

관계와 무관하게 **위험의 구조는 같다**: `REPAY` 인 집에서 이 숫자를 예약금·입금에 더하면
원 결제가 환불된 돈을 다시 세는 것이라 **주문 하나 값만큼 총액이 부풀어 오른다.**
그래서 R1 은 4485 의 관계 확정을 기다리지 않고 진행할 수 있다 — 고치는 것은 표기 규칙이지
특정 주문이 아니다.

**고칠 자리는 표시뿐이다.** 기록 항목에 `relation` 이 이미 들어 있으므로(`promotion.py:177`)
데이터 마이그레이션 없이 화면만 가르면 된다 → §6 **R1**.

## 5. 함정 목록 (실제 코드에서 확인한 것만)

### 함정 1 — 4단계와 7단계 사이에 집이 목록에서 사라질 수 있다

목록 모집단은 **확인 큐 ∪ 발주확인 전 집**이다(`naver_ingest.py:1378-1450` `_work_groups`).

- 원천 1 = `COLLECTED|LINKED` + **`reviewed_at IS NULL`** (`naver_ingest.py:649-670` `_queue_links`,
  술어 `:666`)
- 원천 2 = **발주확인 전** 집(`_place_pending_clause()`), 그중 우리가 취소한 집은 뺀다
  (`naver_ingest.py:1322-1367`, 제외 `:1367`)

따라서 **발주확인 완료 + `확인 완료` 누름** 이면 두 원천 모두에서 빠진다 → 그 집은 목록에
없다. 그런데 재결제 집은 D1 개정 뒤 **발주확인과 발송처리 사이에 며칠이 뜬다**(§2 5단계).
그 사이 7단계를 먼저 누르면 6단계 버튼에 도달할 길이 사라진다.

돌아갈 길도 좁다: 이력 탭 행은 `order_id` 가 있으면 `처리 탭에서 열기` 링크를 **내지 않고**
주문 링크만 낸다(`templates/admin/naver_workbench.html:550-562`). 주문 편집 화면 도크에도
워크벤치로 가는 링크가 없다(`static/js/orders/erp-naver-dock.js` 에 `href` 0건). 남은 길은
`?tab=work&link_id=<N>` 주소를 손으로 만드는 것뿐이다(그 경로는 살아 있고 "목록 밖 집" 경고가
뜬다 — `naver_workbench_pane.html:114-118`).

→ 절차로는 §2 7단계의 "**반드시 6단계 뒤에**" 로 막는다. 화면으로는 §6 **R2**.

### 함정 2 — 재결제 금액이 "추가결제"로 표시된다

§4.4 전문. 근거: `erp-naver-dock.js:158-162`(라벨 하드코딩) · `dock.py:236-243`(관계 무시 합산).

### 함정 3 — `되돌리기` 는 FOMS 장부만 되돌린다

`detach_link_from_order` 에는 발송·취소·발주확인 가드가 **없다**(`promotion.py:483-523`).
발주확인이나 발송처리를 이미 네이버로 보낸 뒤에도 되돌리기가 성공한다. 그러면:

- FOMS 는 관계·금액 기록을 잊는다(`relation='NEW'`, `order_id=None`, 기록 삭제 `:512-518`).
- **네이버 쪽 발주확인·발송처리는 그대로 살아 있다.** `triage_state['fulfillment']` 도 지워지지
  않는다(detach 는 그 키를 만지지 않는다).

즉 "되돌리기 = 되돌릴 수 있음"은 **2단계 직후에만 참**이다. 4·6단계를 지난 뒤의 되돌리기는
장부와 네이버가 어긋나게 만든다. §3.2-3(취소 뒤 기록 정리)은 이 성질을 **의도적으로** 쓰는
유일한 경우다.

### 함정 4 — 취소·반품 집도 `REPAY` 로는 붙는다

`attach_link_to_order` 의 클레임 차단은 **`ADDON` 에만** 걸린다(`promotion.py:450-458`).
설계 의도는 "재결제는 원 주문이 취소된 경우라 허용"인데, 실제로는 **새 집 B 자체가 취소·반품
중이어도** `REPAY` 로 붙는다. 담당자가 원 주문 집(A, 취소된 쪽)을 재결제 집으로 착각해 붙이면
성공하고, **환불된 금액이 `extra_payments` 에 기록된다.**

방어선은 두 개뿐이다: ① 붙은 뒤 그 집은 `locked` 라 네이버로 나가는 호출이 전부 닫힌다
(`naver_workbench_pane.html:26-29`) ② `되돌리기` 로 기록을 걷어낼 수 있다.
→ 절차로 막는다: §2 1단계에서 **"붙이려는 집에 빨간 클레임 배지가 없는지"** 를 확인한다.

### 함정 5 — 붙이기는 집 전체를 붙인다 (한 건이 아니다)

`_group_siblings_for_attach` 는 같은 집의 링크를 **전부** 모은다 — 승격용 `_group_siblings`
와 달리 **이미 주문이 붙은 형제까지** 포함한다(`promotion.py:525-551`). 그래서 6건 묶음을
붙이면 `extra_payments` 항목이 6건 생긴다(4485 실사례).
형제 중 하나라도 **다른** 주문에 붙어 있으면 전체가 거절된다(`promotion.py:461-465`).

### 함정 6 — 금액 기록은 멱등, 되돌리기는 `external_id` 기준

같은 `external_id` 가 이미 기록돼 있으면 건너뛴다(`promotion.py:217-222`) — 붙이기를 두 번

### R3 — Q3 이행: 붙이기·되돌리기 `OrderEvent`

- 범위: `foms/web/admin/naver_ingest.py` 의 attach/detach 라우트(`:2227-2316`),
  라벨 사전 `foms/services/order_event_display.py:128-`.
- 설계: 붙이기 성공 시 `OrderEvent(order_id=N, event_type='NAVER_ORDER_ATTACHED',
  created_by_user_id=…, payload={relation, external_order_no, product_order_count, amount_total})`
  1건. 되돌리기 성공 시 `'NAVER_ORDER_DETACHED'` 1건. **append-only** — 되돌리기가 붙이기
  이벤트를 지우지 않는다(금액 기록은 지우지만 이력은 남는다).
- 라벨 사전에 두 타입을 한글로 등재한다("네이버 수집분 연결" / "네이버 수집분 연결 해제").

  > **미등재 실패 모드는 "영문 코드"가 아니다.** `translate_event_type_to_korean` 이
  > `return labels.get(key, "기타 변경")`(`foms/services/order_event_display.py:186`)이라,
  > 등재를 빼먹으면 화면에 **한글 "기타 변경"** 으로 조용히 뭉개진다 — 다른 미등재
  > 이벤트와 구분이 안 된다. 눈으로도 "한글로 뜬다" 류 완료 기준으로도 못 잡는다.
- 새 라우트가 아니므로 mutation manifest 등재는 해당 없다. `log_access` 감사 라벨은 기존
  `NAVER_INGEST_ATTACH_ORDER`/`NAVER_INGEST_DETACH_ORDER` 를 그대로 쓴다(추가 없음).
- 완료 기준:
  - 붙인 뒤 `/api/orders/<N>/events` 에 이벤트 1건, 관리자 `변경 로그` 에 정확히
    **`네이버 수집분 연결`** 이 뜨고 **`기타 변경`이 뜨지 않는다**(부정 단언을 함께 건다).
  - 라벨 사전에서 두 타입을 빼면 그 회귀가 **red 가 되는지 확인한다** — red 사유가
    "`기타 변경` 이 떴다" 인지까지 본다.
  - 되돌린 뒤 이벤트 2건(붙임 + 해제) — 붙임 이벤트가 **살아 있다**.
  - 이벤트 기록 실패가 붙이기를 깨뜨리는지(같은 트랜잭션이라 롤백된다) 리뷰에서 판정한다.
  - 회귀 3건, red 먼저 확인.

**R1 → R2 → R3.** R1 이 금액 오독(§4.4)을 직접 막고, R2 는 절차가 끊기는 자리를 잇고,
