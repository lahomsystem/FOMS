# 네이버 수집분 관계 판별 + 발주확인·발송처리 (NAVER-INGEST-02) — SPEC

- 상태: **승인 대기** (2026-08-19 작성)
- 선행: NAVER-INGEST-01 (`docs/specs/2026-08-13-naver-order-ingest_SPEC.md`, 원장 `docs/plans/2026-08-13-naver-order-ingest-ledger.md`)
- 작성 근거: 2026-08-19 사용자 제기 3케이스 + 스테이징 실데이터 조사

---

## 1. 문제 (실측)

수집기는 **`productOrderStatus == PAYED` 하나로만** 신규를 판정하고, 멱등 키는
`productOrderId` 다(`mapping.is_collectible`). 그래서 아래 세 가지가 전부 "새 집"이 된다.

| 케이스 | 지금 일어나는 일 | 결과 |
|---|---|---|
| ① 주문 취소 후 **재결제** | 네이버가 새 상품주문번호를 발급 → 새 집으로 수집 | 원 주문이 이미 FOMS 주문이면 **주문 2건**. 취소 추적은 표시·알림만 하고 상태를 안 바꾼다(2026-08-15 확정) |
| ② 기존 주문 **차액 결제**(30cm·1cm 상품을 금액 맞춰 구매) | 신규 PAYED → 새 집 | CS가 "주문 만들기"를 누르면 **별개 주문**이 생긴다. 기존 주문에 붙일 경로가 없다 |
| ③ 네이버 **발주확인·발송처리** | FOMS에 기능 없음 | 판매자센터에서 사람이 따로 처리. FOMS는 처리 여부조차 화면에 없다 |

**실데이터 근거(스테이징 39집, 2026-08-19)**
- 같은 고객 2회 이상: 4명(곽미선 — 같은 날 906,000 / 1,230,450 두 집 등)
- 소액 단독 집: 배수경 **94,900원 · 수량 1**, 강지연 158,900원 — 차액 결제의 전형적 모양
- 승격 경로에 고객 매칭 코드는 **0줄**(`promotion.py`) — 사람이 눈치채지 못하면 그대로 중복 생성

**이미 들어와 있는 값**: 원본 스냅샷에 `placeOrderStatus`(예: `"NOT_YET"`)가 실제로 온다
(스테이징 link 148 확인). 즉 **발주확인 여부 표시는 네이버에 쓰지 않고도 오늘 가능**하다.

## 2. 목표 / 비목표

**목표**
1. 수집분이 **신규 / 추가결제(차액) / 재결제** 중 무엇인지 **사람이 한 번에 고를 수 있게** 한다.
   시스템은 후보를 제시하고 근거를 보여줄 뿐, 자동 확정하지 않는다.
2. 추가결제·재결제로 판정된 건은 **새 주문을 만들지 않고 기존 주문에 붙인다**.
3. 네이버 **발주확인 상태를 FOMS에서 본다**(읽기).
4. 네이버 **발주확인·발송처리를 FOMS에서 실행한다**(쓰기, WORKER 단일 출구).
5. 업무 규칙 고정: **신규 = 주문 만든 뒤 발주확인 / 추가결제 = 확인 후 발송처리**.

**비목표**
- 관계 자동 확정(사람 확인 없이 기존 주문에 붙이기). 금액·시공이 걸린 영역이라 금지.
- 반품·교환 동기화(NAVER-INGEST-01 비목표 유지).
- 송장번호 기반 택배 추적. 가구는 자사 배송·시공이다.
- erporder 편집 폼 UX/UI 변경(1px도 안 건드린다 — 2026-08-19 사용자 규칙).

## 3. 설계

### 3.1 관계 축을 링크에 둔다 (`external_order_links.relation`)

`sync_status`(수집 결과)·`reviewed_at`(사람이 봤나)와 **다른 축**이다. 섞으면
"수집 성공 + 사람 확인 + 추가결제로 붙임"을 표현할 수 없다.

```
relation: 'NEW' | 'ADDON' | 'REPAY'   -- NOT NULL, server_default 'NEW'
CHECK (relation IN ('NEW','ADDON','REPAY'))
```

- `NEW` — 지금 동작 그대로(승격 시 새 주문 생성).
- `ADDON` — 기존 주문의 추가 결제. 새 주문을 만들지 않고 `order_id` 에 **기존 주문 id** 를 넣는다.
- `REPAY` — 취소된 주문의 재결제. 마찬가지로 기존 주문에 붙이고, 원 링크의 취소 표시는 남긴다.

`order_id` 의 의미는 바꾸지 않는다("이 상품주문이 속한 FOMS 주문"). ADDON/REPAY 는 주문
생성 없이 그 값만 채운다 — 도크·이력·역조회가 전부 그대로 동작한다.

마이그레이션: `naver_relation_00`(down_revision = 현행 head). `downgrade()` 포함.

### 3.2 후보 제시 — 자동 매칭, 사람 확정

확인 큐 카드와 도크 상단에 **"이 고객의 기존 주문 N건"** 을 띄운다.

매칭 키(AND 아니라 점수):
1. 수취인 전화 digits (`phone_search.normalize_phone_digits`) — 최강 단서
2. 주문자 전화 digits (대리주문 대비)
3. 수취인명 + 주소 앞 10자

범위: 최근 **180일**, 최대 5건, soft delete 제외. hot path 아님(확인 화면 1건 조회 시).
표시: 주문번호·고객명·시공일·출고가·현재 단계 + "이 주문에 붙이기" 버튼.

**금액이 작을수록 추가결제 의심**이라는 힌트도 같이 보여준다(예: 20만원 미만 + 수량 1~3).
힌트일 뿐 자동 판정 근거로 쓰지 않는다.

### 3.3 붙이기(ADDON/REPAY) 처리

```
POST /admin/naver-ingest/<link_id>/attach   {order_id, relation}
```
- 대상 링크(집 전체 = `_group_siblings`)의 `order_id` 를 기존 주문으로, `relation` 을 지정값으로,
  `sync_status='LINKED'` 로 바꾼다. **주문 생성 없음.**
- 멱등: 이미 같은 주문에 붙어 있으면 성공으로 반환한다.
- 감사: `NAVER_INGEST_ATTACH_EXISTING` 이벤트 + `OrderEvent` 1건(무엇이 얼마 붙었는지 문장).
- 취소·반품 blocking 건은 `ADDON` 도 막는다(`REPAY` 는 원 주문이 취소된 경우이므로 허용).

**금액 반영 = (a) 기록만 — 2026-08-19 사용자 확정.**

```
structured_data['pricing']['extra_payments'] = [
  {"paid_at": "2026-08-19T10:16", "amount": 94900, "external_id": "<productOrderId>",
   "external_order_no": "<orderId>", "product": "<상품명>", "recorded_by": <user_id>,
   "recorded_at": "<UTC naive>"}
]
```

- **출고가·잔금·계약금을 자동으로 바꾸지 않는다.** 출고가=품목+배송−할인, 잔금=출고가−예약금
  이라는 기존 정의를 건드리지 않는다(규격 W ↔ 출고가 결합 계산에 손대면 다른 숫자까지 틀어진다).
- 편집기·도크에서 "추가결제 N건 · 합계 M원"으로 **보여만 준다**. 반영은 사람이 판단해서 한다.
- `structured_data` 수정은 프로젝트 규칙대로 `deepcopy` + `flag_modified` 로 한다.
- append-only. 잘못 붙였으면 attach 되돌리기(§5)로 항목까지 같이 걷어낸다.

### 3.4 발주확인 — 읽기 (선행, 무위험)

- `mapping` 에 `extract_place_status(detail)` 추가 → `placeOrderStatus` 를 뽑아
  `summarize_snapshot` 결과와 도크·이력·확인 큐에 싣는다.
- 값 표기: `NOT_YET` = "발주확인 전", `OK` 계열 = "발주확인 완료"(실제 코드값은 실물 표본으로 고정).
- 관리 목록에 필터 1개 추가: **발주확인 전**.
- 네이버 호출 0회 — 이미 받아둔 `raw_snapshot` 만 읽는다. 과거 수집분도 즉시 보인다.

### 3.5 발주확인·발송처리 — 쓰기 (WORKER 단일 출구)

**선행 게이트 — 권한 확인이 통과해야 이 절을 시작한다(2026-08-19 사용자 확정 순서).**
확인 절차는 §7. 결과가 "권한 없음"이면 3.5는 통째로 보류하고 3.4(읽기)까지만 간다.

- 클라이언트에 쓰기 2개 추가:
  - 발주확인: 커머스API "발주 확인 처리" (정확 경로는 apicenter 문서로 확정)
  - 발송처리: `POST /external/v1/pay-order/seller/product-orders/dispatch`
    (`dispatchProductOrders[]`, `deliveryMethod`, `dispatchDate` = ISO8601 밀리초+TZ)
- **웹은 절대 직접 호출하지 않는다.** '지금 수집'과 같은 패턴으로 rq enqueue → WORKER 실행
  (IP 3슬롯 계약, SPEC-01 §3.1). 결과는 링크에 기록하고 화면은 폴링 없이 다음 로드에 반영.
- 멱등: 링크별 `fulfillment_state`(JSONB) 에 `place_confirmed_at` / `dispatched_at` 기록.
  이미 값이 있으면 재호출하지 않는다(네이버 400 을 정상 흐름으로 삼지 않는다).
- 실패는 사유 문장을 남기고 화면에 그대로 보여준다(조용한 실패 금지).
- 버튼 노출 규칙(사용자 확정 규칙 반영):
  - `relation=NEW` → 주문 생성 후에만 **발주확인** 버튼
  - `relation=ADDON` → 사람이 확인 완료한 뒤 **발송처리** 버튼
  - `REPAY` → 신규와 같게(발주확인)

## 4. Task 분해 (원장 T16 계열)

| Task | 내용 | 의존 | 완료 기준 |
|---|---|---|---|
| T16-A | `placeOrderStatus` 읽기 표시 + '발주확인 전' 필터 | — | 스테이징 실데이터에서 상태 표기·필터 동작, 네이버 호출 0회 |
| T16-B | `relation` 컬럼 + 마이그레이션(왕복) | — | `alembic upgrade/downgrade` 왕복 green, 단일 head |
| T16-C | 기존 주문 후보 조회(전화·이름·주소, 180일·5건) | T16-B | 단위 테스트: 전화 일치·대리주문·무관 주문 제외 |
| T16-D | 확인 큐/도크에 후보 표시 + "이 주문에 붙이기" | T16-C | 스테이징에서 실제 차액 건을 기존 주문에 붙여 눈 확인 |
| T16-E | attach 라우트 + 감사·멱등·취소 가드 | T16-B | 계약 테스트(멱등·blocking 차단·권한·감사 이벤트) |
| T16-F | 추가결제 `extra_payments` 기록 + 화면 표시 | T16-E | 기록만 되고 출고가·잔금 계산 회귀 0(계약 테스트), 되돌리기 시 항목도 제거 |
| T16-G | 발주확인·발송처리 클라이언트 + WORKER enqueue | **§7 권한 게이트 통과** | 스텁 테스트 + 스테이징 실호출 1건 성공, 멱등 재클릭 무해 |
| T16-H | 버튼 노출 규칙·상태 표시 | T16-G | 신규/추가결제별 버튼이 규칙대로만 뜬다 |

T16-A·B·C·D·E 는 네이버에 **쓰지 않는다** — 권한 확인 없이도 진행 가능.

## 5. 위험

- **잘못 붙이면 남의 주문에 금액이 섞인다.** 그래서 자동 확정 금지 + 감사 이벤트 필수.
- **발송처리 오발사**: 실제로 안 나간 물건을 발송처리하면 정산·클레임 문제. 버튼은 확인 완료
  이후에만, 그리고 한 번 누르면 상태를 남겨 재호출을 막는다.
- **IP 슬롯**: 쓰기도 WORKER에서만. 웹에서 호출하면 운영 IP 화이트리스트가 깨진다.
- **relation 오분류 후 되돌리기**: attach 는 되돌릴 수 있어야 한다(`relation` 재설정 + `order_id`
  NULL 복귀). T16-E 에 포함.

## 6. 확정·미확정

**확정 (2026-08-19 사용자)**
- Q1 추가결제 금액 = **기록만**(§3.3). 출고가·잔금 자동 변경 없음.
- 진행 순서 = **권한 확인 → 필요 시 스펙 수정 → 계획서 검토 → 구현**.

**미확정 (남은 1개)**
- **Q3. 재결제(REPAY) 시 원 주문의 취소를 어떻게 남기나?** 현행 원칙은 "주문 상태 자동 변경
  없음, 이력·알림만"이다(claim_watch). REPAY 도 같게 갈지, 이때만 원 주문에 취소 배지를
  고정할지. 실제 재결제 건이 나오면 그 화면을 보고 정하는 게 정확하다 — T16-D 시점으로 미룬다.

## 7. 권한 확인 절차 (선행 게이트, 2026-08-19 사용자 지시)

### 7.1 사람이 보는 화면 (1분)

1. https://apicenter.commerce.naver.com 로그인 → **애플리케이션 관리** → FOMS 수집용 앱 선택.
2. 그 앱에 붙어 있는 **API 그룹(권한) 목록**을 본다. 앱 등록 때 그룹을 고르게 돼 있고,
   그룹이 빠져 있으면 그 API 는 호출 자체가 막힌다.
3. 확인할 것: **주문/배송(판매관리) 계열 그룹**이 붙어 있는가.
   - 붙어 있음 → §3.5 진행 가능(T16-G).
   - 없음 → 그룹 추가 후 재발급 필요 여부까지 확인. 추가가 안 되면 §3.5 폐기, §3.4 만.
4. 같은 화면에서 **만료일**도 같이 메모한다(스테이징 `NAVER_COMMERCE_APP_EXPIRES_ON` 미등록
   상태라 D-7 경고가 안 나간다 — 2026-08-19 확인).

### 7.2 코드로 확인 (무변경 프로브, 선택)

사람 눈 확인이 애매하면 **아무것도 바꾸지 않는 프로브**로 판정한다.

- 존재하지 않는 상품주문번호(예: `00000000000000`)로 발송처리 API 를 1회 호출한다.
  - 응답이 **권한 오류** → 앱에 발송 권한이 없다.
  - 응답이 **상품주문번호 오류/처리권한 없는 번호** → 권한은 있고 대상만 없는 것 → 진행 가능.
- **반드시 WORKER 에서 실행한다.** 로컬 PC IP 는 네이버 화이트리스트(3슬롯)에 없어 결과가
  IP 거부로 오염된다. 실행 수단은 스테이징(FOMS-DEV) WORKER 일회성 명령.
- 실제 주문번호로는 절대 시험하지 않는다(발송처리 오발사 = 정산·클레임 사고).

### 7.3 배송방법 코드

권한이 있으면 이어서 확인한다: 택배사·송장이 없는 **자사 직접배송**을 `deliveryMethod` 의
어떤 코드로 넣는지(직접전달/방문수령 계열). 코드가 확정돼야 T16-G 를 설계대로 짤 수 있다.
