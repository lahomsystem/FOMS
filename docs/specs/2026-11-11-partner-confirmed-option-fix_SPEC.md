# 협력사 명세서 — 확정한 옵션 고치기 (2026-11-11)

상태: 2026-11-11 사용자 승인(기본값 그대로) · 구현
선행 설계서: `docs/specs/2026-11-03-partner-statement_SPEC.md`(§5.3 도면팀 옵션 확인 · §5.5 명세서)

## 1. 왜

협력사가 옵션을 틀리게 고르고(예: 도면에 없는 서랍을 고름, 수를 틀림, 있어야 할 옵션을 빠뜨림) 도면 확인에서
"이대로 만들어 주세요"를 누르면, 그 값이 확정본(`order_item_options` CONFIRMED)으로 굳는다. 명세서는 확정본으로만 계산한다.

지금 확정 뒤에 할 수 있는 것은 CS 의 "단가 고치기"뿐이다.

- 필요 없는 옵션: 단가를 0 으로 바꾸고 이유를 적는 우회만 된다. 줄은 남는다.
- 수가 틀린 옵션: 수를 못 바꾼다.
- 빠진 옵션: 넣을 길이 없다.
- 발행한 뒤: 수정본은 "다시 계산"이 막혀 있어(`recalc_draft`, `foms/services/partners/statements.py:183`) 단가만 고친다.

옵션(무엇을 만드는가)과 명세서(얼마인가)가 따로 놀면 협력사 화면의 옵션 칸 · 도면팀 화면 · 명세서가 서로 다른 말을 한다.
그래서 명세서 줄을 손으로 고치지 않고, **확정본 옵션을 고치면 명세서가 다시 계산되게** 한다. 금액은 지금처럼 계산 함수
하나(`calc_item`)가 낸다(선행 설계서 "사람은 숫자를 계산하지 않는다").

## 2. 무엇을 바꾸나

### 2.1 명세서 화면에 "옵션 고치기"
- 우리 CS 명세서 한 장(`/erp/partner-statements/<id>`)의 제품 묶음 머리마다 "옵션 고치기" 단추. 초안(DRAFT)일 때만 보인다
  (수정본 초안 포함). 발행본은 지금처럼 "수정본 만들기"를 먼저 누른다.
- 누르면 그 묶음 표 자리에 확정 옵션 고치기 칸이 열린다(왼쪽 도면은 그대로 보인다). 고르기 부품은 도면팀 전달 창 · CS 옵션 채우기와 같은 것
  (이름 · 수 · 위치 · 지우기 · 커스텀 · 옵션 없음). "상담 후 정함"은 고를 수 없다(이미 확정된 주문).
- 확정본과 달라진 품목은 **바꾼 이유 한 줄이 꼭 있어야** 저장된다. 이유는 협력사에게 보인다.
- 저장하면 같은 트랜잭션에서 명세서 초안을 다시 계산하고(CS 가 넣은 커스텀 금액 · 고친 단가는 지금처럼 같은 줄에 다시 붙음),
  화면이 새 줄로 바뀐다.
- 새 JS 파일 하나(`static/js/cs/partner-statement-options.js`, 300줄 래칫 안). 지금 `partner-statement-edit.js` 는 287줄이라
  단추 자리 · 다시 그리기 연결만 몇 줄 더한다.

### 2.2 쓰기 규칙 (서버)
- API: `GET/POST /api/partner-statements/<id>/options`(정책 `PARTNER_STATEMENT` — 명세서 고치기와 같은 사람: CS 팀 + ADMIN).
- 고치는 값: 그 품목의 `CURRENT` 와 `CONFIRMED` 를 같은 값으로. `PARTNER`(협력사가 처음 고른 원문)는 그대로 둔다 — 그래야
  "처음 고른 것 → 지금" 차이가 남는다.
- `changes`(바뀐 줄과 이유): 원문 대비 차이를 새로 내되, 앞서 도면팀이 고친 줄 중 그대로인 것은 그 이유를 그대로 두고,
  이번에 바뀐 줄에만 새 이유를 붙인다.
- 품목 JSON `option_detail` 요약 글도 새 값으로(deepcopy → 수정 → 재대입 → `flag_modified`).
- 검사는 기존 `clean_item_options` 그대로(단가표에 없는 옵션 · 고를 수 없는 옵션 · 수 1~999).
- 제품(단가표 기본 제품 `base_key`)은 바꾸지 않는다 — 이번 범위는 옵션만.
- 초안 버전 검사(`version`)를 지금처럼 해서 두 사람이 동시에 고치면 뒤 사람이 409 를 받는다. 주문 줄 잠금(`lock_order_row`).
- 감사 기록 `PARTNER_OPTIONS_CORRECTED`: 명세서 id · 품목 · 바뀐 줄 · 이유 · 고치기 전/후 지문.

### 2.3 수정본도 다시 계산
- 수정본 초안은 지금 "다시 계산" 이 막혀 있다. 옵션 고치기로 바뀐 경우에 한해 수정본도 다시 계산한다(같은 줄의 고친 단가 ·
  커스텀 금액은 이어 붙음). 단가표 판은 지금과 같은 규칙(출고일 기준 판)이라 발행본과 같은 판을 쓴다.
- 수정본을 발행하면 지금처럼 옛 발행본은 VOID 가 된다.

### 2.4 협력사에게 보이는 것
- 주문 화면 도면 탭 "옵션" 칸: 지금은 바꾼 이유를 첫 줄 것 하나만 보여 준다. 바뀐 줄마다 그 줄의 이유를 보여 주게 고친다.
  이 칸은 지금 도면 · 확정 단계에서만 보인다 → 최종 도면이 있으면 생산 뒤에도 읽기로 보이게 한다(안내 글은 확정 뒤엔
  "거래명세서 금액 문의로 알려 주세요").
- 명세서 줄: 옵션 줄의 계산 근거 칸이 지금 "고른 옵션" 이다. 우리가 바꾼 줄이면 "바꾼 옵션 · <이유>" 로 보인다.
- 협력사 다시 확인(재승인)은 받지 않는다(§4 결정 1 기본값). 맞지 않으면 협력사는 기존 "금액 문의"로 묻는다.

## 3. 바꾸지 않는 것
- 협력사가 옵션을 고르는 화면 · 도면 확인 흐름 · 도면팀 전달 창.
- 계산 함수(`statement_calc.calc_item`)의 금액 규칙.
- 단가 고치기(이유 필수) · 커스텀 금액 넣기 · 발행 · 취소 흐름.
- 발행본 잠금(발행본은 수정본으로만 고친다).

## 4. 결정할 것 (사용자)
1. 협력사 재승인: **받지 않음(기본 제안)** — 이유가 협력사 화면과 명세서에 보이고, 금액 문의로 되물을 수 있다.
   다른 안: 고친 뒤 협력사가 "확인했어요"를 다시 눌러야 발행 가능.
2. 협력사 알림: **따로 보내지 않음(기본 제안)** — 발행 때 가는 기존 알림으로 충분. 다른 안: 옵션을 고치면 협력사에 바로 알림.
3. 누가 고치나: **CS 팀 + ADMIN(기본 제안, 명세서 권한과 같음)**. 다른 안: 도면팀도.
