# 마법사 "안 보낸 초안" 미등록 알림 — 설계 (2026-10-26 승인·구현)

작성 2026-10-26. 앞선 설계: `docs/plans/2026-10-20-wizard-push-register-safety-spec.md` §3.2(발송한 초안 알림).

## 1. 문제

모바일 주문 마법사에서 고객 이름·연락처까지 적어 놓고 4단계 [주문 등록] 을 누르지 않은 채 화면을 떠나면
주문은 없다. 지금 알림(`foms/services/notifications/draft_send_reminder.py`)은 **알림톡·실측 PUSH 를 보낸
초안만** 챙긴다. 아무것도 보내지 않은 초안은 홈 "작성 중" 줄에만 조용히 남고, TTL(7일)이 지나면 사라진다.

## 2. 운영 실측 (2026-10-26, 읽기 전용)

남아 있는 초안 30개 중 22개는 이름이 비어 있다(마법사를 열기만 한 것). 이름이 적힌 8개:

| 초안 | 작성자 | 단계 | 고객 | 같은 고객 주문 |
|---|---|---|---|---|
| 820 | 하우드 | 1 | 강지현 | 5824 (초안보다 1시간 15분 **먼저** 등록) |
| 814 | 고애희 | 2 | 이화원 | 없음 |
| 811 | 하우드 | 1 | 김영일 | 5801 (하루 전 등록, 이 초안은 별개 건일 수도) |
| 810 | 하우드 | 2 | 최형근 | 없음 |
| 785·786·788 | 한용희 | 1~3 | 박정화 | 5792 (초안 3개 뒤 3분 안에 등록) |
| 779 | 김의종 | 1 | 조윤정 (추가건 | 이름이 달라 자동 대조 불가, 같은 날 5778 있음 |

정말로 빠진 것은 **이화원·최형근(+조윤정 추가건 가능성)** 이다. 나머지는 같은 고객을 다른 초안으로
이미 등록한 것이라, 이름만 보고 알리면 절반이 헛알림이 된다.

## 3. 결정할 것과 제안

D1. **대상** — `order_id IS NULL` 이고, 발송 이력이 없고, 고객명·연락처가 둘 다 적힌 초안.
이름만 있거나 빈 초안은 알리지 않는다(열기만 한 것과 구분이 안 된다).

D2. **이미 등록된 고객은 빼기** — 연락처 숫자만 남긴 값이 같은 주문이 초안 생성 시각 앞뒤 24시간 안에
있으면 알리지 않는다. 이름이 아니라 연락처로 대조한다(위 "조윤정 (추가건" 같은 이름 꾸밈 때문).
대신 "추가건"처럼 일부러 같은 고객의 두 번째 주문을 만들다 떠난 경우는 놓친다 — 받아들인다.

D3. **언제·누구에게** — 마지막 저장(`updated_at`) 뒤 **60분** 동안 손대지 않았으면 작성자에게 **1회**.
발송한 초안(30분·관리자 2시간)보다 느리고 약하게 한다: 고객에게 나간 것이 없어 급하지 않다.
관리자 단계는 두지 않는다. 다시 고쳐 저장하면(`updated_at` 이 알림 뒤로 바뀌면) 한 번 더 알릴 수 있다.

D4. **문구** — 제목 "주문 등록이 안 됐어요", 본문
"{고객} 고객 주문을 적다가 등록하지 않고 나갔어요. 홈 화면 '작성 중' 줄에서 이어서 등록하거나 지워 주세요."
알림 종류는 따로 둔다(`DRAFT_NOT_REGISTERED`) — 발송한 초안 알림과 통계·끄기를 나눌 수 있게.

D5. **알렸다는 표시** — 기존과 같이 `OrderDraft.send_history` 에 별도 키(`draft_idle_reminder`)로
`{owner_at, for_updated_at}` 를 남긴다. 발송 종류 키가 아니므로 "발송함" 판정·등록 승계에 섞이지 않는다.
구현 때 확인한 결과 `has_send_history_clause()` 와 정리 cron(`tools/cron/cleanup_order_drafts.py`)은 열이
비었는지만 봤다 — 그대로 두면 표시만 있는 초안이 "발송함"으로 잡혀 만료돼도 안 지워지고 '작성 중' 목록에
영원히 남는다. 그래서 두 판정을 **발송 종류 키(`alimtalk_measurement`·`channeltalk_push_measure_room`)가
있는가**로 좁혔다(cron 은 앱을 import 하지 않으므로 키 이름을 다시 적고, 테스트가 둘을 맞춘다).
운영 PostgreSQL 에서 옛 판정·새 판정 결과가 같음을 읽기 전용으로 확인했다(지금은 둘 다 0건).

D6. **도는 자리** — 기존 `scripts/maintenance/run_notification_escalation.py` 스윕에 함수 하나를 더 건다
(새 cron 없음). 배달(배지·실시간·웹푸시)도 그 스크립트가 커밋 뒤 맡는 기존 방식 그대로.

## 4. 만들 것

- `foms/services/notifications/draft_send_reminder.py` 옆에 `remind_idle_unsent_drafts(db, now=None)`.
- 연락처 대조용 쿼리 1개(주문 `phone` 숫자 정규화 비교, 대상 초안이 몇 개 안 되므로 초안별 조회로 충분).
- 스윕 스크립트에 호출 추가(`_idle_draft_reminder_once` — 발송 초안 스윕이 실패해도 따로 돈다).
- 스윕 부하를 묶으려고 마지막 저장이 **24시간 안**인 초안만 본다. 그래서 배포 순간 옛 초안에 알림이 몰리지 않는다.
- 폰 알림 종류 목록(`push_sender._DEFAULT_P1_TYPES`)에 `DRAFT_NOT_REGISTERED` 추가(운영에 덮어쓰는 env 없음 확인).
- 테스트: ① 이름+연락처 초안 60분 뒤 1회 ② 60분 전 안 함 ③ 같은 연락처 주문 있으면 안 함
  ④ 이름만 있으면 안 함 ⑤ 발송한 초안은 이 함수가 건드리지 않음 ⑥ 알린 뒤 다시 저장하면 다시 알림
  ⑦ 발송 판정(`has_send_history_clause`·관리자 '발송 후 미등록' 화면)에 새 키가 섞이지 않음.

## 5. 범위 밖

- 이름 빈 초안 22개 정리(열기만 하면 초안이 생기는 구조) — 따로 다룬다.
- 홈 "작성 중" 줄 화면 변경 없음.
