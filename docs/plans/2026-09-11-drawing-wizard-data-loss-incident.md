# 사고 기록 — 주문 폼 저장 1회가 도면 마법사 캔버스를 통째로 지웠다

- 발생: 2026-09-10 07:56:39 UTC (주문 5177), 2026-09-08 23:19~23:28 UTC (주문 5193)
- 발견: 2026-09-11, 도면 담당자가 "마법사에 들어가면 백지가 뜬다"고 보고
- 영향: 도면 마법사로 도면을 만든 운영 주문 **전부**(2건). 둘 다 복구 완료
- 수정: production `5564994a6`(근본) · `93c85b113`(후속, PR #353)

## 무슨 일이 일어났나

영업 담당자의 **ERP 주문 폼 전체 저장** 한 번이 `structured_data['drawing_wizard']` 를
통째로 삭제했다. 시트의 `objects`(손그림)와 서버 소유 키 `pending`·`versions` 가 함께
사라졌고, 감사 원장에는 **`change_count: 0`("변경 0건")** 으로 기록됐다.

16시간 뒤 도면 담당자가 마법사를 열자 GET 이 `state=null` 을 줬고, 클라이언트는 빈 상태로
초기화한 뒤 제품 클릭으로 새 시트를 만들었다. 그 새 시트가 저장되며 사라진 자리를 덮었다.

**널리 퍼진 오해를 먼저 정정한다**: 마법사의 자동 저장이 그림을 덮어쓴 것이 아니다.
자동 저장이 일어났을 때는 이미 16시간 전에 데이터가 없었다. 조사 초기 한 갈래가
"45초 자동저장이 범인"이라고 판정했고 시각 일치(`00:00:09.4 + 45.0 = 00:00:54.4`)까지
제시했지만, 그것은 **빈 자리에 새로 쓴 것**이었다.

## 근본 원인

`_OPERATIONAL_TOP_LEVEL_KEYS`(`foms/api/erp_orders_structured.py`)에 `drawing_wizard` 만
빠져 있었다. 폼은 이 키를 렌더하지도 보내지도 않는다. 그리고
`enforce_form_allowlist`(`foms/services/orders/structured_form_projection.py`)는
**들어온 낯선 키를 걷어낼 뿐 빠진 옛 키를 되살리지 않는다.**

즉 구조가 이랬다 — **보존 목록에 이름을 적어야만 살아남는다.** 적는 것을 잊으면 조용히
사라지고, 폼이 애초에 안 보낸 키라 strip 목록에도 안 남아 **경고 로그조차 없었다.**

이 저장소에서 같은 자리·같은 방식으로 사라진 것이 이번이 **여섯 번째**다:
`source` · `naver` · `pricing` · `alimtalk_measurement` · `schedule.as_visit` · `drawing_wizard`.

## 기존 방어가 못 막은 이유

마법사 PUT 은 방어가 촘촘했다 — REV-00 행 잠금, `base_updated_at` stale 409,
`_project_wizard_state` 화이트리스트. **셋 다 마법사 PUT 만 지키고 있었고, 데이터를 죽인
것은 다른 라우트(주문 폼 저장)였다.**

특히 stale 가드는 구조적으로 못 잡았다:
`if isinstance(saved, dict) and saved.get('updated_at') != ...` — 키가 삭제되면
`saved is None` 이라 **검사를 통째로 건너뛴다.** 상태가 사라진 직후의 첫 저장은
`base_updated_at` 이 무엇이든 무조건 200 이었다.

## 무엇을 고쳤나

**1. 기본값을 뒤집었다 (근본)** — `preserve_non_form_keys()` 신설.
폼이 안 보낸 비-폼 최상위 키는 **기본으로 보존**된다. `enforce_form_allowlist` 의
대칭짝이다: 저쪽은 "클라가 새 키를 못 만들게", 이쪽은 "클라가 남의 키를 못 지우게".
이름을 하나 더 적는 대신 규칙을 바꿨으므로, 앞으로 새 서버 소유 키가 생겨도 등재를
잊어서 데이터가 사라지지 않는다. 의도적으로 제거하는 키만 `SERVER_OWNED_REMOVABLE_KEYS`
에 예외 등재했고(현재 `as_lifecycle` 하나), 복원이 일어나면 `[DATA-01]` 경고를 남긴다.

**2. 상태 소실 뒤 첫 저장을 막는다** — 409 `conflict_reason='vanished'`.
`base_updated_at` 이 있는데 서버 상태가 없으면 = 클라가 있던 상태 위에서 편집 중이었다는
뜻이므로 덮어쓰지 않는다. `base_updated_at` 이 없는 진짜 최초 저장은 통과시킨다.

**3. 못 불러온 상태를 쓰지 않는다** — 클라이언트 `hydrated` 게이트.
load 가 200 으로 렌더까지 마쳐야 저장이 나간다. **로드 성공 여부로만** 판정하므로
"사용자가 다 지웠다"는 정당한 편집을 막지 않는다. 내용 기반 휴리스틱은 쓰지 않았다 —
서버는 "못 불러온 것"과 "지운 것"을 원리적으로 구분할 수 없다.

**4. 사용자가 안 한 변경은 자동 저장하지 않는다** — `userDirty`.
`drew` 동기화·`page_no` 자동 채움처럼 load 가 만드는 변경이 자동 저장으로 서버에 써지던
경로를 끊었다.

**5. 자동 저장이 실패하면 멈추고 계속 보이게 한다**(후속).
아래 "함께 드러난 것" 참조.

**6. 감사에 규모를 남긴다** — `auto`·`sheets_before`·`objects_before`·`sheets`·`objects`.
이번 조사는 이 값이 없어 "SHEET_SAVED 감사행 부재 + 45초 정각 일치"라는 정황 추론에
기댔다. 다음 사고는 감사 한 행으로 "몇 장 몇 개에서 몇 개가 됐는지"가 읽힌다.

## 복구

전달 시점에 `snapshot_and_clear_pending` 이 시트 전체(`objects` 포함)를 R2 에 JSON 으로
올려 둔다: `orders/<id>/drawing_wizard/versions/v*_<sheet_id>.json`.
이번에 사라진 것은 파일이 아니라 **그 파일을 가리키던 포인터 목록**이었고, 접두사로 찾을
수 있어 포인터 없이도 복구됐다.

- 주문 5177: 시트 2장 복구(objects 13·6). 09-10 00:04 전달 시점까지. 그 뒤 00:06·00:15
  보완 저장분은 스냅샷이 없어 못 살렸다.
- 주문 5193: 시트 1장 복구(objects 9). 09-08 07:32 스냅샷까지. 07:34~07:35 편집분 제외.

두 건 모두 복구 전 상태를 파일로 백업한 뒤 `deepcopy` → 수정 → 재대입 패턴으로 썼다.

**전수 확인**: 운영에서 마법사 export 흔적(`/drawing_wizard/exports/`)을 가진 주문은 2건뿐이고
둘 다 피해자였다. 즉 **이 기능을 쓴 주문은 100% 당했다.** 다른 피해는 없다.

## 함께 드러난 것 — 자동 저장이 실패를 숨긴다

5193 감사 원장을 읽다가 별개 문제가 나왔다. 2026-09-08 05:35~07:21, 도면 담당자와 영업
담당자의 마법사 저장이 **CSRF 403 으로 80여 회 연속 차단**됐다. 두 사람이 2시간 가까이
도면을 그리는 동안이다.

```
요청 차단(write-guard): PUT /api/orders/5193/drawing-wizard
  guard=csrf-origin reason=invalid_csrf_token
```

CSRF 자체의 원인(탭 여러 개가 세션 CSRF seed 를 지우던 것)은 `d25ded59b` 로 **2026-09-09
운영 반영**돼 이미 해결됐다. 일자별 차단 수가 이를 보여준다 — 09-08 **95건** → 09-09 8건
→ 09-10 2건 → 수정 이후 마법사 저장 **0건**.

그러나 **증폭기는 남아 있었다**: 자동 저장이 실패해도 `dirty` 를 유지한 채 45초마다 같은
요청을 반복했고, 충돌 경고 토스트는 첫 1회뿐이며 그마저 5초 뒤 사라진다. 그래서 두 사람은
저장되고 있다고 믿었다.

고친 것: 자동 저장이 실패하면(409·403·5xx 무관) **멈추고**, 사라지지 않는 배너로
"자동 저장이 멈췄습니다 / 지금 그리는 내용은 저장되지 않고 있습니다" 를 사유와 함께 띄운다.
재개는 "지금 서버와 맞다"가 확인된 시점에만 한다 — 사람이 저장 버튼을 눌러 성공했거나
재로드가 성공했을 때.

## 다음 사람을 위한 교훈

1. **보존 목록은 안전장치가 아니다.** 사람이 등재를 잊으면 조용히 데이터가 사라진다.
   기본값을 "보존"으로 두고 삭제를 예외로 등재하라. 방향이 반대면 여섯 번째 사고가 난다.
2. **감사 원장에 "변경 0건"이 찍혔다고 아무 일도 안 일어난 게 아니다.** diff 가 폼 필드만
   보면 폼 밖에서 사라진 것은 세지 못한다.
3. **`log_access()` 는 이름과 달리 `security_logs` 에 쓴다.** `access_logs` 만 뒤지면
   이 사건은 통째로 안 보인다(실제로 조사 초기에 그렇게 헛짚었다).
4. **조용한 무한 재시도는 원인만큼 해롭다.** 원인은 하루 만에 고쳐졌지만 증폭기가 남아
   2시간짜리 작업 손실을 만들었다. 실패는 멈추고, 사라지지 않게 알려라.
5. **정황 일치는 증거가 아니다.** "45초 간격이 소수점까지 맞는다"는 강력해 보였지만
   틀렸다. `structured_updated_at` 같은 **독립 축**이 판정을 뒤집었다.
