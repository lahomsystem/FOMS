# 감사 로그 보관 기간 정량 분석 (2026-08-07)

> **질문**: 실 업계 표준 보관 기간은? 오래 보관 시 부담은 얼마나 되나?
> **한 줄 결론**: **스토리지 부담은 사실상 0**(10년 최악 시나리오도 월 $1.11). 보관 기간을
> 제약하는 것은 용량이 아니라 ① `security_logs`의 **timestamp 인덱스 부재로 인한 Seq Scan**,
> ② **로그 본문에 섞인 고객 개인정보**(파기 의무와 충돌)다. 두 가지를 먼저 손보면
> "오래 보관"이 안전하게 가능하다.

## 5. 진짜 부담 ① — 쿼리 성능 (여기가 임계점이다)

### 5-1. 실측: 감사 화면은 지금 **전체 Seq Scan**을 돈다

`EXPLAIN (ANALYZE, BUFFERS)` 실측 (`foms/web/admin/audit.py` 목록 쿼리 형태):

```
Limit (actual time=8.090..8.101 rows=50)
  -> Sort (Sort Key: "timestamp" DESC, top-N heapsort)
       -> Seq Scan on security_logs (actual time=0.016..4.292 rows=24572)
            Buffers: shared hit=1492          ← 매 페이지 로드마다 11.7 MB 전량 스캔
Execution Time: 8.142 ms
```

페이지네이션 `count(*)`도 별도 Seq Scan (4.4 ms, `shared hit=1492`). **합계 약 12.5 ms.**

**근본 원인**: `security_logs`에 **`timestamp` 인덱스가 없다.** 실측 인덱스 목록은
`security_logs_pkey`(0.87 MB) + `ix_security_logs_message_trgm`(8.08 MB) 둘뿐이고,
`pg_stat_user_indexes` 기준 **둘 다 `idx_scan = 0`** — 한 번도 쓰이지 않았다.
T8이 추가하는 `ix_security_logs_target(target_type, target_id, timestamp)`도
**대상 필터 없는 `ORDER BY timestamp DESC`에는 쓸 수 없다.** 즉 승격해도 이 구멍은 남는다.

### 5-2. 임계점 (실측 8.09 ms를 선형 외삽)

| **250,000** | 119 MB | 82 ms | 44 ms | **127 ms** | **주의 구간 시작** |
| **269,830** | **128 MB** | — | — | — | **`shared_buffers` 초과 → 디스크 read 전환** |
| 500,000 | 237 MB | 165 ms | 89 ms | 254 ms | 디스크 read (Railway 네트워크 볼륨 = 실제로는 5~20배 더 느림) |
| 1,000,000 | 474 MB | 329 ms | 178 ms | 507 ms | 명백한 지연 |
| 5,000,000 | 2.3 GB | 1,646 ms | 889 ms | 2,535 ms | 사용 불가 |

**임계 행수 = 약 27만 행** (heap이 `shared_buffers` 128 MB를 넘어 캐시에서 밀려나는 지점).
표의 ms는 전부 `shared hit`(메모리) 기준이라, 이 지점을 넘으면 표보다 **훨씬 더** 나빠진다.

| 시나리오 | 27만 행 도달까지 |
|---|---|
| S1 (95/일) | **7.1년** |
| S2 (190/일) | **3.5년** |
| S3 (475/일) | **1.4년** |

### 5-3. 그런데 이 임계점은 **인덱스 하나로 사라진다**

`CREATE INDEX ix_security_logs_timestamp ON security_logs (timestamp DESC);`

- 목록 쿼리가 Seq Scan → Index Scan + LIMIT 50이 되어 **행 수와 무관하게 O(log n)**.
  1,000만 행에서도 1 ms 미만.
- **T9 purge 잡도 이 인덱스가 필요하다.** `purge_audit_logs.py`는
  `WHERE timestamp < cutoff ORDER BY ... LIMIT batch`로 지우는데, 인덱스가 없으면
  **매일 밤 전체 테이블을 Seq Scan** 한다. 비교로 `access_logs`에는 이미
  `ix_access_logs_timestamp`가 마이그레이션(`access_log_00`)으로 준비돼 있고
  주석에 "T9 retention purge의 keyset 스캔"이라고 목적까지 적혀 있다 —
  **`security_logs`만 빠졌다.**
- 비용: 행당 약 36 B → 27만 행에서 9.7 MB, 100만 행에서 36 MB. 무시 가능.
- 남는 것은 `count(*)` 한 건. keyset 페이지네이션이나 근사 카운트로 바꾸면 이것도 사라진다.

> **결론**: 성능은 보존기간의 함수가 아니라 **인덱스 유무의 함수**다. 인덱스를 넣으면
> 10년 보관이 1년 보관과 성능이 같다.

### 5-4. 파티셔닝이 필요해지는 시점 — **이 사업 규모에선 오지 않는다**

PostgreSQL 네이티브 range 파티셔닝의 실익이 나오는 통상 기준은 **단일 테이블 1,000만 행
또는 5~10 GB**, 그리고 대량 삭제를 `DROP PARTITION`(O(1))으로 바꿔야 할 때다.

| 시나리오 | `security_logs` 1,000만 행 도달 |
|---|---|
| S1 (95/일) | **288년** |
| S2 (190/일) | 144년 |
| S3 (475/일) | **58년** |

또 T9 purge는 keyset 배치 삭제라, 1년치를 지워도 S1 기준 **3.5만 행**에 불과하다 —
파티션 DROP이 필요한 규모가 아니다. **파티셔닝은 계획에서 빼도 된다.**
(단서: `channel_delivery_logs`가 재가동되고 행당 1.4 KB × 대량 발송으로 가면 재검토.)

### 5-5. 백업 부담

DB 전체 94 MB. S3 10년 후에도 7.43 GB. `pg_dump` 기준 현재는 초 단위, 7 GB에서도 분 단위다.
Railway는 볼륨 스냅샷 방식이라 시간은 더 짧다. **백업은 어떤 보존기간에서도 제약이 아니다.**
(Railway 백업 보관 개수·과금은 **미확인**.)

### 7-1-2. 접속기록의 법정 정의와 필수 항목

고시 제2조 제3호: "접속기록"이란 개인정보처리시스템에 접속하는 자가 수행한 업무내역에 대하여
**식별자, 접속일시, 접속지 정보, 처리한 정보주체 정보, 수행업무** 등을 전자적으로 기록한 것.

| # | 항목 | 내용 | FOMS `access_logs` 대응 |
|---|---|---|---|
| ① | 식별자 | 접속자 ID | `user_id` ✅ |
| ② | 접속 일시 | 년-월-일 시:분:초 | `timestamp` ✅ |
| ③ | 접속지 정보 | 단말기 정보 또는 IP | `ip_address`·`user_agent` ✅ |
| ④ | **처리한 정보주체 정보** | 누구의 개인정보를 처리했는지 식별정보 | `additional_data` — **T6 설계 확인 필요** |
| ⑤ | 수행 업무 | 검색·열람·조회·입력·수정·삭제·출력·다운로드 | `action` ✅ |

> 📌 **PIPC 안내서(2024.10) 원문**: "처리한 정보주체 정보와 관련된 사항에는 **민감하거나
> 과도한 개인정보가 저장되지 않게** 하여야 하며, 필요시 이 기준에 따라 암호화해야 한다."
>
> — 이것이 **8-3의 PII 분리 설계를 법이 직접 지지하는 근거**다. 감사로그에는 "누구의 정보를

> 전화번호·주소 원문이 들어가 있는 것은 이 지침과 어긋난다.

### 8-3. PII 분리로 보존기간을 더 늘리고 싶다면 (선택)

개인정보보호법 제21조는 "다른 법령에 따라 보존해야 하는 경우 **다른 개인정보와 분리하여
저장·관리**"를 요구한다(미이행 시 과태료 1천만원 이하). 이 구조를 만들면 감사 추적성은
영구히 남기고 PII만 파기할 수 있다.

**이 설계는 법이 직접 지지한다.** PIPC 「개인정보의 안전성 확보조치 기준」 안내서(2024.10)는
접속기록의 "처리한 정보주체 정보"에 대해 **"민감하거나 과도한 개인정보가 저장되지 않게
하여야 하며, 필요시 암호화해야 한다"**고 명시한다 — 즉 감사로그에는 **식별자만** 넣고
PII 원문은 넣지 말라는 것이 원래 요구사항이다. 현재 `security_logs.message`에 전화번호(12.6 %)와
주소(11.8 %) 원문이 들어가 있는 것은 보존기간 문제 이전에 **이 지침과 어긋난 상태**다.

- `security_logs`: T8 구조화 컬럼(`action`/`target_type`/`target_id`/`detail`)이 이미
  설계돼 있다. **자유 텍스트 `message`에 값 원문을 넣지 말고 `detail` JSONB에 넣은 뒤,
  보존기간 경과 시 `detail`만 NULL로 만들고 행은 남긴다.** 그러면 "누가 언제 무엇을 했다"는
  영구 보존, "그 값이 무엇이었나"만 파기된다.
- `order_events`: 동일 패턴. `payload`의 `from`/`to`만 마스킹.
- 이렇게 하면 `security_logs`·`order_events` **무제한 보관이 법적으로 성립**하고,
  용량은 오히려 줄어든다(마스킹된 행이 더 짧다).
- 부수 효과: `ix_security_logs_message_trgm`(현재 8.08 MB, 감사 인덱스의 90 %)에 대한
  의존이 사라진다. 실측 `idx_scan = 0` — **한 번도 쓰인 적 없는 인덱스**다. 구조화 필터로
  전환하면 이 인덱스를 통째로 drop할 수 있다.

## 9. 요약 — 질문에 대한 직답

**Q. 실 업계 표준 보관 기간은?**
**숫자를 못박은 국제 기준은 PCI-DSS(12개월)와 HIPAA(6년)뿐이다.** ISO 27002 8.15,
SOC 2, NIST AU-11은 전부 "조직이 정하라"다("ISO가 12개월을 요구한다"는 흔한 말은 사실이 아니다).
실제 제품 기본값은 오히려 짧다 — AWS CloudTrail 90일, Salesforce 180일, GitHub 180일,
Oracle Cloud 365일(변경 불가), Datadog 15일. **기본값이 영구 보존인 제품은 하나도 없고,
장기 보관은 예외 없이 별도 티어로 분리한다.**

한국 법정 하한은 **접속기록 1년**(안전성 확보조치 기준 제8조 제1항, 5만명 초과 시 2년) +
**거래기록 5년**(전자상거래법 시행령 제6조 + 국세기본법 제85조의3② + 부가세법 제71조③) +
**CS·분쟁 3년**이다. 다만 침해 식별에 평균 194일이 걸린다는 점에서 1년은 턱걸이라
**2~3년이 실질적 안전선**이다.

**Q. 오래 보관하면 부담이 얼마나 되나?**
**스토리지 부담은 없다고 봐도 된다.** 1년 보존과 10년 보존의 차이는 **620 MB,
Railway 요금 월 $0.09**다. 최악의 5배 성장 시나리오로 10년을 무제한 보관해도 DB 전체
**7.43 GB / 월 $1.11**로, Pro 플랜 볼륨 한도(1 TB)의 0.7 %다.

**Q. 그럼 그냥 오래 보관하면 되나?**
**두 가지만 고치면 그렇다.**
1. `security_logs`에 **`timestamp` 인덱스가 없어서** 감사 화면이 전체 Seq Scan을 돈다.
   27만 행(S1 기준 7년 후)에서 캐시를 이탈해 급격히 느려진다. 인덱스 1개로 영구 해소.
2. **로그 본문에 고객 개인정보가 있다** — `security_logs` 12.6 %에 전화번호,
   `channel_delivery_logs` 30.5 %에 전화번호. 개인정보보호법 제21조 파기 의무 때문에
   **이 두 테이블만은 무제한 보관이 법적으로 안전하지 않다.** 8-3의 PII 분리를 하면
   이 제약도 사라진다.

**권고 요약**: `security_logs` 3년 · `access_logs` 2년 · `order_events` 무제한(+5년 후 PII 마스킹) ·
`channel_delivery_logs` 3년(마스킹 수정 후) · `notification_events` 1년.
**파티셔닝은 필요 없다** (도달까지 58~288년).

**보존기간과 별개로 지금 처리해야 할 것 4가지** (전부 실측·조문 근거 있음)
1. `order_events`의 `ON DELETE CASCADE` 제거(T9 승격) — **안 하면 보존기간 설정 자체가 무의미**
2. `ix_security_logs_timestamp` 인덱스 추가 — 감사 화면 + purge 잡 둘 다의 전제
3. `channel_delivery_logs.masked_request_payload`의 전화번호 마스킹 결함(실측 30.6 %)
4. 고시 개정 대응 — 접속기록 대상 확대 + 점검 주기 내부 관리계획 명문화 (이미 시행 중이거나 3개월 내)
