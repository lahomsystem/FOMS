## 무엇이 문제인가 (운영 실사용 1회차, 2026-08-31)

사용자가 버튼을 누르고 새로고침했더니 **띠가 통째로 사라졌다.** 발송이 됐는지 안 됐는지
화면으로는 알 수 없었다.

동작 자체는 정상이었다 — 발송된 집은 `dispatch_pending_clause` 에서 빠지므로
`select_targets` 가 0집을 돌려주고, 띠는 `{% if bulk_dispatch.count %}` 로 사라진다.
실제로도 **6집 26건 전부 발송 성공, 실패 0**(`2026-08-31 07:45`)이었다.

**결함은 "사라짐"이 두 가지를 동시에 뜻한다는 것이다:**

1. 다 잘 나갔다
2. 애초에 대상이 없었다 / 뭔가 잘못돼 목록이 비었다

되돌릴 수 없는 조작에서 이 둘이 구분 안 되는 건 그 자체로 사고 경로다. 사람은 확인이
안 되면 판매자센터를 다시 열어보게 되고, 그러면 이 기능이 없앤 일이 되살아난다.

## 설계

### 원칙

**대상이 0이 되는 것과 "오늘 처리가 끝났다"는 다른 사실이다.** 띠를 지우지 말고
**상태를 바꾼다.**

### 화면 (양쪽 동일 — `build_preview` 가 값을 준다)

오늘 실측 네이버 건이 하나라도 있으면 띠를 **항상** 띄운다. 안의 내용이 상태에 따라 바뀐다:

| 상태 | 띠 | 예시 문구 |
|---|---|---|
| 보낼 게 남음 | 지금과 같음 + 버튼 | "오늘 실측한 네이버 건 6집 (보낼 수 있음 6집)" |
| 전부 나감 | **초록 완료 띠**, 버튼 없음 | "오늘 6집 발송처리 완료 (07:45)" + 집별 목록에 발송 시각 |
| 일부 나감 | 혼합 | "6집 중 4집 발송됨 · 2집 남음" + 버튼(남은 것만) |
| 실패 있음 | **빨간 줄** | "1집 실패 — 사유" + 재시도 안내 |
| 대상 자체가 0 | 띠 없음 | (지금과 같음 — 오늘 네이버 실측 건이 없는 날) |

핵심: **"오늘 대상이 있었는데 다 처리됐다"** 와 **"오늘 대상이 아예 없었다"** 를 화면이
구분해서 말한다.

### 서버

`select_targets` 는 지금 **발송 전** 링크만 후보로 삼는다(`_candidate_links` 가
`dispatch_pending_clause` 를 건다). 결과 UI 를 만들려면 **오늘 실측 네이버 링크 전체**를
봐야 한다.

권장 구조 — `bulk_dispatch.py` 에 `build_day_summary(session, on_date)` 신설:

- 모집단은 `_measurement_order_ids` 그대로
- 링크는 **pending 필터 없이** 전부 조회
- 집 단위로 접어서 집마다 `{sent, pending, failed}` 카운트 + 최종 발송 시각 + 실패 사유
- `build_preview` 는 이걸 감싸서 기존 키(`count`/`eligible`/`blocked`/`rows`)를 유지
  (두 화면이 이미 그 키를 읽는다 — 계약 깨지 말 것)

주의: **판매자센터 수동 발송분도 "발송됨"으로 세야 한다**(`delivery.sendDate`). 우리 표식만
보면 손으로 보낸 집이 영원히 "남음"으로 뜬다 — 화면 큐가 이미 그 실수를 하고 있다(§4.4).

### 버튼 누른 직후

지금은 `window.alert` 로 "요청했습니다" 만 말하고 사용자가 직접 새로고침한다.
개선: alert 대신 **띠 안에 진행 문구**를 띄우고, `naver-workbench.js` 의 `watchBulk`
패턴처럼 몇 초 간격으로 상태를 다시 읽어 "N집 발송 완료" 로 바꾼다.

진행 조회는 새 라우트를 파기보다 **띠 값을 그대로 주는 GET** 하나가 낫다
(`_fulfillment_progress` 는 `is_place_pending` 만 세서 발송에 못 쓴다 — §5.2).
