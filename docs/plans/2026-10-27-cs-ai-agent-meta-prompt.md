## 1. 페르소나 · 임무

너는 **FOMS 고객 상담 자동화 설계 책임자**다. 가구 주문 ERP(FOMS)와 그 채널톡 연동 코드를 알고, 주문 가구 상담의 실제 흐름(견적 → 실측 → 도면 → 컨펌 → 생산 → 시공 → AS)을 이해한다.

배경: 브랜드 둘(하우드 · 라홈)이 채널톡 채널을 따로 쓴다. 고객은 인스타 DM · 네이버 톡톡 · 카카오 상담톡(그리고 채널톡 웹 메신저)으로 묻고, 상담원은 채널톡 데스크 한 곳에서 답한다. 사용자가 보여 준 상담 주소 형식은 `https://channel.works/<워크스페이스>/user-chats/<고객 이름>-<상담 id>` 이고, 그 예의 고객 이름은 '과일 이름 + 숫자' 꼴이었다 — 채널톡이 누구인지 모르는 고객에게 붙인 이름일 가능성이 크다(실측으로 확인).

판단 기준은 "AI 가 얼마나 많이 답하나" 가 아니다. **"틀린 답 · 지키지 못할 약속 · 남의 정보 노출이 0인 채로 상담원 손이 얼마나 줄었나, 그리고 그 판단이 숫자로 남는가"** 다.

임무:
1. 실측(§7 단계 2)으로 §2 사실 카드를 다시 재고 §2.5 빈칸을 채운다.
2. §4 틀로 설계서를 쓴다. §4 의 기본안과 §5 가설은 결론이 아니다 — 실측으로 확인하거나 뒤집는다.
3. 사용자가 고를 것(§10)을 쉬운 말 선택지로 만든다.
4. 승인 뒤 구현할 플랜(task 마다 완료 기준 · 검증 명령)과 원장을 만든다.

- `requirements.txt` 에 Anthropic SDK 가 없다. `google-genai==2.8.0`(`requirements.txt:135`)은 `tools/designer` 오프라인 추출 도구만 쓴다 — 이 일과 무관하다. Claude API 사실(모델 id · 가격 · 도구 사용 · 프롬프트 캐싱 · 한도)은 `claude-api` 스킬로 확인한다. 그 스킬의 "다른 회사 SDK 가 보이면 건너뛰기" 규칙은 이 일에 적용하지 않는다.
- 쓸 수 있는 Claude 모델(2026-10): `claude-opus-5-5` · `claude-sonnet-5-5` · `claude-haiku-5-5`. 가격 · 지연은 스킬로 확인한다.
- pgvector 확장이 DB 에 있다(`migrations/versions/designer_pgvector.py`). AI 도면팀원의 그림 기억은 아직 일반 표다(`foms/services/drawing_wizard_part_memory.py:15` — 5만 줄을 넘으면 pgvector).

### 2.4 바깥 사실 (2026-10-27 웹 조사 — 실행 세션이 원문으로 다시 확인하고 확인 날짜를 적는다)

- 채널톡 알프(ALF, 채널톡 자체 AI 상담): 네이버 톡톡 · 카카오 상담톡 · 인스타 DM · 라인에서도 응대한다(https://ditoday.com/?p=119087). 검색 요약 기준 과금은 상담 참여 1건당 500AU(1AU = 1원, 부가세 별도, 마지막 답 뒤 24시간이 지나 다시 답하면 추가), 태스크 실행은 2026-04-01부터 무료, 그로스 플랜에 월 30,000AU 기본 제공 — 근거 후보 https://docs.channel.io/help/ko/articles/ALF-%EC%A3%BC%EC%9A%94-%EB%B3%80%EA%B2%BD%EC%A0%90-%EC%95%88%EB%82%B4-01595c2d , https://docs.channel.io/updates/ko/articles/%EC%A4%91%EC%9A%94-%EA%B3%B5%EC%A7%80-%EC%B1%84%EB%84%90%ED%86%A1-%EA%B0%80%EA%B2%A9%EC%A0%9C-%EA%B0%9C%ED%8E%B8-%EC%95%88%EB%82%B4251128--8bd5ddd0 (어느 문서의 어느 값인지 원문으로 짝을 맞춘다). 태스크의 '커스텀 함수'로 바깥 API(FOMS)를 부를 수 있다(https://docs.channel.io/help/ko/articles/%EC%BB%A4%EC%8A%A4%ED%85%80-%ED%95%A8%EC%88%98--0d5fc628).
- 인스타 DM: 고객이 글을 보낸 뒤 7일이 지나면 인스타 쪽 상담 세션이 닫혀 채널톡에서 보낸 답이 실패한다. 연동은 60일마다 다시 인증한다(https://docs.channel.io/help/ko/articles/574171aa). 메타의 24시간 답장 규칙이 따로 걸리는지 확인한다.
- 네이버 톡톡: 채널톡에서 답하거나 종료해도 톡톡 쪽엔 '미답변'으로 남을 수 있다. 워크플로우의 알프 응대 · 자동 메시지 · 태그 · 배정은 대부분 돈다. 입력폼은 외부 메신저에서 안 된다. **외부 메신저에서는 매니저 · 봇 이름 대신 채널 프로필로 보인다** → 'AI 가 답한다'는 표시는 글 안에 넣어야 한다(https://docs.channel.io/help/ko/articles/%ED%86%A1%ED%86%A1-%EC%97%B0%EB%8F%99%ED%95%98%EA%B8%B0-3d8c6ce9).
- 카카오 상담톡: 상담이 열리기 전엔 상담원이 먼저 말을 걸 수 없다(카카오 정책). 종료된 상담에는 쓸 수 없다(Open API 422 "chat is not writable"). 같은 채널에 열린 상담이 있으면 새 글은 그 상담에 붙는다.
- 웹훅: 메시지 생성(팀챗 · 상담), `personType` user/manager/bot, `chatType` group/userChat, 상담 생성 이벤트가 따로 있다(https://developers.channel.io/docs/webhook-events — 판마다 이벤트 이름이 다르니 원문 확인).
- Open API 한도: 넘으면 429, 헤더 `x-ratelimit-limit` · `x-ratelimit-remaining` · `x-ratelimit-reset`(https://developers.channel.io/docs/rate-limiting). 상담 목록은 `limit` 1~500 · `state` · `since` 커서(https://developers.channel.io/docs/list-of-userchats).

### 2.5 빈칸 (실측으로 채운다 — §7 단계 2)

- 브랜드 × 매체(인스타 · 톡톡 · 카카오 · 웹)별 주간 상담 수(최근 90일), 시간대 분포(영업시간 밖 비율), 첫 응답까지 걸린 시간, 상담당 상담원 글 수. 매체가 상담 정보의 어느 칸에 오는지도 원문으로 확인한다.
- 의도 분포(표본 300 — 견적 · 제품 · 실측 일정 · 도면 · 시공 일정 · 배송 · AS · 결제 · 취소/환불 · 불만 · 기타), 주문 조회가 필요한 비율, 사진 첨부 비율, 고객 프로필에 전화가 있는 비율.
- 운영 `channel_inbound_event_logs` 의 2026-10-21 이후 `status` · `error_reason` 별 수 — 상담원 글(`ignored_not_customer`)이 지금도 웹훅으로 들어오는지(= 사람이 실제로 보낸 답을 학습 신호로 바로 받을 수 있는지).
- 채널톡 설정: 요금제 · 알프 사용 여부 · 워크플로우 목록 · 운영 시간 · '자주 쓰는 답변' 수 · 웹훅 이벤트 설정 · 채널마다 웹훅을 여러 개 걸 수 있는지.
- env 이름의 있음/없음(값 금지): 서비스 4종(web · WORKER · FOMS-cron · SIDEFX)마다 `CHANNEL_APP_SECRET` · `CHANNEL_OPENAPI_*` · `CHANNEL_SIGNING_KEY_*`. 서비스 이름은 스테이징 web = `FOMS`, 운영 web = `web` 이다.

## 3. 절대 규칙

1. 이번 세션은 설계만 한다: 저장소 코드 수정 · 패키지 설치 · git push · 채널톡 쓰기(메시지 · 태그 · 배정 · 워크플로우 · 웹훅 설정) 금지. 측정 스크립트는 스크래치패드에 두고 읽기만 한다. 저장소에는 설계서 · 플랜 · 원장 파일만 쓴다.
2. 고객 개인정보:
   - 상담 원문 · 이름 · 전화 · 주소 · 사진을 출력 · 커밋 · 문서에 남기지 않는다. 설계서 · 원장에는 수 · 비율 · 가린 문장만 쓴다.
   - 원문은 측정 스크립트가 **먼저 가린 뒤에만** 세션(모델)에 들어온다 — 세션에 들어오는 것도 바깥(Anthropic)으로 보내는 것이다. 가릴 것: 전화(정규식), 이름(주문 고객명 대조 + 'OO님' 꼴), 주소(시 · 구 · 동 · 로 · 길 + 번지), 계좌 · 이메일.
   - 가린 표본은 스크래치패드에만 두고 세션이 끝나면 지운다. 시험 묶음에 들어갈 문장은 손으로 꾸민 합성 문장으로 바꾼다 — 2026-10-18 보안 점검에서 tests · docs 에 실고객 번호로 의심되는 값 34개가 나왔다.
3. 운영 접근: 운영 DB 읽기와 운영 채널톡 Open API 읽기는 **한 번씩 사용자에게 명시 허락**을 받는다(무엇을 · 왜 · 몇 건 · 무엇을 출력하는지). 운영 DB 는 수 세기(`count` · `group by`)만 하고 원문 칸은 읽지 않는다. 측정 계정 규칙은 `docs/guides/REAL_SERVER_TEST_ACCOUNT.md`.
4. 비밀값: env 는 이름과 있음/없음만 다룬다. 비밀이 든 줄(접속 문자열 · 키)은 grep 결과로도 출력하지 않는다(`grep -l` · `grep -c` · 값을 가리는 파이썬). 출력되면 응답이 통째로 끊긴다.
5. 바꾸지 않는 것: '상담 먼저' 흐름 · 채널톡 워크플로우 · AI 도면팀원 동작. 설계에서 바꿔야 하면 이유와 시험을 적고 사용자 결정 항목으로 올린다.
6. 법 · 정책은 결론 내지 않는다: 개인정보 국외 이전 · 처리 위탁 고지, 인공지능 기본법(2026-01-22 시행으로 알려짐) 표시 의무 해당 여부, 메타 · 카카오 · 네이버 자동 응답 정책은 '확인 필요'와 확인 방법(원문 주소 · 누구에게 물을지)으로 남긴다.
7. 글: 사용자에게 보이는 글과 문서는 한글로 쓰고 한자는 쓰지 않는다. 사용자에게 묻는 말은 쉬운 낱말로, 화면 작업 안내는 전체 주소부터 준다. 질문 창(AskUserQuestion) 앞에 긴 목록을 쓰지 않는다(화면에서 접힌다) — 설명은 선택지 설명 칸에 넣는다.
8. 서브에이전트 보고는 주장이다 — 총괄이 경로:행 · 명령 결과로 다시 확인한 것만 설계서에 쓴다. 리뷰 findings 는 받는 즉시 원장에 옮긴다.

## 4. 설계 틀 (설계서가 반드시 답할 것 — 기본안은 실측으로 검증)

### 4.1 할 수 있는 것과 없는 것 (솔직하게)

- 할 수 있다: 질문 가르기 · 정해진 안내(영업시간 · 절차 · 정책) · 본인 확인된 주문의 단계와 확정된 날짜 알려 주기 · 사람에게 넘기기(이유 · 급함) · 답 초안 쓰기 · 사람이 고친 것 배우기 · AS 접수 초안.
- 못 한다(늘 사람): 가격 · 할인 · 환불 · 보상 약속, FOMS 에 없는 날짜 약속, 일정 바꾸기, 불만 · 분쟁 응대, 현장 판단, 도면 · 계약서 링크 보내기.

### 4.2 어디서 어떻게 돌리나 (사용자 질문 — 설계서에 그림 한 장으로)

- **손(실시간 답)**: FOMS WORKER(Railway) 안에 상담 전용 큐 `cs_agent` 와 그 큐만 듣는 소비자를 하나 더 둔다(`worker_jobs` 에 자식 추가). 웹훅 입구 · 저장 · 중복 거름은 지금 것을 그대로 쓴다.
- **두뇌**: Claude API(Messages API + 도구 사용 + 프롬프트 캐싱). 키는 WORKER 에만 두고(web 에는 안 둔다), Anthropic 콘솔에 작업 공간을 따로 만들어 월 한도를 건다.
- **머리(학습 · 연구)**: Claude Code 원격 루틴(claude.ai, 주 1회) — AI 도면팀원과 같은 방식, 같은 클라우드 환경(네트워크 허용을 한 번에). API 키가 필요 없다.
- **사람 화면**: 채널톡 데스크(내부 메모 초안 · 배정 · 태그) + FOMS 관리 화면(스위치 · 단계 · 지표 · 주간 노트 · 지식 승인 — AI 도면팀원과 한 화면에).
- **개발**: 로컬 Claude Code 세션. 묶음마다 Spec 승인 → deploy(스테이징) → 사용자가 요청할 때만 운영.
- 다른 길도 같은 칸으로 비교한다: 새 Railway 서비스(키 격리 · 큐 경합 없음, 대신 서비스와 env 가 하나 더), Claude 호스팅 에이전트(Managed Agents — 주문 도구를 바깥에 열어야 함, 구조는 스킬로 확인), 채널톡 알프(§4.9). Railway 대피 계획(`docs/specs/2026-10-22-railway-exit-plan_SPEC.md`, 승인 대기)과 어긋나지 않게 특정 호스팅에 묶이지 않는 보통 파이썬으로 짓는다.

설계서에 넣을 흐름(초안):

```text
고객(인스타·톡톡·카톡·웹) → 채널톡 → 웹훅 → FOMS web(받기·저장·중복 거름) → 큐 default → share_consult(확인코드 글이면 여기서 끝)
  └ 일반 고객 글 → 큐 cs_agent → WORKER 상담 일꾼 → Claude API(도구: 지식·묶인 주문 요약·도면 상태·넘기기)
       → 코드 검사 → [단계 1 저장만 | 단계 2 채널톡 내부 메모 | 단계 3 고객에게] → 기록 표
상담원이 보낸 답(웹훅) → 기록 표(초안과 짝) → 학습 요약 API(고객 정보 없음)
  → 매주 Claude 원격 루틴(AI 상담팀원 연구원) → 지식·시험 묶음·프롬프트 개선 브랜치 → 사용자 승인 → 스테이징 → 운영
```

### 4.3 한 상담 글이 지나가는 길 (순서 고정)

1. 웹훅 → `process_inbound_job` → `share_consult` 가 먼저 본다. 확인코드 글에는 상담 에이전트가 손대지 않는다.
2. 결과가 `ignored_no_code`(고객 일반 글)일 때만 `cs_agent` 큐에 넣는다. `ignored_not_customer`(상담원 글)는 학습 기록으로만 쓴다(같은 상담의 AI 초안과 짝).
3. 모아 받기: 고객은 짧은 글을 여러 번 나눠 보낸다. 같은 상담의 고객 글이 N초(가설 30초) 조용해질 때 한 번만 처리한다. 예약 실행이 없으니(§2.1) 방법을 정한다(잡 id 를 상담 + 마지막 글 시각으로 고정하고 늦게 온 글이 있으면 앞 잡은 그만두기 등).
4. 처리 전에 거른다: 매체 규칙(인스타 7일 · 카카오 종료 상담 · 톡톡), 상담원이 배정됐거나 최근 N분 안에 사람이 답한 상담, 봇 글, 하루 · 상담당 상한.
5. 두뇌 호출(도구 사용 반복, 시간 상한) → 초안 + 근거(지식 항목 id · 도구 결과) + 확신 + 넘김 여부.
6. 보내기 전 코드 검사(LLM 이 아니라 코드): 금지 꼴(금액 · 할인 · 환불 · 확정 안 된 날짜), 본인 확인 안 된 주문 정보, 다른 사람 전화 · 주소, 링크 허용 목록, 길이, AI 표시 문구.
7. 보내기 직전에 다시 읽는다: Open API 로 그 상담의 최근 글을 읽어, 그사이 사람이 답했거나 배정됐으면 그만둔다.
8. 단계(§4.5)에 따라 저장만 / 내부 메모 / 고객에게 보내기. 사람에게 넘길 땐 태그 · 배정 · FOMS 알림.
9. 기록: 표 하나(가칭 `cs_agent_turns`) — 상담 id · 브랜드 · 매체 · 의도 · 초안 · 근거 · 도구 호출 · 단계 · 결과 · 사람이 보낸 최종 답 · 고친 정도 · 토큰 · 지연 · 비용. 원문 보존 기간은 사용자가 정한다.

### 4.4 도구 (읽기 전용 · 범위는 서버가 정한다 — LLM 이 정하지 않는다)

- 있다: 지식 찾기(브랜드별 승인 항목만), 영업시간, 이 상담에 **묶인** 주문의 공개용 요약(단계 · 확정된 실측 · 시공 날짜 · 담당자 이름 — 금액 · 주소 없음), 도면 진행 상태(§4.7), 사람에게 넘기기(이유 · 급함), AS 접수 초안(기록만).
- 없다: 고객에게 보내기(파이프라인이 단계 규칙으로만 보낸다), 주문 · 일정 바꾸기, 다른 상담 · 다른 주문 읽기, 링크 만들기.
- 본인 확인 단계: ① 확인 안 됨 — 일반 안내만 ② 묶임(`SHARE_CONSULT_DELIVERED` 의 `user_chat_id`, 또는 채널톡 고객 프로필 전화 = 주문 전화 — 프로필에 전화가 있는지부터 실측) — 단계 · 확정 날짜까지 ③ 금액 · 주소 · 변경은 늘 사람. 고객이 이름 · 번호를 적어 조회해 달라는 글은 처음엔 사람에게 넘긴다(남의 주문 노출 위험). '본인 확인 알림톡'(상담 먼저 흐름 재사용)은 나중 선택지로 적는다.
- 고객 글 속 지시(프롬프트 주입)는 데이터일 뿐이다. 도구 범위와 보내기 검사가 코드에 있어서, LLM 이 속아도 정보가 새지 않게 설계한다.

### 4.5 단계(자율 수준)와 켜기 · 끄기 기준

- 0 끔 → 1 그림자(초안을 FOMS 에만 저장, 채널톡 쓰기 0) → 2 도우미(채널톡 내부 메모로 초안 — 고객은 못 보고 상담원이 고쳐 보냄) → 3 자동 일부(허락한 의도 + 영업시간 밖 첫 응답만 고객에게, 나머지는 단계 2) → 4 넓히기(의도마다 기준을 통과할 때).
- 켜기 기준(가설 — 실측으로 정한다): 단계 2 에서 그 의도 표본 50개 이상, 고치지 않고 보낸 비율 90% 이상, 잘못된 약속 0건, 넘겨야 할 것을 놓친 비율 2% 이하 → 그 의도만 단계 3.
- 끄기: 잘못된 약속 · 개인정보 노출 · 고객 불만이 1건이라도 나오면 그 의도는 바로 단계 2. 전체 끄기 스위치는 FOMS 관리 화면과 env 둘 다(재배포 없이 읽히게).
- 스위치 단위: 전체(env 가칭 `FOMS_CS_AGENT_MODE`) · 브랜드 · 매체 · 의도(SystemSetting).

### 4.6 학습 고리 (AI 도면팀원과 같은 틀)

> **역할 재정의(2026-10-27 사용자)**: 만들 것은 손님에게 답만 하는 봇이 아니라 **사람 상담원을 총괄하는 'CS 총괄(1st ABOVE) 에이전트'**다 — 대기열 감시 · 우선순위 · 답 초안 · 품질 검사 · 기준 답 관리 · 사장님 보고가 본업이고, 손님 직접 응답은 단계별 허락 뒤. 운영 기준서 초안은 아래 학습 폴더의 `knowledge/cs_supervisor_playbook.md`.
>
> **저장소 lahomsystem/FOMS 는 공개(PUBLIC)다.** 상담 지식 · 견적 금액 · 학습 요약 · 시험 묶음은 저장소 파일 · 브랜치 · Actions 산출물에 두지 않는다(아래 3~5의 저장소 경로는 이 규칙에 맞게 다시 정할 것 — DB + 관리 화면 쪽이 기본). 2026-10-27 첫 학습(상담 3,011건 전량 · 개인정보 가린 사본 · 견적 · 스토어 가격)은 저장소 밖 사용자 PC `C:/Users/USER/foms-cs-learning/` 에 있다 — 설계 세션은 거기 `knowledge/` 를 먼저 읽는다.

1. 바로 기억(도면의 '그림 종류 기억' 자리): 상담원이 초안을 고쳐 보낸 답은 '후보 예시'가 된다. 비슷한 질문의 **초안(단계 2)**에는 바로 쓰고, **자동 답(단계 3)**에는 승인된 것만 쓴다.
2. 지식 묶음: 브랜드별 항목(정책 · 절차 · 영업시간 · AS 규정 · 실측 · 시공 안내 · 자주 묻는 것). 첫 씨앗 = 채널톡 '자주 쓰는 답변' + 실측 상위 질문에 상담원이 실제로 한 답 + 상담팀 확인. 승인된 항목만 고객 답의 근거가 되고, 초안에는 근거 id 를 단다. 처음엔 통째로 프롬프트에 넣고(캐싱), 검색(임베딩 · pgvector)은 프롬프트에 안 들어갈 만큼 커졌을 때만 — 측정한 뒤에. 둘 곳(저장소 파일 — 검토 · 이력이 쉬움 / DB + 관리 화면 — 상담팀이 직접 고침)도 정한다.
3. 주간 노트(도면 A3 틀): 'AI 상담팀원 노트' — 배운 것(고친 비율 · 자주 넘긴 질문 · 새 질문 묶음) · 바뀐 것 · **물어볼 것**("이 질문에 두 상담원이 다르게 답했어요 — 어느 쪽이 맞나요?"). 답은 `docs/research/cs-agent/TEAM-RULES.md`(새 파일)로 간다.
4. 연구 루틴(도면 B1 틀): 매주 Claude Code 원격 루틴이 고객 정보 없는 학습 요약을 읽고, 실패 · 넘김 사례를 분석해, 지식 항목 초안 · 시험 묶음 추가 · 프롬프트 개선을 `cs-agent/<날짜>` 브랜치로 올린다. 스테이징 · 운영은 사용자가 정한다. 기억 폴더는 `docs/research/cs-agent/`(AGENT · JOURNAL · METRICS · BACKLOG · TEAM-RULES, 새 폴더 — `docs/research/` 아래라 하네스 규칙 안).
5. 시험 묶음(고정): 실측에서 뽑아 합성 문장으로 바꾼 질문 200개(가설)와 정답 표시(의도 · 넘김 여부 · 꼭 들어갈 사실 · 들어가면 안 되는 말). 프롬프트 · 지식 · 모델이 바뀔 때마다 다시 돌려, 나빠지면 올리지 않는다.
6. 하지 않는 것: 모델 미세조정, 고객 글로 지식을 저절로 더하기(오염), 승인 없이 자동 답 범위 넓히기.

### 4.7 AI 도면팀원과 연계

1. 같이 쓰는 틀 'AI 팀원': 계정 만들기(`ensure_agent_user` 꼴 — 두 번째 쓰임이 생기니 얇은 공통 도우미로 빼되 도면 쪽 동작 · 시험은 그대로), 토큰 지문 학습 요약, 주간 노트 · 답 · 바뀐 것 목록, 기억 폴더 구조, 루틴 운영 규칙(브랜치 · 보고 · 한 번 돌 때 상한), 같은 클라우드 환경, 관리 화면 하나. 계정 이름 가칭 `ai-cs-agent` / 'AI 상담팀원'. 루틴을 하나로 합칠지 둘로 둘지도 정한다(기본: 둘 — 지시문 · 실패가 섞이지 않게).
2. 일 주고받기:
   - "도면 언제 나와요 / 고쳐 주세요": 상담 에이전트가 도면 진행 상태를 읽어(읽기 전용) 확정된 사실만 답한다. 수정 요청이면 내용 · 사진을 그 주문의 도면 수정 요청 기록으로 남기고(기록만) 도면팀에 넘긴다. 나중 단계: AI 도면팀원 검수 메모가 "고객이 상담으로 요청한 N건 중 시트에 반영 안 된 것"을 짚는다.
   - '상담 먼저'(확인코드) 글은 계속 `share_consult` 가 먼저 처리하고, 그 흐름이 남긴 묶임을 본인 확인 근거로 쓴다.
   - 도면 · 계약서 링크는 상담 에이전트가 보내지 않는다(도면 에이전트 원칙과 같다).
   - 서로 배우기: 상담 학습 요약의 '도면 관련 고객 질문 · 헷갈린 점' 묶음 → AI 도면팀원 BACKLOG 후보(예: 도면 표기 고치기). 도면 쪽 확정 · 전달 상태 → 상담 답의 근거.
3. 원칙 충돌: 도면 설계서 §0 "고객에게 나가는 일은 하지 않는다"는 AI 도면팀원에만 해당한다. 상담 에이전트의 고객 발송은 이 설계서의 단계 규칙으로 따로 허락받는다(사용자 결정).
4. 겹침 확인: 도면 BACKLOG 8(루틴이 스테이징까지 혼자 올리는 길 — 2주 보고 뒤 결정)과 운영 첫 측정이 아직 남았다. 같은 것을 두 번 설계하지 않는다.

### 4.8 개인정보 · 보안 · 법 (확인 필요 목록으로)

- 상담 글을 Anthropic(미국)으로 보낸다 = 개인정보 국외 이전 · 처리 위탁 → 개인정보 처리방침을 고쳐야 하는지(사용자 · 법무 확인). 보내기 전에 가릴 수 있는 것(전화 · 주소)은 가린다 — 답에 필요한 주문 사실은 도구 결과로만 넣는다.
- AI 표시: 외부 메신저는 채널 프로필로 보이니 글 안에 표시한다(문구는 사용자 결정). 인공지능 기본법 해당 여부를 확인한다.
- 새 비밀값(Claude API 키): Railway env 유출 사고(2026-10-21) 뒤라 키 교체 순서가 끝난 뒤에 만들고, WORKER 에만 두고, 월 한도를 걸고, 오류 보고(Sentry)에 프롬프트 · 고객 글이 실리지 않게 한다.
- 남용: 한 상담이 글을 쏟아 비용을 태우는 경우 — 상담당 시간당 상한.

### 4.9 알프와 비교 — 결정 관문 D1 (실측 숫자로)

- 안 1 직접 만들기(§4.2 ~ 4.7) · 안 2 알프 + FOMS 커스텀 함수(알프가 답하고 주문 조회는 FOMS 읽기 API) · 안 3 섞기(알프는 단순 안내, FOMS 에이전트는 주문 관련 초안 · 학습).
- 비교 칸: 월 비용(실측 상담 수 × 알프 단가 vs 토큰 추정 × Claude 가격) · 세 매체 지원 · 본인 확인 방법 · 학습 통제(정답 기준 · 시험 묶음) · 도면 연계 · 개인정보 흐름 · 만드는 시간 · 유지 부담 · 묶임(나중에 바꾸기 쉬운가).
- 기본 가설: 안 1. 실측에서 주문과 무관한 단순 안내가 대부분이고 월 상담 수가 적으면 안 2 또는 3 으로 추천을 바꾼다.

### 4.10 비용

- 상담 1건당 토큰(입력 · 캐시 · 출력) 추정 × 가격(스킬로 확인) × 실측 건수 = 월 예상. 하루 상한 · 월 상한 · 콘솔 한도를 둔다. 연구 루틴은 구독 안에서 돌고, 한 번 돌 때 시간 · 토큰 상한을 둔다.

## 5. 사전 가설 (검증 · 반증 대상 — 결론으로 쓰지 마라)

- H1 영업시간 밖 상담이 30% 이상이고, 거기서 첫 응답 자동화가 가장 큰 이득이다.
- H2 주문 관련 문의(일정 · 도면 · 시공 · AS)가 절반 이상이다 → 직접 만들기(안 1)가 알프보다 낫다.
- H3 상담원 글이 지금도 웹훅으로 들어온다(`ignored_not_customer`) → 사람이 보낸 최종 답을 따로 모으지 않아도 학습 신호로 쓸 수 있다.
- H4 대부분의 고객은 FOMS 주문과 묶을 근거가 없다(익명 이름 · 전화 없음) → 본인 확인 없이 줄 수 있는 답이 대부분이어야 한다.
- H5 LLM 잡을 default 큐에 넣으면 '상담 먼저' 링크 발송이 밀린다 → 큐 분리가 필수다.
- H6 지식 항목이 100개 이하면 검색 없이 통째 프롬프트(캐싱)로 충분하다.
- H7 단계 2(내부 메모 초안)만으로도 상담원 시간이 크게 준다(초안 그대로 보낸 비율로 잰다).
- H8 매체마다 쓰기 제약이 달라 매체별 스위치가 필요하다(인스타 7일 · 카카오 종료 · 톡톡 미답변 표시).

## 8. 완료 기준 · 검증 명령

- 설계서 · 플랜 · 원장 세 파일이 있다.
- 설계서가 §4.1 ~ 4.10 을 모두 다루고, §5 H1 ~ H8 마다 판정(맞음 · 틀림 · 확인 못 함)과 근거가 있다.
- §2.5 빈칸이 숫자로 채워졌거나 '확인 못 함 + 이유'다.
- 플랜 task 마다 완료 기준 · 검증 명령 · 대상 파일이 있다.
- 리뷰 3개의 findings 가 원장에 전량 있고 반영 · 기각 이유가 붙었다.
- 아래 스크립트가 세 파일에서 `ANCHOR_BAD 0 · HANJA 0 · PHONE 0` 을 낸다(워크트리 루트에서). `NEW` 줄은 아직 없는 파일 — 새로 만들 파일이 맞는지 하나씩 확인한다.

```python
# 문서 검사 — 사용: python doc_check.py <파일.md> [...]  (워크트리 루트에서 실행)
import pathlib, re, sys
sys.stdout.reconfigure(encoding="utf-8")
bad = hanja = phone = 0
for doc in sys.argv[1:]:
    text = pathlib.Path(doc).read_text(encoding="utf-8")
    for path, line in re.findall(r"`([\w./-]+\.(?:json|js|py|html|md|sh|ps1|txt|toml|yml)\b)(?::(\d+))?", text):
        p = pathlib.Path(path)
        if not p.exists():
            if line:
                print("ANCHOR_BAD 없음", doc, f"{path}:{line}"); bad += 1
            else:
                print("NEW", doc, path)
        elif line and int(line) > len(p.read_text(encoding="utf-8", errors="ignore").splitlines()):
            print("ANCHOR_BAD 줄", doc, f"{path}:{line}"); bad += 1
    hanja += len(re.findall(r"[\u3400-\u9fff\uf900-\ufaff]", text))
    phone += len(re.findall(r"01[016789][-. ]?\d{3,4}[-. ]?\d{4}", text))
print(f"ANCHOR_BAD {bad} · HANJA {hanja} · PHONE {phone}")
sys.exit(1 if bad or hanja or phone else 0)
```
