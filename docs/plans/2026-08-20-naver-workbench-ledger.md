## 미해결 — 추가결제·재결제(ADDON/REPAY) 워크플로가 워크벤치에 없다 (2026-08-22 확인)

사용자 질문("추가결제·재결제는 발주확인 없이 바로 발송처리해야 하는데 워크플로가 확립됐나")에서 드러났다.

### 규칙은 확립돼 있다 (스펙 §3.5 / T16-H)

- **발주확인 생략은 불가능하다.** 네이버는 발주확인이 끝난 상품주문에만 발송처리를 받는다
  (`dispatch_order` 가 우리 쪽에서 먼저 막고, 옛 화면 주석도 "신규·재결제·추가결제 모두 발주확인이 먼저"라 적었다).
- ADDON/REPAY 의 특례는 그 **다음 단계**다: 물건이 따로 나가지 않으므로 **확인 뒤 바로 발송처리로 닫는다**.
  NEW 는 실제 출고·시공 시점에 발송처리한다. 즉 "발주확인 → (ADDON이면 즉시) 발송처리"가 정본이다.

### 화면이 빠졌다 (게이트 ON 상태의 실사용 차단)

`templates/admin/naver_workbench.html` 에 관계 축 UI 가 **하나도 없다**(`candidates|attach|추가결제|재결제|되돌리기`
= 0건, 옛 `naver_triage.html` 은 21건). 없어진 것:

- 관계 배지(이 집이 신규/추가결제/재결제인지)
- **기존 주문 후보 제시 + 붙이기**(`/attach`) · **되돌리기**(`/detach`)
- ADDON 전용 안내("추가결제는 여기서 바로 닫습니다" vs NEW 는 "실제 출고·시공 시점에")

라우트·판정 로직(`find_order_candidates`·`attach_link_to_order`·`relation` 컬럼)은 그대로 살아 있다 — **화면만 없다.**
게이트를 켠 계정은 옛 화면으로 돌아갈 경로도 없다(`/admin/naver-ingest` → 워크벤치 리다이렉트).
스테이징 실데이터: ADDON 2건 · NEW 214건.

### 덧붙은 위험 — 발송처리 버튼의 대상 범위

워크벤치의 발송처리는 "발주확인이 끝난 집 전부"에 열려 있다(2026-08-21 사용자 결정). 옛 화면이 ADDON 에만
열어 둔 이유가 이 업무 규칙이었다 — NEW 를 실제 출고 전에 누르면 구매자에게 "배송 시작"으로 보이고
구매확정·정산 시계가 먼저 돈다. 관계 배지 없이 버튼만 열려 있으면 오조작 여지가 남는다.

### 선택지

1. 워크벤치에 관계 축 UI 이식(배지 + 후보·붙이기·되돌리기 + 관계별 발송처리 안내) — 정공법.
2. 임시로 게이트 off (옛 화면 복귀) 후 이식.
3. 게이트 유지 + 리다이렉트 예외로 옛 화면을 남겨 추가결제만 거기서 처리(두 화면 왕복이 되살아난다).
