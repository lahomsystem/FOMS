## 3순위 — T8 반품 전송 설계 (사용자 답: **연 10건 이상 → 값어치 있다**)

착수 게이트는 **절반만** 열렸다. 공개 문서로 확인된 것: 네이버 커머스API 에 반품 API 군이
이름으로 존재한다(`반품 요청`·`반품 승인`·`반품 보류`·`보류 해제`·`반품 거부(철회)`),
경로 모양은 `POST /external/v1/pay-order/seller/product-orders/{productOrderId}/claim/return/...`
(클레임 타입이 `cancel`·`return`·`exchange` 로 갈린다).

**아직 못 연 것 — 여기부터가 진짜 게이트다**

1. `반품 요청` API 를 **판매자가** 쓸 수 있는가, 아니면 구매자 요청분 승인/거부만인가
2. 우리 앱 권한 그룹에 반품이 **실제로 포함**되는가 (권한 설명에 "반품" 낱말이 없다 —
   `docs/specs/2026-08-19-naver-order-relation-and-fulfillment_SPEC.md:180-188`)
3. **자사 회수**(택배사·송장 없음)를 받는가 — 가구는 우리 차가 간다
4. `DIRECT_DELIVERY`/`NOT_TRACKING` 이 반품 접수 조건을 만족하는가

정확한 body 명세는 apicenter(로그인·JS 필요)라 공개 검색으로는 못 읽는다.
**사용자에게 apicenter 문서 접근을 요청하거나, 사용자가 직접 확인해 줘야 한다.**

FOMS 버튼 하나로 끝나는 갈래는 없다는 판정은 유효하다:
접수 → 수거정보 입력 → **실제 회수(우리 차량)** → 검수(사람) → 승인·환불(판매자센터).
중간 셋은 버튼으로 못 만든다. **읽기(S0)를 먼저 배포한 것이 그래서 옳았다.**

## 남긴 사각 (원장 §CEO 리뷰에 전량)

- **실물 반품 스냅샷이 없다** — `returnInfo`/`return`/`exchange` 블록 이름은 여전히 **가정**이고
  테스트 픽스처도 가정이다. 실물이 오면 그때 눈으로 확인한다.
- **`확인 완료` 게이트가 이전 주문 행까지 체크를 요구**한다 — 죽은 주문에 "반영함"을 찍어야
  버튼이 열린다. 회귀 위험이 있어 이번에 안 건드렸다. 별도 판단 필요.
- **다시 읽기 push 실발송 미확인** — `push_sender._DEFAULT_P1_TYPES` 등재 여부를 코드로만 봤다.
- 5분 스윕이 25초 폴링 창에서 rev 를 흔들면 "완료" 한 번 오표시(확률 낮음, softRefresh 가 덮음).
- `NEW` 집 2개 + `REPAY` 면 둘 다 "이전 주문"이 된다(실데이터 사례 없음).
- `collect_address.zip_code` 를 뽑지만 화면이 안 쓴다. `주문` 이 두 뜻으로 인접한 자리 4곳
  (`수집됨(주문 전) 12주문` 등) — 틀린 건 아니고 읽기 부담.
