## T3 조사 결과 — 위험은 실재한다 (주 세션이 인용 라인을 직접 확인)

발송처리 판정이 **양쪽 다 우리 표식만** 본다. 네이버가 이미 발송을 말하고 있어도 아무도 안 본다.

- `naver_workbench_pane.html:75`
  `can_dispatch = not locked and not dispatched and (not place_pending or close_now)`
- `fulfillment.py:544`
  `todo = [row for row in links if not _state(row).get("dispatched_at")]`

`todo` 가 비지 않으면 `client.dispatch_product_orders(payload)` 가 **실제로 나간다**. 서버가 막는
지점이 없다. `fulfillment.py:10-11` docstring 이 "네이버의 400(이미 처리됨)을 정상 흐름으로 삼지
않는다" 고 적어 둔 것은, 설계자가 **네이버 거절을 안전망으로 기대하지 않았다**는 명시적 진술이다.

구조적 비대칭도 있다: 발주확인(`place_pending`)은 우리 표식이 없어도 컬럼으로 보완하는데
(`fulfillment.py:126-137`), 발송에는 그런 폴백이 없다. 그래서 시간이 지나면 발주확인은 자동으로
풀리지만 **발송은 절대 자동으로 True 가 되지 않아 버튼이 열리는 방향으로 수렴**한다.

**운영 실측은 이 방향 0건**(운영 발송은 FOMS 를 거친다). 스테이징 41건은 판매자센터 직접 발송

### 착수 게이트가 하나 있다 — **네이버에 반품 API 가 있는지 저장소로는 알 수 없다**

우리 클라이언트가 부르는 네이버 경로는 6개고 반품은 0개다(`client.py:304·333·361·389·420·458`).

취소, 교환 등" 인데 **"반품" 이라는 낱말이 없다**(`docs/specs/2026-08-19-naver-order-relation-and-fulfillment_SPEC.md:180-188`).

즉 정확한 상태는 "기능이 없다" 가 아니라 **"API 통로가 있는지 모른다"** 다. 판매자센터에
[판매자 직접 반품] 업무 기능이 있는 것은 매뉴얼로 확인됐지만, 그건 UI 문서지 API 명세가 아니다.
**공식 문서 확인 전에는 구현 착수 자체가 불가능하다.**

### FOMS 버튼 하나로 끝나는 갈래는 없다

접수(어쩌면 가능) → 수거정보 입력 → **실제 회수(우리 차량 — 자사배송이라 택배 수거가 아니다)**
→ 검수(사람) → 승인·환불(판매자센터). 중간 셋은 버튼으로 못 만든다.

### 지금 바로 할 수 있는 것 — **S0: 반품 축 읽기 구멍 3개** (불가역 0 · 네이버 호출 0)

| 구멍 | 사실 |
|---|---|
| `COLLECTING` · `COLLECT_DONE` | 차단 집합(`BLOCKING_CLAIM_STATUSES`)에는 있는데 **라벨이 없다** → 반품 수거중 집이 화면에 **영문 원문**으로 뜬다 |

수거·환불 축(`collectCompletedDate` · `refundExpectedDate` · `refundStandbyStatus/Reason`)도

**보내기보다 읽기가 먼저인 이유**: 반품을 *보내려면* 먼저 반품을 *정확히 읽어야* 한다.
지금은 수거중이 영문으로 뜨고 반품 거부는 잠금조차 안 된다. 보내기부터 만들면 **우리가 만든
클레임의 진행 상황을 우리 화면이 못 읽는다.**

`COLLECT_DONE` 을 실제로 관측한 기록이 저장소에 없다 — 중간 상태를 화면이 어떻게 보여주는지

**라벨 구멍**은 3종이 아니라 **7종**이었다. 차단 집합에 있는데 라벨이 없던 것이
`COLLECTING`·`COLLECT_DONE`·`CANCELING` 말고 `CANCEL_REQUESTED`·`RETURN_REQUESTED` 도
있었고, 거부 비대칭은 `RETURN_REJECT` 말고 `EXCHANGE_REJECT` 도 같았다.
구멍이 다시 생기지 않게 **집합 대 집합** 단언을 걸었다
(`BLOCKING_CLAIM_STATUSES - set(CLAIM_STATUS_LABELS) == []`).

- `COLLECTING`/`COLLECT_DONE` 라벨은 `반품 수거중` 이 아니라 **`수거중`·`수거 완료`** 다.
  수거는 반품·교환 **양쪽**에서 온다 — 반품이라고 적으면 교환 건에서 화면이 틀린 이름을 말한다.
- `RETURN_REJECT`·`EXCHANGE_REJECT` 는 **차단하지 않는다**. `CANCEL_REJECT` 와 같은 규칙이다
  (거부 = 클레임 무산 = 주문 정상 진행). 앞 세션 메모의 "반품 거부는 잠금조차 안 된다" 는
  **잠금이 빠진 게 아니라 라벨이 빠진 것**이었다.

**조용한 유실 하나를 같이 닫았다**: `extract_claim` 이 사유 원문을 `cancel` 블록 **안에서만**
찾았다. 코드가 `returnDetailedReason` 을 읽으려 시도하고 있었는데, 반품이 별도 블록으로 오면
그 키가 `cancel` 안에 있을 리 없어 **영영 빈 문자열**이었다(배송메모 사건과 같은 모양).
`_claim_blocks()` 로 블록 후보를 우선순위 순으로 모아 키별로 처음 값을 쓴다.
`cancel` 이 첫 번째다.

**정정(CEO 리뷰 A1)**: 여기 처음 적었던 "기존 동작 불변"은 **틀렸다**. 블록 목록
마지막에 `currentClaim` **자신**이 들어가서, 클레임 상세가 거기 평평하게 실려 오면
옛 코드가 떨어지던 `order.claimStatus` 대신 그 값을 쓴다 — `blocking` 이 뒤집힐 수
있는 경로다. 값이 더 구체적이라 개선 방향이지만 **불변이 아니다**. 정확한 진술은
"더 구체적인 소스를 먼저 본다"이고, 우선순위를 단언 2건으로 못박았다.

**관측되지 않은 것(정직하게 남긴다)**: 반품 상세가 어느 부모 키로 오는지 실물 확인은
`cancel` 뿐이다. `returnInfo`·`return`·`exchange` 는 **폴백 가정**이고 테스트 픽스처도 가정이다.
실물 반품이 처음 들어오면 그때 눈으로 확인한다.
