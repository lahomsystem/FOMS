# Inbound Failure Playbook (CT-E)

## 1. 개요
ChannelTalk에서 수신한 웹훅 기반 인바운드 처리가 실패했을 때, 운영자와 시스템이 어떻게 대응해야 하는지를 정의한 가이드.

## 2. 상태 코드별 대응 절차

### 2.1 `parse_failed` (파싱 실패)
- **원인**: 수신된 텍스트가 지정된 템플릿(Parser Rulebook)과 일치하지 않거나, 필수 정보가 누락됨.
- **시스템 동작**: 수신 로그를 `parse_failed`로 마킹하고, 실패 사유(`error_reason`)를 저장한다. 가능할 경우 ChannelTalk으로 Quick Reply 실패 메시지를 발송한다.
- **운영자 조치**: 
  1. 어드민 로그 화면에서 `parse_failed` 건의 `raw_payload`를 확인한다.
  2. 파싱 로직의 결함인지 사용자 입력의 오타인지 구분한다.
  3. 사용자 입력 오류인 경우 운영자가 직접 올바른 양식으로 채널톡에 재입력하여 정상 수신되도록 안내한다.

### 2.2 `queue_enqueue_failed` (큐 등록 실패)
- **원인**: Redis 큐 장애 또는 시스템 일시 단절.
- **시스템 동작**: DB에 `queue_enqueue_failed` 상태로 로그를 남기고, Webhook 응답으로 HTTP 503을 반환한다 (Provider Retry 대기).
- **운영자 조치**:
  1. 인프라 상태(Redis, RQ Worker)를 확인한다.
  2. 시스템 복구 후, Provider(ChannelTalk) 측의 자동 재시도를 기다리거나, 내부적으로 구현된 Inbound Sweeper Job을 실행하여 재처리한다.

### 2.3 `rejected_signature` / `rejected_replay`
- **원인**: 인바운드 요청의 X-Signature 서명 검증 실패, 또는 타임스탬프 윈도우 초과 (Replay Attack 방어).
- **시스템 동작**: 요청을 즉시 401/403으로 거부하며, 시스템상으로는 보안 이슈로 분류되어 `rejected_*` 로 저장된다 (처리 시도 안함).
- **운영자 조치**:
  1. 단발성인지 지속적인지 파악한다 (Secret Key 오설정 또는 외부의 고의적 접근 시도).
  2. 지속적인 경우 키를 로테이션하거나 방화벽 규칙을 점검한다.

### 2.4 `rejected_group`
- **원인**: 허용되지 않은 채널톡 그룹(채팅방)에서 온 웹훅 메시지. (화이트리스트 위반)
- **시스템 동작**: 무시하고 `rejected_group`으로 기록. (저장 없이 거부할 수도 있으나 보안 추적을 위해 저장)
- **운영자 조치**: 정상 동작이므로 특이사항 없음. 단, 신규 그룹이 추가되어야 하는데 차단된 거라면 그룹 화이트리스트 환경변수를 수정한다.

### 2.5 비즈니스/도메인 생성 실패 (`worker_processing` -> `error_reason` 기록 후 실패)
- **원인**: 파싱은 성공했으나, ERP 시스템 상의 제약(존재하지 않는 사용자 매핑, 외래키 제약조건 위반 등)으로 인해 Order/Task 생성이 실패함.
- **시스템 동작**: 로그 상태를 변경하고 `error_reason`에 상세 사유 기재.
- **운영자 조치**:
  1. 에러 내역을 확인하고 데이터를 수동 교정한다.
  2. 필요 시 개발팀에 버그 픽스를 요청한다.
