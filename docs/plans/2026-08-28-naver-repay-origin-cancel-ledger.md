## 3. 범위

### Shape A 채택 — "길만 낸다"

옛 집 식별자를 투영에 복원하고, 관계 블록에 원 주문 줄 + `?link_id=<old>` 앵커를 낸다. 불가역 호출은
**옛 주문 자신의 pane 에서 사람이** 기존 모달·기존 가드·기존 감사·기존 권한으로 실행한다. 신규 불가역 경로 0.

### Shape B 기각 — "여기서 누른다"

재결제 pane 에서 옛 집을 겨냥하는 버튼. B 의 판매 논리는 "라우트 재사용, target link_id 만 다름"인데
그 전제가 거짓이다.

1. **모달 재진술이 거짓말이 된다.** `pane:1003-1004` 는 `{{ selected.naver.recipient_name }}님의 상품주문
   {{ member_count }}건` — 자기 집이다. 옛 집을 겨냥하면 **새 결제 고객 이름과 새 집 건수**를 말하면서
   **옛 집을 환불**한다. 불가역 4종 세트 중 ①이 반대로 작동한다.
2. **가드 전부가 자기 집 계산이다.** `locked`(`pane:38`)·`dispatched_any`(`:52`)·`can_cancel`(`:103`)·
   `can_return`(`:114`). 라우트 재사용이 아니라 가드 표면 재구현이다.
3. **코드베이스가 이 사고를 이름으로 안다.** `pane:824-829`: "옛 모달이 남으면 다른 집으로 호출이 나간다."
   Shape B 는 그 사고 모양을 의도된 동작으로 승격시킨다.
4. **다시 읽기가 못 따라온다.** `wb-refresh` 는 `data-link-id="{{ selected.link_id }}"`(`pane:311`) = 자기 집.
   옛 집을 새로 읽을 방법 없이 옛 집에 취소를 건다.
5. **결정 해석에 의존한다.** B 는 "흐름 한정" 해석이 맞아야만 합법. A 는 전면 금지 해석에서도 합법.

### 하는 것

1. 후보/alive-row 투영에 `link_id`·`external_id` 복원 (`order_candidates.py:150-151`, `:226-229`)
2. 관계 블록(`pane:561-574`)에 원 주문 줄 — 상태 + 금액 + 마지막 조회 시각 + `?link_id=<old>` 앵커
3. `OFFICIAL_CANCEL_REASONS` 상수 + 부분집합 계약 테스트
4. `SOLD_OUT` 라벨에 결과 명시
5. 상세 사유 = 구매자에게 그대로 전달됨을 두 모달에 명시 + 오도 플레이스홀더 교체
6. 신선도 표시 의무화 + 표식 부재 시 불가역 버튼 무장 해제
7. '네이버 주문 확인 안 됨' 문구

## 4. '네이버 주문 확인 안 됨' — 화면 문구

### 구별을 거부하는 것

**(가) 네이버에 원래 주문이 없었다** vs **(나) 있었지만 우리가 못 가져왔다** — 구별하지 않는다.
두 경우 모두 관측이 `링크 0행`으로 동일하다. 구별하려면 전화·이름으로 네이버를 조회해야 하는데
링크 테이블에 그 컬럼이 없고 인덱스도 없고 그런 읽기 경로 자체가 없다.
**자신 있게 틀린 말보다 흐릿한 참말이 낫다.**

정정 — 미수집 집합은 조사 서술보다 좁다: 수집 필터는 `productOrderStatus == PAYED` 하나뿐이라
**취소 요청 중인 건은 그대로 수집된다**(`mapping.py:407-411`, 2026-08-14 스테이징 실측:
"상태가 PAYED 인데 claimStatus = CANCEL_REQUEST 인 건이 실재했다"). 못 가져오는 것은 **첫 스윕 시점에
이미 PAYED 를 떠난 주문**(배송중·배송완료·구매확정·취소완료)이다.

현행 `pane:799` 는 이미 "이 주문에 붙은 네이버 **수집분**이 없습니다"라고 참인 형태로 말한다.
필요한 변경은 **그다음에 무엇을 하라**를 붙이는 것뿐이다.

## 5. 신선도 — 실측이 조사보다 나쁘다

`refreshed_at` 은 저장소 전체에서 정확히 2곳: 쓰기 `claim_watch.py:406`, 읽기 `naver_ingest.py:2194`.
읽기 용도는 **폴링 지문 해시 재료**다(`marks.append(...)`). **어떤 템플릿도 이 값을 렌더하지 않는다.**
즉 현행 화면은 신선도 근거 0 으로 "살아 있음"을 확정형으로 말한다.

자동 보충도 없다 — 스윕은 네이버 변경 이벤트에 뜬 건만 다시 읽고, "이벤트가 안 오는 건은 자동 경로로
**영영** 못 잡는다"(`claim_watch.py:510-514`).

**규칙 2개**

1. **표시 의무**: 네이버 상태를 주장하는 모든 자리에 "이 상태는 {시각}에 읽은 것입니다" 또는
   "언제 읽었는지 기록이 없습니다"를 붙인다. 순수 추가, 동작 변경 0.
2. **무장 해제**: `claim_sync.refreshed_at` 이 없으면 취소·반품 버튼을 잠그고 "먼저 **다시 읽기**를
   누르세요"라고 말한다. 다시 읽기는 읽기 전용이라 되돌릴 것이 없고(`naver_ingest.py:2616-2632`)
   버튼은 이미 항상 렌더된다(`pane:310-314`). 되돌릴 수 없는 클릭 앞에 되돌릴 수 있는 클릭.

**시간 임계값은 지금 정하지 않는다** — 정상 갱신 지연 분포 미측정. 표식 부재 차단은 그 데이터 없이도
명확하므로 그것만 먼저 건다.

**Shape A 보너스**: 옛 집 pane 에 서면 `다시 읽기` 가 옛 집을 겨냥한다(`refresh_household`
`claim_watch.py:506-510` 이 link_id 의 집을 읽으므로). Shape B 엔 이 자리가 없다.

## 6. provenance 결함 — 별건 등재, 단 이번 작업에 제약 1개

`_stamp_source_marker`(`promotion.py:326-365`)가 `source` 키가 비면 `NAVER_SMARTSTORE` 를 찍는다(`:358-361`).
호출처는 `attach_link_to_order`(`:499`→`:573`) = 붙이는 순간. `source` 작성자는 `mapping.py:815`(네이버 승격)와
`promotion.py:361` 둘뿐이고 ERP 등록 경로는 아무도 안 쓴다. 따라서 **예약금 건(ERP 직접 등록)에 재결제를
붙이면 그 주문이 네이버 출신으로 뒤집힌다.**

**단순 결함이 아니라 알려진 결합이다.** `:329-338`: "이 한 줄이 없으면 붙이기 결과가 화면에 아예
나타나지 않는다" — 편집 화면은 `source == SOURCE_MARKER` 일 때만 도크를 렌더한다(`foms/web/orders/edit.py`).
2026-08-24 주문 4485 에서 1,610,780원이 기록됐는데 화면이 빈손이던 실사례. 따라서 "그냥 안 찍기"는 오답 —
도크가 닫히고 그 사고가 재발한다.

**근본 원인**: 키 하나가 뜻 두 개를 진다 — ① 주문 출처(provenance) ② 도크 렌더 게이트.
고치려면 둘을 가른다(도크 게이트를 `ExternalOrderLink` 존재 여부로 판정). 편집 화면·대시보드를 건드리는
별건 작업이다.

**파급 추가 확인**: 도크만이 아니다. `foms/services/orders/dashboard_read_model.py:465-467` 이
`source == SOURCE_MARKER` 로 '담당 미지정' 뱃지 모집단을 고른다. 붙인 뒤 예약금 주문이 그 쿼리에 편입된다.

**이번 작업 제약**: `structured_data['source']` 를 "네이버 출신인가" 판정 근거로 쓰는 화면 문구를
만들지 않는다. 링크 행 수는 오염되지 않으므로 §4 판정은 안전하다.

과거 소실분(2026-08-24 실측 9건 중 ERP 편집 흔적 5건이 전부 `source` 유실,
`erp_orders_structured.py:251-257`)은 복구 불가 확정. 재조사 금지.
